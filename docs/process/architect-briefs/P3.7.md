**Subject:** P3.7 is the **Wave-3 closer** and pulls in two things the architect ratified for full Wave-3:

- **(A) content depth** — more agents / templates / skills / **local** connectors (stdio MCP) / **local** plugins (Posture A) to take the product to 完整 breadth (handoff §7; roadmap §4 "extends P3.1/P3.4"). This is **pure additive breadth on the existing P3.4/P3.5 substrate** — no new infra, no new trust surface.
- **(B) remote infrastructure** — the two deferred remote surfaces: **(B1) Posture B subprocess-isolated plugin executor** (ADR-029 D4 — required once provenance is untrusted) and **(B2) remote MCP transport** (ADR-027 D1 — SSE/streamable-http). This is the project's **largest trust surface to date**: it crosses from *operator-curated/local* (which P3.4/P3.5 leaned on as the trust premise) to **untrusted/remote provenance**.

These two halves share almost nothing operationally (footprint, risk, ADR vehicle, review depth, distance-test posture). **Whether they are one slice or two is the lead decision (§a).**

## The substrate that already exists + the deferred-to-P3.7 triggers (verified)

P3.7 does **not** invent the gate, the executor, the MCP client, the plugin loader, or the trust-boundary pattern — all exist. The deferred triggers it absorbs:

| Trigger | Source | P3.7 half |
|---|---|---|
| SSE / streamable-http remote MCP transport | ADR-027 **D1** ("remote = larger trust surface; deferred") | **B2** |
| Posture B subprocess isolation for plugin tool code | ADR-029 **D4** ("REQUIRED once provenance untrusted; reserved for P3.7 remote") + the itemized A→B migration surface | **B1** |
| Remote install / plugin registry / fetch-from-network + discovered-but-not-activated consent | ADR-029 scope + **D5** ("a P3.7 concern when provenance becomes untrusted") | **B1-coupled** (§b) |
| Many connectors | ADR-027 D5/scope ("more connectors → P3.7") | **A** |
| Deferred local tools (network / subprocess / mutation) | ADR-028 **D3** ("each distinct surface warrants its own slice + classification") | **A?** (§e sub-call) |

**The constitutional crux of the remote half (inscribe — this is the heart of B):** ADR-029 D4 accepted Posture A **only because plugins are operator-placed — curation IS the trust boundary**. A **fetched/remote** plugin is **not operator-placed**, so **curation no longer holds**, so **Posture A is constitutionally invalid for remote provenance** and **Posture B is REQUIRED, not optional** (the architect already ruled this in ADR-029 D4). B1 is therefore the *enabling precondition* for any remote-plugin capability — you cannot ship remote-fetch on the in-process executor (that is the inscribed L1/L2 exposures — full host privilege, all secrets, server-wide DoS — with **no curation backstop** = a real vulnerability, not an accepted MVP posture).

## ⭐ THE LEAD DECISION (§a) — split P3.7, or bundle? (architect rules; lean: **split**)

This reshapes the whole slice, exactly as ⭐D-B reshaped P3.6 / (b) reshaped P3.5. **Surface for the architect; do not self-decide (scope/split is the architect's call).**

**Architect-partner lean: SPLIT** — `P3.7-content` (light) + `P3.7-remote` (heavy). Reasoning:

1. **Categorically different risk + process.** (A) is low-risk content (data + established-pattern code) → **single-lens R0-A**, no/trivial ADR, the junior pattern-matches P3.1/P3.4/P3.5. (B) is the heaviest remaining security surface (two *untrusted-remote* trust boundaries + an execution-model migration) → **mandatory dual-lens R0-B + new ADR(s) + fresh-eyes**. Bundling forces light content through the heavy gate (waste) **or** dilutes the dual-lens focus across unrelated content (risk — the cross-family lens must concentrate on the remote trust surface, not on "we added 4 agents").
2. **Disjoint footprints.** (A) = `config/agents,skills` + `plugins/<new>/` + `config/mcp_servers.yaml` entries. (B) = `mcp/transport.py` + `plugins/code.py` rework + new provenance/consent/subprocess code. Independently closeable; clean separate audit trails (separate ADRs, review chains, retros).
3. **The closer logic.** Content depth is the clean "完整 breadth" P3 closer; remote infra is a distinct heavy security epic. Both are in P3 (architect ratified full Wave-3) — splitting lets content **close fast + clean** while remote gets its **own focused heavy cycle**.

## ⭐⭐ The constitutional spine (NON-NEGOTIABLE — carried forward for BOTH halves; inscribe, not chosen)

Per Principle 5 + roadmap §9 — remote/untrusted provenance changes the *trust premise*, **never** the spine. The senior/ADR must inscribe and the impl must enforce:

1. **The gate stays the sole chokepoint — unchanged.** A remote MCP tool **and** a Posture-B/remote plugin tool route through the **same** code autonomy gate (`process_tool_calls → emit_gate_decision`); tier from code-classified reversibility; **unregistered/unclassified → `UnknownToolError` → refused** (fail-closed). A remote transport is a **transport** change (B2), not a gating change (ADR-027 D2 "feed-the-gate-unchanged" holds verbatim).
2. **Remote does NOT bypass the allowlist; routing = code.** A remote MCP server is **still** an allowlist entry; remote/fetched code is **still** opt-in (the *consent granularity* changes — see §b — but never to "auto-trust on fetch"). **Discovery ≠ permission, one level up: *fetching* ≠ *trusting*.** No remote infra brings an LLM routing/judgment decision; model-selection stays the code router + the P2.7 Layer-4 override; **no new routing/judgment `LLMPurpose`**.
3. **Self-asserted tier is never authoritative.** A remote server's protocol hints and a fetched plugin's claimed reversibility are **advisory-capped → host-authoritative-or-default-0** (ADR-027 HR#2 / ADR-029 D5) — a remote source cannot self-classify a write tool to dodge `HARD_CONFIRM`.
4. **Untrusted results — *more* untrusted, not less.** A remote MCP server is **not** a user-launched local subprocess → results stay size-limited, content-gen-interpreted (`TOOL_OUTPUT_INTERPRET`), untrusted-framed, no auto-action; **no tool-result drives a routing/autonomy decision**.
5. **Credential safety + scoped env carry forward.** Remote transports need credentials (auth tokens / TLS) → **`api_key_env` indirection only**, no plaintext; Posture-B subprocesses get a **minimal scoped env** (the c2 env-leak lesson) — and Posture B is exactly what makes the env boundary **real** for plugin code (it is zero under Posture A — ADR-029 D4 L1).
6. **Fail-closed everywhere.** TLS failure / unverified provenance / unreachable remote / fetch failure / subprocess crash-hang-timeout-orphan → **refuse / `TOOL_FAILED`**, never degrade-open, never crash/hang the orchestrator.

## Scope

### §A — content depth (the light half)
**In:** more **agents** (beyond the 6), more **skills** (beyond the 2), more **room templates** as warranted, more **local** connectors (stdio MCP, ADR-027 pattern) + more **local** plugins (Posture A, operator-placed, ADR-029 pattern) — all on the **existing** loaders/registries, gated/allowlisted as today. **Out:** anything remote (that is §B); the network/subprocess local *tools* unless §e rules them in.

### §B — remote infrastructure (the heavy half)
**In:**
- **B1 — Posture B subprocess-isolated plugin executor:** replace the in-process `importlib`/`exec_module` path (`plugins/code.py`) with a **killable subprocess** (minimal scoped env, bounded-timeout, kill-no-orphan, fail-closed → `TOOL_FAILED`) — the ADR-029-D4-itemized A→B migration. This **restores the ADR-028 D5 per-turn liveness bound** (a subprocess is killable; in-process was not) **and** gives a **real isolation/env boundary** (resolves L1). Plus the **remote-provenance / consent** surface it gates (§b): fetched code is run **only** under Posture B; the presence=opt-in consent (valid for operator-placed) is **replaced** for fetched code by an explicit activation/allowlist (ADR-029 D5).
- **B2 — remote MCP transport:** SSE and/or streamable-http (ADR-027 D1), with the **remote trust knobs** (the new surface vs stdio): **TLS verification** (reject plaintext/unverified), **server-URL allowlist** (the remote analog of the stdio command allowlist), **auth/credential via `api_key_env`**, **bounded network timeouts**, **fail-closed**, **untrusted-result handling** — the gating spine **unchanged** (a remote MCP tool gates exactly like a stdio one).
- **One remote demo each** (mirrors P3.4/P3.5's one-demo discipline): one remote MCP connector (a real `https://` endpoint) + one remote/Posture-B plugin demo — end-to-end, proving the loop.

**Out (defer — likely P4):** a full plugin *registry/marketplace*; remote plugin *upgrade/version-coexistence/uninstall* lifecycle; auth beyond the MVP token/TLS; GUI surfacing of remote infra (frontend track); any change to the gate/executor **decision logic**.

## Decisions (surface for the architect — do not self-decide; ⭐ = constitutional/security/scope-reshaping)

**⭐ (a) The split — content vs remote (the LEAD; §above).** Lean: **split** (`P3.7-content` + `P3.7-remote`). Architect rules split-vs-bundle + names + sequence. *This gates everything below.*

**⭐ (b) B1 — Posture B execution model + the remote-provenance coupling.**
- **The A→B migration is already itemized** (ADR-029 D4 Reversibility / R0-B Y6): `plugins/code.py` (`importlib` + `LocalToolFn`) → a subprocess protocol (scoped env, bounded-timeout, kill-on-timeout, fail-closed); `LocalToolFn` → a subprocess-runner adapter. **Design convergence to surface:** ADR-029 D4 already observed *"a Posture-B plugin executable tool ≈ a bundled MCP server."* So **does Posture B REUSE the MCP-server subprocess mechanism** (a plugin tool ≈ a local stdio MCP server — one subprocess trust boundary, maximal reuse of ADR-027 D4) **or a distinct plugin-subprocess protocol?** Senior-design with an architect breadth-confirm. Lean: **converge on the MCP-subprocess pattern** (don't build a second parallel subprocess surface).
- **⭐ Scope coupling (the genuine call):** does B1 land **with** the actual remote-fetch/registry capability, or is **Posture B built + tested standalone first**?
  - **B-coupled** — remote-fetch/registry + its required Posture-B executor together (the full untrusted-remote-plugin story end-to-end).
  - **B-executor-first** *(lean)* — build + test the **Posture B executor migration** demonstrated on a **local** plugin (so the execution-model change is verified in isolation), **defer remote-fetch/registry** to a further slice. Lower-risk: the migration is the hard, testable part; remote-fetch is additive once the safe executor exists. Architect rules.

**⭐ (c) B2 — remote MCP transport + trust surface.** Architect rules:
- **Transport:** SSE / streamable-http (the two the MCP SDK offers). Lean: **streamable-http** (current standard; SSE is the legacy variant) — confirm.
- **Remote trust knobs** (the new surface — a remote server is *not* a user-launched local process): TLS verification + server-URL allowlist + auth-via-`api_key_env` + bounded timeouts + fail-closed + untrusted-result limits. Confirm the posture (the stdio allowlist/credential pattern, lifted to `https://` endpoints).

**⭐ (d) ADR vehicle(s) + dual-lens dispatch.**
- **ADR(s):** B1 (Posture B + remote-provenance) is an **execution-model change + a trust-premise shift** → likely a **new ADR** (e.g. **ADR-031**, *Posture-B / remote-plugin-provenance*) rather than a mere ADR-029 amendment. B2 (remote transport) could be a **new ADR** (**ADR-032**, *remote MCP transport*) **or** an **ADR-027 D1 amendment** (D1 scoped remote as "additive/deferred"). Architect rules the vehicle(s). If split, each sub-slice carries its own. **RC-23-safe** (Proposed; no literal `Accepted` substring until accepted).
- **⭐ Dual-lens R0-B — MANDATORY for the remote half (B); single-lens R0-A for content (A).** ≥2 dual-lens criteria hold decisively for B: **(1)** new concurrency surface (the Posture-B subprocess executor — kill/timeout/orphan, the ADR-027/028 dual-lens class); **(2)** new cross-package edge (remote-fetch/provenance; the subprocess executor replacing in-process); **(3)** a contract ≥5 future tasks bind (the remote-plugin/registry + remote-transport config = the P4 extensibility story); **(4)** **first runtime exercise of untrusted-remote-provenance code execution** — the largest trust surface to date, **exceeding** P3.4/P3.5 (those were *local/operator-curated*; this is *fetched/untrusted*). The trust-premise shift (curation no longer holds) is exactly the cross-family failure-mode lens (malicious fetched code, subprocess escape, TLS bypass, provenance spoofing, env-leak). `requires_cross_family_review: **true**` for B.

**(e) MVP scope per half.**
- **(A)** Breadth target — how many more agents/skills/templates/local-connectors/local-plugins? **Sub-call:** do the **deferred local *tools*** (ADR-028 D3 network/subprocess/mutation — each its own trust surface + classification; note confirm-then-execute now exists per ADR-030, so mutation-tier tools are runnable post-confirm) belong in content depth, or are they **their own trust-surfaced slices**? Lean: agents/skills/templates + a couple more local connectors/plugins **as content**; the network/subprocess **tools stay separate** (not lumped into "content"). Architect rules.
- **(B)** Demo scope — one remote MCP connector + one remote/Posture-B plugin demo (lean — the one-demo discipline). Architect rules.
