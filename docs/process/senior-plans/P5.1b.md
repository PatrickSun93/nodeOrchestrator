# Senior plan — P5.1b: recurring pipeline scheduler + schedule persistence + restart re-arm

## 1. Context

P5.1b is the **second slice** of the P5.1 analysis-pipeline wave. P5.1a (ADR-041, merged
PR #67) shipped the *safe* primitive: a deterministic `fetch → fan-out(analyze×N) → reduce`
runner, the `sources/` read abstraction, reversible-only room output, owner-private
`/pipelines*` CRUD, a **manual** `POST /pipelines/{id}/run`, and the deliberately
schedule-free `pipelines`/`pipeline_runs` side tables. P5.1b makes the pipeline
**unattended on a timer**: a recurring scheduler, schedule-definition persistence, and
restart re-arm.

The architect ratified the decision surface (`docs/process/architect-briefs/P5.1b.md`)
**entirely on the arch-partner leans** (all-by-lean, B0–B6). I am planning against those
ratified decisions and have drafted **ADR-042** (`docs/decisions/ADR-042-recurring-pipeline-scheduler.md`,
Status: Proposed) as the new contract surface (B6). The constitutional crux this slice
turns on — verified at `origin/main @ 811412a`: the scheduler is the **second *caller*** of
the byte-unchanged `run_pipeline` (it does **not** edit the runner), and it inherits ADR-041
D5's `countdown_auto_fire=None`, so a *scheduled* run is still **reversible-only** and can
**never** headless-actuate an irreversible op (that crossing is P5.1c's `RB-PIPELINE-EMAIL`).
This slice introduces the honest **`RB-PIPELINE-SCHED`** residual — the **first headless
*initiation* surface** in the product (ADR-042 D8), categorically **milder** than ADR-040's
`RB-AUTOFIRE` (which actuates a *gated* pending).

**This is product, not dev harness** (the scheduler triggers the product pipeline) — full
plan-stage dual-lens applies (`requires_cross_family_review: true`, already set): Lens A =
scheduler safety + headless-initiation correctness; Lens B = spine + auto-fire no-regression.

**Verified seams (the precision base — all confirmed by read, not the dispatch's shorthand):**
- `run_pipeline(pipeline_id, definition, *, deps, owner_user_id)` **self-generates** `run_id`
  (`pipeline/runner.py:263`) and returns it on `PipelineRunResult.run_id` (`:430-439`);
  `create_pipeline_run(..., run_id=...)` **accepts** a caller `run_id` (`store.py:134-165`);
  `/run` threads `result.run_id` into the store row (`app.py:1687-1694`). **The scheduler
  does the same on the writer — never passes a run_id *into* run_pipeline.**
- `countdown_auto_fire=None` is honored by the stamp guard `if … countdown_auto_fire is not
  None and .enabled` (`agents/tool_dispatch.py:138-145`) → pipeline pendings are never
  stamped `expires_at` → never auto-fireable. Preserved unchanged.
- The sweeper pattern: `_countdown_sweeper` (`app.py:476-539`), `_discover_expired_pendings`
  (`:430-473`, reader path), lifespan start-when-enabled + clean teardown (`:1742-1759`),
  `CountdownAutoFireConfig` (`autonomy/config.py:17-30`).
- `init_pipeline_schema` is `CREATE TABLE IF NOT EXISTS`, called at `_build_context`
  (`app.py:638-641`); a **new table needs no ALTER**. `AppContext` (`app.py:102-130`) carries
  config fields; `_build_context` loads config (`app.py:669-789`).

### P5.1b-1 — `pipeline/schedule.py`: pure `next_fire` arithmetic (**interval-only**; cron deferred)

> **Architect-routed Y1 = (c) interval-only, defer cron** (`architect-routing-on-plan.md`):
> a hand-rolled cron evaluator is the greenfield-correctness class P5.1a cyc1 shipped as the
> RSS billion-laughs hole — kept **out** of the scheduler dual-lens. The `kind` column stays
> (P5.1b-2) for forward-compat; cron evaluation lands in a focused follow-on with its own
> review. This routing narrows **only** this module — P5.1b-2/-4/-5 are unchanged.

- **What:** A new self-contained module computing `compute_next_fire(kind: str, expr: str,
  after_ms: int) -> int` and `validate_schedule_expr(kind, expr) -> None`, with **no LLM and
  no I/O** — orchestration = code (ADR-042 D3). **P5.1b implements `interval` only.**
- **Where:** new `src/orchestrator/pipeline/schedule.py`; tests `tests/pipeline/test_schedule.py`.
- **Why:** ADR-042 D3. Scheduling timing is deterministic code; the **only** LLM in a
  scheduled run stays the analyze/reduce content-gen inside the unchanged `run_pipeline`. No
  new routing `LLMPurpose`.
- **Acceptance criteria:**
  - `kind == "interval"`: `expr` is a positive integer seconds string; `compute_next_fire`
    returns `after_ms + int(expr) * 1000`. Non-positive / non-integer `expr` →
    `validate_schedule_expr` raises `ValueError`.
  - `kind == "cron"`: **deferred** — `validate_schedule_expr` raises `ValueError` ("cron
    scheduling is deferred to a follow-on slice") and `compute_next_fire` raises
    `NotImplementedError`. The `kind` column's existence (P5.1b-2) **must never imply a
    working cron path** — `kind=cron` is rejected at create time (P5.1b-5, 422), so the
    sweeper never sees a cron schedule.
  - Unknown `kind` → `ValueError`.
  - **Module doc-comment (N2):** note that the act recomputes `next_fire =
    compute_next_fire(kind, expr, now)` at **claim time** (P5.1b-4 step 3), so an `interval`
    schedule drifts by up to `sweep_interval_s` (+ writer queueing) per fire — the **correct
    price of the ratified skip-to-next posture** (B3 / ADR-042 D4/D5); computing from the old
    `next_fire` would re-introduce the backfill storm B3 rejects.
  - **Interval unit tests (Lens A):** boundary (`interval=1`), large-interval overflow safety,
    non-positive / non-integer / empty-string rejection, unknown-kind rejection, and `kind=cron
    → ValueError / NotImplementedError`. Deterministic — pass `after_ms` explicitly, never read
    the wall clock in a test assertion path.
- **Out of scope:** **cron evaluation** (deferred follow-on — its own greenfield-correctness
  review); timezones other than UTC; any third-party cron dependency (Y1 routing rejected
  both (a) hand-rolled and (b) `croniter` for P5.1b).

### P5.1b-4 — sibling `_schedule_sweeper` + `_discover_due_schedules` + boot re-arm + lifespan

- **What:** A sibling background sweeper parallel to `_countdown_sweeper`, sharing **no**
  spine-critical code: reader-path discovery, writer-path act (claim-then-run), a boot re-arm
  step, and lifespan start-when-enabled + clean teardown.
- **Where:** `src/orchestrator/api/app.py` — new `_discover_due_schedules`, `_schedule_sweeper`,
  `_rearm_schedules_on_boot` (near the countdown sweeper, ~`:430-539`), and lifespan wiring
  (~`:1742-1759`); tests `tests/api/test_schedule_sweeper.py` (+ async tests like the
  countdown-sweeper suite).
- **Why:** ADR-042 D1 (sibling, duplicate the ~10-line skeleton, share nothing — ADR-041 D2
  precedent), D4 (discover-on-reader / act-on-writer; **claim `next_fire` before run**;
  writer-side authoritative re-check = the double-fire/TOCTOU guard), D5 (boot re-arm =
  skip-to-next; advance-without-running past-due schedules), D6 (second caller of
  `run_pipeline`, `result.run_id` → `create_pipeline_run`).
- **Acceptance criteria:**
  - `_discover_due_schedules(ctx, now_ms)` runs on the **reader** (`ctx.get_reader_conn()` /
    reader executor), returns due `schedule_id`s via `list_due_schedules`. Never appends.
  - `_schedule_sweeper(ctx, cfg, loop)` loop body mirrors `_countdown_sweeper`
    (`app.py:494-538`): `await asyncio.sleep(cfg.sweep_interval_s)`; discover on
    `reader_executor`; for each due schedule, run the **act** on `writer_executor`; `except
    asyncio.CancelledError: raise`; `except Exception: log + continue`. **Imports/calls none
    of** `_countdown_sweeper` / `_discover_expired_pendings` / `_writer_approve_helper`.
  - **Act (single function on the writer), in this exact order (ADR-042 D4):**
    1. Re-read the schedule on the writer conn; **skip** (log) unless `enabled=1 AND
       next_fire <= now`.
    2. `get_pipeline(writer_conn, pipeline_id)`: if missing → skip; if `pipelines.enabled=0`
       → advance `next_fire` and skip the run.
    3. **`update_schedule_next_fire(writer_conn, schedule_id, compute_next_fire(kind, expr,
       now))` BEFORE the run** (claim; skip-to-next).
    4. `run_pipeline(pipeline_id, definition, deps=PipelineDeps(...), owner_user_id=
       schedule.owner_user_id)` → `create_pipeline_run(writer_conn, pipeline_id=…,
       room_id=result.room_id, owner_user_id=schedule.owner_user_id, run_id=result.run_id,
       status="completed" if result.succeeded else "failed")`. `PipelineDeps` constructed
       exactly as the `/run` endpoint does (`app.py:1668-1683`).
  - `_rearm_schedules_on_boot(ctx)` runs on the **writer at lifespan startup, before the
    sweeper task is created**, only when enabled: `UPDATE … SET next_fire =
    compute_next_fire(kind, expr, now) WHERE enabled=1 AND next_fire <= now` (advance-without-
    running; future `next_fire` left untouched).
  - **Lifespan** (mirror `app.py:1742-1759`): when `ctx.pipeline_scheduler.enabled`, run boot
    re-arm, then `asyncio.create_task(_schedule_sweeper(...), name="schedule-sweeper")`; in
    teardown `cancel()` + `with suppress(asyncio.CancelledError): await` **before**
    `ctx.shutdown()`. When disabled, nothing is started (byte-identical to P5.1a).
  - **Tests (Lens A):** fires only due+enabled; disabled/future skipped; `pipelines.enabled=0`
    → no run but `next_fire` advances; **claim-before-run double-fire guard** — a schedule
    discovered by two ticks (stale reader) runs **once** (second act sees advanced
    `next_fire`); boot re-arm advances past-due **without running**; run attributed to
    `schedule.owner_user_id`; clean teardown (no pending-task warning).
  - **Tests (Lens B):** with the scheduler OFF, the app behaves byte-identically (no task
    started); the countdown sweeper + its discovery + `_writer_approve_helper` are
    **untouched** (a grep/AST assertion that `_schedule_sweeper` references none of them);
    `run_pipeline` unchanged (the scheduler imports it, does not edit it).
- **Out of scope:** schedule-management endpoints (P5.1b-5); editing `run_pipeline`,
  `_countdown_sweeper`, `_writer_approve_helper`, or the gate.

### P5.1b-5 — owner-private schedule-management endpoints

- **What:** Minimal CRUD so schedules can exist: create / list / delete / enable-disable,
  all owner-private + fail-closed.
- **Where:** `src/orchestrator/api/app.py` (`_register_routes`, near the `/pipelines*` routes
  ~`:1534-1707`) + request/response Pydantic models near `:291-320`; tests
  `tests/api/test_schedule_endpoints.py`.
- **Why:** ADR-042 D9 — the sweeper is inert without a create path (the ADR-041 D7
  "minimal CRUD so there is something to run" precedent), owner-private (ADR-041 D7 / R0-A F3)
  under fail-closed server-derived principal (ADR-039 D1). **See §5 push-back #2** —
  included as necessary-for-the-slice-to-function; architect may trim.
- **Acceptance criteria:**
  - `POST /pipelines/{pipeline_id}/schedules` — body `{kind, expr}`; load the pipeline on the
    reader, **403 if `record.owner_user_id != principal.user_id`**, 404 if missing;
    `validate_schedule_expr(kind, expr)` → **422 on malformed**. Per Y1 routing,
    `validate_schedule_expr` raises for `kind=cron`, so **`kind=cron` is rejected at create
    with 422** ("cron scheduling deferred") until the follow-on lands — the `kind` column's
    presence never implies a usable cron path. For `kind=interval`, compute the initial
    `next_fire = compute_next_fire(kind, expr, now)`; `create_schedule(...)` on the writer with
    `owner_user_id = principal.user_id`; return the schedule record. Principal is
    `request.state.principal` (the `/run` pattern, `app.py:1650-1666`) — never from the body.
  - `GET /pipelines/{pipeline_id}/schedules` — owner-only; returns that pipeline's schedules.
  - `DELETE /pipelines/{pipeline_id}/schedules/{schedule_id}` — owner-only; `delete_schedule`.
  - `PATCH /pipelines/{pipeline_id}/schedules/{schedule_id}` body `{enabled: bool}` —
    owner-only; `set_schedule_enabled`. (On enable, recompute `next_fire` from now so a
    long-disabled schedule does not fire immediately.)
  - Owner-check reuses the **parent pipeline's** `owner_user_id` (a schedule inherits its
    pipeline's owner); a non-owner gets **403** on every verb.
  - Tests: owner happy-path each verb (interval); non-owner 403 each verb; missing-pipeline
    404; malformed-`expr` 422; **`kind=cron` → 422** (deferred); created interval schedule
    appears in `list_due_schedules` once due.
- **Out of scope:** sharing/collaborative access (owner-private is the safer default,
  ADR-041 D7); editing the pipeline definition (P5.1a CRUD owns that).

## 5. Where I'd push back

**#1 — Cron parser mechanism — RESOLVED (architect routed Y1 = (c) interval-only).**
The repo has **no cron dependency** (`pyproject.toml:6-11`); the ratified B2 table carries
`kind (cron|interval)` but *how* to parse cron was outside the decision surface. The architect
routed **(c) interval-only, defer cron** (`architect-routing-on-plan.md`): a hand-rolled cron
evaluator is the same greenfield-correctness class as the P5.1a RSS billion-laughs hole and is
kept out of the scheduler dual-lens (mirrors B0's defer-incrementality discipline). **Absorbed:**
P5.1b-1 is now interval-only (cron → `ValueError`/`NotImplementedError`); ADR-042 D3 rewritten;
P5.1b-5 rejects `kind=cron` at create (422). The `kind` column stays for forward-compat; the
table (P5.1b-2), sweeper (P5.1b-4), and endpoint shape (P5.1b-5) are otherwise unchanged.

**#2 — Schedule-management endpoints (P5.1b-5) — RESOLVED (architect routed Y2 = keep).**
B0–B6 did not name an HTTP create surface, but a scheduler with no create path is inert; I
included a minimal owner-private CRUD per the ADR-041 D7 "minimal CRUD so there is something
to run" precedent. Architect routed **keep** — P5.1b-5 + ADR-042 D9 stand unchanged.

**#3 — Config home (low-stakes).** I put the config in a dedicated `config/pipeline.yaml` +
`pipeline/config.py` (keeps the scheduler a pipeline concern; `autonomy/` stays gate-only).
The brief offered `config/autonomy.yaml §pipeline_scheduler` as the alternative (the lighter
mirror of `CountdownAutoFireConfig`). If you prefer the autonomy.yaml home, P5.1b-3 moves the
section + the model location; nothing else changes.

**#4 — Boot-re-arm vs sweeper-discovery semantics (flagging, not blocking).** ADR-042 D5
makes boot re-arm **advance-without-running** for past-due-during-downtime schedules
(skip-to-next, B3-ii), which is *distinct* from the sweeper's discover-**and-run**. The act
also **claims `next_fire` before running** (D4) so a crash mid-run cannot double-fire on
reboot. These two points are the load-bearing Lens-A invariants; I've made them explicit
acceptance criteria in P5.1b-4 so they don't get implemented as "discover → run → re-arm"
(which would double-fire on crash and run-on-boot stale data). Surfacing in case the intended
catch-up posture differs.

No other push-backs — B0–B6 are ratified and the seams verified clean at `811412a`.
