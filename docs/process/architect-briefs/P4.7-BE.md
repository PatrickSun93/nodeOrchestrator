# Architect brief — P4.7-BE: plugin management endpoints — realizing the pinned contract on the admission + authz trust boundary (decision-surface)

**Task:** P4.7-BE — build the **backend management endpoints** for the plugin registry: `GET /plugins`, `POST /plugins/{id}/enable·disable·admit`, `DELETE /plugins/{id}` (the contract **pinned** in ADR-038 D5, with its **authz dimension** pinned in ADR-039 D9). The architect split P4.7 into two tracks: **this BE track** (management endpoints — full ADR-008 lifecycle + mandatory dual-lens, because it touches the **plugin-admission trust boundary + auth/authz**) and the **frontend UI** (E2/E3, a later light track binding these endpoints). This slice is the **producer** the two prior inscribe-before-producer ADRs (ADR-038 D5, ADR-039 D9) were pinned *for*.

**Class:** trust-boundary slice — touches the **admission** boundary (ADR-031/038: what code gets admitted) **and** the **identity/authz** boundary (ADR-039: who may actuate). `requires_cross_family_review: true` (set in `.workflow/P4.7-BE.yaml`). Mandatory dual-lens (DP5). **Likely no new ADR** — the contract is pinned; this realizes it + inscribes amendments — **unless** the scope fork or DP1 reopens a deferred ADR-038 decision (DP4).

**Status of this doc:** a **DECISION-SURFACE**, not a plan and not a set of decisions. Five decision points (the architect's DP1–DP5) carry **architect-ratifiable leans + tradeoffs**; the architect-partner does **not** decide. The load-bearing calls are **⭐⭐ DP1 (write-semantics vs boot-only registry)** and **⭐⭐ DP2 (authz)**. Note honestly: **DP2's main axis is already ratified** (ADR-039 D9 pinned authenticated⇒allowed under DP3a) — what's genuinely open there is a *seam-granularity* sub-question. A **scope fork** (plugin-endpoints-only vs +config-mgmt) sits above DP4 and should be ruled first. No senior plan is drafted until the architect ratifies (≥ scope, DP1, DP2).

**The two boundaries this slice turns on.** ADR-038 answered *what gets admitted* (config-file registry, boot-only, digest floor); ADR-039 answered *who is calling + what they may do* (authenticated principal, all-or-nothing operator). P4.7-BE is the **first endpoint surface that actuates both at once**: an authenticated HTTP request that **mutates the admission registry**. The contract is pinned on both axes — so the slice's job is to **realize it without (a) reopening ADR-038's deferred runtime-mutation surface or (b) letting an endpoint relax the admission floor or the fail-closed config-write discipline.**

**Scope fork (rule first — it sizes the slice + feeds DP4).** The commit title reads "plugin/**config** management endpoints." Two readings:
- **(scope-A, lean)** **Plugin endpoints only** — "config" = `config/plugins.yaml` (the plugin registry *is* a config file; enable/disable/admit *are* config writes). This is the ADR-038 D5 pinned contract, end-to-end realize.
- **(scope-B)** **Plugin + config-management endpoints** — also build E3-style writes (MCP-server / agent / model / autonomy-tier config). These have **no pinned contract**, a **much larger arbitrary-config-mutation trust surface**, and would be **genuinely new decisions → ADR-041**.

**Lean: scope-A (plugin-endpoints-only).** The dispatch's DP1–DP5 are all plugin-centric; E3 is a *separate* roadmap surface with no pinned contract; folding it in would smuggle a new ADR's worth of trust surface into a "realize the pinned contract" slice. But this is the architect's call — confirm before the senior plans.

## 1. ⭐⭐ DP1 — Endpoint write-semantics vs the boot-only registry (THE load-bearing call)

The承重点 the architect named. The registry is a **config file, boot-only** (ADR-038 D1/D2, "zero new runtime-mutation surface"). How do the *write* endpoints (`enable`/`disable`/`admit`/`DELETE`) land their effect?

| Option | What it builds | Trade-off / honest residual |
|---|---|---|
| **(a) Write `config/plugins.yaml`, effect next restart** (lean) | A config-file **writer**: each write mutates `config/plugins.yaml` on disk and the response **signals "effect next restart"** — **no live mutation** of the running `AppContext`. Needs validate-before-write + atomic temp+rename + a round-trip through `load_plugin_registry`'s validator (DP3b). | **This is literally what ADR-038 D5 says** ("every write edits `config/plugins.yaml` and takes effect at next restart (boot-only, D2)"). Lowest new surface; the boot-only liveness/consistency argument (no mid-turn `MCPSession` teardown, no rebuild on the `max_workers=1` writer) is preserved. **But** the GUI shows *intent that lands on restart*, not live state — and a config-file **writer** is itself new code requiring fail-closed discipline (DP3b). |
| **(b) Runtime-mutable store / hot-reload** | A backend-owned mutable store (or live `AppContext` mutation) so enable/disable/admit take effect **without restart**. | **ADR-038 explicitly DEFERRED this** (Considered-alternatives "Runtime store (DP1a)" + "Hot-reload (DP2b)"; residuals "Runtime-store deferred" / "Hot-reload deferred"). It reopens the single-writer-consistency + mid-turn `MCPSession`-teardown liveness surface (ADR-028 D5 / ADR-037 D3). **Choosing it reverses an Accepted ADR-038 deferral → new ADR-041 + a large trust/liveness surface.** |

**Lean: (a) — realize the pinned boot-only config-write contract.** It is the ratified ADR-038 posture; (b) is a deliberate ADR-038 deferral, not a gap to fill opportunistically — picking it is an architect re-decision.

**⭐⭐ architect-weight + the flip condition:** the whole slice's shape (a config-file *writer* vs a *runtime store*) hangs here. **If the near-term product goal demands LIVE plugin management** (operators toggling plugins without a restart), **(b) is required-in-slice** → ADR-041 + the deferred liveness surface comes due now. The architect rules whether boot-only is still the posture for the *endpoint* era.

**Embedded sub-decision — `admit` semantics (genuinely open).** ADR-038 D2 separates **fetch** (`fetch_plugin_bundle` puts digest-verified bytes on disk) from **admit** (author the entry). The D5 row says admit = "Author/replace a fetched entry (source_url + digest + version)." So does `POST /plugins/{id}/admit`:
- **(i)** *only author the registry entry* (fetch is a separate out-of-band/CLI action) — aligns ADR-038 D2's fetch≠admit split, but leaves *"who fetches the bytes"*: an entry whose bytes aren't on disk yet will be **refused at next boot** until fetched (a named residual);
- **(ii)** *also trigger `fetch_plugin_bundle`* synchronously (download + digest-verify + extract) as part of the endpoint — one-step admit, but couples a network fetch + the gauntlet into an HTTP handler (timeout/size/failure surface).

Surface both; this is a real fork (it determines whether the endpoint surface needs a fetch trigger at all). It interacts with DP3a (either way, the gauntlet must run — the endpoint never relaxes the digest floor).

## 2. ⭐⭐ DP2 — Authorization: who may call these endpoints?

**The main axis is already pinned + ratified** (ADR-039 D9 + D5 seam #2): these are operator actions requiring an authenticated principal; under **DP3a** (architect-ratified, all-or-nothing operator on the fully-trusted-members assumption) **any authenticated user** is a full operator.

**Lean: authenticated⇒allowed + plant the D5 seam #2 code comment**, mirroring the realized seam #1 (`app.py:997` — read `request.state.principal`, no role check, named-comment marks where DP3b would gate). Build **no** role check (DP3b is deferred unless members become non-fully-trusted — ADR-039 D5/D10). This is *realizing the pinned ADR-039 D9 contract*, not a new decision.

**The genuinely-open sub-question — seam granularity.** ADR-039 D5 lumps **"plugin-admit/enable/disable"** as a **single** seam (#2). But **admit** (introduces *new fetched code* into the trust boundary) is a strictly **higher-trust** action than **enable/disable** (toggles *already-vetted* code). Under DP3a they are identical (all authenticated⇒allowed). The cheap, expensive-to-retrofit inscription question: **one seam, or give `admit` its own finer seam granularity now** (an extra named comment) so a future DP3b can gate *"who may admit"* stricter than *"who may toggle"*?

| Option | Trade-off |
|---|---|
| **One seam (#2 as pinned)** | Faithful to ADR-039 D5 verbatim; minimal. The admit/toggle trust gap is implicit. |
| **Admit-gets-its-own-seam** (inscribe finer now) | Makes the admit>toggle trust gradient explicit at the seam, so DP3b is additive at the right granularity. A small ADR-039 D5 annotation; near-zero code cost. |

**⭐⭐ but mostly ratify-the-pinned.** Confirm: (1) realize authenticated⇒allowed + seam #2 (not activate DP3b); (2) the seam-granularity sub-question. **Flip condition (inherited ADR-039 D5/D10):** if members become non-fully-trusted, DP3b becomes required-in-slice — `RB-AUTHZ` flips dangerous (any authenticated/compromised account can admit arbitrary fetched code, the highest-trust actuator).

## 3. DP3 — The admission trust boundary: endpoints must not pierce the gauntlet (mostly ratify)

Two halves, both **constitutional** (ADR-038 Constitutional carry-forward: "the registry/lifecycle must not become a path to admit code that skips activation + integrity"; *"'It's sandboxed' is never a reason to admit unverified code"*).

**(3a) The admit endpoint cannot bypass the integrity floor.** Whether admit authors-only (DP1-i) or triggers fetch (DP1-ii), the **digest-before-extract gauntlet (`fetch.py`) still runs** and a digest-bearing operator-authored entry stays **mandatory** for fetched plugins; the shape↔root mismatch + duplicate-id + `isinstance(enabled, bool)` validators (`provenance.py:282-355`) stay the fail-closed floor. The endpoint writes operator **intent** — it never lowers the bar. **Lean: ratify** — the endpoint is a thin authoring surface over the *unchanged* gauntlet.

**(3b) Config-write is only as fail-closed as the writer.** The new writer **MUST validate the proposed mutation by round-tripping it through `load_plugin_registry`'s validator BEFORE persisting**, and write **atomically** (temp + rename), so an endpoint write can **never** produce a malformed `config/plugins.yaml` that trips `REGISTRY_REFUSE_ALL` at next boot — which would **disable every plugin** (a self-inflicted outage; `app.py:508` / `loader.py:630`). This is the "registry only as fail-closed as its parser" residual (ADR-038 D5) **extended to the write path**. **Lean: validate-before-persist + atomic + reject-any-write-whose-result-would-refuse-all.** This is the heart of why the slice is dual-lens.

## 4. DP4 — New ADR-041, or realize + amend?

**For the plugin endpoints:** the contract is pinned on **both** axes (ADR-038 D5 shapes + ADR-039 D9 authz). Building them is **realize + inscribe amendments**: annotate ADR-038 D5 ("built in P4.7-BE") and realize ADR-039 D5 seam #2 in code. No new architectural *decision* → **no new ADR required** for the endpoints themselves; amendment-at-impl suffices (the ADR-037/038/039 precedent — amendments inscribed at impl, matching Accepted status).

**A new ADR-041 IS required iff** any of:
1. **Scope-B** is ruled in (config-mgmt endpoints — no pinned contract + arbitrary-config-mutation trust surface = genuinely new decisions);
2. **DP1 = (b)** runtime-store/hot-reload (reverses ADR-038's deferral);
3. The architect judges the **config-file-writer surface itself a genuinely-new runtime trust boundary** — ADR-038 contemplated *"edit `config/plugins.yaml`"* as an **operator's hand on the file**, not via an **authenticated HTTP write path**; if that HTTP-triggered on-disk mutation is "new enough," a small ADR-041 captures it (vs an ADR-038 D2/D5 amendment).

**Lean: plugin-endpoints-only (scope-A) + DP1(a) → amend ADR-038 D5 / realize ADR-039 D9 at impl, no new ADR.** This ties DP4 to the scope fork (§0) + DP1. The architect rules whether the HTTP-config-writer crosses the "new ADR" line (3) or rides as an ADR-038 amendment.

## 5. DP5 — The dual-lens two-lens design (`requires_cross_family_review: true`, already set)

Following the architect's suggested split (and the ADR-038/039 precedent: Lens A = trust boundary, Lens B = spine preservation). Plan-stage writes `docs/process/reviews/P4.7-BE/external-r0b-prompt.md`.

- **Lens A — the management-endpoint admission/authz trust boundary** (the "endpoint done wrong" adversary). Can an endpoint: (1) **admit unverified code** / bypass the digest-before-extract gauntlet (DP3a); (2) **act as an unauthenticated or wrong principal** — the fail-closed boundary holds + the principal is server-derived, never request-read (ADR-039 D7); (3) **accidentally land on the public allowlist** (`PUBLIC_PATHS`) — a write endpoint must never be exempt; (4) **produce a malformed/refuse-all `config/plugins.yaml`** (DP3b fail-closed config-write); (5) **forge a shape↔root mismatch / provenance** through the write path.
- **Lens B — spine-preservation / no-regression** (the "did the endpoints break the existing constitution" adversary). Is the **boot-only invariant preserved** (NO runtime mutation of the running `AppContext`, no hot-reload snuck in — DP1)? Is `load_plugin_registry`'s validator **byte-unchanged** and the write-path **round-trips it**? Does the **autonomy gate stay untouched** (admission stays a non-gated operator action, no new `LLMPurpose` — ADR-038 DP2c)? Do the **existing routes + auth middleware + the realized seam #1** regress? `_execute_local_call` / gate byte-frozen (ADR-038 constitutional carry-forward).

*(Genuinely orthogonal — "the endpoints are insecure / pierce admission" vs "the endpoints broke ADR-038/039's boot-only + spine." That orthogonality is the dual-lens design goal — `dual-lens-r0b.md`.)*

## 6. Residual set — inscribe, don't soften (the `RB-FS/NET` / `RB-ADMIT` / `RB-AUTHZ` discipline)

- **`RB-AUTHZ`** (inherited ADR-039 D10) — endpoints are authenticated⇒allowed; **any authenticated (or compromised) account can admit/enable/disable any plugin** — the highest-trust actuator. Persists until DP3b (a role model at seam #2).
- **`RB-ADMIT`** (inherited ADR-038 D3) — admit-via-endpoint inherits the same **no-author-identity / no-revocation / no-update-trust** residual; the endpoint authors operator intent and does **not** change the integrity floor.
- **Boot-only / no-live-management** (inherited ADR-038 D2, under DP1(a)) — endpoint writes show **intent that lands at next restart**; the GUI renders "effect next restart," not live state. (If DP1(b): this residual is *retired* but ADR-041 + the liveness surface is *incurred*.)
- **Config-mgmt endpoints (E3)** — under scope-A, a **named residual** (deferred to a follow-on BE slice + ADR-041).
- **Rate-limiting** on the new write chokepoints (`POST`/`DELETE /plugins/*`) — if deferred, a named residual (inherited ADR-039 D10; the post-auth per-identity limiter applies).
- **DP1's admit-fetch-trigger leftover** — if admit authors-only (DP1-i), inscribe: an entry whose bytes aren't yet fetched is **refused at next boot** until the separate fetch action runs.

## 7. What the architect ratifies (the routing surface)

1. **SCOPE** (rule first) — **scope-A plugin-endpoints-only** (lean) vs scope-B +config-mgmt (no pinned contract → ADR-041). *Sizes the slice + feeds DP4.*
2. **⭐⭐ DP1 — write-semantics** (lean: **(a)** config-file write, boot-only — realizes ADR-038 D5; **(b)** reopens the deferred runtime-store/hot-reload → ADR-041 + liveness surface). *Plus the `admit` sub-fork: (i) author-entry-only vs (ii) also-trigger-fetch.* **THE load-bearing call.**
3. **⭐⭐ DP2 — authz** (lean: realize **authenticated⇒allowed + seam #2** under DP3a, mirror the live seam #1; **do not** activate DP3b). *Open sub-question: one seam vs give `admit` its own finer seam granularity now.*
4. **DP3 — admission boundary** (lean: ratify both — the endpoint never relaxes the digest gauntlet (3a); the writer is **validate-before-persist + atomic + reject-refuse-all** (3b)).
5. **DP4 — ADR posture** (lean: **no new ADR** — amend ADR-038 D5 / realize ADR-039 D9 at impl — **unless** scope-B, or DP1(b), or the HTTP-config-writer is judged a new boundary → ADR-041).
6. **DP5 — dual-lens** (confirm Lens A admission/authz + Lens B boot-only/spine; `requires_cross_family_review: true` already set).

Once ratified, P4.7-BE gets the senior plan (+ ADR-038/039 amendments, or ADR-041 if forced) → impl → mandatory dual-lens (R0-A ∥ R0-B) → plan-vs-impl → merge.
