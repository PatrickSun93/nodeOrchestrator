# Architect brief — P5.1: scheduled analysis pipeline — deterministic staged headless execution (decision-surface)

**Task:** P5.1 — the **first P5 feature** and the first **deterministic, staged, unattended** product capability. A pipeline: **(trigger)** scheduled (cron / every-N-hours / daily) *and* manual; **(read)** multi-source — web URL (`web_fetch`) + RSS/API/feed + local file; **(analyze)** a fan-out of **dynamic, per-round-different** analysis prompts (not one fixed persona); **(reduce)** into a summary; **(output)** a room (GUI-visible) + email/notification. Core: **deterministic stages** (fetch → fan-out-analyze → reduce), **headless** (no human in the loop), **schedulable + persistable + restart-recoverable**.

**Class:** **heavy**; `requires_cross_family_review: true` (set in `.workflow/P5.1.yaml`); **new ADR-041** (next unused — ADR-040 is the highest existing). Dual-lens (two orthogonal failure-family lenses, DP8). Greenfield in **execution model** (a new deterministic primitive), **scheduling** (a recurring scheduler), **read sources** (RSS/feed + a source abstraction), and **headless actuator authorization** (a posture *beyond* P4.6's `RB-AUTOFIRE`).

**Status of this doc:** a **DECISION-SURFACE**, not a plan and not a set of decisions. The decision points carry **architect-ratifiable leans + tradeoffs**; the architect-partner does **not** decide. **The core tension** is that the orchestrator today is a **conversational, emergent, human-driven** system — agents respond *emergently* per `should_agent_speak`, a turn is driven *interactively* by a human `POST /intent`, and every irreversible actuator (`send_email`) is *human-confirmed* — whereas P5.1 is **deterministic** (fixed stage order, explicit fan-out + reduce), **headless** (a timer drives it, no human), and wants to **actuate an external irreversible output unattended**. **The load-bearing trio — decide together:**
- **⭐⭐ DP1 — the pipeline execution model** (ride on the room/event model vs an independent deterministic primitive over the same substrate),
- **⭐⭐ DP2 — the scheduling mechanism** (generalize P4.6's ADR-040 sweeper vs a sibling scheduler), and
- **⭐⭐ DP6 — the headless actuator-authorization boundary** (the honesty crux: P4.6's `RB-AUTOFIRE` deliberately **excluded exactly this** — `send_email` is **HARD-tier** *and* **reversibility=3 below the floor=5**, so headless email inverts the *two* guards `RB-AUTOFIRE` installed).

No plan / ADR-041 is drafted until the architect ratifies (≥ DP0 scope, DP1, DP2, DP6).

P5.1 **reuses heavily** but must add the *deterministic, headless, scheduled* spine the conversational model never needed.

**The framing that keeps P5.1 constitutional (carry through every DP).** P4's spine held **byte-frozen across all 8 slices**: `_execute_local_call` + the autonomy gate (`score`/`decide_tier`/`emit_gate_decision`) **zero-diff**, **no new `LLMPurpose` beyond content-gen**. P5.1 must hold the same line: **the pipeline's *orchestration* — stage order, fan-out count, source list, output routing, schedule timing — is all CODE/CONFIG, never an LLM judgment** (CLAUDE.md "Never LLM-judge a routing decision"). The **only** LLM in the pipeline is the **analyze content-gen** (generate analysis text from fetched data — an `AGENT_RESPONSE`-class content purpose). The scheduler **actuates, never decides** (exactly as ADR-040's timer); the pipeline **stages, never emerges**.

## 0′. ⭐ DP0 — Scope: one heavy slice, or a P5 wave? (decide first — it shapes everything)

P5.1 as briefed spans **four greenfield subsystems** (deterministic execution primitive + recurring scheduler + multi-source reader + headless-actuator authorization) **plus** a new constitutional crossing (DP6) **plus** persistence + dynamic-prompt plumbing. That is **substantially larger** than any single P4 slice (each of which was one ADR-sized surface). Two shapes:

| Option | What | Trade-off |
|---|---|---|
| **(a) One heavy slice P5.1** | One brief → one senior plan → one ADR-041 → one impl → one dual-lens. | Matches the `.workflow/P5.1.yaml` setup as-is. **But** the impl is large enough to risk junior context exhaustion, and the **DP6 crossing** (the riskiest surface) is entangled with four build-outs in a single review — the dual-lens adversary has to hold the whole pipeline *and* the email-authorization posture at once. |
| **(b) A P5.1 wave (lean)** | Decompose: **P5.1a** deterministic pipeline primitive + multi-source read + dynamic prompts + **reversible-only output** (room summary; **no email** — fully safe, no crossing); **P5.1b** the recurring scheduler + persistence + manual trigger + restart re-arm; **P5.1c** the **headless email actuator authorization** (the `RB-AUTOFIRE`-beyond crossing — *isolated* for a focused dual-lens). | Each sub-slice is P4-sized; the **constitutional crossing (P5.1c) gets its own honest dual-lens** instead of riding inside a big feature; P5.1a delivers a *working, safe* headless pipeline (GUI output) with **zero** new authorization surface. Cost: three brief/plan/ADR cycles (though P5.1b/c may share ADR-041 sections or get ADR-042/043). |

**Lean: (b) a wave** — specifically, **carve P5.1c (headless email) out from day one** so the safe pipeline (P5.1a, reversible output only) is never blocked on the email-posture ratification, and the crossing gets the isolated scrutiny `RB-FS/NET`/`RB-AUTOFIRE` got. **But this is the architect's scope call** — if you want P5.1 as one slice, the DPs below still hold; they just land in one ADR-041 instead of split. *(The rest of this brief surfaces the full surface; the wave-vs-monolith call only changes how it is packaged.)*

## 1. ⭐⭐ DP1 — The pipeline execution model (load-bearing — the architecture)

The orchestrator is **conversational + emergent**: a turn is driven by a human `POST /intent`, the agent *set* is decided per-turn by `should_agent_speak`, and the loop **re-dispatches on result events**. A pipeline is **deterministic + staged**: fetch the configured sources, fan out *exactly* the configured analyses, reduce. Where does the pipeline's execution live?

| Option | What it builds | Trade-off / honest residual |
|---|---|---|
| **(a) Ride on the room/event model** — pipeline = a special headless "room run" | A new `RoomType` (e.g. `pipeline`) + a trivial state machine; the stages are driven through the existing `dispatch_turn` / turn-loop by injecting synthetic `current_event`s. | Maximal reuse of room machinery — **but fights the grain hard**: the room model's two non-determinisms (emergent agent *set* via `should_speak`; result-driven *re-dispatch*) are exactly what a pipeline must **suppress**. You'd be configuring the conversational engine to *not* be conversational (single-agent rooms, trigger hacks, fan-out faked as sequential turns). Pollutes the room/agent contracts (ADR-010/011/012) with a non-conversational special case. |
| **(b) Independent deterministic primitive over the same substrate** (lean) | A new `src/orchestrator/pipeline/` **stage driver**: a `StageGraph{fetch → fan_out(analyze×N) → reduce}` executor that **reuses the lower-level units** — the **agent-turn unit** (one agent + supplied prompt + context, run to tool-completion, ADR-033), **`execute_pending_tool_calls`** for tool execution, **the SSRF/sandbox read primitives** (DP3), and **the event store** — but does **NOT** use the emergent room *dispatch* (`should_speak` / result-driven re-dispatch). Its events **land in a room** (greenfield: a pipeline-run room) so the GUI sees them. | **Clean separation**: the conversational contracts stay untouched; the pipeline gets *real* determinism (explicit stages, explicit fan-out, explicit reduce). Reuses ~80% of the execution code (turn unit + tools + store) without inheriting the conversational semantics. **Cost / residuals:** (i) a **net-new headless driver on the writer** (none exists today — `_write_and_turn` is HTTP-bound); (ii) **the single-writer invariant (ADR-028 D1) bounds "fan-out"** — the analyze branches' **LLM calls can overlap** (not writes), but **every event append serializes on `writer_executor`** (like the countdown sweeper actuates on the writer); fan-out is *logically parallel, write-serialized* — inscribe honestly; (iii) a deterministic stage-runner is new orchestration to test. |
| **(c) Hybrid** — independent stage graph that *delegates each analyze branch* to the existing bounded turn-loop | (b)'s stage driver, but each "analyze branch" = one invocation of the **existing** ADR-033 turn-loop (bounded, gate-routed, tool-capable), not a re-implemented mini-loop. | The **pragmatic sweet spot** — get determinism at the stage layer, reuse the *proven, gate-correct* turn-loop at the branch layer (no duplicated gate/executor reasoning → a Lens-B win). Effectively (b) with an explicit "don't re-implement the turn" rule. **Lean folds (c) into (b).** |

**Lean: (b)/(c)** — an **independent deterministic stage-runner that reuses the agent-turn + tool-execution + read primitives but bypasses the emergent room dispatch**, writing its events into a (greenfield) pipeline-run room for GUI visibility. It is the only option that gives genuine stage determinism without bending the conversational contracts into a shape they were explicitly designed *not* to take (ADR-010/011/012). **But this is the architect's architecture call** — (a) is defensible if you want a single execution engine and accept the room-contract pollution. **Embedded sub-decisions:** the **fan-out concurrency model** (write-serialized; LLM-overlap yes/no — a perf vs simplicity call); whether a pipeline run reuses an **ordinary room** (GUI "just works") or a **distinguished pipeline-room subtype** (clearer audit, more surface).

## 2. ⭐⭐ DP2 — Scheduling mechanism + manual trigger (load-bearing — the durable timer)

The user needs **cron / every-N-hours / daily** schedules **and** a manual "run now." P4.6/ADR-040 already built the **exact architectural template**: a single lifespan-started asyncio sweeper, durable next-fire on events, reader-discovery + writer-actuation, **boot re-arm**, opt-in. The question is **reuse-the-code vs reuse-the-pattern**.

| Option | What it builds | Trade-off / honest residual |
|---|---|---|
| **(a) Generalize the ADR-040 sweeper** into a shared timer/scheduler both COUNTDOWN auto-fire and pipeline schedules ride | One `Scheduler` abstraction; COUNTDOWN deadlines + pipeline schedules are both "things with a next-fire." | DRY — **but couples two very unlike concerns**: the COUNTDOWN sweeper is **spine-load-bearing** (its still-pending predicate + writer-atomic actuation are the `RB-AUTOFIRE` security crux, ADR-040 D5). A one-shot gated-call deadline and a **recurring** cron schedule (re-arm-after-fire, catch-up semantics, schedule CRUD) share *shape*, not *invariants*. Generalizing risks **regressing the auto-fire spine** under a refactor — a Lens-B hazard the architect should weigh. |
| **(b) A sibling scheduler following the ADR-040 pattern** (lean) | A new `_schedule_sweeper` **parallel** to `_countdown_sweeper`: same lifespan-asyncio shape, same durable-defs + boot re-arm + opt-in posture, but **independent code** for the recurring-schedule unit (cron/interval parse, next-fire compute, re-arm-after-fire). | **Reuses the proven pattern, not the spine-critical code** — the two sweepers stay decoupled; a bug in schedule logic can't regress auto-fire idempotency. The ADR-040 boot-re-arm derivation (`api/app.py:~380-423`) is a direct template for "a schedule whose fire-time elapsed during downtime" (DP7). Cost: a second background task in the lifespan (ADR-025 D6 note — bounded, must shut down cleanly). |
| **(c) External scheduler** (cron / APScheduler / separate process) | Offload timing outside the process. | **Already rejected by ADR-040 D1** for the same reasons: new dependency + deployment surface, breaks the single-process localhost posture. **Lean: reject** unless a distributed deployment is foreseen. |

**Lean: (b)** — a sibling scheduler reusing the ADR-040 *pattern*. **Manual trigger:** a thin API endpoint (e.g. `POST /pipelines/{id}/run` or `/schedules/{id}/run`) that invokes **the same execution path** the scheduler fires (a human-initiated headless run) — *not* a second code path. **Embedded sub-decisions:** **catch-up semantics** for a schedule whose fire-time passed during downtime — **(i) run-once-immediately on boot**, **(ii) skip-to-next**, or **(iii) re-arm a fresh interval** — the direct analog of ADR-040 DP1″ (lean **(ii) skip-to-next** for a periodic analysis: a missed 9am run is usually stale by noon; but it is a posture call); **cron-expression dependency** (a cron parser is a small new dep — acceptable, or restrict to interval+daily to avoid it).

## 3. ⭐ DP3 — Multi-source read abstraction (web + RSS + local file)

Three source kinds; two have tools today (`web_fetch`, `read_file`), one is greenfield (RSS/feed). The deeper question: the pipeline reads a **deterministic, configured** source set — should that be **agent-tool-calls** (LLM-mediated) or a **deterministic fetch stage**?

| Option | What it builds | Trade-off / honest residual |
|---|---|---|
| **(a) No abstraction — wire the existing tools + one new feed tool** | The fetch stage has an agent call `web_fetch` / `read_file` / a new `rss_feed_fetch`; the LLM composes them. | Minimal build. **But** it makes **which sources get read an LLM decision** — non-deterministic, and brushes "orchestration = code, not LLM." Fine if the pipeline's source set is genuinely agent-discovered; wrong if it's a fixed configured list. |
| **(b) A declarative source abstraction (lean)** — `src/orchestrator/sources/` (NOT `connectors/`) | A typed `Source{kind: web\|rss\|file, locator, …}` list **in the schedule/pipeline config**; the fetch stage reads them **deterministically** (no LLM choosing *what* to fetch), reusing the **SSRF-validating client** (`net_trust.py`) for web/rss and the **path-sandbox** (`local.py`) for files. New: an **RSS/Atom parser** + (for incrementality) **last-seen feed state** (DP7). | **Deterministic fetch** (the user's "确定性分阶段" — the configured sources are read every run, reliably), reusing the **security floors** that already exist (SSRF, sandbox) without re-deriving them. **Name-collision guard: do NOT reuse `connectors/`** — it is ADR-019 ground-truth *output* producers; a read-source *input* abstraction in `connectors/` would invert the directory's meaning. **Cost:** RSS parsing + feed-state are genuinely new; the source abstraction is new surface (keep it thin — a fetch function per kind, not a plugin framework). |

**Lean: (b)** — a thin **declarative `sources/` abstraction** read deterministically, reusing the SSRF + sandbox primitives, with RSS/feed parsing as the one substantive greenfield piece. **Surface explicitly:** (i) **`connectors/` is the wrong home** (ADR-019 collision) — name it `sources/`/`readers/`/`ingest/`; (ii) **generic-API-poll** beyond plain HTTP (auth headers, GraphQL) is *further* greenfield — scope it in or defer; (iii) the SSRF floor **applies to RSS URLs too** (a feed URL is attacker-influenceable if user-supplied) — reuse `net_trust.py`, don't bypass it.

## 4. ⭐ DP4 — Dynamic, per-round analysis prompts

Today an agent's system prompt = **static persona** + **code-selected skills** (`decide_skills_for_context`, pure code) + a snapshot excerpt (`agents/dispatch.py:114-120`, `agents/selection.py:198-228`). The user wants **per-round-different** analysis prompts — *not* one fixed persona. Where do they come from?

| Option | Trade-off |
|---|---|
| **(a) Prompts as pipeline-config data (lean)** | The schedule/pipeline definition carries an explicit **ordered list of analysis prompts** (or prompt-refs); each fan-out branch (DP1) runs an ephemeral agent-turn with **the supplied prompt** as its task/system text + the fetched data as context. Prompts are **DATA**, injected at dispatch. **Constitutionally clean** — the prompt list is config (the operator's standing intent), not an LLM judgment; the LLM only generates analysis *content* from it (`AGENT_RESPONSE`-class). **Cost:** a new dispatch path that injects an explicit per-branch prompt (today the system block is persona+skills; supplying a per-branch prompt is a light, additive extension). |
| **(b) Prompts as skills** | Author the analysis prompts as `config/skills/` files, selected per-round by the existing pure-code selector. | Reuses the skill machinery exactly — **but** skills are *static authored artifacts selected by context*, not *per-run-varying data*; "dynamic / 每轮不同" fits config-data better. Viable if the architect wants prompts to be governed, reusable, version-controlled artifacts rather than free schedule config. |
| **(c) Runtime-generated prompts** (an LLM writes the next round's prompt) | A meta-agent generates each round's analysis prompt. | Most "dynamic" — **but** introduces an LLM *deciding what to analyze*. Stays content-gen *only if* it never gates/routes (it generates text, doesn't pick tiers/tools). **Surface the constitutional edge**; likely defer (over-builds the user's stated need, which is a *varying configured set*, not self-authored prompts). |

**Lean: (a)** — prompts are **first-class pipeline-config data** injected per fan-out branch; the analyze LLM call is **content-gen** (no new routing `LLMPurpose`). Surface (b) as the "make prompts governed artifacts" alternative and (c) as deferred-with-a-constitutional-caveat.

## 5. ⭐ DP5 — Output fan-out (room summary + email/notification)

The reduce-summary goes to **two** surfaces with **opposite** risk profiles — and the split is the architecture of DP6.

| Surface | Mechanism | Reversibility / gate | Lean |
|---|---|---|---|
| **Room (GUI)** | Append the reduce-summary as an **`OBSERVATION`** or **`SUMMARY_SNAPSHOT`** event to the pipeline-run room; it streams live to the GUI. | **Internal, reversible, NOT autonomy-gated** — always fires headless, no authorization. | **The safe default output** — every pipeline run produces a GUI-visible summary with **zero** new authorization surface. Lean: `SUMMARY_SNAPSHOT` if the reduce is structured, `OBSERVATION` if free-form (minor; architect/senior can pick). |
| **Email / notification** | `send_email` — the **only** external actuator. **reversibility=3 → HARD_CONFIRM.** | **External, irreversible, gated** — the headless crossing (DP6). | The **risky output** — needs the DP6 authorization story. **No other notification surface exists** (no webhook/push); the GUI stream *is* the free reversible channel, email *is* the irreversible one. |

**Lean:** the **room/GUI summary is the always-on, safe, reversible output**; **email is a separable, opt-in, authorization-gated add-on (DP6)**. This makes the **unattended pipeline safe-by-default** (it can run fully headless producing GUI output with no new authorization), and isolates the entire risk surface into the email actuator. Surface whether **notification beyond email** (a webhook) is in scope — if so it is *more* greenfield, and each external channel inherits the DP6 question.

## 6. ⭐⭐ DP6 — Headless actuator authorization (load-bearing — the honesty crux)

**This is P5.1's `RB-FS/NET` / `RB-AUTOFIRE` moment** — where the human-out-of-loop boundary is *physically drawn* for an **external irreversible** actuator. The verified crux:

**`send_email` is excluded from P4.6's auto-fire by the *two* guards `RB-AUTOFIRE` deliberately installed** (`agents/tool_dispatch.py:137-145`, verified):
1. **Tier guard** — `expires_at` is stamped **iff `tier == COUNTDOWN_CONFIRM`**; `send_email` is **HARD_CONFIRM** → never stamped (line 134: *"HARD_CONFIRM always stays None (4a)"*).
2. **Reversibility floor** — even a COUNTDOWN call needs `reversibility ≥ floor` (default **5**); `send_email` is **reversibility=3 < 5** → excluded again.
3. (And opt-in `enabled=false` by default — the sweeper never even starts.)

So **headless email is not a tuning of `RB-AUTOFIRE` — it *inverts the exact two guards `RB-AUTOFIRE` was built to enforce*** (HARD-never → HARD-yes; floored-reversible → sub-floor-irreversible). That is a **qualitatively new, more aggressive** human-out-of-loop posture, and it must be inscribed at least as honestly as `RB-AUTOFIRE` was. Four sub-calls:

**(6a) ⭐⭐ Does the headless pipeline send email at all — or only reversible output?**

| Option | Trade-off |
|---|---|
| **(b1) Reversible-output-only headless** | The pipeline headless-fires **only** the room/GUI summary (DP5, safe). For email it appends a **`TOOL_CALL_PENDING`** and **leaves it for a human** `POST /confirm` (today's HARD path, unchanged). The pipeline is *"headless analysis + GUI output, human-gated email."* | **Zero new crossing** — the HARD invariant + `RB-AUTOFIRE`'s exclusions stay fully intact; the spine is byte-untouched. **But** it does **not** deliver the user's *unattended* email/notification — a human must approve each run's mail. Honest, conservative, ships P5.1a (DP0) with no new ADR-risk. |
| **(b2) Opt-in headless email actuator (the crossing)** | A **new** config-time authorization (mirroring `RB-AUTOFIRE`'s shape): the operator **opts in**, per-schedule, to let the pipeline send email headless, **bounded** by (i) **opt-in default OFF**, (ii) a **recipient allowlist** (+ the existing `send_email` domain allowlist, ADR-036), (iii) attribution to the **config-time schedule owner**, and (iv) honest residual inscription. Mechanically: the gate still produces the pending (no gate bypass); a **pipeline-email-authorizer** actuates it headless via the **same `_writer_approve_helper` closure** the HTTP-confirm and countdown-sweeper already share — a **third caller**, recording `approval_source="auto_pipeline"` (a new positive marker, never a silent null). | **Delivers the unattended capability** while **reusing the proven actuation closure** (no new execution path, idempotency inherited — the ADR-040 D3 win). **But** it is the **real crossing**: an external, irreversible op fires with **no human at fire time** — beyond `RB-AUTOFIRE` on both axes. Must be Accepted as the **real** surface (a new residual, candidate **`RB-PIPELINE-EMAIL`**), bounded and opt-in, **not softened**. |

**Lean: (6a) = (b1) by default, (b2) only as an explicit, isolated opt-in (DP0's P5.1c).** Ship the safe headless pipeline first (reversible output); make headless email a **deliberate, separately-ratified crossing** with `RB-AUTOFIRE`-class bounding — **but the posture is THE architect call.** This is the place the human-out-of-loop boundary is drawn for an *irreversible external* actuator; it deserves the isolation `RB-FS/NET` got.

**(6b) Don't bypass the gate — actuate a gate-produced pending.** Whichever way (6a) goes, the email **must** still flow through the autonomy gate to a `TOOL_CALL_PENDING` (the spine: `_execute_local_call` + gate zero-diff). (b2) adds a **bounded actuator** that fires that pending under config-time authorization — it does **not** re-tier email to AUTO, does **not** edit the gate, does **not** lower the global floor. (Re-tiering `send_email` or dropping the floor would weaken the *interactive* posture too — reject; the authorization must be **pipeline-scoped + opt-in**, not a global gate change.)

**(6c) Identity — attribute the headless send to the config-time owner.** The schedule's `owner_user_id` (captured when the schedule was created, from the verified principal — DP7) is the audit owner. Mirror ADR-040 D4: record **`approval_source="auto_pipeline"`** + either `approver_user_id = owner_user_id` (the owner stood behind it at config-time) **or** `None` (no human approved *this* send) — lean **owner-attribution with the positive marker** so the audit reads *"sent headless by pipeline, on behalf of `<owner>`, no per-send human approval."* The honest deep inscription (the ADR-040 D8 move): **the human-in-the-loop moment moves to config-time** — defining the schedule + opting into email + the recipient allowlist.

**(6d) The residual — Accept it, don't soften it.** If (b2) is chosen, inscribe a named residual (candidate **`RB-PIPELINE-EMAIL`**, the `RB-AUTOFIRE` convention): *"When pipeline headless email is enabled, an **external, irreversible** actuator (`send_email`, HARD-tier, reversibility=3) **executes with no human in the loop at fire time** — a posture **beyond `RB-AUTOFIRE`**, which excluded exactly this (HARD-never + reversibility-floor). The human-in-the-loop moment is the **config-time** act of creating the schedule + opting into email + bounding the recipient allowlist. Bounded by: opt-in default OFF; per-schedule (not a global gate change); recipient + domain allowlist; owner attribution + `approval_source="auto_pipeline"` audit marker."* This must read as honestly as `RB-FS/NET` / `RB-AUTOFIRE` did (the P4-roadmap §177 discipline).

## 7. ⭐ DP7 — Persistence (schedule definitions + run history + restart + owner)

Two kinds of durable state with **different mutability**, so possibly different homes:

| State | Nature | Options | Lean |
|---|---|---|---|
| **Schedule definitions** (cron/interval, sources, prompts, output config, `enabled`, `owner_user_id`, `next_fire`) | **Mutable operational config** — created, edited, disabled, deleted. | **(a) Side table** (like `users`/`sessions`, P4.5) — mutable rows, natural CRUD, the existing non-event-store precedent. **(b) Event-sourced** (`SCHEDULE_DEFINITION` events, edits as supersession) — audit-native, restart-recoverable like ADR-040 — **but** modeling *mutable config* on an *append-only* log means edits/disables are supersession events (the ADR-040 store-invariant-#1 friction: no in-place update). **(c) Config YAML** — simplest, but no runtime/GUI CRUD, no per-schedule owner. | **(a) side table** — schedules are mutable operational state; the `users`/`sessions` precedent fits exactly, and CRUD is clean. *(If the architect wants the full append-only audit trail of every schedule edit, (b) — but weigh the supersession friction.)* |
| **Run history** (each run: when, which schedule, owner, outcome, the analysis events) | **Append-only facts** — a run happened. | The **event log already is this** — a pipeline run's events live in its room, threadable via `parent_id`; a thin run-index (room id + schedule id + timestamps) can be a side-table row or a per-run root event. | **Event-log-native** for the run's content (free, audit-native); a light run-index for listing. |

**Restart recovery:** the **lifespan hook** (`api/app.py:~1498-1523`) re-loads schedules at boot and re-arms the scheduler (DP2), exactly as the countdown sweeper re-arms — durable defs (side table or events) survive restart; the boot path re-computes next-fire with the chosen catch-up semantics (DP2 sub-decision). **Owner identity:** capture `owner_user_id` from the **creating principal** at schedule-definition time (`Principal`, `build_user_author`, ADR-039 D1/D6) — the single source for DP6c attribution.

**Lean:** **schedule defs → side table** (mutable-config precedent), **run history → event log** (+ a thin index), **restart → lifespan re-arm** (ADR-040 pattern), **owner → config-time principal**. Surface the side-table-vs-event-sourced call explicitly — it is a real "where does mutable config live" architecture decision, and the append-only store was *designed* for facts, not editable config.

## 8. ⭐ DP8 — New ADR-041 + the dual-lens two-lens design

**ADR-041 (new contract):** the deterministic pipeline primitive (DP1), the recurring scheduler + manual trigger (DP2), the source abstraction + RSS greenfield (DP3), dynamic-prompt injection (DP4), the dual-output split (DP5), **the headless actuator-authorization posture + `RB-PIPELINE-EMAIL` residual (DP6)**, and the persistence model (DP7). Expensive-to-change (the schedule schema + the headless-authorization posture bind future consumers) → **inscribe-before-producer**. *(If DP0 = wave, this may split into ADR-041 [pipeline+scheduler] + a focused ADR for the email crossing — architect's call with DP0.)*

**Amendments this slice likely carries:** **ADR-001** (a new event type if run-roots/schedule-events are event-sourced — DP7); **ADR-019** (a note disambiguating `connectors/` from the new `sources/` — DP3); **ADR-025 D6** (a second bounded background-task surface — the scheduler — beside the single writer); **ADR-036** (`send_email`'s confirm posture gains a *pipeline-scoped, opt-in, headless* actuation path — the honest amendment, if DP6=b2); **ADR-040** (a note: `RB-AUTOFIRE`'s exclusions are *referenced* by `RB-PIPELINE-EMAIL` as the boundary it consciously steps beyond).

**Dual-lens — two orthogonal failure-family lenses** (`requires_cross_family_review: true`; `dual-lens-r0b.md`):
- **Lens A — pipeline/scheduler safety + headless over-authorization (the "unattended execution done wrong" adversary).** Does the scheduler fire **only** on schedule (never when disabled, never double-fire across a restart — the ADR-040 boot-re-arm hazard)? Is **fetch SSRF/sandbox-floored** (a malicious feed URL can't reach internal services; a file source can't escape the sandbox)? Is the pipeline **deterministic** (all stages + the full configured fan-out run; no silent partial)? **Can email fire without the DP6 opt-in?** Is the **recipient allowlist** honored? Is the **no-human-at-fire-time fact recorded honestly** (`approval_source="auto_pipeline"`, not a silent null)? Does the headless run ever actuate **beyond** the configured boundary (a non-email actuator, a non-allowlisted recipient)?
- **Lens B — spine no-regression (the "did the pipeline break the existing constitution" adversary).** Is the autonomy gate **byte-frozen** (`score`/`decide_tier`/`emit_gate_decision`; **no new routing `LLMPurpose`** — the analyze prompts are **content-gen**, the orchestration is **code/config**)? Is **`_execute_local_call` zero-diff** (the P4 spine invariant)? Does the email actuator **reuse `_writer_approve_helper`** (no second actuation path; idempotency inherited)? Does the **interactive** posture stay unchanged (email is still HARD for a human; the headless path is *pipeline-scoped + opt-in*, not a global gate/floor change)? Does the new scheduler preserve **single-writer + reader-liveness** (ADR-025 D6)? Is the conversational **room/agent contract (ADR-010/011/012) untouched** by the pipeline primitive?

*(The two are genuinely orthogonal — "the unattended pipeline is unsafe / over-authorized" vs "the pipeline regressed the gate/spine/room-contracts" — the dual-lens design goal.)*

## 9. Constitutional carry-forward watch-list (carry into the plan + ADR-041)

- **Orchestration = code/config, never LLM (the load-bearing framing).** Stage order, fan-out count, source list, output routing, schedule timing, email authorization — **all code/config**. The **only** LLM is the analyze **content-gen** (`AGENT_RESPONSE`-class). **No new routing `LLMPurpose`** (CLAUDE.md "Never LLM-judge a routing decision"; the P4 "no new `LLMPurpose` beyond content-gen" invariant).
- **The scheduler actuates, never decides** (the ADR-040 timer discipline) — it fires a configured schedule; it does not *choose* to.
- **Gate + executor spine byte-frozen.** `_execute_local_call` + `score`/`decide_tier`/`emit_gate_decision` zero-diff (held across all 8 P4 slices). The email actuator (DP6) **reuses** the confirm closure, does **not** re-tier email or lower the global floor.
- **Backend-authoritative + no gate bypass.** Headless email flows **through the gate** to a pending, then a **bounded, opt-in, owner-attributed** actuator fires it — never an invented call, never a global weakening.
- **Single-writer + reader-liveness (ADR-025 D6) preserved** — the scheduler + pipeline append on the writer; discovery on the reader path; fan-out is write-serialized (honest residual, DP1).
- **Opt-in, fail-closed, posture-ratified** (the P2.7-S3 → P4.5 → `RB-AUTOFIRE` discipline) — headless email default OFF, per-schedule, allowlist-bounded, owner-attributed.
- **Honest-residual inscription.** If headless email is enabled, Accept the **real** crossing (`RB-PIPELINE-EMAIL`) — *beyond* `RB-AUTOFIRE` on tier + reversibility — never a softened one (roadmap §177).
- **`connectors/` is not `sources/`** — don't invert ADR-019's directory meaning (DP3).
