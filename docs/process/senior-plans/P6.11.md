# P6.11 — pipeline-ingress hardening (H1 🔴 + H2 + fetch wall-clock + H3)

## 1. Context

The holistic-2026-06 review of the P5.1 analysis-pipeline surfaced a re-opened **OOM/HoL
🔴 (H1)** plus a bundle of **missing ingress caps (H2)** and one **SSRF-floor-scope
confirmation (H3)**. The architect ratified scope on 2026-06-16 (brief
`docs/process/architect-briefs/P6.11.md` §Ratification): **routine, ADR-041 amended in
place, `plan_has_adr=False`, no new ADR**. This plan turns that ratification into atomic
implementation tasks.

The 🔴 (H1) is concrete and verify-cited: both pipeline source readers materialise the
**entire** HTTP body into RAM *before* bounding it. `read_web_source`
(`src/orchestrator/sources/web.py:26-28`) does `client.get(...)` → `raw =
response.content` → only then `raw[:max_bytes]` (`:38-39`). `read_rss_source`
(`src/orchestrator/sources/rss.py:120-122`) is identical, then **parses** the full body
(`:132-133`) and truncates the *rendered* output (`:150-152`). These run on the
**single** `writer_executor` (`max_workers=1`), so an over-cap source is not just OOM — it
monopolises every room's writes (head-of-line). This is the exact ADR-028/035 D2/D3 OOM
vector the project's `_stream_bounded` helper (`src/orchestrator/tools/network_tools.py:98`)
was built to prevent; `_inprocess_web_fetch` already uses it correctly via
`client.send(req, stream=True)` + `_stream_bounded(response)` (`:243-248`).

H2 adds four hardcoded safety ceilings (not config) the pipeline ingress currently lacks;
the fetch-stage wall-clock budget (ratified **in-cycle**, overriding the brief's defer
lean) bounds the *time* dimension of writer-HoL that the source-count cap alone leaves
open. H3 confirms-and-inscribes that pipeline `sources/` reads correctly use the
**in-process SSRF floor** (`build_ssrf_client`), not the ADR-037 egress-sandbox container
(which is wired only into the `web_fetch` *tool* via `posture_resolver`).

**Spine note (verify-cited).** `web_fetch` stays byte-frozen: the H1 seam parametrizes
`_stream_bounded(response, max_bytes=MAX_RESULT_BYTES)` with a **default** equal to the
current hardcoded value, so the existing `_inprocess_web_fetch` caller (passes nothing →
64 KiB) is byte-identical. No new `LLMPurpose`; the gate (`_execute_local_call` /
`score` / `decide_tier`), `_write_and_turn`, and the countdown spine are untouched.
Product change, cross-family (resource-exhaustion + SSRF-scope = the Lens-A adversarial
surface ADR-041's own risks named: *"must be tested adversarially (Lens A)"*,
ADR-041:384).

**Two semantic shifts to flag for R0-A** (both intentional, both ratified):
1. **RSS `truncated` meaning changes.** Today it means "the *rendered* output exceeded
   `max_bytes`" (post-parse, `rss.py:150-152`). After A1 it means "the *raw XML fetch* hit
   the cap" — the OOM-relevant place. An over-cap feed now truncates the raw XML →
   `defusedxml` raises `ET.ParseError` → `_parse_feed` raises `SourceReadError`
   (`rss.py:77-78`) → the runner per-source `try/except` (`runner.py:292`) records an
   OBSERVATION and **continues** (fail-closed; no lenient partial-XML parse).
2. **Existing source tests mock the wrong path.** `tests/sources/test_sources.py`'s web/rss
   success+truncation tests mock `mock_client.get(...)` + `mock_response.content`
   (`:233`, `:246`, and the RSS equivalents). After A1 the readers use
   `client.send(..., stream=True)` + `response.iter_bytes()`, so these existing tests MUST
   be rewritten to mock the streaming path — they are not merely augmented.

## 2. Tasks (atomic; each independently revert-gated)

### P6.11-A2 — H2 schema ceilings (lands first; introduces the shared ceiling constant)

- **What**: Add `_MAX_SOURCES_PER_RUN = 16` as `max_length` on
  `PipelineDefinition.sources`, and `_SOURCE_MAX_BYTES_CEILING = 5 * 1024 * 1024` as
  `le=` on `SourceOptions.max_bytes` (plus introduce the constant that A1 imports).
- **Where**:
  - `src/orchestrator/sources/schema.py:15` — add module-level
    `_SOURCE_MAX_BYTES_CEILING = 5 * 1024 * 1024` and change the field to
    `Field(default=512 * 1024, gt=0, le=_SOURCE_MAX_BYTES_CEILING)`.
  - `src/orchestrator/pipeline/schema.py:33` — add module-level
    `_MAX_SOURCES_PER_RUN = 16` and change to
    `Field(min_length=1, max_length=_MAX_SOURCES_PER_RUN)`.
  - `tests/sources/test_sources.py`, `tests/pipeline/test_store.py` (or new cases) — tests.
- **Why**: Brief H2 (a)+(c); ADR-041 D4/D8 narrowing validators (hardening, no new field,
  reverses nothing). Rejected at `POST /pipelines` because `PipelineDefinition(...)` is
  constructed inside the endpoint's `try/except` → HTTP 422 (`app.py:2024-2032`),
  fail-closed before any run. The `le=` is belt; A1's `min()` clamp is suspenders (a stored
  definition predating this validator still cannot defeat the stream bound).
- **Acceptance criteria**:
  - `PipelineDefinition(sources=[<17 sources>], ...)` raises `ValidationError`;
    `[<16 sources>]` accepted (boundary). **Revert the `max_length` → 17 accepted.**
  - `SourceOptions(max_bytes=6 * 1024 * 1024)` raises `ValidationError`;
    `max_bytes=5 * 1024 * 1024` exactly accepted. **Revert the `le=` → 6 MiB accepted.**
  - **Migration test**: `SourceOptions()` (default 512 KiB) and a default-options
    `PipelineDefinition` still validate. (Verify-cited: the only stored-definition fixture,
    `tests/pipeline/fixtures/example_pipeline.json`, is 3 sources × 524288 B — under both
    ceilings; no fixture/seed exceeds them.)
- **Out of scope**: making either ceiling operator-tunable (they are safety floors, not
  config); `timeout_s` ceiling (not in this brief).

### P6.11-A1 — H1 🔴: stream-bound both source readers

- **What**: Parametrize `_stream_bounded` with a defaulted `max_bytes`, and rewrite
  `read_web_source` + `read_rss_source` to stream via it (mirroring `_inprocess_web_fetch`),
  never buffering `response.content`.
- **Where**:
  - `src/orchestrator/tools/network_tools.py:98-117` — signature →
    `def _stream_bounded(response: httpx.Response, max_bytes: int = MAX_RESULT_BYTES)`;
    replace **both** internal `MAX_RESULT_BYTES` uses (`:108`, `:112`) with the `max_bytes`
    param. Existing caller (`:248`) passes nothing → unchanged.
  - `src/orchestrator/sources/web.py:24-40` — replace `client.get()` + `.content` with the
    `_inprocess_web_fetch` idiom: `with build_ssrf_client(...) as client:` →
    `response = client.send(client.build_request("GET", source.locator), stream=True)` →
    `response.raise_for_status()` →
    `content, truncated_at = _stream_bounded(response, max_bytes=min(source.options.max_bytes, _SOURCE_MAX_BYTES_CEILING))`.
    Set `SourceReadResult.truncated = truncated_at is not None`. **Preserve** the existing
    `HTTPStatusError` handler (`:31`) and `SourceReadError` re-raise (`:29`).
  - `src/orchestrator/sources/rss.py:118-153` — same streaming rewrite for the raw XML
    fetch; `_stream_bounded` returns the bounded `xml_text`; feed it to `_parse_feed`
    unchanged. Over-cap → truncated XML → `ET.ParseError` → `SourceReadError` (existing
    path, fail-closed). The post-render truncation block (`:150-152`) is **subsumed** by
    the fetch-stage bound and removed; `truncated` now reflects the raw-fetch cap.
  - Import `_stream_bounded` from `orchestrator.tools.network_tools` and
    `_SOURCE_MAX_BYTES_CEILING` from `orchestrator.sources.schema` (cross-module `_`-private
    reuse matches the `sources/file.py` ← `tools/local._check_path` precedent).
  - `tests/sources/test_sources.py` — **rewrite** the existing `.get()/.content` web+rss
    mocks to the streaming path; **add** the H1 revert-gate tests below.
- **Why**: Brief H1 🔴; ADR-028/035 D2/D3 OOM guard restored on the single writer; mirrors
  `_inprocess_web_fetch` (`network_tools.py:243-248`).
- **Acceptance criteria** (the 🔴 revert-gates):
  - **OOM/stream**: a mock `httpx.Response` whose `iter_bytes()` yields chunks summing past
    the cap (or a generator that raises if fully drained) → the reader returns content
    bounded to `max_bytes` **and stops iterating at the cap** (assert via chunk-counter or
    the would-raise generator). **Revert to `.content` → test fails (full drain).** This is
    the 🔴's revert-gate.
  - **stream idiom**: the reader takes the `send(stream=True)` path, not `.get().content`
    (structural assertion — the practical HoL revert-gate).
  - **cap honoured**: a ~300 KiB body with default options is **not** truncated (proves the
    param carries `source.options.max_bytes` = 512 KiB, not the 64 KiB default). **Revert
    the parametrization → truncates at 64 KiB.**
  - **RSS over-cap fail-closed**: feed XML > `max_bytes`, truncated mid-document →
    `read_rss_source` raises `SourceReadError` (no OOM, no crash).
  - **web_fetch byte-identical**: `tests/tools/test_network_tools.py` web_fetch suite
    (already mocks `send` + `iter_bytes`; `test_web_fetch_over_size_truncated` expects
    truncation at `MAX_RESULT_BYTES`, `:143-155`) stays green unchanged.
- **Out of scope**: lenient partial-XML parsing; touching `read_file_source` (already
  bounded via `_check_path`); the H2-b entry slice and H2-d context truncate (A3).

### P6.11-A3 — H2 runtime caps: RSS entry slice (b) + fetched_context truncate (d)

- **What**: Cap the RSS entry count after extraction, and cap the joined analyze context
  with a visible marker.
- **Where**:
  - `src/orchestrator/sources/rss.py` — add module-level `_MAX_FEED_ENTRIES = 256`; slice
    `entries = _parse_feed(xml_text)[:_MAX_FEED_ENTRIES]` immediately after the parse
    (currently `:133`) so the render loop and DOM-derived list are both bounded.
  - `src/orchestrator/pipeline/runner.py:308` — add module-level
    `_MAX_FETCHED_CONTEXT_BYTES = 1 * 1024 * 1024`; after building
    `fetched_context = "\n\n".join(...)`, if its UTF-8 length exceeds the cap, truncate to
    the cap and append `\n\n[context truncated at {_MAX_FETCHED_CONTEXT_BYTES} bytes]`
    (decode with `errors="replace"`, consistent with existing `truncated` semantics).
  - `tests/sources/test_sources.py`, `tests/pipeline/test_runner.py` — tests.
- **Why**: Brief H2 (b)+(d). (b) caps the render explosion (a 100k-item feed → 100k lines);
  (d) bounds the context fed to **every** analyze branch (≈250k tokens at 1 MiB), bounding
  LLM cost + memory. Truncate (don't reject), consistent with existing semantics.
- **Acceptance criteria**:
  - A feed with 300 entries → rendered output lists exactly 256. **Revert the slice → 300.**
  - Sources whose joined content > 1 MiB → the analyze stage receives ≤ 1 MiB **plus** the
    `[context truncated at …]` marker. **Revert → full context, no marker.**
- **Out of scope**: per-entry field truncation; changing the render format.

### P6.11-A4 — fetch-stage wall-clock budget (the *time* dimension of HoL)

- **What**: Add a wall-clock budget to the fetch loop, mirroring the analyze stage's
  `_PIPELINE_MAX_WALL_CLOCK_S`, so worst-case single-writer occupancy is time-bounded (not
  only memory-bounded via the source-count cap).
- **Where**: `src/orchestrator/pipeline/runner.py:287-306` — add module-level
  `_PIPELINE_FETCH_MAX_WALL_CLOCK_S = 90.0` (sibling to `_PIPELINE_MAX_WALL_CLOCK_S = 120.0`
  at `:58`). Stamp `loop_start = time.monotonic()` before the `for src in
  definition.sources` loop; at the top of each iteration, if
  `time.monotonic() - loop_start >= _PIPELINE_FETCH_MAX_WALL_CLOCK_S`, append an OBSERVATION
  event (same shape as the per-source-failure OBSERVATION at `:296-306`) noting the budget
  was exceeded and the remaining sources skipped, then `break`. Fail-closed.
- **Why**: Brief §Ratification (fetch wall-clock = **in-cycle**). The analyze stage has a
  120 s budget (`runner.py:58/169`); the fetch loop has none — only per-source `timeout_s`
  (default 15 s, **no ceiling**), so 16 sources × 15 s = 240 s of single-writer hog is
  reachable. The source-count cap bounds memory but not time; this bounds time.
- **Acceptance criteria**:
  - With a stubbed `read_source` that sleeps past the budget across N sources, the loop
    stops early, records the OBSERVATION, and `run_pipeline` proceeds to the analyze stage
    with the sources fetched so far (no crash). **Revert the budget check → all N fetched.**
  - A normal fast multi-source run is unaffected (budget not hit).
- **Out of scope**: per-source `timeout_s` ceiling; parallelising fetch (ADR-041 D3 keeps
  fetch sequential).
- **Value note (senior pick, architect-delegated)**: `90.0 s`. The architect delegated the
  value ("senior picks the value — a fetch budget can be ≤ the analyze 120 s since fetches
  should be quick"). 90 s sits comfortably above any legitimate handful-of-sources fetch
  yet below the analyze 120 s, and bounds the 240 s worst case. One-line constant; re-pin if
  you'd prefer a different ceiling.

## 3. Execution order

Mostly sequential — the chain shares two files and one constant:

1. **A2 first.** It introduces `_SOURCE_MAX_BYTES_CEILING` (in `sources/schema.py`) and
   `_MAX_SOURCES_PER_RUN` (in `pipeline/schema.py`) in their natural schema homes. A1's
   readers import `_SOURCE_MAX_BYTES_CEILING` for the `min()` clamp, so the constant must
   exist before A1. A2 is a trivial 2-validator change.
2. **A1** (the 🔴) — depends on A2's constant; rewrites `network_tools._stream_bounded` +
   both readers + their tests.
3. **A3** — re-touches `rss.py` (the entry slice sits after A1's rewritten parse call) and
   `runner.py`; must follow A1.
4. **A4** — touches `runner.py` (the fetch loop); sequenced after A3 to avoid same-file
   churn (different region, but serial is cleaner for a single junior).
5. **A5** (docs) — last, so the inscriptions reflect the final four constants.

Single junior, serial (no parallelism: A1→A3→A4 share files; A2 gates A1). One atomic =
one commit, one commit subject (`P6.11-A2: …`, `P6.11-A1: …`, …) per RC-17.
