---

**Subject:** Build **P4.2-B5** — implement the deferred **mutation local tools** so an agent can finally **act on its investigation**: write a fix (`apply_edit`), send a notification (`send_email`), publish work (`git_push`). After B3 (subprocess) + B4 (network), an agent can read / search / test / lint / read git-history / fetch-the-web **in-turn** — but it **cannot change anything**. B5 adds the **"act" half** of the flagship bug-fix loop (investigate → … → **apply the fix + push it**). These are the **HARD/COUNTDOWN-tier** tools ADR-028 D3 called *"provably dead until confirm-then-execute lands"* — **it landed in P3.6 (ADR-030)**, so they are now unblocked. B5 is **mostly wiring**: the confirm-then-execute path, the executor, the per-turn caps, and the output-untrusted machinery **all exist**; the three impls are thin closures over reused primitives. The genuinely-**new** surface is narrow: (a) `apply_edit` is the **FIRST tool that WRITES the workspace** (turning `_check_path` from a read-gate into a write-gate); (b) the **first real actuation** of the ADR-030 confirm loop (it has only ever hit `not_implemented`); (c) the **`git_push` credential tension** — B3's `scoped_env()` strips the very secret `git_push` needs to authenticate.

## The foundation P4.2-B5 completes (verified — what's missing, precisely)

The confirm-then-execute machinery is **fully built and cross-family-reviewed** (ADR-030, P3.6 `requires_cross_family_review: true`) — but it actuates **nothing**: every mutation tool is `not_implemented`, so a human can approve a pending `apply_edit` and the executor fires `_execute_local_call` → fail-closed `not_implemented`. B5 makes the approval **do something**. The work is **plug the impls into the existing path**, not build a path: the gate already tiers these (rev 1/2/3 → COUNTDOWN/HARD under the shipped agent configs); the confirm endpoint already reconstructs + appends the `TOOL_CALL`; the executor already routes any `TOOL_CALL` to `_execute_local_call`. The reusable parts (sandbox `_check_path`, B3 `run_scoped_command`/`scoped_env`, B4 `_NetworkToolFn`/provider-config, the caps, the untrusted-output union) cover ~all of it — the load-bearing new bits are the **first WRITE containment**, the **`git_push` credential exception**, and inscribing the **gate-decides-tier / confirm-actuates** flow so the first mutation surface is an *Accepted* boundary, not an open door.

## ⭐⭐ Constitutional carry-forward (NON-NEGOTIABLE — inscribe in ADR-036; **not** decisions)

Per P4-roadmap §10 + the ADR-028/030 spine. The senior inscribes; the impl enforces; R0-A (and R0-B if dispatched) probe each:

1. **Execution stays DOWNSTREAM of the gate; the executor is tier-AGNOSTIC and tool-AGNOSTIC (ADR-028 #1 / ADR-030 HR#3 / t4).** Mutation tools route the **unchanged** `process_tool_calls`→`emit_gate_decision` path. **The gate decides the tier; B5 never re-gates and never special-cases a mutation.** A COUNTDOWN/HARD call → `TOOL_CALL_PENDING` (not executed); a confirm-approved (or, if the gate so decides, an AUTO) `TOOL_CALL` → `_execute_local_call`. The executor cannot tell a confirmed mutation from an AUTO read — and **must not** (a mutation-specific "always confirm" check in the executor would be re-gating downstream = a t2/t4 violation).
2. **No LLM judgment; no new `LLMPurpose` (t2/t3).** The mutation path is pure code — no "is this edit/recipient/push safe" LLM judgment. Output is **not** interpreted by default (see threat model (3)); if ever interpreted it reuses the existing content-gen `TOOL_OUTPUT_INTERPRET` — no new purpose.
3. **The mutation trust boundary is REAL, HONEST about its residuals.** `apply_edit` sandbox-bound (write-time `_check_path`, no traversal/symlink-escape, bounded size); `send_email` credential-scoped (key only to the fixed provider) + recipient-bounded; `git_push` argv-never-shell + credential-scoped + remote-output-untrusted. **Honest residuals:** the `git_push` push-credential (a narrow named exception to B3's secret-stripping), the `send_email` exfil-by-recipient (the B4 public-host-exfil analog), and the inherited FS/network `RB-FS/NET` (retired by P4.3).
4. **Reuse, don't rebuild — no new execution substrate, no new confirm machinery.** `apply_edit` reuses `_check_path`; `send_email` reuses the B4 `_NetworkToolFn` marker + the `web_search` provider-config-with-`api_key_env` shape; `git_push` reuses B3 `run_scoped_command` + `scoped_env` + `_SubprocessToolFn`. The ADR-030 confirm path is reused **whole** — B5 adds **zero** confirm/endpoint/snapshot code.
5. **`tools/` stays a downstream leaf (t1); `_execute_local_call` stays byte-unchanged (empty-executor-diff, 4th time).** The per-turn caps (subprocess for `git_push`, network for `send_email`) live in the existing `execute_pending_tool_calls` **loop**; `apply_edit` rides the plain in-process branch (no marker, no cap, like `read_file`). B5 adds **no** executor-decision edit.
6. **The gate-produced `TOOL_CALL` is the SOLE entry to actuation.** No mutation executes except via a `TOOL_CALL` the gate produced — AUTO (turn-loop) or confirm-approved (ADR-030 D3 step 5, the human-second-factor). B5 introduces no side path that mutates without a gate-produced `TOOL_CALL`.

## Decision points (surface — ⭐ = architect's genuine call; do NOT self-decide)

### (1) MVP tool set + classification confirm — the 3 mutations; `propose_edit` as a separate question

- **The 3 true mutations stand: `apply_edit` (rev 2) / `send_email` (rev 3) / `git_push` (rev 1).** Classifications are PLACEHOLDER (`tools.yaml` header) but reasonable; they **stand as-is** unless re-tiered. **Verified tier (gate = reversibility-only, `scoring.py`) across all 6 shipped agent configs, no user-intent:** `git_push` (1) → **HARD everywhere**; `apply_edit` (2) → **COUNTDOWN** (facilitator/mentor `confirm=2`) or **HARD** (others); `send_email` (3) → **COUNTDOWN** (facilitator/investigator/operator/mentor) or **HARD** (skeptic/prober). **None reaches AUTO without intent** (every `threshold_auto` ≥ 4 > 3). *(The AUTO-under-intent edge is decision (2)'s ⭐.)*
- **⭐ `propose_edit` (rev 5) is a DIFFERENT surface — surface in or out.** It **generates a reviewable diff** and does **not** apply it (`tools.yaml:30` — *"diff is reviewable but apply is not"*); at rev 5 it **reaches AUTO** for facilitator/mentor (`auto=4 ≤ 5`). So it is closer to a **B2-class read-only/content-gen tool** than a mutation. **Your call:** (a) ship the **3 true mutations only** in B5 (cleanest scope; `propose_edit` lands later beside `apply_edit`'s UX); (b) **add `propose_edit`** as a thin near-read-only diff-generator now (it pairs naturally with `apply_edit`). **Lean (a)** — keep B5 to the actual state-changing surface; `propose_edit`'s tier/UX story is orthogonal.

### (2) ⭐⭐ Confirm-then-execute integration — the gate decides the tier; confirm only actuates (THE core)

This is the lead inscription, and the cleanest of the three P4.2 cores: **the path already exists; B5 plugs into it.** Inscribe the flow precisely in ADR-036:

- **The gate decides the tier** (`process_tool_calls`→`emit_gate_decision`, unchanged). Rev 1/2/3 → COUNTDOWN/HARD (default) → `process_tool_calls` appends a **`TOOL_CALL_PENDING`** (ADR-030 D1) — **not executed**. The P4.1 turn-loop's `execute_pending_tool_calls` filters on `EventType.TOOL_CALL` only, so a `TOOL_CALL_PENDING` is **skipped** — the mutation does **not** auto-fire in-turn. ✓
- **Confirm actuates.** Human `POST /confirm {pending_event_id, approve}` → the confirm endpoint (ADR-030 D3 step 5) reconstructs a real `TOOL_CALL` from the persisted record + invokes the **existing** `execute_pending_tool_calls([that TOOL_CALL])` → `_execute_local_call` → **the B5 impl runs.** So **B5's "confirm-then-execute integration" = implement + register the impls.** The confirm machinery already routes a confirmed `TOOL_CALL` through the existing executor; **the executor is tier-agnostic.** The gate decided countdown/hard; the human supplied the second factor; **confirm only actuates** — it adds no decision.
- **⭐ The honest edge the architect must rule on (the gate CAN route a mutation to AUTO).** `decide_tier` lowers `eff_auto = threshold_auto − user_intent_modifier` under `user_explicit_intent`. **Verified:** with explicit intent, `send_email` (rev 3) reaches **AUTO** for operator (6−3=3) and facilitator (4−1=3) — it then executes **in-turn, no confirm**, like any AUTO local tool. A permissively-configured agent could do likewise. **B5 does NOT special-case this, and MUST NOT** (carry-forward #1 — an executor-side "mutations always confirm" override is downstream re-gating). **Your call:** (i) **accept the gate-owned tier** — the operator owns the human-in-the-loop guarantee via thresholds; B5 stays a pure tool-impl slice (**lean**); or (ii) **a never-AUTO floor for mutations** (a hard-guard forcing destructive/external-visibility ops to ≥COUNTDOWN regardless of score/intent) — but that is an **autonomy-gate change, OUT of B5's tool-impl scope**, and re-opens the P1.3 `hard_guards.py` placeholder (still un-implemented). **Lean (i)**; if you want a hard mutation-confirm guarantee, it is a **separate autonomy slice**, surfaced here, not bundled into B5.

### (3) Threat model — per tool (inscribe in ADR-036)

- **`apply_edit` — the FIRST tool that WRITES the workspace.** Untrusted input = the LLM-proposed path **+ content**. Reuse `_check_path` — but it was built for **read** containment; a **write** through it is higher-stakes (an out-of-sandbox overwrite is destructive, not just an info-leak). The senior pins: **write-time containment** (re-resolve at write, not only pre-check — TOCTOU); **symlink-write policy** (refuse to write *through* an in-sandbox symlink that escapes — the read tools only *skip* such, a writer must *refuse*; `O_NOFOLLOW`-class); **bounded content size** (the `MAX_RESULT_BYTES` analog on input); **atomic write / no partial-file on failure**. **Output = local status** (bytes written / path) — agent-supplied content, **TRUSTED → NOT in the external-output set.**
- **`send_email` — external egress + recipient/credential surface; data-exfil-by-email.** Reuse the **`web_search` shape**: a **FIXED provider endpoint** (operator-configured SMTP/API) + an `api_key_env` credential sent **only** to the provider — so **SSRF is N/A** for the connection (fixed endpoint, not agent-chosen). The agent-chosen part is the **RECIPIENT** — the **exfil vector**: a prompt-injected agent mails `<secret>` to `attacker@evil.com`. **Mitigations:** the operator-configured provider + (⭐ knob) a **recipient allowlist / domain-allowlist** (the egress-allowlist analog to B4's data-exfil residual). **Honest residual** (without a recipient allowlist): exfil-by-recipient — Accept honestly, name the allowlist as the operator tightening (don't claim solved). Credential: key to the provider header **only**, never logged/echoed/onto any other surface. **Output = provider send-status** — mostly local; **sub-call:** conservative-include `send_email` in the untrusted set (consistent with `web_search`, ~free) **vs** treat status-only as trusted — surface; **lean conservative-include.**
- **`git_push` — mutates a REMOTE; ⭐ the credential tension is B5's load-bearing new question.** Reuse B3 `run_scoped_command` + **argv-never-shell** + bounded output. **But `scoped_env()` strips ALL secrets** (the c2 lesson) — and `git_push` **needs** a push credential (SSH key / token) to authenticate. **The mechanism B3 built to prevent secret-leak prevents `git_push` from pushing.** The senior must resolve **what credential `git_push` gets, scoped how, without re-opening the c2 env-leak** — e.g. (a) a **single explicitly-allowlisted push credential** injected into the otherwise-scoped env (a narrow, named, inscribed exception); (b) MVP targets only **ambiently-authed / local** remotes; (c) a credential-helper seam. **This is the new security surface of B5.** Other threats: **force-push / history-rewrite** (rev 1, the most irreversible tool — argv discipline: no `--force`/`--force-with-lease` unless explicitly allowed; ref/branch constraints, no `--mirror`); **remote-output-untrusted** — `git_push` stdout carries **remote-controlled** text (pre-receive/update hook output, branch-protection rejection messages, remote MOTD) → attacker-authorable → **UNTRUSTED → `git_push` joins `_SUBPROCESS_TOOL_NAMES`** (free if it rides `build_subprocess_tool_registry` — the output-untrusted union already covers that set, and the drift-sync test enforces it).

### (4) Where it executes — existing `_execute_local_call` (empty-executor-diff); placement is the senior call

- **All three ride the EXISTING `execute_pending_tool_calls` → `_execute_local_call`** (no executor-decision edit): `apply_edit` = plain in-process branch (no marker/cap, like `read_file`); `send_email` = `_is_network_tool` (network cap); `git_push` = `_is_posture_b_subprocess` (subprocess cap). **Per-turn caps are trivially satisfied on the confirm path** (one confirmed call per `/confirm`), but the markers still route `git_push`/`send_email` through the capped branches for consistency.
- **⭐ Placement (file layout) — a senior call with sync-test + constitution consequences:**
  - **Organize-by-substrate (lean — max reuse):** `send_email` → `network_tools.py` (auto-synced to `_NETWORK_TOOL_NAMES` + its drift-test; gets `_is_network_tool` free); `git_push` → `subprocess_tools.py` (auto-synced to `_SUBPROCESS_TOOL_NAMES` → output-untrusted free; gets `_is_posture_b_subprocess` + `run_scoped_command` free); `apply_edit` → an in-process home. **Cost:** the "mutation surface" is **scattered** across files.
  - **Organize-by-surface (clean module):** all three in a new `mutation_tools.py`. **Cost:** re-wire the markers, a **new `_MUTATION_TOOL_NAMES` set + drift-test + output-untrusted union extension** + per-tool cap decisions — **more scaffolding** (cuts against "lean").
  - **Lean: organize-by-substrate** (the B3/B4 "reuse don't rebuild" precedent — caps, drift-tests, and output-untrusted sets all come free). **Surface because** (a) it scatters the surface, and (b) **`apply_edit`'s home touches the `local.py` read-only convention**: constitution **t6 only bans *subprocess* in `local.py`** (`test_constitution.py:344`), **not writes** — so an in-process `apply_edit` is *permitted* there, but `local.py` is read-only-by-convention; the senior chooses `local.py` (+ a possible new constitution note that local.py may write) **vs** a dedicated `mutation_tools.py` home for `apply_edit`. Architect ratifies if it's a constitution-test change.
- **Confirm carry-forward holds:** t1 (`tools/` leaf), t2 (no autonomy decision), t3 (no new `LLMPurpose`), t4 (execute-on-`TOOL_CALL`-only — the confirm-approved `TOOL_CALL` is the ADR-030-broadened second appender, already inscribed + guarded), t6 (`local.py` no-subprocess — `git_push`/`send_email` stay OUT of `local.py`; `apply_edit` is in-process). The gate stays the sole chokepoint; **confirm carry-forward — no new `LLMPurpose`.**
