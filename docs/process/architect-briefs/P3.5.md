**Subject:** Build P3.5 — a **plugin system** (a `plugins/` package: a **manifest schema** + a **loader** that discovers / validates / registers plugins) that packages **skills + tools + MCP-config + roles** (handoff §3.3) into a **distribution unit**, merging a plugin's contributions into the existing agents/skills/tools/MCP registries **at the existing `_build_context` merge point, reusing the four existing per-surface loaders**. This is the **Wave-2 closer / backend-track join** (roadmap §4/§5): it is the *convergence* of P3.1 (roles/skills) + P3.4 (MCP config), not a new leaf — and it brings the **third-party-trust boundary one level up** (a plugin bundles servers **and** tools **and** roles at once).

## The substrate that already exists — this is what P3.5 *wraps*, not reinvents (verified)

A clean finding, exactly parallel to P3.4's "the gate is tool-source-agnostic": **all four things a plugin packages already have loaders, and they already converge in one place.** `_build_context` is the single merge point; each surface is a `discover → validate → register` loader (`load_agents`, `load_skills`, `load_tools_config`, `load_mcp_servers_config`/`build_mcp_tool_registry…`). So a plugin loader is an **aggregation layer above the four**: it discovers plugin manifests, validates them, and **feeds the same four registries** — it builds **no** new agent/skill/tool/MCP machinery and **no** new decision surface. And ADR-027 **D5 pre-committed the MCP half** (the `mcp_servers` block is plugin-shaped already). P3.5 plugs into this; it does not re-architect it.

## ⭐⭐ The constitutional spine (NON-NEGOTIABLE — inscribe ADR-029; carries ADR-005/006/027 forward — *not* new choices)

The most important section. Per Principle 5 + roadmap §9, the senior/ADR must inscribe and the impl must enforce — a plugin is third-party; **none of these are negotiable**:

1. **Plugin-delivered tools route through the existing CODE autonomy gate, unchanged.** A plugin's tool contributes a `ToolMeta` into the **same** `tools: dict[str,ToolMeta]` that flows `_build_context → process_tool_calls → emit_gate_decision`. It gates **identically** to a local/MCP tool: classified → tier from reversibility (code); **unregistered/unclassified → `UnknownToolError` → refused** (ADR-006 fail-closed). **No second decision surface; the gate stays the sole chokepoint.**
2. **Plugin-delivered MCP servers route through the existing trust boundary (ADR-027 D4), unchanged.** A plugin's `mcp_servers` block is the ADR-027 D5 shape; the **same** allowlist + `api_key_env` credential-indirection + scoped-subprocess-env + result-size-limit + fail-closed posture applies. A plugin **cannot** deliver a server that bypasses the allowlist — its declared server *is* an allowlist entry, which makes **loading a plugin = opting into its servers** (the magnified consent surface — Decision c).
3. **Plugin loading is deterministic CODE/config, never an LLM judgment.** Discovery + manifest-validation + registration is code (mirrors the four loaders). **No `LLMPurpose` decides whether to load a plugin, whether it validates, or what its contributions do.** A constitution test forbids `plugins/` referencing `decide_tier`/`emit_gate_decision`/`gate`/`select_model_and_provider` or any `llm/` provider call (the ADR-027 D2 analog).
4. **A plugin introduces NO new routing/judgment `LLMPurpose` and NO routing decision.** It packages **roles** (agents — activation `should_agent_speak` stays **code**, responses stay content-gen `AGENT_RESPONSE`), **skills** (SKILL.md mental scripts — content), **tool-classifications** (gated), **MCP config** (gated + allowlisted). None introduces an LLM routing/judgment decision; model-selection stays the code router (+ the P2.7 Layer-4 override). (roadmap §9.)
5. **Fail-closed loading.** A bad/unparseable manifest, an unknown schema-version, a **missing declared dependency** (a role's `model_id` absent from the host model registry; a required `room_type` absent), a tool with no usable classification, a server not matching the D4-validatable shape, or a **name collision** → the plugin **fails to load (refused)** — never partially-registers, never silently degrades into a half-wired/unsafe state. (The discovery≠permission analog: *bundling ≠ trust*; load only the valid, fully-satisfiable, classified bundle.)

## ⭐ The trust boundary (NON-NEGOTIABLE — the P2.7-S3 → MCP pattern, now a *bundle*; inscribe)

A plugin is **third-party code/config** (roadmap §3(B)/§9). The magnification vs MCP: one plugin can bundle MCP servers **and** tool-classifications **and** roles **and** skills at once — so **loading one plugin = trusting the whole bundle.** The S3 / ADR-027-D4 posture carries forward and *composes*: **opt-in** (a plugin is loaded only by explicit presence/declaration — never auto-fetched), **manifest-validated** (schema + dependency + classification checks **before** any registration), **credential-safe** (servers reuse `api_key_env`; the manifest carries no plaintext secret), **fail-closed** (§spine 5). **The worst a malicious plugin does is bounded by the gate + allowlist it cannot bypass**: its tools still gate (unclassified / over-claimed → HARD_CONFIRM or refused), its servers still need the allowlist + scoped-env, its roles still cannot route (code activation), its skills are content (no execution). Opt-in + manifest-validation + the **unbypassed** gate/allowlist are the layered defense — exactly S3, one level up.

**The call that distinguishes a plugin from MCP** (Decision b, the lead): whether this trust surface includes third-party **executable code** or only third-party **config/declarations**. Lean: **declarations-only for the MVP** — see (b).

## Scope

**In scope (P3.5 MVP):**
- A new **`plugins/` package**: a **plugin-manifest schema** (`plugin.yaml`: identity, version + **schema-version**, declared contributions `{roles, skills, tools, mcp_servers}`, declared **dependencies**) + a **plugin loader** (discover → validate → register: merge a plugin's roles/skills/tool-classifications/mcp-config into the agents/skills/tools/MCP registries **at the `_build_context` merge point, reusing the four existing loaders** — not reimplementing them).
- **Fail-closed loading** (§spine 5) + the **trust-boundary carry-forward** (§trust): opt-in discovery + manifest-validation + credential-indirection reuse + the gate/allowlist **unbypassed**, at the ruled MVP posture (§Decisions c).
- **ONE demo plugin** end-to-end (mirrors P3.4's one demo connector): a plugin bundling a **role** (reuse e.g. `facilitator`) + a **skill** (reuse an existing SKILL.md) + an **MCP-server config** (reuse ADR-027's filesystem demo) + a **tool-classification** — proving the loader merges **all four** surfaces and that the merged tools still gate / servers still allowlist. (Which surfaces the demo must exercise = Decision a.)
- **Discovery config**: a `plugins/` content dir (mirroring `config/skills/` + `config/agents/` directory-discovery) — **local-dir discovery** for the MVP (§Decisions a).

**Out of scope (defer):**
- **Remote install / a plugin registry / fetch-from-network** (a network + bigger-trust surface) — **defer to P3.7** (the P3.4 "defer remote MCP transport" parallel).
- **Plugin-provided executable tool *code*** (arbitrary Python on load — import isolation / sandboxing / a code-trust model) — **defer** unless architect rules it in (§Decisions b); the MVP lean is **declarations-only**.
- **Plugin lifecycle beyond load** (runtime enable/disable/upgrade/uninstall; versioned coexistence) — MVP **loads at bootstrap** (like the existing loaders); runtime lifecycle is later.
- **GUI plugin-management** (frontend track); any change to the **autonomy gate / MCP-client decision logic** — P3.5 **feeds** the registries; it does **not** change the gate (`score`/`decide_tier`/`emit_gate_decision`/`process_tool_calls`) or the MCP client/adapter.

## Decisions (surface for the architect — do not self-decide; ⭐ = constitutional/security)

**(a) Discovery mechanism + MVP scope.**
- **Discovery — lean: local-directory discovery** (a `plugins/` dir; each plugin a subdir with a `plugin.yaml` + its content), discovered + validated + merged at bootstrap — mirrors `config/skills/` + `config/agents/` directory-discovery and ADR-027's "local = most-trusted tier; defer remote." **Defer** remote-install/registry/fetch (P3.7). Architect rules.
- **Scope — lean: the loader + ONE demo plugin** bundling **all four** surfaces minimally (a reused role + a reused skill + the ADR-027 filesystem MCP-server config + one tool-classification), to prove the merge end-to-end across every surface; not many plugins (P3.7). Architect rules which surfaces the demo must exercise (lean: all four — the integration point's value *is* proving the bundle merges).

**⭐ (b) The lead call — does a plugin carry CODE or only CONFIG/declarations?** This sets the entire trust surface.
- Three of the four packaged surfaces are unambiguously **pure data/config** with existing loaders: **roles** (agent YAML), **skills** (SKILL.md), **MCP config** (the ADR-027 D5 block). The fourth — **"tools"** — is ambiguous: a plugin's tool could be **(i)** a **declaration/classification** (a `ToolMeta` reversibility entry — config; the *impl* stays a host builtin or an MCP server) or **(ii)** an **executable implementation** (third-party Python — arbitrary code on load).
- **Lean: declarations-only for the MVP (i).** The trust surface is then "third-party *config*" — bounded by the gate/allowlist it cannot bypass, with **no new code-execution / sandboxing surface**. Plugin-provided executable tool code **(ii)** is a categorically larger trust surface (import isolation, sandboxing, a code-trust model) — **defer to a dedicated later slice.** Architect rules (declarations-only-MVP **vs** admit-plugin-code-now). **This is the single biggest scope + security call in P3.5.**

**⭐ (c) The trust/consent posture (the knobs around the non-negotiable boundary; ADR-027 D4 carried forward).** Architect rules, like S3's / MCP's allowlist:
- **Consent / opt-in model** — loading a plugin = opting into its bundled servers + tool-classifications. Is plugin *presence in the `plugins/` dir* the opt-in (mirrors config — **lean**), or is a separate per-plugin host allowlist/consent entry required (manifest *discovered* but only *activated* when listed)? Lean: **presence = opt-in** for the local-dir MVP (the dir IS the host's curation), with the per-surface guards (gate/allowlist) still applying. Architect rules the consent granularity.
- **Plugin-asserted reversibility authority** — when a plugin declares a tool's reversibility, is it **authoritative**, **advisory-capped** (host may only *lower* trust, never raise — a plugin can't claim rev=10 to dodge HARD_CONFIRM), or **ignored** (host re-classifies / default 0)? Lean: **advisory-capped → host-authoritative-or-default-0** (the ADR-027 HR#2 analog — a third-party self-claim is never authoritative for the tier). Architect rules.
- **Credential + scoped-env** for plugin-delivered servers — reuse ADR-027 D4 verbatim (`api_key_env`, scoped subprocess env). Confirm carry-forward.

**(d) Manifest contract + dependency model + collision policy** (mostly senior-design within ADR-029; the **fail-closed posture + collision policy** want an architect nod).
- **Manifest fields** — identity (id/name), version + **schema-version** (loader rejects an unknown schema-version → fail-closed), declared contributions `{roles, skills, tools, mcp_servers}`, **declared dependencies** (a role's `model_id`s / required `room_type`s / a minimum host-contract version) — **fail-closed if a dependency is unmet** (the "missing dependency → refused" case). Senior designs the exact schema (frozen + `extra="forbid"`, validated by a loader mirroring `load_tools_config`/`load_mcp_servers_config`).
- **Collision policy** — two plugins (or a plugin + core config) both define a role `operator` / a tool name / a skill id: **fail-closed on collision** (lean) vs **namespace plugin contributions** (`<plugin>__<id>`, the MCP-namespacing analog) vs **declared precedence**. Lean: **fail-closed on collision** for the MVP (loudest, safest); namespacing is the considered alternative. Architect nods the policy; senior designs.

**⭐ (e) dual-lens R0-B? — lean: DISPATCH** (per `dual-lens-r0b.md`). **≥2 criteria hold:** **(2)** a new **cross-package layering edge with runtime consequences** — a new `plugins/` package aggregating into the agents/skills/tools/MCP registries via `_build_context` (plugin tools become gate-callable; plugin servers become connectable); **(3)** a **contract referenced by ≥5 future tasks** — the manifest is THE distribution unit (every future plugin, P3.7 content depth, the whole extensibility story binds it; inscribe-before-producer). Plus the **magnified trust boundary** (a third-party *bundle*) + the roadmap's explicit pre-flag (§4/§8: "P3.5/P3.4 will likely want dual-lens R0-B … like P2.7-S3"). Consistent with P3.4. Architect confirms (if yes: senior authors `reviews/P3.5/external-r0b-prompt.md`; `requires_cross_family_review: true`).

- **P3.5 is the backend track's CLOSER / integration point** (roadmap §4/§5): it packages roles/skills (P3.1) + MCP config (P3.4) — the *convergence*, not a parallel leaf; both predecessors are **closed**. ## Constraints (do not violate)
- **The constitutional spine + trust boundary above** (gate-unbypassed plugin tools; allowlist-unbypassed plugin servers; load-is-code-not-LLM; no-new-routing-`LLMPurpose`; fail-closed loading; opt-in / manifest-validated / credential-safe third-party bundle).
- **Feed the registries, don't change the gate/MCP-client** — `_build_context`'s merge + the four loaders + the autonomy gate + the MCP client/adapter decision logic are **unchanged**; plugins contribute **into** the existing registries via the existing merge point. **Reuse the four loaders; do not reimplement them.**
- **Bind ADR-027 D4/D5, don't restate** — the plugin `mcp_servers` block IS the ADR-027 D5 shape; the trust posture IS ADR-027 D4. ADR-029 composes them.
- **Inscribe-before-producer** — the manifest contract is referenced by P3.7 (more plugins) + the extensibility story; pin it in ADR-029 before plugins are authored against it.
