## In scope

### #1 (mandatory) — `skills/loader.py:121-129`: redundant rglob + `StopIteration` footgun

Inside the duplicate-id branch (`if skill.id in skills:`) the code re-traverses
the whole tree — `next(p for p in directory.rglob("*.md") if p.stem == skill.id
and p != md_path)` — purely to name the earlier path in the error message. Two
defects:
- **(a)** a redundant full `rglob` on the error path;
- **(b)** `next()` has **no default** → raises a bare `StopIteration` if the
  generator is empty, masking the real `SkillError`.

**Fix direction:** track a `stem→path` (≡ `id→path`, since stem == id) mapping on
the first pass; on duplicate, raise `SkillError` citing both paths from the map —
no re-traversal, no `next()`. Preserve the existing raise-on-duplicate contract
and ADR-009 D8 (filename stem == id) **exactly**.

> Framing: this is **error-path-only**, not a hot-path O(n²). Fix it as a
> correctness/robustness cleanup, not a performance win. (The intake's "~1M
> filesystem calls" claim is false — the re-scan runs once, immediately before a
> fatal raise.)

### #6 — `autonomy/config.py` (`CountdownAutoFireConfig`, fields at `:28-29`): missing cross-field validator

`window_s` (`ge=1`) and `sweep_interval_s` (`ge=1`) are each validated
individually, but nothing enforces `window_s >= sweep_interval_s`. A sweep
coarser than the window lets COUNTDOWN auto-fire overshoot the window by up to
one sweep interval — and auto-fire is the human-out-of-loop path (RB-AUTOFIRE),
so overshoot matters.

**Fix direction:** add a Pydantic `model_validator` rejecting
`window_s < sweep_interval_s` at load → `ValueError`, consistent with ADR-040
D7's existing fail-closed refuse-start posture. (Defaults 300/30 already satisfy
it.)

> **Senior judgment call:** confirm whether this new constraint warrants an
> **ADR-040 D7 amendment note**. Architect-partner lean: **no** — it tightens
> *within* the existing fail-closed contract, it doesn't change a decision — but
> surface to the architect if you disagree.

### #7 — `autonomy/scoring.py:178`: undocumented floor semantics (doc-only)

`eff_confirm = max(0, threshold_confirm - user_intent_modifier)` floors the
effective confirm-threshold at 0. The `max(0, …)` is correct but unexplained.

**Fix direction:** add a short inline comment / docstring line explaining the
floor (per ADR-005 D4/D5). **Docstring-only — no behavior change.**

> **⚠ Guardrail — do NOT touch the adjacent `eff_auto` (`:177`).** `eff_auto`
> has *no* floor **by design**; the "eff_auto trace-clamp" is a **P6 deferred
> residual (inscribed, not a bug)**. Adding a clamp here is an out-of-scope
> bundle — the P1.5.5 RC-19 failure class. #7 is documentation only.
