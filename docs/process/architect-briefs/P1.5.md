## Architect-settled design decisions

### 1. Room state machine is code-driven, event-triggered (handoff §3.1)

State transitions are deterministic functions of `(current_room_state, recent_event_stream, current_event)`. No LLM judgment. Constitutional test enforces. Each `RoomType` has its own state set; transitions are typed per RoomType.

This is the third code-driven decision-function module in the project (after `autonomy/gate`, `skills/decide_skills_for_context`, `agents/decide_agents_for_room` + `should_agent_speak`). The pattern stays consistent: pure function consumes event stream + state; returns next state OR None.

### 2. State machine integrates with `dispatch_turn` post-loop

After `dispatch_turn` completes a turn, the orchestrator calls `next_room_state(room, snapshot, current_event=current_event)`. If it returns a new state, a `state_transition` event is appended to the stream (using `StateTransitionMeta(new_state)` from P1.4-4). The next turn's snapshot includes this event; `should_agent_speak` for state_change triggers fires per ADR-010 D1.

Where exactly this integration happens — inline in `dispatch_turn` body, or as a separate caller (`RoomRuntime`?) — is senior's call. Architect-partner lean: separate caller, because:
- `dispatch_turn` is already complex (10 atomic tasks of P1.4 impl); coupling state-machine drive into it would inflate.
- Separate caller is testable in isolation; mirrors the dispatch-vs-context-builder separation from ADR-011 D4.
- The eventual "room runtime" is P1.5+ scope per `handoff.md`; introducing it now (even as a thin shim) is the natural home.

### 3. `agent.applies_to.room_types` shape mirrors ADR-009 Skill.applies_to

Pydantic field on `Agent`:
```python
class AgentAppliesTo(BaseModel):
    model_config = ConfigDict(frozen=True, extra="forbid")
    room_types: list[RoomType] | Literal["*"]   # or use ["*"] sentinel per ADR-009 D3
    room_states: list[str] | Literal["*"]       # state names are RoomType-specific
```

Or senior picks `list[str]` everywhere with `["*"]` sentinel (per ADR-009 D3 exact precedent — more consistent with skills). Architect-partner lean: use the same sentinel shape as `Skill.applies_to.agents` (`list[str]` with `["*"]` sentinel; validate-non-empty + reject-`["*", "other"]`). This is the **third use of the `["*"]` sentinel pattern** — sufficient signal for the convention to be codified at the schema level (architect-partner-direct addendum, not a senior decision).

`decide_agents_for_room` updated signature:
```python
def decide_agents_for_room(
    room_type: RoomType, room_state: str,
    *, available_agents: dict[str, Agent],
) -> AgentSelection: ...
```
The `room_type` + `room_state` parameters that DeepSeek R0-B 🟡#3 had us drop in P1.4 come back for real consumption.

### 4. Five RoomTypes have state machines; only Research is fully implemented in P1.5

`handoff.md` §5.2 lists 5 templates: `free_chat`, `bug_fix`, `research`, `code_review`, `idea_validation`. P1.5 implements **research fully**; the other 4 land as **placeholder state machines** that have only `{setup, closed}` states (no architecturally interesting transitions). This is the analog of P1.3's "2 sample skills demonstrate the format; full library is content task downstream" — the architectural surface is the state machine + filtering; the per-room-content is a P2 content-polish task.

If senior judges that any of the other 4 templates is trivial enough to fully implement alongside research (e.g., `bug_fix` has only operator with a 2-state machine: `setup → debugging → closed`), include — but **don't grow scope to land all 5 fully**.

## Constraints (do not violate)

- **`handoff.md` §3.1 compliance**. The room state machine is code; no LLM. Constitutional test forbids LLM imports in `src/orchestrator/rooms/`.
- **Event stream as single source of truth**. State transitions append `state_transition` events; state derivable from event stream replay. No side state.
- **No new `LLMPurpose` values** (P1.5 introduces no LLM calls in `rooms/`).
- **Layering** per §7 above. Four new constitutional tests.
- **Decision-trace pattern**. `next_room_state` returns enough context to explain *why* it transitioned (or didn't). Senior decides exact trace shape; could be embedded in the returned state OR returned as a sibling `StateTransitionTrace` model.
- **`Agent.applies_to` is additive**: existing skeptic.yaml + prober.yaml get default `{room_types: ["*"], room_states: ["*"]}`; they continue to load without yaml changes. New agent yamls (P1.5.5 operator) declare specific filters.
- **`decide_agents_for_room` signature change is a breaking change** for the P1.4 callers — but P1.4 has no real callers outside its own tests (the room runtime is P1.5 scope). The breaking change is contained.

## Predicted senior self-discoveries

- **`state_transition` events need a `from_state` field too** (currently `StateTransitionMeta` has only `new_state`). Senior picks; could match `should_agent_speak`'s snapshot semantic (read what's relevant to the trigger).
- **Cycle-detection in state machines**: are state-machine cycles allowed? E.g., Research room can go `exploration → divergence → exploration → divergence → ...` (revisiting cycle). Senior decides whether to enforce no-cycles vs allow-with-cycle-count-warning vs allow-freely.
- **What happens when `next_room_state` would transition to a state that no agent has `applies_to.room_states` for?** Empty room loaded means no agent speaks; dispatch silent. Surface; lean: that's the system telling you the room is silent until user input.
