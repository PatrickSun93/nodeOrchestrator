# ADR-039: Auth / identity model — the first human-identity trust boundary (per-request authenticated principal, cookie-session + per-user token, all-or-nothing operator authz, the spine-threading + remote-bind)

**Status:** Accepted (architect, 2026-06-06) — senior-drafted for P4.5, the Wave-2 trust-hardening final slice; architect Accepted after plan-stage dual-lens cleared 0🔴 (R0-A-on-plan 0🔴1🟡10🟢 + R0-B-on-plan cross-family 0🔴4🟡7🟢), the A-2 deployment-topology ruled (same-origin / SameSite=Strict), all 6 🟡 absorbed (α), and the five §5 sub-decisions confirmed (RC-3: senior did **not** self-accept). `requires_cross_family_review: true`, P4-roadmap §8 — mandatory dual-lens, D1+D2 heavy / D3 single-lens.

**Ratification + amendment context.** All five decision-surface points (DP1–DP5) were **architect-ratified** along the lean lines in the brief (`docs/process/architect-briefs/P4.5.md`) + the ratification commit `9356bea`: **DP1 = (b)** real multi-user seam (per-request authenticated principal; `author="user"` → `user:<id>`; simplest credential now, OAuth/OIDC additive); **DP3 = (a)** all-or-nothing authenticated-operator (no speculative RBAC; pin the checkpoints; inscribe `RB-AUTHZ`); **DP2** cookie-session for the GUI + optional per-user static token, `auth + multi-user + remote-bind` IN, **TLS terminated at the deployment/reverse-proxy layer** (documented, not in-app), rate-limiting thin-on-write-chokepoints or named residual, **D2 (remote-MCP OAuth) deferred** to a follow-on; **DP4** gate stays identity-blind, confirm gains authenticated approver provenance, forge-guard generalises (principal server-derived from the verified session, never the request body), pin the ADR-038 D5 management-endpoint authz dimension (build no endpoint code); **DP5** this new ADR + amendments to ADR-025 / ADR-026 / ADR-030 (+ ADR-038 D5). The architect Accepts — **the senior does not self-accept (RC-3).** Amendments to ADR-025/026/030/038 are inscribed at impl (plan task P4.5-8), matching the eventual Accepted status (the ADR-037 / ADR-038 precedent).

**Scope:** The **identity substrate** — the project's first human-authentication trust boundary, orthogonal to the existing forge-prevention spine. Everything before P4.5 assumed *one trusted operator on localhost* (ADR-025 D7: "Auth: none"). This ADR inscribes: the **per-request authenticated `Principal`** (DP1b) + its expensive-to-change shape (the `author="user"` → `user:<id>` generalisation, D1); the **user store + credential model** (password hashing, first-account bootstrap, D2); the **auth mechanism** (cookie-session login→server-session + optional per-user static bearer token, D3); the **fail-closed authentication boundary** (a server-side principal-deriving gate over every route + the WS, D4); the **all-or-nothing authenticated-operator authz model** (DP3a) + the **pinned permission-checkpoint seams** (confirm-approve / plugin-admit / config-write) that make a role model additive (D5); the **confirm approver provenance** (the ADR-030 N1 hook landed, D6); the **forge-guard generalisation** (principal server-derived, never request-read — ADR-025 D4 one level up, D7); the **remote-bind + transport posture** (configurable host, fail-closed-when-non-localhost, CORS, TLS-at-deployment, rate-limiting, D8); the **ADR-038 D5 management-endpoint authz dimension** (who may admit/enable/disable — pinned, no endpoint code, D9); and **P4.5's honest residual set** (`RB-AUTHZ`, TLS-at-deployment, rate-limiting-if-deferred, deferred-D2/MCP-OAuth, credential-posture, first-account-bootstrap — D10). Does **NOT** govern: the autonomy gate's **decision logic** (stays identity-blind — `score`/`decide_tier`/`emit_gate_decision` byte-frozen, DP4a / D4); the executed `TOOL_CALL`'s authorship (stays `agent:<initiating_agent>` — ADR-030 D3 step 5, unchanged; D6 adds only approver *provenance*); **remote-MCP OAuth** (D2 of the ledger — deferred follow-on, rides this identity work — D10); the **plugin management endpoints' code** (pinned-not-built, ADR-038 D5 / P4.7 — D9 fixes only their authz dimension); the **React GUI login surface** (frontend-track follow-on — this ADR pins the integration contract, builds no `ui/` code; the ADR-038-D5 / P4.7 precedent); **in-app TLS termination** (deployment-layer concern, documented not coded — D8); a **role/permission model** (DP3b — deferred, `RB-AUTHZ`; the checkpoint seams D5 make it additive).

## Context

Verified against `origin/main` @ `9356bea`. **There is zero human authentication or identity anywhere in the product** — the surfaces this ADR threads:

- **No auth layer.** `api/app.py` registers all 7 HTTP routes (`POST /rooms`, `GET /rooms/{id}`·`/events`·`/snapshot`, `GET /events/{id}/thread`, `POST /rooms/{id}/intent`, `POST /rooms/{id}/confirm`) + the 1 WS stream (`/rooms/{id}/stream`) with **no middleware, no `Depends`, no header/cookie parsing, no request principal** (verified: `grep -i cors/middleware app.py` → none — even the ADR-025 D7 "CORS restricted to the local GUI origin" promise was **never built**). Context is closure-captured (`AppContext`, `app.py:95-120`; `_register_routes`, `app.py:379-836`); there is **no DI seam** for a principal today.
- **Request identity is `author="user"`, hardcoded server-side** (`app.py:486`, "HARDCODED — never read from request"). `IntentRequest` omits `author`/`id`/`timestamp` (`wire.py:48-61`, ADR-025 D4). The server *prevents a client forging who it is* — but there is only **one** "who". `is_valid_author` (`core/event.py:405`) admits `^(user|system|agent:[a-zA-Z0-9_-]+)$`; a user event is `author="user"`.
- **`user_id` exists but is an audit string, not a principal.** `DecisionMeta.user_id` is required iff `promotion=True` (`core/event.py:139-177`); `record_preference(key, value, user_id, …)` mandates a non-empty `user_id` (`memory/entity.py:107-180`); `verified_knowledge.promoted_by_user_id` (NOT NULL) records the promoting user. None is **authenticated** — they record *who declared/confirmed*, asserted by no one.
- **Confirm approver is anonymous.** `ConfirmRequest{pending_event_id, decision}` (`wire.py:121-131`) carries **no approver**; the resulting `TOOL_CALL` is `author=build_author(pending_meta.initiating_agent)` (the **agent**, `app.py:677/699`), not the human. ADR-030 D3 step 5 / N1 **explicitly dropped** `user_id`: *"no `user_id` provenance … a user-identity audit field is a forward hook when auth lands."* — this ADR is when it lands.
- **The autonomy gate scores actions, not actors.** `Operation{tool_id, initiating_agent, user_explicit_intent, …}` (`autonomy/scoring.py:19-34`); `user_explicit_intent` is a **boolean**, the tier is reversibility-only — no human-approver concept.
- **"Operator" is an implicit, file-based role** — whoever can edit `config/plugins.yaml` / reach localhost. Plugin admission is an "operator action, not a gated agent op" (ADR-038 DP2c). ADR-038 D5 froze the management-endpoint contract (`GET /plugins`, `POST /plugins/{id}/enable·disable·admit`, `DELETE /plugins/{id}`) **with no authz dimension** and deferred *building* it to P4.7.
- **Storage idiom: SQLite co-location.** `core/event_store.py` (events, append-only, schema TRIGGERs) + `memory/store.py` (hypothesis / verified_knowledge / entity) share one DB file. The two-connection model (ADR-025 D6): a serialized **writer** connection + single-thread `writer_executor` (`max_workers=1`) for all writes/`run_turn`; a separate read-only **WAL reader** + read executor for GETs/WS-replay (the origin/main baseline is a *single shared* reader connection — **P4.5 RW7 evolves the reader side into a per-thread WAL reader pool**, each `reader_executor` worker owning its own read connection for multi-user concurrent-read correctness; the writer side is unchanged — see the ADR-025 D6 P4.5 note). Config is YAML in `config/` + env vars (no secrets store; MCP uses `api_key_env` → `Authorization: Bearer`, `mcp/transport.py:97-108`). **No `users`/`sessions`/`credentials` table or config exists.**
- **Bind** is `--host` default `127.0.0.1` (`api/__main__.py`); the comment says "Production deployment must add authentication/TLS before exposing externally" — there is **no guard** preventing a `--host 0.0.0.0` bind with auth off today.

**The boundary this ADR turns on.** Every prior slice protected against a *client forging the backend's decisions* (forge-prevention, backend-authoritative — ADR-025 D4, ADR-026 HR#1/#2, ADR-030 HR#1). P4.5 adds an **orthogonal** boundary: *proving which human is on the other end*, and *what that human is allowed to do*. The constitutional spine is **unchanged** (no new principle); this is the first slice where "the operator" stops being an assumption and becomes a **modeled, authenticated primitive**. The primitive's *shape* (the principal, the `author` generalisation, the checkpoint seams, the management-endpoint authz dimension) is **expensive-to-reverse** and gates D2/D3 and the P4.7 GUI — hence inscribe-before-producer (roadmap §10).

## Hard requirements — the constitutional spine (NON-NEGOTIABLE; inscribed, carried forward; the dual-lens R0-B Lens B re-probes them)

1. **Backend-authoritative — the principal is server-derived, never request-read (ADR-025 D4 generalised, one level up).** The authenticated identity is derived **only** from a server-verified session cookie or a server-issued token, **on the server**; `IntentRequest`/`ConfirmRequest`/any wire body **never** carries a `user_id`/`author`/`principal` field (type-impossible — `extra="forbid"`). A client cannot assert who it is, exactly as it cannot forge `author` today. The GUI carries a credential but **decides nothing** (ADR-026 HR#1/#2 intact; the API is the sole boundary).
2. **Fail-closed on unauthenticated.** Once auth is on, **no route runs without a verified principal** — an unauthenticated request to any non-public endpoint is rejected (`401`) **before** any handler logic / append / `run_turn`. The public allowlist (login + bootstrap + health) is explicit and minimal; default is **closed**.
3. **No decision surface / the gate stays identity-blind (DP4a).** Auth is mechanical verification — **no new `LLMPurpose`**, no per-user LLM judgment, no routing/scoring change. The autonomy gate scores action reversibility, **never the actor** (`score`/`decide_tier`/`emit_gate_decision` byte-frozen). Authz (D5) gates *who may approve/admit*, never *how an action is scored*.
4. **Confirm stays human-in-the-loop + idempotent (ADR-030 D7).** D6 *adds* authenticated approver provenance; it must not regress the still-pending / position-anchored idempotency / partial-turn / crash-window invariants, and the executed `TOOL_CALL` stays **agent-authored** (the gate approved *that agent's* op; the human supplied approval, not authorship).
5. **Honest-residual inscription.** Accept the *real* post-P4.5 identity surface (D10) — `RB-AUTHZ` (no least-privilege; any authenticated account is a full operator), TLS-at-deployment, deferred-D2, the unbuilt credential posture — never a softened one. They must read as honestly as `RB-FS/NET` / `RB-ADMIT` did.

## Decisions

### D1. The principal shape + the `author="user"` → `user:<id>` generalisation (DP1b — the do-not-reverse primitive)

A per-request authenticated **`Principal`** (a frozen model: `user_id: str` + the carried session/token provenance) is derived by the auth boundary (D4) and threaded to the handlers. The identity primitive:

- **`user_id`** is the stable account identifier (the `users` table key, D2), constrained to `[a-zA-Z0-9_-]+` so it is **author-embeddable**.
- **The `author` of a user-authored event generalises** from the hardcoded `"user"` to **`user:<user_id>`** — stamped **server-side from the principal** (D7), never the request. `is_valid_author` (`core/event.py:405`) generalises its regex to `^(user|user:[a-zA-Z0-9_-]+|system|agent:[a-zA-Z0-9_-]+)$`: **bare `user` stays valid** (backward-compat for the events already in the store + the system-of-record default), and `user:<id>` is the new authenticated form. A symmetric `build_user_author(user_id)` factory mirrors `build_author` (the single point of truth for the format; raises on empty id).
- **`DecisionMeta.user_id` + the confirm approver `user_id` (D6) carry the bare `<user_id>`** (no `user:` prefix — they are id fields, not author fields), the **same namespace** as the principal. The `record_preference` / promotion `user_id` becomes the **authenticated** principal's id, no longer a free string asserted by no one.

**Why this is the load-bearing call:** the `author` format + the `user_id` namespace bind D6 (confirm provenance), the P4.7 GUI's author-label rendering, and any future OAuth subject mapping (DP1c — a federated subject maps to a `user_id` behind the **same** primitive). Reversing the format after producers bind it is a contract migration. The regex generalisation is the t4-appender-guard-adjacent change Lens B re-probes (the `author` validator + every test asserting `author=="user"`).

### D2. User store + credential model (the simplest credential now, swappable)

A **`users` table** co-located in the same SQLite DB (the ADR-020/025 storage idiom), written on the **writer** connection, read on the **reader** connection. Shape (frozen model + schema): `user_id` (PK, `[a-zA-Z0-9_-]+`), `password_hash`, `password_salt` (+ algorithm/params), `created_at`, `disabled` (bool, default false — the account-disable seam). Credential = **password, hashed with a memory-hard stdlib KDF (`hashlib.scrypt`)** — **no new dependency** (the honest MVP; argon2/bcrypt is an additive swap behind the verify interface). Constant-time comparison (`hmac.compare_digest`). **The hash/salt is never logged, never returned on the wire, never in an event** (the `api_key_env`-never-inlined discipline, `mcp/transport.py:107`).

**First-account bootstrap (the chicken-and-egg — surfaced + inscribed, DP5).** Auth gates everything, including creating users — so the **first** operator account cannot be created through an authenticated endpoint. MVP: an **out-of-band admin CLI** (`python -m orchestrator.api.admin create-user <id>` reading a password from stdin/env, writing directly to the `users` table). The operator who can run the server already has filesystem + DB access — that **is** the pre-auth trust root (the same root that authors `config/plugins.yaml`); the CLI does not widen it. Subsequent user creation is an authenticated operator action (D5 — under DP3a, any authenticated user; the user-create endpoint is a **pinned seam**, see D5/D9 — built minimally or named-residual per the plan §5 call). **Residual:** password reset / rotation / MFA / lockout / self-service signup are **not** built (D10).

### D3. Auth mechanism — cookie-session (GUI) + optional per-user static token (programmatic) (DP2a)

- **Login → server session (cookie).** `POST /login {user_id, password}` verifies the credential (D2), creates a **server-side session** (a `sessions` table: `session_id` (opaque, cryptographically-random, the `secrets` module), `user_id`, `created_at`, `expires_at`, `revoked`), and sets an **`HttpOnly`, `Secure`, `SameSite=Strict`** session cookie carrying only the opaque `session_id`. `POST /logout` revokes the session. Sessions are **persisted** (survive restart; validated on the **per-thread WAL reader pool**, created/revoked on the writer connection — fits the writer + reader connection model; the per-thread reader pool is P4.5 RW7's (app.py routes) + RW8's (HTTP auth middleware, `middleware.py`) landed model — RW7 fixed the route lambdas, RW8 fixed the `_resolve_principal` path that shared `ctx.reader_store.conn` on the loop thread; see the ADR-025 D6 P4.5 note) with a TTL + idle expiry.
- **⭐ Same-origin deployment assumption (architect-ruled A-2, R0-B-on-plan A-2).** The GUI and API are deployed **same-origin** (the React build served by / reverse-proxied behind the **same origin** as the API — the ADR-026 local-app topology). The `SameSite=Strict` cookie value is **derived from this assumption** and is correct under it: the browser sends the session cookie on every same-origin request, and a cross-site context cannot send it (CSRF mitigated by the cookie itself — no separate CSRF token). **This resolves the SameSite/CORS footgun** (R0-B-on-plan A-2): under same-origin, `SameSite=Strict` works and **CORS is not required for the GUI at all** — the CORS middleware (D8) is purely a **future remote-/cross-origin-client affordance**, not a GUI dependency. A future cross-origin client would require `SameSite=None`+`Secure`+a CSRF token — a **named residual** (D10), not this slice's posture. The "same-origin" wording is unified across D3 and D8 to eliminate the topology ambiguity the review flagged.

  **CSRF posture:** `SameSite=Strict` under the same-origin assumption mitigates CSRF for the MVP (no cross-site cookie send); inscribed, not a separate token.
- **Optional per-user static token (programmatic).** A per-user **bearer token** (`Authorization: Bearer <token>`, the existing MCP-client header idiom one level up) for non-browser clients — server-issued, stored hashed (token table or a `users` column), revocable. This is the per-user generalisation of the single shared-secret (a-)option, riding the multi-user store.

**Why session + token (not JWT):** server-side opaque sessions are **revocable** (a stolen cookie is killed by revoking the row) and carry no client-readable claims; a stateless JWT would defer revocation to expiry and is only justified under DP1c federation (deferred). The mechanism is swappable behind D4's principal-derivation interface (OIDC bearer is an additive provider — DP1c).

### D4. The fail-closed authentication boundary — a server-side principal-deriving gate (HR#1/#2)

Authentication is enforced by a **single server-side gate** that runs **before** every non-public handler and derives the `Principal` (D1) from the verified session cookie **or** the bearer token — **never** from the request body. Two implementable shapes (the plan §5 surfaces the choice; lean = **middleware-with-explicit-public-allowlist** for fail-closed-by-default):

- **Middleware (lean):** a Starlette/FastAPI middleware that, for any path **not** in the explicit public allowlist (`/login`, `/health`, the bootstrap), requires a valid session/token → else `401` **before** the route runs. Fail-closed-**by-default**: a newly-added route is protected unless explicitly allow-listed (no per-route opt-in to forget). The derived principal is attached to the request scope; handlers read it (not the body).
- **⭐ The wiring seam — registered at construction, ctx via `app.state` (architect-routed Y1 / R0-A-on-plan Y1).** The middleware must reach the session store (to validate a cookie/token) — i.e. it needs `ctx`. But Starlette builds its middleware stack on first `__call__` and `add_middleware` then raises `RuntimeError: Cannot add middleware after an application has started`; `create_app` builds `ctx` **inside** `lifespan` (`app.py:849-850`), *after* startup begins — so the middleware **cannot** reuse the closure-capture site, and there is **no `app.state` usage today** (the codebase is pure closure-capture). Resolution: a **single construction-time `configure` step that both app factories call** (`create_app` **and** `_make_test_app`, `app.py:862`) registers the auth middleware **at construction, before `ctx` exists**; **`ctx` is stowed on `app.state` at lifespan startup** and the middleware reads `request.app.state` at request-time. **This is load-bearing for testability:** all 37/37 API tests build via `_make_test_app` (0 use `create_app`) — registering the middleware only in `create_app` would leave the shipped boundary exercised by **zero tests** (tested-app ≠ shipped-app at the security crux). The shared `configure` step means the fail-closed boundary is wired **once** and exercised by the suite **through the production wiring**.
- **WS auth at handshake — reject BEFORE `accept()` (architect-routed A-1 / R0-A-on-plan M3 / R0-B-on-plan A-1).** `/rooms/{id}/stream` validates the session cookie (browsers send cookies on the WS upgrade) or a bearer token (query-param/subprotocol for programmatic) **at connect** and **rejects/closes the upgrade *before* `websocket.accept()`** (`app.py:795` calls `accept()` first today) — accept-then-`close()` admits the connection briefly (a **half-open-stream window**). A `BaseHTTPMiddleware` **does not see the WS scope**, so the WS handshake check is an **explicit in-handler pre-`accept()` check** — **necessary, not redundant** with the HTTP middleware. The WS stays read-only push (ADR-025 D2 unchanged).

The gate makes **no decision** (HR#3) — it verifies a credential and resolves a principal; it never scores, routes, or LLM-judges.

### D5. Authorization — all-or-nothing authenticated-operator (DP3a) + the pinned checkpoint seams

**Every authenticated user is a full operator** (DP3a): may `POST /intent`, approve **HARD/COUNTDOWN** confirms, admit/enable/disable plugins (when P4.7 builds those endpoints — D9), edit config, create users. **No role/permission model is built** — there is no `viewer`/`member`/`operator` differentiation, no per-action permission check beyond "is authenticated." This matches the ratified deployment intent (members assumed **fully trusted**).

**But the permission checkpoints are pinned as named seams** so a role model (DP3b) is **additive, not a re-architecture** — the three constitutional actuators where an authz check *would* sit are identified in code + ADR (each currently a no-op "authenticated ⇒ allowed", with a named comment marking the seam):

1. **confirm-approve** — `POST /confirm` (who may approve a HARD/COUNTDOWN action). Today: any authenticated principal.
2. **plugin-admit/enable/disable** — the ADR-038 D5 management endpoints (D9). Today: any authenticated principal (pinned; no endpoint code).
3. **config-write** — user-create + any future config-mutating endpoint. Today: any authenticated principal.

**`RB-AUTHZ` residual (inscribe, don't soften — D10):** no least-privilege; **any authenticated (or compromised) account has full actuation** — including irreversible HARD tools (`git_push`/`send_email`/`apply_edit`, ADR-036) and plugin admission (ADR-038). Persists until a role model (DP3b) is separately built at a checkpoint seam. **This flips dangerous if members become non-fully-trusted** — that is the deployment-intent condition under which DP3b becomes required-in-slice (the architect ratified DP3a on the fully-trusted-members assumption).

### D6. Confirm approver provenance — the ADR-030 N1 hook landed (amend ADR-030)

`POST /confirm` records **which authenticated human approved** a HARD/COUNTDOWN action — the `user_id` ADR-030 D3 step 5 / N1 deferred "until auth lands." The principal's `user_id` (D1, from D4 — **not** the request body) is recorded as **approver provenance**.

**⭐ Exact landing — an optional nullable field on the EXISTING confirm metadata, NOT a new event type (architect-routed B-2 / R0-A-on-plan M4 / R0-B-on-plan B-2).** The approver `user_id` lands as an **optional `str | None` field on both existing confirm-appended metadata schemas** — `ToolCallMeta` (`core/event.py:203-212`, the **approve** append) and `ToolCallCancelledMeta` (`core/event.py:362-370`, the **cancel** append) — **not** as a new approval event type. A new event type would ripple into `PENDING_RESOLUTION_TYPES` (the position-anchored still-pending idempotency layer 1, `app.py:659-668`) and the snapshot pending-confirm derivation — both of which HR#4 / ADR-030 D3/D7 require **unchanged**. The field is **nullable** for **backward-compat with pre-P4.5 events** (which have no approver recorded) and because under single-user/legacy the value may be absent; the still-pending scan keys on `type ∈ PENDING_RESOLUTION_TYPES` + matching `call_id` (`app.py:659-668`) and **never inspects `user_id`**, so the additive field cannot affect idempotency on any path (R0-B-on-plan B-2 traced this).

**The executed `TOOL_CALL` stays `author=agent:<initiating_agent>`** (ADR-030 D3 step 5, byte-unchanged — the gate approved *that agent's* op; the human supplied approval, not authorship). The audit trail gains the missing fact: `AUTONOMY_DECISION` → `TOOL_CALL_PENDING` → `TOOL_CALL` (agent-authored, **`user_id`-approved**) → `TOOL_RESULT`. Idempotency / position-anchored still-pending / partial-turn (ADR-030 D3/D5/D7) are **unchanged** (HR#4). **If DP3b were in-slice**, this is also where the *who-may-approve* check would gate; under DP3a it is provenance-only (the D5 seam #1).

### D7. Forge-guard generalisation — the principal is server-derived (do-not-reverse; ADR-025 D4 one level up)

The server stamps `author` (ADR-025 D4); P4.5 generalises `author="user"` → `user:<principal.user_id>` (D1), stamped **from the verified session/token (D4), never from the request body**. `IntentRequest`/`ConfirmRequest` **never** gain an identity field (the forge vector — `extra="forbid"` keeps it type-impossible). The GUI carries a credential (the session cookie) but **still decides nothing** — auth is enforced at the **API (the sole boundary)**, not the client (ADR-026 HR#1/#2 intact). This is the exact ADR-025 D4 discipline ("let the client set `author` → rejected, constitutionally") applied to identity: the client proves *a* credential; the server resolves *which* principal and stamps it. **Lens A's primary probe** (can a request act as someone it isn't) + **Lens B's** (does the generalised `author` break the appender guards / `is_valid_author`).

### D8. Remote-bind + transport posture (DP2b — which of D1's five things land)

- **Remote-bind IN, fail-closed.** `--host` stays configurable, **but** binding beyond **localhost** with **no users provisioned** (or auth-disabled) is **refused at startup** (loud) — a remote bind must have the auth boundary armed. (The opposite of today's silent `--host 0.0.0.0` + auth-off.) This closes the ADR-025 D7 gap without forcing localhost. **"localhost" is `127.0.0.0/8` + `::1` + the literal `localhost` (architect-routed M1 / R0-A-on-plan M1)** — *not* the literal string `127.0.0.1`, so a legitimate `::1` bind is not falsely refused and a specific-LAN-IP bind cannot slip the guard.
- **CORS — NOT a GUI dependency under the same-origin assumption (architect-ruled A-2; reframes the ADR-025 D7 promise).** Given the same-origin deployment (D3), the GUI needs **no** CORS at all (same-origin requests are not CORS-gated). The CORS middleware is therefore **optional, future-only** — a **remote-/cross-origin-client affordance** — and if built it restricts origins to a configured allowlist with credentials allowed; it is **never** `*`-with-credentials (the credentialed-wildcard footgun). (Verified: no CORS exists today despite ADR-025 D7's "CORS restricted to the local GUI origin" promise — but under same-origin that promise was moot for the GUI; the honest reframe is "CORS is a future cross-origin affordance, not a GUI requirement.")
- **TLS — terminated at the deployment/reverse-proxy layer (documented, NOT in-app).** Bolting cert-management into uvicorn couples deployment concerns into the app; the forge / no-decision-surface invariants hold regardless of transport (ADR-025 D7). Inscribed as a **deployment requirement + `TLS-at-deployment` residual** (D10) — the session cookie is `Secure` (D3), which *requires* TLS at the proxy in any remote deployment (documented).
- **Rate-limiting — thin-or-deferred (architect-confirmed §5 #3).** If built, the one chokepoint with a real security argument is **`/login`** (credential brute-force). **`/login` throttling can only be per-claimed-`user_id` / per-IP — there is no authenticated principal at `/login` yet** (architect-routed M2 / R0-A-on-plan M2); a **per-identity** limiter applies only to `/intent`·`/confirm` (post-auth). If rate-limiting is deferred, the chokepoints are unthrottled — a **named residual** (D10).

### D9. Pin the ADR-038 D5 management-endpoint authz dimension (amend ADR-038; build no endpoint code)

ADR-038 D5 froze `GET /plugins` / `POST /plugins/{id}/enable·disable·admit` / `DELETE /plugins/{id}` as a forward-contract **with no authz dimension**, built in P4.7. P4.5 **pins the authz dimension** of that contract: these are **operator actions requiring an authenticated principal** (under DP3a — any authenticated user; the checkpoint seam D5 #2 is where a role check would later gate). **P4.5 builds no endpoint code** (the P4.7 frontend track owns that); it only fixes the contract's identity gap so P4.7 builds against an authz-aware contract rather than inheriting an authz-blind one (inscribe-before-producer). Inscribed as an ADR-038 D5 annotation (plan task P4.5-8).

### D10. Honest residual set (inscribe, don't soften — DP5; the routing-dependent set, now fixed by the ratified DP1b/DP3a)

- **`RB-AUTHZ`** (DP3a) — no least-privilege; any authenticated account is a full operator (irreversible HARD tools + plugin admission). Persists until a role model (DP3b) is separately built at a D5 checkpoint seam.
- **`TLS-at-deployment`** (DP2b) — the app does not terminate TLS; secure transport is a deployment requirement (reverse proxy), named not coded. The `Secure` session cookie *requires* it for any remote deployment.
- **Cross-origin GUI posture** (A-2) — the slice assumes **same-origin** GUI+API deployment (D3); a future **cross-origin** client would require `SameSite=None`+`Secure`+a CSRF token + the CORS-with-credentials path (D8). Named, not built — the same-origin assumption is the MVP posture, the cross-origin posture is the additive residual.
- **Rate-limiting** — if deferred (plan §5), the write chokepoints (`/intent`/`/confirm`/`/login`) are unthrottled — a named residual.
- **D2 / MCP-OAuth** — deferred to a follow-on (it "rides D1" — roadmap §3.D; the identity primitive now exists, so OAuth/token-refresh for remote MCP is a clean additive slice over ADR-032).
- **Credential posture** (DP1b) — **not** built: password reset / rotation / MFA / session-revocation-UX / account lockout / self-service signup. The real surface, inscribed.
- **First-account bootstrap** — the initial operator is provisioned out-of-band (D2 admin CLI); no in-product first-run onboarding.
- **React GUI login** — the integration contract is pinned (D3 cookie semantics + the `401` handling ADR-026 carries); no `ui/` code this slice (frontend-track follow-on, the P4.7 precedent).
- **Bearer-token-no-expiry** — per-user static bearer tokens have **no expiry date**, only revoke-on-request. A compromised token lives until explicitly revoked. Expiry (TTL + auto-rotation) is additive via the token schema (a new column); named residual, architect-ratified not-built-this-cycle.
- **Session-no-idle-expiry** — sessions carry a 24-hour **absolute TTL** (`expires_at`) but no idle/inactivity expiry. A session remains valid for 24 h regardless of use; the sliding-window expiry pattern (reset `expires_at` on each validated request) is additive. Named residual, same class as reset/rotation/MFA above.

## Considered alternatives

- **DP1(a) single-operator + shared secret** — Rejected (architect-ratified DP1b): under-delivers the ledger's "multi-user" and leaves D3 (per-user confirm provenance) moot (still one "who"). Legitimate only if the goal were "one operator, now remote" — it is not.
- **DP1(c) OAuth/OIDC-federated from day one** — Deferred (architect-ratified DP1b): the "right" long-term answer for a networked product, but heavier (provider config, callback flows, token validation, an external dependency for *every* login) and best added **once the identity primitive exists** (it becomes "another auth provider" behind D4, not a re-architecture). Co-designed with the deferred D2.
- **DP3(b) role/permission model in-slice** — Deferred (architect-ratified DP3a): real least-privilege, but introduces a permission surface the confirm path + plugin-admit + config-write must consult, plus role-assignment/bootstrap — heavier than a *first* boundary needs **when members are fully trusted**. The D5 checkpoint seams make it additive. **Required-in-slice only if members are non-fully-trusted** (the deployment-intent condition the architect ruled out for this slice).
- **Stateless JWT sessions** — Rejected (D3): defers revocation to token expiry (a stolen token lives to expiry) + leaks client-readable claims; opaque server-side sessions are revocable and claim-free. JWT is the DP1c-federation shape (deferred).
- **A new password-hashing dependency (argon2/bcrypt)** — Rejected for the MVP (D2): `hashlib.scrypt` (memory-hard, stdlib since 3.6) needs **no new dep** and is an additive swap behind the verify interface. (Revisitable if a hardening pass justifies argon2.)
- **In-app TLS termination (uvicorn `--ssl-*`)** — Rejected (D8): couples cert-management/rotation into the app; the reverse-proxy layer is the standard termination point and the invariants hold regardless of transport. Documented as a deployment requirement.
- **Per-route `Depends(get_principal)` instead of fail-closed middleware** — Considered (D4, plan §5): idiomatic FastAPI, but **fail-open-by-omission** (a new route without the dependency is unprotected). Middleware-with-explicit-public-allowlist is fail-closed-by-default; the per-route shape is the alternative the architect may rule.
- **Let the client send `user_id` (trust the GUI)** — Rejected, **constitutionally** (HR#1 / D7): that *is* the identity forge vector — the exact ADR-025 D4 mistake one level up. The server derives the principal from the verified session, never the body.

## Consequences

**Easier:** the product gains its first real "who is calling" — multi-user becomes real, remote deployment is unblocked (fail-closed remote-bind), the confirm audit trail finally records the approver (D6), and OAuth/OIDC (DP1c) + remote-MCP-OAuth (D2) + a role model (DP3b) are all **additive** behind the inscribed primitive (the principal shape, the D4 derivation interface, the D5 checkpoint seams). The P4.7 GUI + plugin-management endpoints plan against an authz-aware contract.

**Harder:** a new auth module + two SQLite tables (users, sessions) + a credential KDF + the fail-closed boundary (a new middleware/DI surface + WS-handshake auth) to test heavily; the `author="user"` → `user:<id>` generalisation ripples into `is_valid_author`, every test asserting `author=="user"`, and the GUI author-label (frontend follow-on); a new concurrency surface (sessions on the single-writer; remote-bind exposing the pub/sub stream to non-localhost). These are the dual-lens R0-B subjects (§Review).

**Neutral:** all-or-nothing authz (DP3a) trades least-privilege for MVP simplicity (`RB-AUTHZ` named); cookie-session trades a session store for revocability + claim-freedom; stdlib scrypt trades argon2's tuning for zero-dep. TLS-at-deployment trades in-app convenience for deployment-layer standardness.

**Crash/concurrency posture (Lens B subject).** Sessions are created/revoked on the **writer** executor (serialized, single-writer-consistent — no TOCTOU between session-create and the cookie set) and validated on the **per-thread WAL reader pool** (read-mostly — each `reader_executor` worker validates on its own read connection, so concurrent auth checks never contend on a shared reader connection and a multi-second `run_turn` does not block them; the ADR-025 D6 liveness property preserved, the per-thread reader pool added by P4.5 RW7 for app.py route lambdas and extended by RW8 to the HTTP auth middleware path — `middleware.py _resolve_principal` now also calls `ctx.get_reader_conn()` at run-time on the worker thread, completing the per-thread pool coverage across both HTTP and WS auth surfaces). A crash mid-login leaves no half-session (the session row is a single durable append-equivalent insert; the cookie is only set on success). Remote-bind exposing the pub/sub stream is now gated by the WS-handshake auth (D4) — an unauthenticated subscriber is rejected at connect.
