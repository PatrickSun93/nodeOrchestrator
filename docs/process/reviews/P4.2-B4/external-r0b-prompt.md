## What B4 ships (orientation)

Two network tools — `web_fetch` (an **agent-chosen** URL) and `web_search` (a **fixed-provider** query), both rev-10 AUTO — run **in-process** on the single writer, **before** the P4.3 egress sandbox. `web_fetch` routes every request (initial + every redirect hop) through an **SSRF-validating resolve-then-pin transport** (`tools/net_trust.py`): scheme allowlist (`http`/`https`), an IP-range denylist floor (loopback/private/link-local incl. cloud-metadata `169.254.169.254`/`0.0.0.0`/multicast/reserved, IPv4-mapped-IPv6 unwrapped), resolve-then-pin DNS-rebind defense (validate all resolved IPs, connect to a pinned IP, no re-resolve), redirect re-validation (bounded `max_redirects`), a credential-stripped anonymous client (`verify=True`, no auth/cookies/env), bounded streamed size + timeout + a per-turn **network** cap (`MAX_NETWORK_CALLS_PER_TURN`, separate from the subprocess cap). `web_search` hits a single operator-configured provider endpoint (SSRF N/A) with an env-supplied api-key sent **only** to that endpoint. New code: `tools/net_trust.py` + `tools/network_tools.py`; the executor gains a network cap branch (`_execute_local_call` byte-frozen); the `snapshot_excerpt` exclusion widens to the web tools. **The honest residual:** without P4.3, **data-exfil to a *public* attacker URL is NOT prevented** (the IP floor permits public hosts, the URL is agent-chosen) — the **active** network half of `RB-FS/NET` (ADR-031 D1a), Accepted, retired by P4.3.

## Lens (a) — SSRF / data-exfil **trust boundary**

Probe whether the boundary is real where claimed and **honest** where not. Test the SSRF validator against the **standard SSRF-bypass checklist**:

1. **IP-range floor completeness.** Are **all** of these denied — `127.0.0.0/8`, `::1`, `10/8`, `172.16/12`, `192.168/16`, `fc00::/7`, `169.254.0.0/16` (incl. **`169.254.169.254`** explicitly), `fe80::/10`, `0.0.0.0`, `::`, multicast, reserved? Is the **IPv4-mapped-IPv6** bypass (`::ffff:127.0.0.1`) unwrapped and re-classified? Is classification done on the **resolved** IP (so **IP-literal encodings** — octal `0177.0.0.1`, hex `0x7f.0.0.1`, decimal `2130706433`, mixed) cannot smuggle an internal address past a string check? Any range the denylist misses?
2. **DNS-rebind / TOCTOU (the resolve-then-pin claim).** Is the host resolved **once**, **all** resolved IPs validated, and the connection made to a **pinned** IP (not re-resolved at connect)? Construct the rebind: a hostname that validates as public but resolves (or re-resolves) to an internal IP at connect — is it blocked? A **multi-A-record** host where one IP is internal — denied? Is the pin enforced **inside** the transport (not advisory)? Does TLS still verify against the original **hostname** (`verify=True`) while connecting to the pinned IP?
3. **Redirect + credential-on-redirect.** Does **every** redirect hop re-run the full scheme + IP check (a `302 → http://169.254.169.254` re-rejected)? Is `max_redirects` bounded? Since the client is anonymous (no auth/cookies sent), confirm a cross-origin redirect has **nothing** to forward — and that no code path *adds* auth/cookies/env to the `web_fetch` client. For `web_search`: is the provider key sent **only** to the fixed provider endpoint (its auth header), **never** onto a fetched URL, never logged?
4. **Scheme allowlist.** Is `http`/`https` enforced and `file://`/`gopher://`/`ftp://`/`data://`/… rejected **before** resolving?
5. **No-bypass (test-enforced).** Does the constitution test (`t10`) actually catch (i) a re-introduced `verify=False` on the network surface and (ii) a `web_fetch` path that uses a plain/non-validating `httpx` client? Is `tools/net_trust.py` genuinely the **only** client `web_fetch` uses?
6. **Output-as-untrusted framing + the filter extension.** Web content is the **most** untrusted output. Verify: (i) it is rendered **raw** (exact bytes, bounded), **not** interpreted→`OBSERVATION`; (ii) it is **excluded** from `snapshot_excerpt` (`_NETWORK_TOOL_NAMES`) — and the exclusion set stays in sync with the registry (the drift sync-test). **Critically:** confirm excluding it does **not** blind the acting agent — the raw bytes still reach it via `current_event` (`api/app.py:454`). Can crafted result text in a `web_fetch` `TOOL_RESULT` steer a **re-dispatched** agent through the system block?
7. **Residual honesty — the load-bearing call.** Is the **data-exfil-to-a-public-URL** residual inscribed as the **real, unsolved** surface (ADR-035 D2 / D3-ii) — **not** softened or claimed solved by the framing/filter (which only shrink the *injection* vector)? Is it correctly scoped as the **active** (agent-chosen-URL) network half of `RB-FS/NET`, more active than B3's *latent* one, wired to **one** P4.3 retirement path (P4.3 wraps the egress)? Is the operator egress-allowlist named as the opt-in tightening? **Flag any place the ADR over-claims "isolation"/"sandbox"/"prevents exfil."**

## Lens (b) — **Liveness** under the single writer × the turn-loop's N passes

Probe whether the single-writer block stays absolutely bounded when network calls multiply by `(1+N)`:

1. **Bounded streamed read.** Is the response body read **as it streams**, stopping at `MAX_RESULT_BYTES` (so an unbounded/huge or slow-drip response never buffers fully into the single `max_workers=1` writer)? Confirm an OOM-via-response-body path is closed (the B3 R0-A Y1 lesson at network scale). Is a **slowloris / never-completing** response bounded by the timeout (not just total bytes)?
2. **Bounded timeout that actually unblocks the writer.** Is `httpx.Timeout` bounded on connect **and** read **and** pool? Does a hung fetch (DNS hang, connect hang, slow body) reliably raise within the timeout and unblock the writer — including across the resolve-then-pin custom transport (no unbounded `getaddrinfo` / no resolution outside the deadline)?
3. **Per-turn network cap.** Does `MAX_NETWORK_CALLS_PER_TURN` bound network calls **per pass**, with excess → `TOOL_FAILED(turn_network_cap_exceeded)`? Is it **separate** from the subprocess cap (so they don't blur), counted in `execute_pending_tool_calls` (mechanism) and **not** in `_execute_local_call` (empty-decision-diff, t3b)? Is the B3 subprocess cap branch **byte-unchanged**?
4. **The compounding term.** The worst-case single-writer block is `≤ MAX_NETWORK_CALLS_PER_TURN × network_timeout × (1+N) passes` (ADR-028 D5 × ADR-033 D4). Is every term finite and the multiplier inscribed (not accidental)? Are `WEB_FETCH_TIMEOUT_S` / `WEB_SEARCH_TIMEOUT_S` high enough to be useful yet bounded enough not to stall every room's writes? Flag any unbounded inline dependency (e.g. an unbounded redirect chain, an unbounded resolver, a retry loop) on the network path.
