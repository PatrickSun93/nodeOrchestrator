**主题:** 实现 P1.5.5 —— **operator agent + autonomy-aware tool dispatch + content agents(divergence_mapper, logger)**。关闭最后一个 P1.4 + P1.5 deferred 的大块工作:那个会调 orchestrator tools 的 agent,加上 autonomy gate 作为 LLM 提议 tool call 和 event stream `tool_call` 落地之间的安全层。

这个 task **主要是集成**,不是新架构:autonomy gate 存在(ADR-005);`tool_call` 事件有 typed metadata(P0 时期的 ToolCallMeta);`dispatch_turn` 存在(ADR-011);operator 的 `llm_config.required_capabilities: [tools]` 由现有 LLMRouter 处理(ADR-002 + ADR-003)。新的是 **接线**:某个 agent 提议一个 tool call → gate 评估 reversibility → tier 决定 tool_call 事件能不能落到流上。

**Tool 本身的执行(跑 `read_file`、`web_search` 等等)NOT 在本 task 范围内。** P1.5.5 落地 gating + 事件发射;执行层(消费 `tool_call` 事件、产出 `tool_result` 事件)是 P1.6 或更晚的事。

## Architect-settled design decisions

### 1. Tool-call gating 是 code,不是 LLM(handoff §3.1)

"这个 tool call 该不该执行?" 的决定是 `autonomy.gate(operation, tools, thresholds)` —— 已经是 pure function(ADR-005)。LLM 只在它的响应里产出 tool-call 提议;gate 决定提议能不能变成流上的事件。Gating 路径里没有 LLM。

这是 **P1.2 inscribe 的架构首次 runtime exercise**。Pattern:LLM 提议 → code 决定 → 事件发射。

### 2. Tier-to-event mapping

从 gate tier 到 event-stream emission 的 mapping 是固定的,按 ADR-005 D4/D5 + ADR-005 D6 + ADR-007:

| `gate()` 返回的 tier | 发射的事件(按顺序) |
|---|---|
| `AUTO_EXECUTE` | `autonomy_decision`(按 ADR-005 D6,在 tool dispatch 之前同步发射);`tool_call`(按 P0 的 ToolCallMeta) |
| `COUNTDOWN_CONFIRM` | 只发 `autonomy_decision`(tool_call defer 到 P2 的 UI countdown loop;如果用户不干预,P2 logic 重新发 tool_call) |
| `HARD_CONFIRM` | 只发 `autonomy_decision`(tool_call 需要显式用户批准;P2 territory) |
| `gate()` raises `UnknownToolError`(ADR-006) | `autonomy_refusal` with `refusal_reason: "unknown_tool"` 按 ADR-007 |

**按已经存在的 ADR,这个不可商量。** P1.5.5 实现;不重新设计。

### 3. operator 的 `llm_config` 按 handoff §5.5

```yaml
llm_config:
  default_model: deepseek_v4_flash
  fallback_chain: [qwen_mlx_30b]
  temperature: 0.3
  required_capabilities: [tools]
```

按 handoff §5.5:operator **必须** 用 API(不能用 Claude Code per ADR-003),因为 Claude Code 不能接受 orchestrator tool 定义。`required_capabilities: [tools]` 是 LLMRouter 用来对 model_profile 的 capabilities 校验的(`deepseek_v4_flash` 有 `[tools]`;`claude_code_*` 没有)。如果 fallback model 都不满足,启动时 fail-fast。

`operator.autonomy_thresholds`:按 handoff §5.5 例子或 ADR-005 D3 placeholder 值。Senior 钉。

### 4. Tool execution defer —— 严格只发事件

P1.5.5 发 `tool_call` 事件;**不执行 tools**。P1.5.5 不产 `tool_result` 事件。架构上的理由:`tool_call` 是 LLM 的提议;`tool_result` 是执行。把它们分开,让执行层(P1.6 或 P1.7+)能从任何来源(operator、未来的用户显式调用、定时任务)统一消费 `tool_call` 事件。

在 P1.5.5 里这可能感觉别扭(operator 提议;什么都没发生)。理由:ADR-001 的 event store 是 single source of truth;事件代表 intent + outcome;把提议(LLM output)和结果(执行)分开,保持 event 词汇干净。

### 5. Architect-partner R0-A-on-plan: dispatch(RC-9)

Architect 在 senior plan + ADR-013(如果起草了)push 之后 dispatch R0-A-on-plan。比 P1.5 stakes 低(主要是集成;surface 小);但 architect-partner 在 tier-to-event mapping 上的 lens 是这个长期 contract 最关键的 review surface。

## Constraints (不能违反)

- **`handoff.md` §3.1 compliance**:tool-call gating 是 code;LLM 只产出提议。Constitutional test `test_constitution_no_llm_calls_in_autonomy_module` 继续 apply;P1.5.5 不能违反。
- **Event stream 是 single source of truth**:每个 gate decision 发 `autonomy_decision` 事件(或 error path 上的 `autonomy_refusal`),按 ADR-005 D6 + ADR-007 D3。
- **`LLMPurpose.AGENT_RESPONSE` 复用**:P1.5.5 **不引入** 新 LLMPurpose。Operator 的 LLM call 是 `AGENT_RESPONSE` with `caller_agent_id="operator"`。不需要新 purpose ADR。
- **ADR-003 honored**:operator 的 `fallback_chain` 只能有 API-capable providers(不能有 Claude Code)。LLMRouter capabilities check 已经强制;P1.5.5 只是确认 yaml 是对的。
- **不执行 tools**:P1.5.5 **不** 执行 tools。事件发射是 deliverable;其他人(P1.6+)消费。
