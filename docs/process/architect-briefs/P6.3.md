# P6.3 — bug-fix slice (record_preference resets created_at + fetch_plugin_bundle unbounded in-memory download)

## TL;DR for the orchestrator / architect

- **Bug G (`record_preference` resets `created_at`)** — **real, contained, single atom.** The upsert UPDATE
  path (`memory/entity.py:143-156`) writes `created_at = ts` on every re-declaration → the first-creation
  time is destroyed each time a preference value changes, *and* the returned `Entity` reports the new ts as
  its `created_at`. ADR-020 D2 says a re-declaration "updates that row's **value** in place" — resetting
  create-time is a **deviation**; the fix is **conformance** (same shape as P6.2 Bug D). **One load-bearing
  scope flag:** there is **no `updated_at` column anywhere** — schema-wide zero hits in `src/` and `tests/`.

  **preserve `created_at`**; *adding* an `updated_at` column = schema migration + ADR-020 amendment, **out
  of scope** for a correctness bug-fix (DP-1). No contract touch under the minimal reading.

- **Bug H (`fetch_plugin_bundle` unbounded in-memory download)** — **real, contained, single atom,
  security-adjacent.** `_download` (`plugins/fetch.py:222-236`) does `response.content` → buffers the
  **entire** body into memory; the 50 MB `_MAX_BUNDLE_BYTES` cap (`:36`) is only checked **AFTER** that
  buffer (`:171`, post-hoc) → a multi-GB body OOMs at `:164/:230` **before the cap ever runs.** *The cap
  exists but sits downstream of the unbounded read.* **ADR correction (the architect flagged ADR-038):** the
  governing contract is **ADR-031 D5** (digest-before-extract), **NOT ADR-038** — ADR-038 §Scope explicitly
  *"Does NOT govern … the digest-before-extract fetch mechanism (ADR-031 D5, unchanged)"*, and admission is
  **decoupled** from fetch (`app.py:1777` "No fetch_plugin_bundle call here"). Stream-to-temp-file +
  incremental hash + cap-**during**-stream **preserves** the D5 ordering and **strengthens** the cap → pure
  impl hardening, **no contract touch.**

**My lean: ship both as two independent atoms (G1 + H1) in ONE slice (P6.3)** — same shape as P6.1 and P6.2
(each shipped 2 bugs / 1 slice). Dual-lens is already set (`requires_cross_family_review=true`); **H1

## Bug G — `record_preference` overwrites `created_at` on upsert-update

### Verify-cited state

`src/orchestrator/memory/entity.py:143-156` (the existing-preference UPDATE branch; review said "~146" —
accurate at HEAD, the `UPDATE` statement is `:145-147`):

```python
if existing_id is not None:
    with conn:
        conn.execute(
            "UPDATE entity SET attributes = ?, evidence = ?, created_at = ? WHERE id = ?",
            (json.dumps(new_attrs), json.dumps(new_evidence), ts, existing_id),   # ts = now_ms()
        )
    return Entity(
        id=existing_id, type=EntityType.PREFERENCE, attributes=new_attrs,
        scope=scope, evidence=new_evidence, created_at=ts,                        # ← also reports new ts
    )
```

`ts = now if now is not None else now_ms()` (`:125`). So a second `record_preference(same user_id, key,
scope)` **resets `created_at` to "now"** in **two** places: (i) the persisted row (`SET … created_at = ?`),
and (ii) the returned `Entity(… created_at=ts)`. The matched row's original `created_at` is available in the
scan loop (`:136-141`, `row["created_at"]` is in scope at the `break`) but is **not captured** today.

**The data model has only `created_at`, no `updated_at`** (verified): `entity` DDL `store.py:73-80` has
`created_at INTEGER NOT NULL` and nothing else time-shaped; `Entity` schema `schema.py:137` has
`created_at: TimestampMs` only; `_row_to_entity` `store.py:355-362` reads `created_at` only. `grep
updated_at src/ tests/` → **zero hits, whole repo.**

### Contract touch — none (conformance to ADR-020 D2)

ADR-020 D2 (`docs/decisions/ADR-020-*.md:51`): a preference *"upserts — there is exactly one preference row
per (user_id, key, scope), and a re-declaration **updates that row's value in place**."* It pins the value
and the row-identity; it says **nothing** about mutating `created_at`, and the data model it inscribes
(`:36/:73`) carries **no `updated_at`**. So overwriting create-time is a **deviation from "value in place"**;
preserving it makes code match the inscribed decision. Pure bug-fix — no amendment, no new ADR. (The
existing upsert test `tests/memory/test_entity.py:227-240` asserts count==1 + latest value but **does not**
assert anything about `created_at`, so no buggy behavior is test-locked — a `created_at`-preservation assert
is a clean fail-on-revert addition.)

### Fix options

- **G-lean — preserve `created_at`.** Capture `existing_created_at = row["created_at"]` at the loop match
  (`:139-141`); drop `created_at` from the `UPDATE … SET` clause (update only `attributes`, `evidence`);
  return `Entity(… created_at=TimestampMs(existing_created_at))`. ~4 lines, contained, both the DB and
  returned-entity halves fixed.
- **G-alt — keep `created_at` in the SET, bind the original** (`SET … created_at = existing_created_at`).
  Same DB result; rejected-lean (a no-op re-write of an unchanged column reads worse than dropping it).
- **Scope-OUT — add an `updated_at` column** (track modification time). This is a **schema migration**
  (ADR-016 `ALTER TABLE` territory, `store.py:125-136`) + an **ADR-020 data-model amendment** +
  `Entity`/`_row_to_entity` changes. **NOT a bug-fix** — its own slice if ever wanted (DP-1).

**My lean: G-lean** (preserve, don't add). Minimal, conforms to ADR-020 D2, no schema/data-model change.

## Bug H — `fetch_plugin_bundle` reads the whole bundle into memory before the size cap

### Verify-cited state (the precise defect: post-hoc cap)

`src/orchestrator/plugins/fetch.py` — the OOM vector and why the existing cap doesn't stop it:

```python
# :164   step 2 "download to temp file" — but first buffers the WHOLE body in RAM:
bundle_bytes = _download(source_url, http_client)        # _download → response.content (:230/:236)
# :168
tmp_bundle.write_bytes(bundle_bytes)
# :171   step 3 — the cap is checked AFTER the full read already happened:
if len(bundle_bytes) > _MAX_BUNDLE_BYTES:                # _MAX_BUNDLE_BYTES = 50 MB (:36)
    raise FetchError("bundle too large: …")
# :175   digest over the full compressed bytes (ADR-031 D5 property):
actual_digest = _compute_sha256(bundle_bytes)
# :187   extract reads the in-memory bytes:
_detect_and_extract(bundle_bytes, tmp_staging, source_url)
```

`_download` (`:222-236`) returns `response.content` — httpx reads the **entire** body into memory. A
malicious / misconfigured pinned source serving a multi-GB body OOMs the process at `:164` **before** the
`:171` cap is ever evaluated. **The 50 MB guard exists but is positioned after the unbounded read**, so it
caps *post-hoc* (rejects an already-materialized oversized buffer) instead of *bounding* the download. Note
the code **already stages to a temp file** (`tmp_bundle`, `:168`) — the fix streams *into* that existing
file rather than buffering first. httpx is `>=0.28.1` (`pyproject.toml`) → `client.stream("GET", url)` +
`response.iter_bytes()` are available.

### Contract touch — none; and it's **ADR-031 D5, not ADR-038** (the architect's flagged point)

- **Governing ADR = ADR-031 D5** *"The minimal remote-fetch contract — pinned source, integrity-checked,
  fail-closed"* (`ADR-031:78`). The security property is the **digest-before-extract ordering**: sha256 of
  the **compressed bundle bytes** computed and verified **before** any extraction.
- **ADR-038 explicitly does NOT govern fetch.** ADR-038 §Scope (`:5`): *"Does **NOT** govern … the
  digest-before-extract fetch mechanism (ADR-031 D5, unchanged)"*; ADR-038 `:52` / `:66` both re-cite the
  digest-before-extract property as *"(ADR-031 D5, unchanged)"*. And **admission is decoupled from fetch**:
  `app.py:1777` *"No fetch_plugin_bundle call here: admit authors operator intent only."* So a streaming
  change to `fetch.py` touches the **admission-proof path zero**.
- **Does streaming break "digest needs the complete bytes"?** No. We hash **incrementally** over the stream
  (running `hashlib.sha256`), finalize, and verify **before** extraction — the bytes and the ordering are
  identical to today. There is **no signature/keyring** step that needs the full buffer in RAM (ADR-038 `:77`
  / `RB-ADMIT`: *"no crypto signature/keyring"* — the sha256 digest is the only integrity check). The 50 MB
  value is an impl constant, **not** a pinned contract term.

→ **Pure implementation hardening.** The D5 ordering is **preserved**; the size cap moves from *post-hoc* to
*enforced-during-stream* (strictly stronger). No amendment, no new ADR.

### Fix options

- **H-lean — stream + incremental hash + cap-during-download.** Replace `_download`'s `response.content`
  with `client.stream("GET", url)` → iterate `response.iter_bytes()`, writing each chunk to `tmp_bundle`
  while maintaining (i) a running `hashlib.sha256` and (ii) a running byte count; **abort with
  `FetchError("…too large")` the moment the count exceeds `_MAX_BUNDLE_BYTES`** (this is the OOM fix — the
  cap now bounds the download). After the stream completes, compare the streamed digest (verify-before-
  extract preserved), then extract. Set an explicit httpx timeout while restructuring (`_download` currently
  relies on httpx's implicit default).
- **H mechanism sub-choice (senior's design call) — extraction source after the fix.** `_extract_zip` /
  `_extract_tar` currently take `bundle_bytes: bytes`. Either **(a)** read the now-verified **≤50 MB** temp
  file back into memory and pass bytes to the existing extractors (minimal diff; bounded-safe — the OOM
  vector was the *unbounded* download, a capped ≤50 MB read is fine), or **(b)** refactor the extractors to
  open the file path. **Lean (a)** (DP-3).
- **Scope notes.** Keep the 50 MB value (not a contract term; don't retune it here). Keep the digest-before-
  extract ordering. Same-source retry / resume is **out** (new behavior, not this bug-fix).

**My lean: H-lean + mechanism (a).**
