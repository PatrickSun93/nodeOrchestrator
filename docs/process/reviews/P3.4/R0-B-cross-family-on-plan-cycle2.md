## Lens preamble

Cycle-2 is the system's **first component that actually executes tools at runtime** — a new post-dispatch stage with concurrency, failure, event-loop, and trust-boundary semantics. The cross-family lens is exactly what caught cycle-1's Y2 (the runtime-wiring gap — "the function exists, therefore it's integrated" Claude bias) and the cycle-1 timeout/env-leak; the same class of error repeats here. The external prompt names the highest-value probes: (1) AUTONOMY-BYPASS — can anything execute without a TOOL_CALL event? (2) DOUBLE-EXECUTION — can a call_id fire twice? (3) TURN/FAILURE — does a tool failure cascade? (4) SINGLE-WRITER LIVENESS — is the bounded-block claim real? (5) LOCAL SANDBOX — path-escape / TOCTOU / oversized-before-store. (6) GATE-DRIFT — is the gate diff really empty?

Over-correcting for Claude biases: the ADR repeatedly claims "structural" / "downstream" / "bounded" / "fail-closed" — these are claims, not facts, until traced through the actual execution path. A claim that the executor is "downstream of the gate" because it keys on TOOL_CALL events is only as strong as the filter that checks event types — it's a behavioral filter, not a structural/type-level gate.

| R1 | 🔴 | **MCP interpret LLM call has no timeout — contradicts ADR-028 D5's bounded-liveness claim. An LLM hang blocks the single writer indefinitely.** ADR-028 D5 claims the execution stage's writer block is **bounded**: "a slow MCP tool blocks all writes for up to the bounded timeout" (the cycle-1 `asyncio.wait_for` + subprocess-kill). But the cycle-2 executor ALSO calls `interpret_mcp_tool_result` for each MCP `TOOL_RESULT` — and that function calls `llm_router.call(request)` with **no timeout** (verified: `agents/mcp_interpret.py:39`, `response = llm_router.call(request)` — no `wait_for`, no timeout wrapper, no `run_in_executor` with deadline). The interpret runs **inline on the single writer** (per ADR-028 D5). If the LLM provider hangs (network partition, API outage, slow response), the single writer thread is blocked **indefinitely** — not for the bounded MCP timeout, but for however long the LLM takes (which could be until the HTTP client's own timeout, or forever if the HTTP client has no read timeout). This **contradicts the ADR's liveness claim**: the bound isn't Σ(MCP timeouts) but Σ(MCP timeouts + unbounded-LLM-calls). The interpret IS advisory (content-gen) and could be deferred, async'd, timeout-wrapped, or even skipped — but right now it's a **single-point-of-failure for all room writes**. ## Synthesis

The design is **structurally sound on autonomy-bypass** — the gate→TOOL_CALL→executor chain has no bypass path. The session-retention fix is safe (per-call subprocess lifecycle). The `not_implemented` fail-closed seam is honest and correctly scoped. The feed-the-gate discipline is verifiable (empty diff + constitution tests). The local-tool breadth is appropriately conservative.

But the design has a **single-writer liveness contradiction that is blocking at plan stage** (R1): the MCP interpret LLM call runs inline on the single writer with no timeout, contradicting the ADR's bounded-liveness claim. This is a concrete, traceable gap — the cycle-1 code (`agents/mcp_interpret.py:39`) has no timeout on `llm_router.call()`, and the cycle-2 design calls it inline in the executor. An LLM hang = all room writes blocked indefinitely. The fix is straightforward (wrap in a timeout, or async the interpret off the writer, or make it non-blocking/advisory), but the design must address it **before** the ADR is Accepted and the junior builds the executor loop.

The four 🟡 are design clarifications, not blockers: the double-execution guard's scope needs pinning (Y1), the sandbox TOCTOU posture needs acknowledgment (Y2), the t4 "structural" claim should be named accurately (Y3), and the Σ-of-bounds should recommend a per-turn MCP call cap (Y4). The Y1/Y2/Y3 are exactly the class of "the claim says X, but the mechanism is Y" that a cross-family lens catches — in-family review tends to read claims as facts; cross-family traces the mechanism.
