# Architect brief — P4.5: auth / multi-user / OAuth — the first identity boundary (decision-surface)

**Task:** P4.5 (D1 + D2 + D3) — introduce the project's **first human-identity trust boundary**. D1 = API auth / multi-user / remote-bind / TLS / rate-limiting (the first identity boundary, P4-roadmap §3.D / ADR-025 D7 forward hook). D2 = remote-MCP OAuth (ADR-032 considered-alt). D3 = user-identity audit provenance on confirm (ADR-030 N1). The **Wave-2 trust-hardening final slice** (roadmap §4: capability → **trust hardening** → completeness; `P4.5 [unblocks networked deployment]`); independent of the plugin cluster (roadmap §5: "P4.5 (auth) ∥ most — auth is an API/transport concern").

**Class:** heavy trust slice — the **security-densest** of P4 alongside P4.3 (roadmap §1: "P4 front-loads exactly the trust/security surfaces P3 deferred … the auth/multi-user boundary"). `requires_cross_family_review: true` (set in `.workflow/P4.5.yaml`). Mandatory dual-lens for D1+D2; D3 single-lens (roadmap §8). **New ADR-039** (next unused; ADR-038 is the highest existing) + amendments (DP5).

**Status of this doc:** a **DECISION-SURFACE**, not a plan and not a set of decisions. Five decision points carry **architect-ratifiable leans + tradeoffs**; the architect-partner does **not** decide. The load-bearing call is **DP1 (identity model)** — the shape the whole slice hangs on — with **DP3 (authorization model)** its constitutional twin (decide them together). No plan / ADR-039 is drafted until the architect ratifies (≥ DP1, DP2, DP3). **This is the project's first identity primitive**: everything before P4.5 assumed *one trusted operator on localhost* — the brief's job is to surface how far up the multi-user ladder this slice climbs and how identity threads the existing constitutional spine.

---

## 0. What exists today + what each ledger item extends (verify-cited `origin/main`)

**There is zero human authentication or identity anywhere in the product.** The API is a FastAPI server (`api/app.py`) ruled **localhost-trust, single-user** (ADR-025 D7: bind `127.0.0.1` only; **"Auth: none (localhost-trust)"**; `__main__.py:7` "Production deployment must add authentication/TLS before exposing externally"). All 7 HTTP routes + the 1 WS stream (`/rooms`, `/rooms/{id}` ·`/events`·`/snapshot`, `/events/{id}/thread`, `POST /intent`, `POST /confirm`, `WS /rooms/{id}/stream`) are **unauthenticated** — no middleware, no `Depends`, no header parsing, no request principal.

The crux distinction P4.5 must hold onto: **what exists today is forge-*prevention*, not identity.**

| Surface | What exists **today** (verified) | The gap P4.5 weighs | Src |
|---|---|---|---|
| **Request identity** | **None.** Every human event is stamped `author="user"` — **hardcoded server-side** (`app.py:486` "HARDCODED — never read from request"); `IntentRequest` omits `author/id/timestamp` (ADR-025 D4). The server *prevents a client forging who it is* — but there is only **one** "who". | The first *real* "who is calling" — a request must carry + prove a human identity. | ADR-025 D4/D7 |
| **`user_id`** | Exists but **audit-only, a free string, not a principal**: `DecisionMeta.user_id` required iff `promotion=True` (`core/event.py:151-176`); `record_preference(user_id,…)` (`memory/entity.py:107-125`). Records *who declared/confirmed a memory* — **not authenticated**, not an access boundary. | Promote `user_id` from a free audit string to an **authenticated** identity; extend it to the confirm path (D3). | ADR-016; ADR-030 N1 |
| **Confirm approver** | `ConfirmRequest{pending_event_id, decision}` (`wire.py:121-131`) — **no approver identity**; the resulting `TOOL_CALL` is authored by the **agent** (`agent:<initiating_agent>`), not the human. ADR-030 N1 explicitly dropped `user_id`: *"no `user_id` provenance … a user-identity audit field is a forward hook when auth lands."* | **THE D3 hook.** Record *which authenticated human* approved a HARD/COUNTDOWN action; (if DP3=roles) gate *who is allowed to*. | ADR-030 D3 step 5 / N1 |
| **Autonomy gate** | Scores **actions, not actors**: `Operation{tool_id, initiating_agent, user_explicit_intent}` (`autonomy/scoring.py:19-33`); `user_explicit_intent` is a **boolean**, not a who; the tier is reversibility-only. No human-approver concept. | Decide whether the gate becomes identity-aware or stays identity-blind (DP4a). | ADR-005/027 |
| **"operator"** | An **implicit, file-based** role — whoever can edit `config/plugins.yaml` / reach localhost. Plugin admission is an **"operator action, not a gated agent op"** outside the autonomy gate (ADR-038 D1/DP2c, L30/73). There is **no identity behind "operator."** | Decide whether "operator" becomes an **authenticated identity / role** (DP3) — and what authorizes the *operator actions* (plugin admit, config write, HARD approve). | ADR-038 DP2c |
| **Plugin mgmt endpoints** | **Pinned-but-NOT-built.** ADR-038 D5 froze `GET /plugins`, `POST /plugins/{id}/enable·disable·admit`, `DELETE /plugins/{id}` as a **forward-contract** — **"NOT implemented in P4.4 … built in P4.7"** (L99/108). So *"who can call them now"* = **nobody (no code)**; but the **contract was pinned with zero auth/authz dimension.** | P4.5 should pin the **authz dimension** of that contract (who may admit/enable/disable) **before** P4.7 builds it — else P4.7 inherits an authz-blind contract (inscribe-before-producer). | ADR-038 D5 |
| **Remote MCP** | The MCP client speaks stdio + streamable-http with **`api_key_env`→`Authorization: Bearer` static headers** (`mcp/transport.py:97-114`); **OAuth was explicitly out of MVP** (ADR-032 considered-alt L71: "OAuth via `mcp/client/auth` … out of scope"). | D2 — token-refresh/OAuth flows for remote MCP, **riding the D1 identity work**. | ADR-032 |

**Framing the boundary P4.5 turns on.** Every prior slice protected against a *client forging the backend's decisions* (forge-prevention, backend-authoritative — ADR-025 D4, ADR-026 HR#2, ADR-030 HR#1). P4.5 adds an **orthogonal** boundary: *proving which human is on the other end*, and (maybe) *what that human is allowed to do*. The constitutional spine is **unchanged** (no new principle) — but this is the first slice where "the operator" stops being an assumption and becomes a **modeled, authenticated primitive**. Getting the primitive's *shape* right (DP1) is expensive-to-reverse and gates D2/D3 and the P4.7 GUI.

## 1. ⭐⭐ DP1 — Identity model: how far up the multi-user ladder does this slice climb? (THE load-bearing call)

This is the ambition axis **and** the shape decision — folded together because the model *is* the scope. The ladder:

| Option | What it builds | Trade-off / honest residual |
|---|---|---|
| **(a) Single-operator + shared secret** | One token / API key gates *network access* to the existing server; bind beyond `127.0.0.1`; `author="user"` stays. **No users table, no per-user identity.** | The literal-minimal "harden ADR-025 D7" reading — **lowest** new surface, every existing invariant byte-unchanged. **But it is not multi-user** ("single-operator, now remote") — it does **not** satisfy the "multi-user" ledger item, and D3 (per-user confirm provenance) is **moot** (still one "who"). |
| **(b) Real multi-user — users + sessions** (lean) | A user store + credential + login→session; **per-request authenticated identity**; `author="user"` generalises to a real `user:<id>` (or an identity field). The **first true identity boundary**. | Medium-heavy: introduces credential storage (password hashing) + a session mechanism + the `author` generalisation (DP4c). Unlocks D3 and any DP3 authz. The honest floor for "multi-user." |
| **(c) OAuth / OIDC-federated** | Delegate identity to an external IdP (Google/GitHub/…); **no local password storage**; identity is a federated subject; dovetails with D2 (MCP OAuth). | The "right" long-term answer for a networked product — **but** heavier integration (provider config, callback/flows, token validation) and an external dependency for *every* login. More than a *first* boundary strictly needs if the seam is built right. |

**Lean: (b) — build the identity *seam* (per-request authenticated principal) and fill it now with the simplest credential, structured so OAuth/OIDC (c) is an additive provider behind the same primitive.** Rationale: (a) under-delivers the ledger's "multi-user" and leaves D3 moot; (c)'s federation is best added *once the identity primitive exists* (it becomes "another auth provider," not a re-architecture) and is naturally co-designed with D2. (b) is the honest *first* boundary: it forces the expensive-to-reverse decisions (how `author`/principal generalises, where authz checkpoints sit) now, while keeping the credential mechanism swappable.

**⭐⭐ But this is an architect-weight call, not a lean to bank.** It sets the ambition of the entire slice and is do-not-reverse-cheaply (the principal shape binds D2/D3 + the P4.7 GUI). If the near-term deployment goal is *"one operator, just reachable from my other machine,"* (a) is legitimately enough (and tiny). If *"a small trusted team,"* (b). If *"federated SSO from day one,"* (c). **Decide DP1 before DP2–DP4; they are all downstream of it.**

## 2. ⭐ DP2 — Authentication mechanism + which of D1's five things land this slice

**(2a) The mechanism** (given DP1's model, how a request proves identity):

| Option | Fit | Trade-off |
|---|---|---|
| **Static API token / key** | Programmatic clients; DP1(a); or per-user tokens under DP1(b). | Simplest; no session store. Weak for human multi-user (per-user ⇒ per-user-token issuance/rotation); no logout semantics. |
| **Session cookie (login→server session)** (lean for the GUI under DP1(b)) | The browser GUI (ADR-026) — natural for human login. | Needs a session store + expiry + CSRF posture; the GUI carries the credential, the API stays the sole boundary (DP4c). |
| **OAuth2 / OIDC bearer (JWT)** | DP1(c); rides D2. | Federated, no local secrets — but the heaviest, and only justified if DP1=(c). |

**Lean: cookie-session for the human GUI + (optionally) a static per-user API token for programmatic access, under DP1(b).** If DP1=(c), the mechanism *is* OIDC and this DP collapses into it.

**(2b) D1 is five things — which land in P4.5, which defer (surface explicitly).** "API auth / multi-user / **remote-bind** / **TLS** / **rate-limiting**" (roadmap §3.D D1). Not all are app-code:

- **Auth + multi-user + remote-bind** — the core of this slice (DP1/DP2a).
- **TLS** — **lean: terminate at the deployment layer (reverse proxy), documented not coded** — bolting TLS into uvicorn couples cert-management into the app; the forge/no-decision-surface invariants already hold regardless of transport (ADR-025 D7: "hardening is additive … without touching the invariants"). Inscribe as a deployment requirement + residual, not an in-app build — unless the architect wants in-app TLS.
- **Rate-limiting** — **lean: a thin per-identity limiter on the write chokepoints (`/intent`, `/confirm`) or defer as a named residual.** Surface the choice; don't silently drop it.

*(The architect rules which of the five are in-scope for P4.5 vs deferred — this prevents the "D1 = one ADR" reading from silently swallowing TLS/rate-limiting.)*

## 3. ⭐⭐ DP3 — Authorization / permission model: are all authenticated users equal operators? (DP1's constitutional twin)

Once DP1 admits **>1 identity**, the unavoidable question: is every authenticated user a full operator, or is there differentiation?

| Option | What | Trade-off / honest residual |
|---|---|---|
| **(a) All-or-nothing operator** | Authenticated ⇒ full operator: may `POST /intent`, approve **HARD** confirms, admit plugins, edit config — everything. | Simplest; matches today's single-operator mental model + auth. **But no least-privilege**: any authenticated (or compromised) account has full actuation — including `git_push`/`send_email`/`apply_edit` via HARD-confirm (ADR-036) and plugin admission (ADR-038). The residual (**`RB-AUTHZ`**) must be inscribed. |
| **(b) Role / permission model** | Roles (e.g. `operator` / `member` / `viewer`) gate the **constitutional actuators**: who approves HARD-confirm (ADR-030), who admits/enables plugins (ADR-038 "operator action"), who edits config, who may only chat/view. | Real least-privilege — **but** introduces a permission surface the **confirm path + plugin-admit + config-write must consult** (DP4), and a role-assignment/bootstrap question. Heavier; the first genuine authz machinery in the project. |

**Lean (conditional on DP1): for a *first* identity boundary, (a) all-or-nothing authenticated-operator is the honest MVP — do NOT build speculative RBAC — BUT pin where the permission checkpoints *would* sit (confirm-approve, plugin-admit, config-write) so (b) is additive, and inscribe `RB-AUTHZ`.** Caveat that flips the lean: **if DP1's deployment goal is multi-user with *non-fully-trusted* members, (a) is dangerous** (every member can actuate irreversible HARD tools + admit code) — then (b) is required *in this slice*, not deferred. **⭐⭐ architect-weight**: this is where identity meets the constitutional spine, and the (a)/(b) call depends on *who the other users are* — the architect's deployment-intent call, decided with DP1.

## 4. ⭐ DP4 — How identity threads the four existing constitutional surfaces

Mostly *ratify-the-threading* (leans), with a few embedded decisions. Each must preserve the spine:

**(4a) Autonomy gate — identity-blind or identity-aware?** The gate scores *action reversibility*, not the actor (`scoring.py:19-33`). **Lean: keep the gate identity-blind** — reversibility is intrinsic to the action; "routing/scoring = code, no per-user LLM judgment" (CLAUDE.md; roadmap §10). Identity gates **who may approve** an action, not **how it is scored**. (Per-user *thresholds* would be a new config axis — surface as out-of-scope unless the architect wants it.)

**(4b) Confirm path = the D3 landing site.** Today the approver is anonymous and the `TOOL_CALL` is agent-authored (ADR-030 D3 step 5). **D3 = record the authenticated approver** (the `user_id` ADR-030 N1 deferred "until auth lands" — now it lands) in the confirm event flow; **if DP3=(b), also gate** *who may approve a HARD confirm*. **Lean: add an authenticated `user_id` to the confirm provenance (amend ADR-030); keep the executed `TOOL_CALL` agent-authored** (the gate approved *that agent's* op; the human supplied approval, not authorship — ADR-030's existing split) — the human identity rides as approval provenance, not as the tool author.

**(4c) Backend-authoritative — the forge guard generalises (do-not-reverse).** The server stamps `author` (ADR-025 D4); P4.5 generalises `author="user"` → the **authenticated** principal, stamped **from the verified session, never from the request body** (the exact ADR-025 D4 discipline, one level up). The GUI carries a credential but **still decides nothing** (ADR-026 HR#1/HR#2 intact); auth is enforced at the **API (the sole boundary)**, not the client. **Lean: extend forge-prevention to identity** — the principal is server-derived from the authenticated session; `IntentRequest`/`ConfirmRequest` never carry it. This is load-bearing and the dual-lens (DP5) probes it.

**(4d) Plugin admission — pin the management-endpoint authz dimension now.** ADR-038 froze the mgmt-endpoint contract **without an authz dimension** and deferred *building* it to P4.7 (§0). Admission is an "operator action" (ADR-038 DP2c) — with DP1/DP3 that becomes "an action requiring the **operator role/permission**." **Lean: P4.5 pins the authz dimension of the ADR-038 D5 contract** (who may admit/enable/disable — the operator role under DP3, or "any authenticated user" under DP3(a)) **so P4.7 builds against it** — but P4.5 builds **no endpoint code** (frontend track). Inscribe that *enforcement* lands with P4.7; P4.5 only fixes the contract's identity gap.

## 5. ⭐ DP5 — New ADR-039 + amendments + the dual-lens two-lens design + residual set

**ADR-039 (new contract — the auth/identity model):** the identity primitive (DP1) + the auth mechanism (DP2) + the authz model (DP3) + the spine-threading (DP4). Expensive-to-change (D2/D3 + the P4.7 GUI bind the principal shape) → **inscribe-before-producer** (roadmap §10, RC-23-safe).

**Amendments this slice carries** (roadmap §3.D classification): **ADR-025** (D7 localhost-trust → authenticated posture + remote-bind + TLS/rate-limiting disposition); **ADR-030** (D3 — `user_id` confirm provenance, the N1 forward hook landed); **ADR-026** (the GUI carries a credential, still view+intent-only); **ADR-032** (D2 OAuth/token-refresh — *if* D2 is in-scope this slice); **ADR-038** (D5 mgmt-endpoint authz dimension — DP4d). Mark amended-at-impl, the ADR-037 precedent.

**Residual set — inscribe, don't soften (roadmap §10; the `RB-FS/NET`/`RB-ADMIT` discipline). The set is a *function of the DP1/DP3 routing*:**
- **`RB-AUTHZ`** (if DP3=(a)) — no least-privilege; any authenticated account is a full operator (irreversible HARD tools + plugin admission). Persists until a role model (DP3(b)) is separately built.
- **TLS-at-deployment** (if DP2b leans proxy) — the app does not terminate TLS; secure transport is a deployment requirement, named not coded.
- **Rate-limiting** — if deferred, a named residual (the write chokepoints are unthrottled).
- **D2 / MCP-OAuth** — if deferred to keep the slice to the human-identity core, inscribe (it "rides D1" — roadmap §3.D — so it *can* be a clean follow-on).
- **Credential posture** (under DP1(b)) — whatever is *not* built: password reset / rotation / MFA / session-revocation / lockout. Inscribe the real surface.
- **First-account bootstrap** — how the initial operator account is provisioned (the chicken-and-egg of "auth gates everything incl. creating the first user"). Surface + inscribe the chosen bootstrap.

**Review posture:** `requires_cross_family_review: true` → **mandatory dual-lens** (roadmap §8: D1+D2 heavy; D3 single-lens). Plan-stage writes `docs/process/reviews/P4.5/external-r0b-prompt.md` (the P4.3/P4.4 precedent) with **two orthogonal failure-family lenses**:

- **Lens A — the identity/authn/authz trust boundary (the "auth done wrong" adversary).** Can a request **act as someone it isn't**? Probe: identity forgery / session fixation·hijack·replay / token leakage / privilege escalation / **missing-authz on a constitutional actuator** (HARD-confirm approve, plugin-admit, config-write) / the ADR-038 mgmt-endpoint authz gap / credential storage (hashing, secrets-handling) / the first-account bootstrap / fail-closed-on-unauthenticated.
- **Lens B — spine-preservation / no-regression (the "did identity break the existing constitution" adversary).** Does adding auth **regress** backend-authoritative / forge-prevention / no-decision-surface / fail-closed / the confirm idempotency + crash-window posture (ADR-030 D7)? Plus the **new concurrency/liveness surface**: sessions on the single-writer (ADR-025 D6), remote-bind exposing the pub/sub stream, the `author`-principal generalisation not breaking the t4 appender guards / `is_valid_author`.

*(These two are genuinely orthogonal — "auth is insecure" vs "auth broke ADR-025/026/030." That orthogonality is the dual-lens design goal — dual-lens-r0b.md.)*

## 6. Constitutional carry-forward watch-list (carry into the plan + ADR-039)

- **Trust boundary** (P2.7-S3 → P3.5 → P3.7-remote → P4.3/P4.4, now the **identity** layer) — opt-in, fail-closed, credential-safe, posture-ratified. Unauthenticated ⇒ **fail-closed** (no endpoint runs without a verified principal, once auth is on).
- **Backend-authoritative** (ADR-025 D4 / ADR-026 HR#2) — the principal is **server-derived from the verified session, never from the request** (the forge guard, generalised — DP4c). The GUI carries a credential but **decides nothing**.
- **No decision surface / no new `LLMPurpose`** — auth is mechanical verification; **the autonomy gate stays identity-blind** (DP4a); routing/scoring stays code (CLAUDE.md). No role/permission is ever LLM-judged.
- **Confirm stays human-in-the-loop + idempotent** (ADR-030 D7) — D3 *adds* approver provenance; it must not regress the idempotency / partial-turn / crash-window invariants.
- **Inscribe-before-producer** — the principal shape + the mgmt-endpoint authz dimension are expensive-to-change; pin in ADR-039 **before** D2/D3 + the P4.7 GUI bind (roadmap §10).
- **Honest-residual inscription** — Accept the *real* post-P4.5 identity surface (DP5), never a softened one. `RB-AUTHZ` / TLS-at-deployment / deferred-D2 must read as honestly as `RB-FS/NET` did.

## 7. What the architect ratifies (the routing surface)

1. **⭐⭐ DP1 — identity model** (lean: **(b)** real multi-user seam, simplest credential now, OAuth/OIDC additive — **but architect-weight**: (a) if "one operator, now remote" suffices; (c) if federated-SSO-from-day-one). *THE load-bearing call; decide first.*
2. **DP2 — auth mechanism + D1's five-things scope** (lean: cookie-session for the GUI + optional per-user token; **TLS at the deployment/proxy layer**; rate-limiting thin-or-deferred). *Rule which of auth/multi-user/remote-bind/TLS/rate-limiting are in-scope.*
3. **⭐⭐ DP3 — authorization model** (lean: **(a)** all-or-nothing authenticated-operator + inscribe `RB-AUTHZ` + pin the checkpoints — **unless** the deployment is multi-user-with-non-fully-trusted-members, then **(b)** roles in-slice). *DP1's constitutional twin; decide together.*
4. **DP4 — identity × the four surfaces** (lean: gate identity-blind; D3 = authenticated approver provenance on confirm, tool stays agent-authored; forge-guard generalises to the principal; **pin the ADR-038 mgmt-endpoint authz dimension now**, build no endpoint code).
5. **DP5 — ADR-039 + amendments + dual-lens** (confirm: new ADR-039; amend ADR-025/030/026 (+ADR-032 if D2 in, +ADR-038 D5 authz); the two lenses A/B; the routing-dependent residual set).

Plus the mechanical confirms: **new ADR-039**, `requires_cross_family_review: true` (already set); D1+D2 dual-lens, D3 single-lens (roadmap §8); **is D2 (MCP OAuth) in this slice or a follow-on** (it rides D1 — roadmap §3.D).

Once ratified, P4.5 gets the senior plan → ADR-039 → impl → mandatory dual-lens (R0-A ∥ R0-B) → plan-vs-impl → merge.
