## Architect-settled decisions

### 1. Aggregation semantic — all-or-nothing, not granular

`_read_adr_status` returns one of `"proposed" | "accepted" | "none"` per its current return type. Multi-ADR aggregation collapses to the same Literal:

- **All ADR files present + all status Accepted** → `"accepted"`. State machine auto-advances `awaiting_architect_accept → awaiting_junior_impl`.
- **All ADR files present + at least one status Proposed (or Superseded)** → `"proposed"`. State stays at `awaiting_architect_accept`.
- **At least one ADR file missing (glob returns 0 matches)** → `"none"`. State stays at `awaiting_architect_accept` (matches single-ADR case where missing-ADR returns "none").

No new return value, no new state. The Literal stays as-is; W-002.5 only changes the **aggregation across N entries** of the same return type.

**Granular semantic deferred to W-003**: "awaiting Accept of N-of-M ADRs" with per-ADR tracking would need a new state shape (`TaskState.adr_accept_progress: dict[str, str]` or similar). W-002.5 explicitly does NOT add this; all-or-nothing aggregation is sufficient for P1.4's 2-ADR case.

### 2. `adr` field shape — `str | list[str]`, union-typed

The plan frontmatter `adr` field accepts either:
- A bare string: `adr: ADR-099` (W-002 behavior preserved)
- A list of strings: `adr: [ADR-010, ADR-011]` (new; for P1.4)

`_read_adr_status` discriminates by `isinstance(adr_val, str)` vs `isinstance(adr_val, list)`. Empty list (`adr: []`) raises `WorkflowError` (authoring error — declared multi-ADR but specified zero ADRs). Mixed-type lists (`adr: ["ADR-010", 42]`) raise `WorkflowError` per existing per-element type check.

### 3. P1.4 plan frontmatter authored manually by architect-partner post-W-002.5 merge

P1.4 plan currently has no frontmatter. After W-002.5 lands, architect-partner adds:
```yaml
---
task_id: P1.4
adr: [ADR-010, ADR-011]
---
```
to the top of `docs/process/senior-plans/P1.4.md` as a **one-line edit commit** on main (architect-partner direct precedent). This is what activates W-002.5's multi-ADR path for P1.4. The edit lands before ADR-010 + ADR-011 status bumps.

**Why not bundle this into W-002.5 impl**: keeping W-002.5 scope-pure (code-only) means the impl can land independent of P1.4 plan edits. Architect-partner does the P1.4 frontmatter edit as a separate trivial-fix commit (RC-5 trivial-fix-routing exception applies: single-file ≤30-LoC architect→junior shortcut, here architect→architect-partner-direct since it's a plan-stage doc edit).

### 4. No ADR drafted

W-002.5 is mechanical extension of W-002-1's existing `adr` field handling. No architectural decision worth ADR inscription. ADR-008 stays untouched (same Y1→β discipline from W-002).
