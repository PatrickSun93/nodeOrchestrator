## Bug A — event-order tiebreak

### Verify-cited state (citations in the original review were stale)

The review cited `api/app.py:311 / :326-333`. **Those lines are stale** — at HEAD they are pipeline
response models (`_PipelineResponse` etc.), not event ordering. The actual `(timestamp, id)` sort
surface is wider than the review stated. Current sites (HEAD):

| Site | Code | Layer |
|---|---|---|
| `api/app.py:418, :503, :647, :1605` | `sorted(all_events, key=lambda e: (e.timestamp, e.id))` | API / confirm-gate |
| `derived/snapshot.py:115` | `sorted(events, key=lambda e: (e.timestamp, e.id))` | derived (snapshot) |
| `derived/snapshot.py:190` | `max(st_events, key=lambda e: (e.timestamp, e.id))` | derived (`last_state_transition`, D2.5) |
| `derived/decision_log.py:77` | `entries.sort(key=lambda e: (e.timestamp, e.event_id))` | derived (decision log, ADR-015 D4) |
| `reentry/digest.py:105` | `sort(key=lambda x: (x.occurred_at, x.ref_id))` | derived (reentry, ADR-021 D8) |

`Event.id` is `evt_<uuid4-hex>` (`core/event.py:38-51`) — **random, not monotonic**; the docstring
there says so outright ("Chronological ordering is the responsibility of the timestamp column, not
the id"). So `(timestamp, id)` is a deterministic-but-**non-causal** total order: for same-ms events
it reflects UUID order, not insertion order.

### The contract finding (this is the load-bearing part)

The `(timestamp, event_id)` tie-break is **not an accident** — it is inscribed in **three ADRs**
(`ADR-014 D2.1/D2.5`, `ADR-015 D4`, `ADR-021 D8`) and implemented at the 9 sites above. More
importantly, **`ADR-015 D4` (lines 85-95) already litigated exactly this question:**

1. The project **already hit this bug once** — P1.5 R1 retro caught "random-UUID tiebreak
   instability" in `get_room_events` where insertion order was load-bearing; the fix (commit
   `307a8fa`) switched the **store** to `ORDER BY timestamp ASC, rowid ASC` (`event_store.py:374,
   :495` + the design comment at `:69-71`: "rowid … is the insertion-order tiebreaker").
2. D4 then made a **deliberate scope decision** for the *derived* layer: *"stay with lex tie-break,
   do NOT migrate to rowid"*, explicitly **conditional** on "no downstream consumer in P1.6 scope
   requires insertion-order preservation across same-ms."
3. D4 **named the revisit path**: *"If causal/insertion ordering becomes load-bearing … revisit via
   ADR-015 amendment toward rowid-based ordering … by passing rowid as a derived field on Event
   (caller-pre-fetched)."* — i.e. the "fix" is a **constitutional `Event`-model change + ADR
   amendment**, because the derived layer is a pure function over `list[Event]` and the `Event`
   objects carry **no** insertion-order signal (the `SELECT` at `event_store.py:370-371` does not
   surface `rowid`).

**Two unambiguous defects do exist (both small):**
- **A0 (doc drift):** `get_room_events`'s docstring (`event_store.py:360-363`) claims
  `(timestamp ASC, id ASC)` and names an index `idx_events_room_ts_id` — but the SQL does
  `(timestamp, rowid)` and the real index is `idx_events_room_ts` on `(room_id, timestamp)`. The
  docstring is wrong three ways (id-vs-rowid, nonexistent index name, false "no sort step"). Leftover
  from the P1.5 R1 fix. **Clean, isolated, real.**
- The **store↔derived inconsistency**: the store's canonical order is `(timestamp, rowid)` = insertion
  order; the derived/API layer re-sorts the same events by `(timestamp, uuid)`, so a snapshot /
  decision-log / excerpt can present same-ms events in an order that *contradicts* the source of
  truth. This is the part `ADR-015 D4` **already decided was acceptable** for the derived layer.

### Is the precondition now invalidated? (the actual question for you)

`ADR-030 D2/D3` (post-D4) introduced a **position-anchored pending-confirm scan** —
`snapshot.py:166-175` and the confirm-gate at `app.py:418-440` — that reads "is there a resolution
event *after* this PENDING's position?" over the `(timestamp, id)`-sorted list. This **is** a same-ms
causal-order-dependent consumer, the kind D4 said would trigger the revisit.

**Honest reachability assessment (senior must confirm):** the harm (a same-ms `(PENDING, resolution)`
pair flipping to a false "still-pending") appears **low-reachability** because resolutions arrive from
a *later* request/turn (human confirm, auto-fire sweeper ADR-040, auto_pipeline ADR-043, cancel) →
later `now_ms()` → different ms than the gate-time PENDING. `last_state_transition` (D2.5) same-ms
ties (two STATE_TRANSITIONs in one ms) and excerpt same-ms display-order are likewise rare/cosmetic.
**I am not certain this is reachable; I am certain it is not a clean bug-fix atom.** The senior should
verify same-ms `(pending, resolution)` reachability across *all* resolution paths before any work.

### Fix-direction options (your call — do NOT read these as routed)

- **A-i — Close as already-decided (+ A0 doc fix).** Accept ADR-015 D4 stands; the derived
  `(timestamp, id)` order is deterministic-but-non-causal *by inscribed decision*; fix only the A0
  docstring drift; optionally add a one-line note to ADR-014 D2.5 / ADR-015 D4 that the precondition
  was re-reviewed at P6.1 and still holds. **Lowest cost; defensible given D4.**
- **A-ii — Do the amendment D4 named (separate slice).** Surface an insertion sequence (`rowid` or a
  dedicated monotonic `seq`) onto the `Event` model; reconcile all 9 sites to `(timestamp, seq)`;
  amend `ADR-014 D2.1/D2.5` + `ADR-015 D4` (+ touch `ADR-021 D8`) + `event-model.md`; revisit the
  `produce_snapshot`/`produce_decision_log` D1 purity contract (rowid as caller-pre-fetched field).
  **Constitutional; its own ADR-bearing slice; far bigger than a bug-fix atom.**
- **A-iii — uuid7 ids.** Make `generate_event_id` time-sortable so `(timestamp, id)` ≈ insertion order
  going forward (the docstring already anticipates this). Helps only new events; historical uuid4 stay
  random; still an ordering-semantic change → ADR touch. Partial.

**My lean:** **A-i** for P6.1 (close-as-decided + A0 doc fix), *unless* you judge ADR-030's
position-anchored scan invalidates D4's precondition — in which case **A-ii** as a **separate**
ADR-amendment slice, not bundled here. **This is the one decision I most need from you.**

## Bug B — TOOL_FAILED excerpt leak

### Verify-cited state (real bug)

`agents/selection.py:169-176` builds the excerpt and excludes untrusted external bytes — but the
exclusion clause checks **`e.type == EventType.TOOL_RESULT`** only:

```python
relevant = [
    e for e in snapshot
    if e.type in _EXCERPT_EVENT_TYPES
    and not (
        e.type == EventType.TOOL_RESULT                                 # <-- TOOL_RESULT only
        and str(e.metadata.get("call_id", "")) in external_result_ids
    )
]
```

`TOOL_FAILED` is in `_EXCERPT_EVENT_TYPES` (`:86`), so it is rendered by default, and the exclusion
never removes it. The untrusted-tool call_id set (`_external_output_tool_result_call_ids`, `:121-149`)
already covers `mcp__` / subprocess / network tools and is keyed on the `TOOL_CALL`'s call_id — and
**`TOOL_FAILED` carries that same `call_id`** (`ToolResultMeta.call_id`; MCP `mcp/execution.py:136-140`,
executor `executor.py:459-463`). So a failed untrusted call's bytes reach the cross-agent system-block
steering surface uncensored.

**Attacker-byte reality (the load-bearing sub-question, verify-cited):**
- **MCP — real.** `mcp/execution.py:135`: `content = f"mcp_tool_failed: {reason}"`; `reason` carries
  the untrusted MCP server's error / malformed-payload text → attacker-authorable.
- **Network — partial.** `executor.py:458`: `content = f"tool_failed: {reason}"`; for web tools
  `reason` is `fetch_failed:` / `search_provider_error:` (may embed upstream/provider error fragments).
- **Subprocess — low.** `reason` is our framing (`subprocess_timeout:` / `subprocess_spawn_failed:`);
  bulk untrusted stdout goes to `TOOL_RESULT` (already excluded) per ADR-034 §86.

So the leak is **confirmed real for MCP**, partial for network, defense-in-depth for subprocess.

### Contract touch

The exclusion is inscribed across `ADR-033 D6/R2-N1`, `ADR-034 D3-iv`, `ADR-035 D3-iii` — all three say
**"TOOL_RESULT"** and none mention `TOOL_FAILED`. The *intent* ("injected external bytes cannot steer a
re-dispatched agent via the excerpt") plainly covers untrusted `TOOL_FAILED`. So the fix is a
**tightening/clarification of an existing decision**, not a new contract. **Whether it needs a one-line
amendment-note on ADR-034 D3-iv / ADR-035 D3-iii (vs. pure bug-fix) is a small architect call.**

### Fix options

- **B-α (lean) — symmetric exclusion, scoped to untrusted tools.** Change the clause to
  `e.type in {TOOL_RESULT, TOOL_FAILED}` (same `external_result_ids` correlation). Untrusted-tool
  `TOOL_FAILED` excluded; **trusted-local `TOOL_FAILED` stays in the excerpt** (preserves the
  flagship loop's useful failure signal — "your local tool failed"). Faithful to ADR intent; one clause.
- **B-β — blanket-exclude all `TOOL_FAILED`** (drop from `_EXCERPT_EVENT_TYPES`). Rejected-lean:
  removes trusted-local failure signal the turn-loop (ADR-033 D2) relies on; over-broad.

**My lean: B-α**, with a one-line note added to ADR-034 D3-iv / ADR-035 D3-iii that the exclusion
covers both result-class event types of untrusted tools. (Side-effect, inscribe-don't-discover:
excluding a *failed* MCP call means it has neither an excerpt presence nor an `OBSERVATION` proxy — it
survives only as `current_event`. This is the *same* already-accepted "batched-non-last invisible"
known-limitation as ADR-034 D3-iv / ADR-035 D3-iii, now extended to failures. Acceptable; note it.)
