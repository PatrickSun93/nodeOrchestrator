---

**Subject:** Build P3.2 — a **thin HTTP/WS API/server layer** over the event store + room runtime + bootstrap, so an external client (the P3.3 GUI) can **read** a room's event/room stream (snapshot + live) and **send user intent**. The server appends a user-authored intent event and drives `run_turn`; the **backend** (state machine, LLM router, autonomy gate — all existing code) decides everything. This unblocks the frontend track (roadmap §5's largest parallelism opportunity — §"Parallelism").

## The substrate (verified) — what's there, what the API wraps

- **Read surface** (the GUI's view): `EventStore.get_room`, `get_room_events`, `get_event`, `get_thread`, `get_relations_*` → `Room` + `Event` (both Pydantic, `frozen=True`).
- **Write/intent path:** `EventStore.append(Event)` then `run_turn(room, current_event, *, available_agents, available_skills, event_store, llm_router, regex_registry, tools)`. `run_turn` is **sync**, reads a snapshot, evaluates `next_room_state` (appends a `state_transition` event — **`room.state` is never mutated by the caller**), filters agents, and `dispatch_turn`s (which invokes the **autonomy gate** + **LLM router**). The API triggers this; it does not reimplement any of it.
- **Append-only store** (schema TRIGGERs block UPDATE/DELETE) on **sync sqlite3, caller-owns-connection**. → the server must manage connection lifecycle across concurrent clients and bridge sync core ↔ async I/O.
- **No change-notification** on the store → a live WS stream needs a push mechanism (in-process pub/sub fed by append/`run_turn`, or cursor-poll) — a design point, §Decisions(a).

## ⭐ The constitutional / security spine (NON-NEGOTIABLE — inscribe in the ADR, do not treat as a choice)

This is the most important part of the slice. The API is a **view + intent transport; backend-authoritative** (handoff §899 "UI 接口契约 … backend authoritative"; roadmap §9). Concretely, the senior must preserve and the ADR must inscribe:

1. **No decision surface in the API.** The server never decides state, agent activation, routing/model, or autonomy. It appends a user event and calls `run_turn`; the **state machine / `should_agent_speak` / LLM router / autonomy gate (all backend code) decide.** No new `LLMPurpose`; no routing/judgment logic in `api/` (Principle 5; CLAUDE.md "never LLM-judge a routing decision").
2. **Write-surface forge-prevention (the "operation-gating = code" analogue).** `Event.author` is validated as `user` | `agent:<id>` | `system` (`event.py:364`). A client may append **only `author:"user"` events of an intent-type allowlist** (`USER_INPUT`, and — architect to scope — user `UTTERANCE`/`DECISION`/`RETRACTION`). The API must make it **impossible for a client to forge** an `author:"system"`/`"agent:<id>"` event or a `STATE_TRANSITION` / `AUTONOMY_DECISION`. The backend is the sole author of system/agent/transition events. Fail-closed on anything off-allowlist.
3. **State machine 不暴露 (handoff §6.2 / §748).** Internal vocabulary (`state machine`, `skill`, `autonomy level`, `dissent dimension`) is never surfaced as user-facing concepts; the GUI maps to human terms via `config/ui_strings/`. (Whether the **API wire** carries raw `state`/event-type names with the GUI translating, vs. the API pre-humanizing, is a design point — §Decisions(c).)
4. **Trust boundary** (the P2.7-S3 pattern, magnified — first network surface): bind scope, authn, input validation, fail-closed. Posture knobs are architect-ruled (§Decisions(c)); the *existence* of the boundary is non-negotiable.

## Scope

**In scope (P3.2):**
- A new `api/` package: an HTTP/WS server exposing the **read** surface (get room + events; snapshot/replay; thread) and a **live event stream** (WS subscribe per room), plus a **user-intent** endpoint (append user event → `run_turn` → surface resulting events).
- A **pinned API contract** (the wire schemas for `Room`/`Event` + the endpoint/message shapes + the OpenAPI/AsyncAPI doc) — the inscribe-before-producer artifact the P3.3 frontend binds to (roadmap §9; §Decisions(d)).
- **Server bootstrap/integration**: compose `load_and_validate_llm_layer` + event-store connection + agent/skill/room/`regex_registry`/`tools` loading into the app context the handlers share (§Integration).
- The security spine above, with the posture knobs the architect rules (§Decisions(c)).

**Out of scope (defer):**
- The **GUI itself** (P3.3) — this slice only pins the contract it needs.
- **MCP / plugins** (Wave 2), **GUI completeness** (P3.6), **content depth** (P3.7).
- Multi-user / remote-network hardening beyond the ruled MVP posture (auth federation, TLS termination, rate-limiting at scale) — unless the architect scopes it in (c).
- Any change to `core/`, `rooms/`, `autonomy/`, `llm/` decision logic — the API wraps them unchanged.

## Decisions (surface for the architect — do not self-decide)

**(a) API tech stack + HTTP/WS boundary + push mechanism.**
- **Stack — lean: FastAPI** (native Pydantic ↔ our `frozen=True` `Event`/`Room` schemas; async + first-class WS; auto-generates the OpenAPI contract = a pinnable artifact). Alternatives: Starlette (lighter base), Flask (sync, no native WS), aiohttp. **Sync-core bridge:** the store + `run_turn` are sync → either async handlers + `run_in_executor`/threadpool, or sync `def` handlers (FastAPI threadpools them). Architect rules stack + sync-bridge style.
- **HTTP vs WS split — lean:** HTTP for create/list/get-room + snapshot replay + (optionally) post-intent; **WS for the live per-room event stream** (push new events as appended). Is user-intent sent over HTTP POST or bidirectionally over WS? Architect rules.
- **Push mechanism — lean:** in-process pub/sub (an observer that `append`/`run_turn` notifies → fans out to WS subscribers) over cursor-polling. Architect rules (this is the core concurrency design).

**(b) dual-lens R0-B? — lean: DISPATCH** (per `dual-lens-r0b.md`). **3 of 4 criteria hold:** (1) new concurrency surface (async server + WS lifecycle + concurrent clients over sync sqlite); (2) new cross-package layering edge with runtime consequences (`api/ → core/rooms/bootstrap/autonomy`); (3) contract referenced by ≥5 future tasks (P3.3, P3.6, future external clients — roadmap names it the convergence point). Plus the trust/auth boundary. The true-cross-family lens is precisely the one that catches the runtime/failure-mode/concurrency errors an in-family pass misses (the P1.4 precedent: DeepSeek caught the `event_store` failure-path + caller-contract bugs). **Architect confirms dispatch** (if yes, senior also authors `docs/process/reviews/P3.2/external-r0b-prompt.md`).

**(c) Security posture (the knobs around the non-negotiable spine).** Architect rules, like P2.7-S3's allowlist:
- **Bind scope** — localhost-only MVP (the GUI is a local app) vs network-exposed?
- **Authn/authz** — none (localhost-trust) / a session token / per-request token, for the MVP?
- **User-intent type allowlist** — exact set a client may append (`USER_INPUT` only? + `UTTERANCE`/`DECISION`/`RETRACTION` for user confirms/retracts?).
- **Wire representation** — does the API emit **raw** `state`/event-type names (internal product contract; GUI does the §6.2 human-term mapping) or **pre-humanized**? (Lean: raw — it's the product's own internal contract; GUI owns `ui_strings`. But this shapes the trust boundary if ever third-party-exposed.)

**(d) Split + the contract-first lever (+ parallelism).**
- **Contract-first** is the high-value move regardless of split: pin the API contract (ADR-025 + the Pydantic response models + OpenAPI) as the **first deliverable/commit**, so the P3.3 frontend track can start immediately (roadmap §5). Lean: contract-pin first, then the server impl.
- **Split vs single task** — a possible decomposition: S1 contract/schema pin → S2 read surface + WS stream → S3 intent/write path + push + `run_turn` wiring → S4 security posture + bootstrap integration. **But** these interlock tightly (contract ↔ read ↔ write ↔ push), so a single coupled task (contract-pinned-early *within* it) may be cleaner than cross-session splits that risk contract drift. **Lean: single task, contract pinned as its first atomic** (mirrors the architect's P2.7 batched-over-split ruling). Architect rules split vs single. *(Per the serial-junior principle, this is NOT a within-slice multi-junior proposal — see §Parallelism.)*

## Parallelism assessment (explicit ask — roadmap §5's biggest opportunity)

The lever is the **API contract pin (ADR-025)**, not parallelizing P3.2's own implementation:
- **Within P3.2:** keep it **single-junior serial** (new infra, tightly coupled — contract/read/write/push interlock). No within-slice parallelism.
- **Across slices (the real opportunity):** once the contract is pinned, the **frontend track (P3.3 GUI → P3.6) runs as a concurrent *track* with the backend track (P3.4 MCP → P3.5 plugin)** — a distinct codebase + skillset (React/TS vs Python) binding only to the frozen contract. This is *slice-level* track parallelism (separate ADR-008 cycles), exactly the "P2.7-style independent slices" case — **not** multi-session work on one slice's impl. Net: pin the contract early → P3.3 stops blocking on P3.2-internal churn and the two tracks proceed independently to the plugin-integration join (P3.5).

## Constraints (do not violate)
- **The constitutional/security spine above** (backend-authoritative; no API decision surface; write-surface forge-prevention; state-machine 不暴露; trust boundary; no new `LLMPurpose`; routing/gating stay backend code).
- **Wrap, don't reimplement** — `core/`/`rooms/`/`autonomy/`/`llm/` decision logic is unchanged; the API only reads the store + appends user events + calls `run_turn`.
- **Inscribe-before-producer** — pin the contract (ADR-025) before the P3.3 frontend binds (roadmap §9; P1.6/P2 discipline).
- **RC-23-safe** ADR-025 — Proposed; no literal `Status: Accepted` substring until accepted.
- **Append-only respected** — the store's append-only invariant holds; the API adds no update/delete path.
