## 2. The dogfood — meta-lesson

**The single most important observation from W-001 is the dogfood.**

W-001-impl built the workflow state machine. The very first real task to use the state machine was W-001-impl itself — the task created `.workflow/W-001-impl.yaml` as its own bootstrap state file (impl-7), then advanced through three transitions while the impl was being reviewed and merged:

```
1. impl-7 bootstrap:           state = awaiting_junior_impl
2. impl-9 deterministic land:  state = awaiting_senior_plan_vs_impl
3. workflow advance (× 2):     → awaiting_R0_A → awaiting_PR_merge
4. workflow advance (post-PR): → closed
```

Four state transitions executed during the cycle. Zero state-machine bugs surfaced. Every trigger fired correctly:

- **Plan-vs-impl appearing** → state advanced to `awaiting_R0_A` (frontmatter `verdict: clean` read; auto-trigger fired).
- **R0-A appearing with `verdict: clean`** (after retroactive update post-fix; see §5) → state advanced to `awaiting_PR_merge` (verdict + merge-clean both checked).
- **PR #5 merged** → state advanced to `closed`.

The thing this proves is not that the state machine WORKS — that's testable in unit tests. The thing this proves is that **the state machine works under its own design discipline.** The exact same architect → senior → junior → reviewer cycle that the state machine was built to govern was the cycle that built it. There was no escape hatch where the harness-builders could break their own rules and silently invalidate the harness.

**Two project-level observations follow**:

1. **The "workflow building workflow" loop is sound.** Future workflow extensions (W-002, W-003, …) can rely on the same closed loop. The state machine's first real-world stress test was its own birth, and it passed.
2. **Self-bootstrapping infrastructure is verifiable.** The temptation in workflow design is to assume the workflow works because we built it carefully; W-001-impl gave actual evidence. P1.3+ tasks inherit a tested harness.

## 5. New observation worth surfacing — post-resolution frontmatter update

W-001-impl introduced a previously-unused review pattern: **retroactive verdict update after a finding is resolved by a fix commit.**

The R0-A.md (commit `e2cf573`) had `verdict: needs_architect` with 1 🟡 (R0-A-1). Junior fixed R0-A-1 (`8af18bd`). Architect-partner then updated the same R0-A.md frontmatter to `verdict: clean` with `yellow: 0` (commit `96c1469`), adding an inline body note explaining the temporal sequence.

**This is not in `reviews/README.md` or any process doc.** It emerged organically because the state machine reads frontmatter as live signal, and the state machine needed an updated signal to advance.

**Two competing pressures on the pattern:**

- (i) **Frontmatter as live signal** — update when reality changes. State machine advances. Git history preserves the original verdict (audit intact). Cleaner state-machine ergonomics.
- (ii) **Frontmatter as audit snapshot** — review records what was found *at write time*. Don't retroactively rewrite. Use `workflow override` to advance state without touching the review file.

W-001-impl used (i). (ii) was the alternative architect-partner surfaced when proposing the resolution. Architect picked (i).

**Status: capture as RC-10 candidate** for P1.3 close-out evaluation. The pattern works but should be codified one way or the other. If (i) wins: `reviews/README.md` adds a section on the post-resolution update protocol (when to update, what body note to include, how to preserve original verdict in git history). If (ii) wins: forbid retroactive frontmatter updates, mandate `workflow override` for state-machine advancement post-fix.

Both options are defensible; precedent goes either way. **Architect-partner lean: (i) — frontmatter is a live signal, audit is in git.** But P1.3 should test whether (i) creates confusion for future readers.

1. **P1.3 runs entirely through the harness.** `workflow init --task-id P1.3 --state awaiting_senior_plan` creates the state file at brief publish time; the rest of the lifecycle advances per ADR-008 Decision 1. The harness is the default; no opt-out for P1.3.
2. **Test RC-7 mitigation under recurrence pressure.** P1.3 sessions exercise the SessionStart hook; if any session encounters stale workspace and the hook doesn't surface it (or surfaces it but the session ignores), document the gap.
3. **R0-B trigger criteria evaluated case-by-case for P1.3** per §6 above. Default skip; dispatch when (a)/(b)/(c) apply.
4. **Distance test stays strict (X) by default** per §4 RC-8 deferral. If a fresh-eye-after-sleep-cycle moment arrives during P1.3, surface as the third instance for codification.
5. **Post-resolution frontmatter update protocol** (RC-10 candidate): use (i) — update in place + body note. P1.3 reviewers should follow the W-001-impl precedent until codified otherwise at P1.3 close.

### Specific predictions to test in P1.3

- **The state machine handles a non-self-referential task.** W-001-impl was the harness building itself; P1.3 is the harness being a tool for unrelated work. If the harness only works for self-referential tasks, P1.3 surfaces the gap immediately.
- **`workflow verify-workspace` fires under real stale-workspace conditions.** If a senior or junior session walks in with stale local files, the hook should surface it before any work is done. Untested under recurrence as of W-001-impl close.
- **Frontmatter parsing handles the realistic case of multiple R-rounds.** R0-A → R0-A-fix → R1-A would test the cycle counter in `record_override` (warn at cycle ≥ 4). Untested under real recurrence.

### Anti-recommendations

- **Don't add new RC items per minor observation.** The candidate file is for substantive process-meta surfacing, not nits. P1.2 retro §5 anti-recommendation carries forward.
- **Don't graduate RC-8 prematurely on a P1.3 single instance.** Two instances are data; one more is the threshold. Don't anchor on the W-001-impl 5-day pause as "the rule" — that pause was forced by illness, not a deliberate process choice.
- **Don't pre-commit to (i) over (ii) for post-resolution frontmatter** before P1.3 tests both. The pattern is new; let it earn its codification.

## 9. Meta-lesson

P1.1 ended on the four-layer pipeline (type system → constitutional tests → doc-spec discipline → process discipline). P1.2 ended on the precondition: the layers only work if the roles are distinct.

**W-001 ends on the next layer down: the roles only work if the workflow is observable.**

Through P1.1 and P1.2, "what should happen next" lived in the architect's head and in chat history. P1.2 retro §9 named "role collapse" as the project risk; what it didn't name (but assumed) was that the cure for role collapse is *making the role state observable in artifacts*. Until W-001, that observability was achieved by **convention** — locked file paths, naming, who-writes-what tables. Convention is a substrate humans can drift from.

W-001 made the role state observable in **code** — `.workflow/{task-id}.yaml` is a typed file; the state machine reads it; sessions check on launch. The state is no longer a thing chat-memory-or-architect-judgment alone has to maintain. It's a thing the harness maintains, and the harness is testable.

The W-001-impl dogfood proved this isn't theatre. The harness ran its own birth. If the project's discipline at the role-coordination layer ever drifts, the state file diverges from reality, and the next session's `workflow status` surfaces the gap immediately.

P1.2 said: roles must be distinct. W-001 says: distinctness needs a substrate. The substrate is now the state machine. P1.3 is the first cycle where the substrate is the default mode, not the new tool being tested.

If P1.3 runs cleanly through the harness, the workflow-building-the-workflow loop has produced exactly what it was built to produce: a project that can step away for a sick week and step back without losing track of where things are.
