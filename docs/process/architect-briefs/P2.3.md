**Subject:** Implement P2.3 — **promotion rule (c): external ground-truth validation**. When an external source confirms a hypothesis's claim, surface that hypothesis as a promotion candidate (advisory; the user still promotes via rule (b)). This completes the promotion triad ((a) cross-room corroboration, (b) user-confirm, (c) external validation). The load-bearing design question is **how to represent "external ground truth" so the validation decision is deterministic code, not an LLM judging truth** (Principle 5). P2.3 ships the *contract + consumer*; the external connectors that *produce* ground-truth signals are out of scope (no connector infrastructure exists — this is why rule (c) was deferred).

## The crux — Principle 5: validate truth WITHOUT an LLM judging truth (push-back #1, the whole ballgame)

`handoff.md` §3.1 + ADR-016 Hard Requirements: **promotion eligibility is code, not LLM judgment**; `memory/` never calls an LLM (constitutional, rglob-enforced). Rule (c) is the sharpest test of this rule in the entire project, because "is this claim externally true?" *sounds* like exactly the judgment Principle 5 forbids.

The resolution is **relocation, not elimination, of judgment** — and getting this framing right is the brief's reason to exist:

- The truth-judgment happens **outside `memory/` and outside this slice** — in some future external connector (a test suite passing, a paper's DOI resolving, a benchmark score, a price feed, a curated dataset, a CI result, even an LLM-in-a-connector interpreting a tool result). That connector emits a **typed verdict**.
- `memory/` then makes a **deterministic code decision over the typed verdict** — structurally identical to how rule (b)'s eligibility is `status == PENDING` (a column read) and rule (a)'s grouping is tag-set equality (pure code). Rule (c)'s decision is, e.g., *"a validation record exists for hypothesis H with `verdict == confirmed` → flag H."* A column/field read. No truth-judging in `memory/`.

So **push-back #1 is the representation: what is the typed external-validation input, such that consuming it is a code predicate?** Senior must propose + defend, NOT inherit a pre-baked answer. Candidate shapes to weigh (not exhaustive, not ranked):

- **(i) An `external_validation` event** in the event stream — typed metadata `{source, verdict, evidence_ref, validated_hypothesis_id}`, appended by a (future) connector; rule (c) reads it. **Note:** a new EventType requires an ADR per `core/event.py` convention — ADR-019 would add it. Keeps the canonical log authoritative (Principle 1).
- **(ii) A typed `ExternalValidation` record/table** keyed to a hypothesis (new dataclass + SQLite table in `memory/`), with `verdict` + `source` + `evidence` columns; rule (c) is a deterministic query over it. Mirrors the registry's own-table pattern.
- **(iii) A signal on the hypothesis** (a field/column) — lowest surface, but conflates external-validation state into the Hypothesis row and offers nowhere to record source/evidence.

The deciding criteria senior should reason about: where does the canonical record of "external validation happened" live (event stream vs derived table — the ADR-014/016 tension); how does a connector *write* it without coupling to `memory/` internals; what does `verdict` enumerate (`confirmed | refuted | inconclusive`?); and how `refuted` interacts with the `status` lifecycle (does an external *refutation* map to `status = REJECTED`, or is that also advisory? — see push-back #4). **Lean: (i) or (ii)** (a real typed artifact a connector produces), not (iii); but the architect has NOT decided — this is the senior's core design contribution.

## Scope

**In scope (P2.3):**
- **The external-validation input representation** (push-back #1 resolves which) — the typed shape a future connector produces and rule (c) consumes. Pure schema/contract; no connector.
- **The rule-(c) decision function** in `memory/` — deterministic, no LLM. Reads the typed verdict(s), applies the eligibility predicate, and (lean, push-back #2) flips an advisory flag — never creates a VK, never calls `promote_hypothesis`. Mirrors `run_matcher`'s advisory-only orthogonality.
- **A reader/surface** so the rule-(c) signal is consumable end-to-end (parallels `list_promotion_candidates`; see push-back #3 on whether it's the same reader or distinct).
- **ADR-019** (Proposed) — pins the representation, the deterministic eligibility predicate, the advisory-only orthogonality (D10/D11 unchanged), the composition with rules (a)+(b), and the connector-producer deferral.
- **e2e (Scenario Z)** — an external-validation signal (test-injected, since no connector exists) → rule (c) flags the hypothesis → it surfaces as a candidate → `promote_hypothesis` (rule b) still works on it (and on un-flagged rows — orthogonality). Plus the no-auto-promote assertion (rule (c) creates no VK, emits no promotion `decision` event).
- **Constitutional guard** — the no-LLM rglob already covers any new `memory/` file; **add** an advisory-orthogonality guard (rule (c) cannot promote by construction — AST check, per P2.2's B→α precedent, NOT a whole-file substring scan — RC-23/RC-24 family).
- **`handoff.md` §4.5 light-touch** — rule (c) materialized; the triad complete.

**Out of scope (defer):**
- **External connectors / ground-truth sources** — CI hooks, paper-DB lookups, price feeds, benchmark runners, dataset checkers. No connector infrastructure exists; building one is its own slice (or P3). P2.3 ships the *contract the connector will produce against*, exactly as rule (a) shipped the matcher but deferred the auto-tagging producer. **rule (c) is "dormant-until-fed" by design** (see the scope push-back).
- **Auto-promotion on external confirmation** — forbidden by D10 (constitutional). Push-back #2 surfaces the temptation and the lean against it.
- **LLM-in-`memory/`** — the judgment lives in the connector, never here.
- **Multi-source aggregation / trust-weighting** of validations (e.g. "3 sources confirm, 1 refutes") — if the representation admits multiple validations per hypothesis, the *aggregation policy* is likely a forward hook, not P2.3. Senior surfaces.

## Architect-settled (the constraints — deliberately minimal)

1. **It's rule (c), external ground-truth validation**, completing the §4.5 triad. ADR-019, fresh, senior-drafted.
2. **D10 holds (constitutional): no auto-promote.** No code path promotes without an explicit `promote_hypothesis` call. Rule (c), whatever its strength, does not create a VK.
3. **`promote_hypothesis` stays the SOLE promotion path** (rule b). Rules (a) and (c) are advisory *surfacers*; rule (b) is the only *actuator*.
4. **Principle 5 holds (constitutional): the validation decision is code; `memory/` calls no LLM.** Judgment is relocated to the (out-of-scope) connector. *How* the typed input makes this true is push-back #1.
5. **D11 atomicity** preserved for any multi-write the rule performs (reuse the registry/promotion transaction posture if rule (c) writes + emits).

Everything else — the representation, the flag shape, the composition, the lifecycle interaction — is **open** (push-backs below). This brief intentionally does not pre-bake them.

## Places I expect you to push back (address in plan §5)

- **#1 — The external-validation representation (THE design question).** What typed input represents "external ground truth," such that rule (c) is a deterministic predicate? Options (i) event / (ii) typed record-table / (iii) hypothesis field, above. Propose + defend; reason about canonical-log-vs-derived-table, connector-write-without-coupling, the `verdict` enum, and the new-EventType-needs-ADR note if you go (i). **Lean: (i) or (ii); NOT pre-decided.** This is where the plan earns its keep.
- **#2 — Advisory vs stronger (the D10 temptation).** Lean: **advisory** — rule (c) flips a candidate flag and stops, orthogonal to D10, exactly like rule (a). But surface honestly: rule (c) is arguably the *strongest* signal (external truth, not mere corroboration), so it *tempts* a D10 exception ("if ground truth confirms it, why must the user still click?"). Defend why D10 holds regardless of signal strength (constitutional; promotion is a permanent user act; advisory is reversible-by-ignoring) — or, if you think rule (c) genuinely warrants more than advisory, surface it as an explicit architect decision (do NOT just implement a stronger action). **Architect decides if you challenge the lean.**
- **#3 — Composition with rule (a)'s flag + the reader.** Does rule (c) **reuse `candidate_for_promotion`** (simple; but conflates "cross-room corroborated" and "externally validated" into one boolean — the user/reader can't tell *why* something is a candidate), or introduce a **distinct signal** (e.g. a separate flag/field, or the typed record itself as the surface) that preserves provenance? And does `list_promotion_candidates` surface both, or does rule (c) get its own reader? Lean: **distinct provenance** (rule (c) is a different, stronger signal worth distinguishing) — but weigh the schema cost. Not pre-decided.
- **#4 — `verdict == refuted` vs the `status` lifecycle.** If the representation carries a refutation verdict, does an external *refutation* advisorily flag toward `status = REJECTED`/`STALE`, or does rule (c) only ever surface *positive* candidates and ignore refutations this slice? Lean: **P2.3 handles `confirmed` only** (surface positive candidates); `refuted`/`inconclusive` handling is a forward hook — keeps the slice bounded and avoids rule (c) mutating the status lifecycle (which is `promote_hypothesis`/user territory). Confirm or challenge.
- **#5 — Scope: a third dormant mechanism.** Rule (a) is dormant until a tagging producer ships; rule (c) would be dormant until external connectors ship. That's two inscribed-but-unfed advisory mechanisms. Is completing the contract now worth it? Lean: **yes** (Principle 9 inscribe-before-producer; completing the triad fixes the promotion-eligibility contract every future connector binds to; the contract is the valuable, expensive-to-change-later part) — same justification rule (a) used. But if senior thinks rule (c) should wait for a concrete connector consumer (the "real consumer scenario" bar P1.6 set for cross-room memory), **surface it** — the architect would rather hear "this is premature" now than ship dead machinery.

## Constraints (do not violate)
- **No LLM in `memory/`** (`handoff.md` §3.1; `tests/memory/test_constitution.py` rglob covers any new file). Rule (c) is pure code; the verdict it reads was produced elsewhere.
- **D10 no-auto-promote** + **`promote_hypothesis` sole VK-creating path** — rule (c) creates no VK, emits no promotion `decision` event. e2e + the AST orthogonality guard assert it.
- **D11 atomicity** for any multi-write (reuse the transaction-neutral / `append_in_transaction` posture from ADR-016 D11 / ADR-018 if rule (c) both writes a record and emits an event).
- **Determinism** (Principle 11): same validation input → same rule-(c) decision, scan-order-independent.
- **Dependency direction**: rule (c) lives in `memory/`, imports `core/` (+ `memory/`); `core/` MUST NOT import `memory/`.
- **⚠️ RC-23 / RC-24** — ADR-019 must not write the literal `Status: Accepted`/`Status: Proposed` substring in prose when referencing other ADRs (paraphrase); and the new constitutional orthogonality guard must be a **real AST call/import check**, not a whole-file substring scan (P2.2 B→α precedent). Verify: `grep -i "status:.*\(accepted\|proposed\)" ADR-019` matches only ADR-019's own status line.

## Predicted senior self-discoveries (verify against `origin/main`)
- **Judgment is relocated, not removed** — the cleanest framing for ADR-019's Context: rule (c) is Principle-5-clean because the verdict is produced *outside* `memory/`, and `memory/` reads it as a column, exactly like rule (b)'s `status == PENDING`. Make this explicit or the ADR reads as doing the forbidden thing (same "not-the-weak-matcher" reconciliation burden ADR-017 carried).
- **New EventType needs an ADR** — if representation (i): adding `external_validation` to `core/event.py`'s EventType is an ADR-gated change; ADR-019 is that ADR. Verify the type list + the "adding a type requires an ADR" convention.
- **Don't touch `status`** — `status = VERIFIED` means "promoted to VK" (set by `promote_hypothesis`). External-validation is a *pre-promotion advisory* signal; conflating it with `status` would break rule (b)'s contract. (Tie to #4.)
- **Orthogonality guard must be AST** (RC-24) — not a substring scan. Reuse P2.2's `test_matcher_advisory_orthogonality_ast_guard` shape.
- **D11 transaction posture** — if rule (c) writes a record AND appends an event, reuse `append_in_transaction` + transaction-neutral helpers; don't reinvent the atomicity mechanism.

## RC-15 dual-lens R0-B dispatch recommendation

**Lean: DISPATCH dual-lens R0-B (cross-family).** A genuine architect call, with the honest split.

**Mechanical RC-15 read (~1.5/4):** (1) new concurrency/transaction surface — *maybe* (only if #1 lands on a record+event write; advisory-flag-only = no); (2) new cross-package edge — no (rule (c) in `memory/`, same memory→core edge); (3) contract referenced by ≥5 future tasks — **strong yes, and more**: ADR-019 defines the **external-integration contract every future ground-truth connector binds to** — not just "≥5 tasks" but an integration boundary expensive to change post-hoc; (4) runtime/failure-mode-rich — low if advisory-flag-only.

**Why I lean DISPATCH despite the low mechanical count (two reasons that dominate):**
- **(a) Highest Principle-5 stakes in the project.** Rule (c) is the single most likely place to *accidentally* smuggle LLM-judgment into a code decision — it literally validates truth. A cross-family lens tracing "is this genuinely a deterministic predicate over a typed input, or did a judgment sneak in / did the representation quietly require an LLM to populate `verdict` inside the boundary?" is exactly the constitutional check that matters most here, and it's the check the in-family lens is most at risk of rationalizing past. This is higher-stakes than P2.2's invariant-tracing.
- **(b) It defines an integration contract.** Getting the typed external-validation representation wrong is costly to change once connectors bind to it. A second independent lens on the *representation* (push-back #1's resolution) before it's accepted is cheap insurance on an expensive-to-reverse decision.
- Plus the standing RC-20 evidence: cross-family R0-B has already paid for itself twice in this family (P2.1 caught my R0-A false positive; P2.2 confirmed clean with a structural contribution).

**The honest counter (rule against me if):** if push-back #1 lands on a minimal advisory-flag-only shape with a trivially-typed verdict, the runtime surface is genuinely low and a **proxy-only** R0-B (in-session contrarian) might suffice — RC-20's own observation is that external net-new co-varies with runtime surface. But the Principle-5-boundary + integration-contract stakes tip me past that: this is the rule where a missed constitutional violation is most expensive. **My net: DISPATCH dual-lens.** `requires_cross_family_review` left **false** in the bootstrap; flip to true if you accept.
