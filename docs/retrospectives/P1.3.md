## 2. The harness held under non-self-referential pressure — meta-lesson

**The single most important observation from P1.3 is that the state machine did not need to be the unit of work to function correctly.**

W-001 retro §9 staked the claim: "P1.3 is the first cycle where the substrate is the default mode, not the new tool being tested." This was a falsifiable prediction. If the state machine only worked for self-referential tasks (a recurring failure mode in orchestration systems), P1.3 would have surfaced it.

It didn't. The harness ran through five state transitions on a task that has nothing to do with workflow:

```
1. brief publish (a688ce4):       state = awaiting_senior_plan
2. plan-vs-impl auto-trigger:     awaiting_senior_plan → awaiting_architect_accept  ✅ fired
3. architect-partner override:    awaiting_architect_accept → awaiting_junior_impl  ⚠ manual (RC-11)
4. R0-A clean + merge auto:       awaiting_junior_impl → awaiting_senior_plan_vs_impl → awaiting_R0_A → awaiting_PR_merge  ✅ fired (3 transitions)
5. PR #7 merge auto:              awaiting_PR_merge → closed  ✅ fired
```

Of the five transitions, four fired correctly without any code in the state machine being modified. The one transition that did not fire (#3) failed for a reason that does not generalize across all non-self-referential tasks: it only blocks tasks that draft ADRs. Tasks without ADRs — most P1.x-style mechanical impl work — would have advanced through this state automatically (it would have skipped `awaiting_architect_accept` entirely).

**Three project-level observations follow:**

1. **The harness is task-shape-agnostic.** It works for "the harness builds itself" (W-001-impl) and for "the harness moves an unrelated module through review" (P1.3). The fear that workflow tooling only validates against itself is no longer hypothetical — there is concrete counter-evidence.

2. **The W-001 retro's predictive framing was accurate.** §8 prediction #1 said the gap would surface "exactly where predicted." It did. This is not luck; it's evidence that the post-mortem framework the project uses to identify untested transitions correctly identified which transitions had not yet been tested. P1.4+ predictions should be taken seriously (see §8 of this retro).

3. **The state file as audit log earned its first override.** RC-11 produced the first non-trivial entry in `override_history`. The override reason field captured the link to the retro candidate, the commit that should have triggered the auto-advance (`99aae9e`), and the rationale. A future reader doing forensics on why P1.3 cycled twice will find the trail in the file, not in chat history. This is exactly what ADR-008 Decision 12 (override capability + auditability) was designed for.

## 4. Retrospective candidates — graduation decisions

### RC-7 — Stale-workspace-as-truth pattern

**P1.3 update:** one instance recurred — junior session opened with stale local state (post-PR-#6 merge not pulled) and reported `awaiting_senior_plan` when actual `.workflow/P1.3.yaml` on main was `awaiting_junior_impl`. **The SessionStart hook did not catch this** because the hook only runs `workflow status` + `workflow verify-workspace` — neither of which compares local state-file content against `origin/main`. The junior surfaced it as "ah? it doesn't start" rather than as a verify-workspace error, and architect manually told junior to pull.

**Graduation: ⏸ MITIGATION GAP CONFIRMED.** The W-001 retro framed RC-7 as "not yet stress-tested." P1.3 supplied the stress test. The hook in its current shape catches "branch behind on `git` operations" — it does not catch "local workflow state file diverges from origin." The gap is small but real.

**Recommendation:** fold into W-002 scope. `verify-workspace` could fetch the `.workflow/*.yaml` files from `origin/main` and warn on local divergence. **Low priority** — the current workaround (junior surfaces immediately because the state-machine self-organization rules don't match what their state file claims) is itself a self-organizing recovery mechanism. The gap is detectable in <60 seconds.

**RC-7 does NOT graduate at this retro.** It remains open as "mitigated for branch-behind cases; gap confirmed for state-file divergence cases."

### RC-8 — Distance test letter vs spirit

**P1.3 status:** No new instance of letter-vs-spirit divergence. P1.3 ran in a high-density window (architect chose density-over-distance after the 5-day illness pause), so the distance test was exercised in its (Y)-substrate form throughout — every architectural inscription (ADR-009 Accept; senior plan Accept) had a sleep-cycle + fresh-eye gap because the architect physically slept between sessions, not because the calendar said 24h+ had elapsed.

**Status update from W-001 retro §4:** RC-8 was already **GRADUATED 2026-05-26** during this same cycle via option α — `docs/process/distance-test.md` codified the substrate as canonical rule + 24h+ as proxy/default reminder. The W-001-candidates.md file was updated to reflect graduation. P1.3 ran the new substrate without incident.

**Graduation: ✅ COMPLETED at codification time + ✅ VALIDATED in P1.3.** First post-codification cycle ran cleanly under the substrate rule. No further action.

### RC-9 — Architect-dispatched R0-A-on-plan as gated transition

### RC-11 — State machine task→ADR mapping gap + `record_override` cycle-counter bug

**Surfaced:** 2026-05-26 (P1.3, this cycle). Captured in `P1.3-candidates.md`. Two sub-findings sharing a root cause area (state-machine impl assumes simpler cases than P1.3 exercises).

**Sub-finding (a): task→ADR mapping gap.** `_read_adr_status(task_id, repo_root)` cannot identify which ADR belongs to which task. ADR-008 dogfood (W-001-impl) was the harness building itself, so ADR-008's Accept-by-bump was implicit. P1.3's ADR-009 is the first ADR whose Accept needs to drive a separate task's state transition. The state machine has no `task_id → adr_id` mapping in `TaskState`. **Workaround used:** architect-partner `workflow override` (cfbf087) with audit-trail reason field.

**Sub-finding (b): `record_override` cycle-counter bug.** Per ADR-008 Decision 11, `cycle` increments only on rework transitions (`awaiting_architect_decision → awaiting_junior_impl`). The override I performed was `awaiting_architect_accept → awaiting_junior_impl` — categorically NOT a rework. Cycle should have stayed at 1; it incremented to 2. The impl in `record_override` increments cycle on every override regardless of from-state semantics. **Workaround:** none; the bug is benign for audit purposes (override reason captures the truth), but the cycle counter on `.workflow/P1.3.yaml` final state reads `cycle: 2` for a single-cycle task.

**Graduation: ✅ MOVED TO W-002 BRIEF.** Both sub-findings are tractable code fixes in the workflow module. W-002 brief (this same close-out triplet) folds them into a scoped task. RC-11 closes here as "captured and dispatched."

### Predicted-failure-validation note (W-001 retro §8 #1)

W-001 retro §8 specific prediction #1 said: "If the harness only works for self-referential tasks, P1.3 surfaces the gap immediately." That's exactly what RC-11 is: the gap surfaced in the first non-self-referential task, and it surfaced cleanly enough to be fixable rather than catastrophic. The retrospective framework worked.

This earns the project a small but real epistemic win: when the W-001 retro listed predicted-failures for P1.3 to test, the prediction was specific enough to be falsified, and it was falsified in the predicted way. P1.4 should inherit this discipline (see §8).

## 5. New observations worth surfacing

### 5.1 Senior plan absorbed all design surface; impl was mechanical

The P1.3 plan-vs-impl review came in 0 🔴 / 0 🟡 / 3 🟢. The R0-A on the impl came in 0 🔴 / 0 🟡 / 4 🟢. The R0-A-on-plan (pre-impl review of plan + ADR) came in 0 🔴 / 2 🟡 / 3 🟢, and **all five findings on the plan absorbed into ADR-009 revisions** before junior touched code.

This is the cleanest impl phase of any P1.x module to date. The implication is that when the plan + ADR are reviewed pre-impl (RC-9 architect-dispatched R0-A-on-plan pattern), the impl-stage review effectively has nothing to find. The substantive findings shift one stage earlier in the cycle.

**Project-level observation:** the architect-dispatched R0-A-on-plan pattern is paying its keep. It costs one extra review round; it saves the cost of post-impl rework on issues that would have been found anyway. Worth keeping as the default for any cycle that drafts an ADR alongside the plan.

### 5.2 Non-skill `.md` in `config/skills/` (R0-A-1 finding, watch carried)

The R0-A on impl surfaced this: `load_skills` does not gracefully handle non-skill `.md` files dropped into `config/skills/` (e.g., a future README.md). The function would attempt to parse the file as a skill and fail with `SkillFrontmatterError`. This is correct behavior under "fail loudly" semantics, but it makes the directory inflexible — a future maintainer cannot put a `README.md` in `config/skills/` to explain the layout.

**Surfaced but not graduated**: this is a 1-finding watch item, not a retrospective candidate yet. If a second instance of "skills directory needs to hold non-skill files" appears (e.g., during P1.4 agent-runtime integration), it earns a real RC. For now, captured here so future readers know the constraint is intentional-not-blocking.

**Disposition:** the W-002 brief includes this as an optional inclusion. If W-002 has spare scope, fix; if not, defer.

## 8. Recommendations for P1.4 (Skeptic + multi-agent)

### Process recommendations

1. **P1.4 must run through the harness.** No exception. The harness has now demonstrated correctness on self-referential (W-001-impl) and non-self-referential mechanical-impl (P1.3) shapes. P1.4 is the third shape: **true architectural shape change with concurrency**.

2. **Cross-family R0-B is no longer optional.** RC-2 stayed accepted through 6 rounds of P1.2-shape work. P1.4 introduces (a) multi-agent dispatch (new concurrency surface), (b) `should_agent_speak` decision function (new gating predicate the architecture has no precedent for), (c) Skeptic agent role (new role with potential for cross-agent state interaction). **The brief mandates dispatch.** See P1.4 brief §"Cross-family R0-B for P1.4".

3. **Architect-dispatched R0-A-on-plan should be the default for P1.4** given the cycle-1 evidence (P1.3 plan-stage caught 5 findings; impl stage found 0). For a shape-changing module, the pre-impl plan review pays its keep even more.

4. **State machine fixes from W-002 should land before P1.4 starts.** Both RC-11 sub-findings (task→ADR mapping; `record_override` cycle bug) will be exercised by P1.4 — P1.4 drafts at least one ADR (probably more), and the override path is hot. If W-002 isn't done by P1.4 start, P1.4 inherits the manual-override workaround. **Sequence: W-002 before P1.4.**

5. **Distance test stays in substrate form per RC-8 graduation.** P1.4 is high-stakes shape change; architect should plan for at least one full sleep cycle between ADR draft and ADR Accept regardless of what the calendar says.

### Specific predictions to test in P1.4 (mirror W-001 retro §8 framing)

- **The state machine handles a task with multiple ADRs.** P1.3 had one ADR; W-001 had one ADR. P1.4 likely needs two or three (agent-runtime, `should_agent_speak` design, summoning rules). The current state machine has one `awaiting_architect_accept` state — there is no "awaiting Accept of N-of-M ADRs" semantic. If P1.4 needs to draft and stage three ADRs, the harness needs to know what to wait for. **W-002 may need to address this.**

- **`should_agent_speak` is a new category of decision function** — selection/gating across multiple agents per turn, not per-tool. The skills `decide_skills_for_context` precedent (decision-trace returned for explainability) should extend; expect a new `AgentSpeechDecisionTrace` of similar shape.

- **Multi-agent concurrency surfaces the test-coverage-standard §2 category** for the first time. P1.1 → P1.3 were all single-actor; concurrency safety was N/A. P1.4 introduces it. The test plan should explicitly itemize §2 coverage.

- **The skills `applies_to.agents` field gets exercised under real load.** P1.3 ships two sample skills with two shapes (specific agent list + `["*"]`); P1.4 will dispatch actual agents that consume them. If the matching function's shape doesn't survive real consumption, a P1.4 finding rewinds into P1.3 territory.

### Anti-recommendations

- **Don't bundle W-002 into P1.4.** They have different shapes (W-002 is small + mechanical workflow refinement; P1.4 is shape-change with high design surface). Bundling them re-introduces the role-collapse risk P1.2 retro §9 warned about.

- **Don't graduate RC-7 from P1.3 single recurrence.** The mitigation gap is confirmed but the cost of bypassing it (60-second manual recovery) is lower than the cost of adding more hook complexity. Let it accumulate at least one more instance before W-003-scope mitigation.

- **Don't skip cross-family R0-B for P1.4 on the basis of "6 prior rounds clean."** The 6 prior rounds were all in-family work shapes; P1.4 is the first shape change. RC-2 graduation specifically called out P1.4 as the re-evaluation point.

## 9. Meta-lesson

P1.1 ended on the four-layer pipeline. P1.2 ended on the precondition (roles must be distinct). W-001 ended on the substrate (distinctness needs a state machine). **P1.3 ends on the proof that the substrate works under non-self-referential pressure.**

The W-001 retro's stake — "if the harness only works for self-referential tasks, P1.3 surfaces the gap immediately" — is now empirically resolved in the affirmative direction. The harness works. The one gap it has (RC-11) is exactly the kind of gap a normal task scoped at the size of W-002 will close.

The interesting next-layer question is: **does the substrate hold under shape change?** P1.3 was a non-self-referential task, but it was still a P1.x-shape mechanical impl. P1.4 is the first cycle where the work itself introduces categories the project has no precedent for: multi-agent concurrency, agent-speech decisions, summoning rules.

P1.1 → "the layers work." P1.2 → "the layers need distinct roles." W-001 → "distinctness needs a substrate." P1.3 → "the substrate works on non-self-referential work." **P1.4 → does the substrate hold under shape change?**

If P1.4 lands without the harness needing to be modified mid-stream, the project has earned the right to stop testing the harness and start trusting it. If P1.4 requires mid-stream harness changes, that's the cycle where W-003 is born.
