# Senior plan — P4.3: container syscall/egress sandbox (the RB-FS/NET retirement)

## 1. Context

P4.2 shipped the heavy tool surfaces (B3 subprocess / B4 network / B5 mutation) and ADR-031 the Posture-B fetched-plugin executor — **each Accepting an honest `RB-FS/NET`-class residual on one named retirement path: the sandbox WRAPS the existing exec; the app-level scoping does not reverse** (ADR-031 D1a Reversibility; ADR-034 D2 forward-watch; ADR-035 D2). P4.3 is that retirement: it does **not** rebuild the execution substrate — it wraps it in an **OS container** with a real FS/net/syscall/UID/resource boundary. This is the Wave-2 opener (P4-roadmap §4) and the foundation P4.4 (plugin registry/lifecycle/signature) depends on.

**The architect ratified all 5 decision-surface points (DP1–DP5) in the dispatch — plan to these, do not re-litigate.** The load-bearing override of the brief: **DP1 = OS containers (Docker/podman), cross-platform** — the brief leaned bubblewrap/nsjail (the lighter Linux-native sweet spot), but the **product deploys cross-platform (mac/win/linux)**, so Linux-only mechanisms are rejected in favour of containers behind a runtime abstraction. The ratified set is inscribed in **ADR-037** (this plan's task P4.3-0); the brief's R1–R9 ledger + 5 DPs + watch-list are the authority.

**The seam topology I verified (load-bearing — read before implementing):**
- **Subprocess seam:** `run_scoped_command` (`mcp/subprocess_trust.py:202`) is called by B3 tools via `subprocess_tools.py::_dispatch` (`:114`, `:251`) **and** `git_push`; the Posture-B plugin spawn is `plugins/code.py::_PostureBFn._async_call` → `subprocess_mcp_stdio` (`subprocess_trust.py:343`). Both already funnel `start_new_session=True` spawns through `subprocess_trust`.
- **In-process egress seam:** `web_fetch` (`network_tools.py:134`) builds a per-call `build_ssrf_client` (`net_trust.py:178`) — in-process `httpx` with resolve-then-pin SSRF floor.
- **In-process FS:** `apply_edit` (`mutation_tools.py:_make_apply_edit`) — in-process `O_NOFOLLOW`-temp + `os.replace`.
- **Composition root:** all registries are built in `api/app.py:206-262` (the only place that may inject sandbox config + posture detection — local.py stays in-process-pristine, constitution t6).

**Constitutional invariants this plan must not break** (ADR-037 carry-forward; guarded by P4.3-12): `_execute_local_call` byte-frozen (empty-executor-diff, ADR-028 D6 — the wrap lives BELOW the executor); no new `LLMPurpose`; single-writer liveness bounded (the container setup/teardown is the new finite term, ADR-028 D5 / ADR-033 D4); no silent fail-open; the app-level scoping retained as defense-in-depth.

**Design calls the dispatch left to me are surfaced in §5** (the egress-allowlist mechanism, the subprocess container image, the cross-platform `openat2` fallback, and the R5 scope question) — these are genuine architect surfaces, banked into the plan to a lean but flagged.

### P4.3-1 — Runtime detection + abstraction (`sandbox/runtime.py`)
- **What:** Detect the available container runtime (`podman` then `docker`; prefer rootless/podman userns semantics), probe daemon liveness (`<runtime> info`), expose `SandboxRuntime` with `available() -> bool` + `run(spec) -> SubprocessResult`-shaped result + a kill primitive (`<runtime> kill` + `rm -f`). Cross-platform: handle Docker-Desktop-via-WSL (the CLI is a `/mnt/c/...` shim) and native engine; the **daemon-down path returns `available()==False`** (does not raise).
- **Where:** `src/orchestrator/sandbox/runtime.py` (new package, `__init__.py`); `tests/sandbox/test_runtime.py`.
- **Why:** ADR-037 D1; cross-platform requirement.
- **Acceptance:** Detection probes podman→docker, returns the first live one; `available()` is **liveness, not just CLI-presence** (a present CLI with a dead daemon → `False`); no exception escapes detection (fail-closed-friendly); the container CLI is the only mechanism touched (no runtime assumed by name downstream). Tests mock the runtime probe (no live daemon required in CI) for: both-absent, docker-present-daemon-down, podman-present-live.
- **Out of scope:** Building the container invocation args (P4.3-2); the posture decision (P4.3-4).

### P4.3-2 — Isolation profile builder (`sandbox/profile.py` + seccomp asset)
- **What:** Build the per-call container invocation args from a `SandboxProfile` (FS: `--read-only` rootfs + workspace bind-mount rw; net: `--network none` deny-default OR an egress spec; `--security-opt seccomp=<profile>` + `--cap-drop=ALL` + `--security-opt no-new-privileges`; `--user`/userns nonroot; `--memory`/`--cpus`/`--pids`; `--rm`). Ship the tightened seccomp JSON asset (runtime default minus `ptrace`/`mount`/`keyctl`/raw-`socket`/`AF_PACKET`).
- **Where:** `src/orchestrator/sandbox/profile.py`; `src/orchestrator/sandbox/seccomp.json` (asset); `tests/sandbox/test_profile.py`.
- **Why:** ADR-037 D2.
- **Acceptance:** A `SandboxProfile` → arg-list builder; deny-default profile emits `--network none`; the FS profile bind-mounts only `sandbox_root` rw and nothing else; seccomp/cap-drop/no-new-privileges/nonroot always present; resource limits always present. Tests assert the arg-list shape per profile variant (no live container needed); a test asserts the seccomp asset denies the escape-class syscalls.
- **Out of scope:** Spawning (P4.3-3); the egress-allowlist spec mechanism (P4.3-7 / §5).

### P4.3-3 — The one sandboxed-spawn interface (`sandbox/spawn.py`)
- **What:** `sandboxed_run(argv, *, cwd, env, timeout_s, max_bytes, profile) -> SubprocessResult` — build the container invocation (runtime + profile), spawn it **reusing the existing bounded-read + timeout + shielded-kill machinery** (`run_scoped_command`'s reader/`run_sync` pattern), re-home the kill to the **container kill** (`<runtime> kill` + `rm -f` — the subtree-kill that retires R3), and **measure + log the setup/teardown latency** (the ADR-028 D5 budget term — a `_log.info`/metric, the R0-B liveness anchor).
- **Where:** `src/orchestrator/sandbox/spawn.py`; `tests/sandbox/test_spawn.py`.
- **Why:** ADR-037 D3 (one seam); D2 (subtree-kill → R3); carry-forward (reuse, don't rebuild the bounded-read/kill machinery).
- **Acceptance:** Signature returns the same `SubprocessResult` shape `run_scoped_command` returns (so callers are substitutable); bounded read stops at `max_bytes`; timeout kills the **container** (not just a pgid); the setup/teardown duration is logged; on runtime-unavailable it raises a typed `SandboxUnavailableError` (the fail-closed signal for P4.3-4) — it **never** falls through to a raw host spawn. Tests (runtime mocked): result-shape parity, timeout→container-kill, max_bytes bound, unavailable→raises.
- **Out of scope:** The posture/fail-mode decision (P4.3-4); wiring callers (P4.3-5/6/7).

### P4.3-4 — Posture + fail-mode + config (`sandbox/posture.py` + `config/sandbox.yaml`)
- **What:** The posture resolver: **default-on where the runtime is available**; **fail-closed by default** when unavailable (raise/propagate `SandboxUnavailableError` → `TOOL_FAILED`, loud surfaced log); an **explicit operator opt-in** (`degraded_app_level: true` in `config/sandbox.yaml`) to the today posture (raw `run_scoped_command` / in-process SSRF / current `apply_edit`) that is **LOUDLY LOGGED (`WARNING`) + surfaced on every degraded call** — never silent. Config schema: `runtime` (auto|docker|podman), `image`, `egress_allowlist`, `degraded_app_level`.
- **Where:** `src/orchestrator/sandbox/posture.py`; `config/sandbox.yaml.example`; `tests/sandbox/test_posture.py`.
- **Why:** ADR-037 D4 (the sharpest honest-posture call).
- **Acceptance:** runtime-available → sandboxed path chosen; runtime-unavailable + no opt-in → **fail-closed** (`SandboxUnavailableError` surfaced, no host exec); runtime-unavailable + opt-in → degraded path runs **and emits a `WARNING` every call**; the degraded decision is logged with enough context to audit. A test asserts no code path reaches a raw host spawn when unavailable-and-not-opted-in (the fail-closed invariant). The `.example` config documents the opt-in as a conscious unsandboxed choice (ADR-031 D4 analog).
- **Out of scope:** The wiring (P4.3-5/6/7); the egress-allowlist enforcement (P4.3-7).

## 5. Where you'd push back / surface

> The architect ratified DP1–DP5; these are the **design calls the dispatch delegated to me** (the engineering seam shape) where a choice point is real. Banked into the plan to a lean, flagged for confirm. None re-litigates a ratified DP.

**5.1 — The egress-allowlist *mechanism* (deny-default is trivial; the allowlist is not).** `--network none` gives deny-default for free, but an operator **host-allowlist** inside a container is non-trivial cross-platform: Docker has no native per-host egress filter. Options: (a) **parent-pinned-IP per-call egress** — the parent resolves+validates+pins (the SSRF floor it already does), and the per-call container is permitted egress only to that pinned IP:port (a per-call network + firewall rule, or a tight bridge); (b) a **host-side filtering proxy** the container routes through (`HTTPS_PROXY` + allowlist) — but proxies don't cover git's ssh transport (`git_push`); (c) **deny-default only**, ship the allowlist as a named follow-up residual. **My lean: (a) for web_fetch** (the pinned IP is already computed by the SSRF floor — clean reuse), and for **git_push** the configured remote host resolved+validated+pinned the same way. **Confirm: parent-pinned-IP per-call egress as the allowlist mechanism, or do you want the proxy model / defer the allowlist to a follow-up?**

**5.2 — The subprocess container image (the toolchain-completeness burden).** `run_tests`/`run_lint` execute the **workspace's own toolchain** (pytest/ruff + the project's deps) — which must exist **inside** the container. This is the real operational cost of containers over an in-process jailer: the operator must provide a **toolchain-complete image** (workspace deps baked in or a mounted venv). **My lean: operator-configured `image` in `config/sandbox.yaml` (no default that silently lacks the toolchain); an incomplete image fails the tool fail-closed (loud).** **Confirm: operator-provided image (fail-closed if incomplete), or do you want a default base image + a documented "bring your deps" contract?**

**5.3 — `openat2(RESOLVE_NO_SYMLINKS)` is Linux-only — the R7 cross-platform tail.** The ratified DP3 names `openat2` for R7, but it is **Linux 5.6+ only**; the product is cross-platform. **My lean: `openat2` on Linux; a per-component dir-fd `O_NOFOLLOW` walk fallback on macOS; on Windows R7 stays at the current final-component residual (inscribed in ADR-037 D5).** This is banked into P4.3-8 + ADR-037 D5 — flagging because it means **R7 is fully retired only on Linux**; surface if you want the non-Linux posture stated differently.

**5.4 — R5 (DNS head-of-line) scope — a brief-vs-dispatch gap.** The brief §0 ledger lists **R5** (the `max_workers=1` `getaddrinfo` head-of-line, ADR-035 impl-degradation) as folding into P4.3. The **dispatch's DP2 residual set did not re-list R5** (it named R6 NAT64 + R9 DLP). Since P4.3-7 re-homes exactly the `web_fetch` egress code that owns the DNS executor, R5 is *touchable* this slice — but I will **not bank it** without your call (the "surface, don't improvise" discipline + the brief/dispatch gap). **Confirm: fold R5 in this slice (a small `net_trust` executor fix, ride P4.3-7/9), or leave it deferred?** I've left it OUT of the banked atomics pending this.

**5.5 — Per-call container latency vs the D5 budget (not a decision — a flag to the R0-B liveness lens).** Per-call containers add setup/teardown to the single-writer block × `(1+N)` passes (ADR-033 D4), and **web_fetch now pays it too** (it was in-process). P4.3-3 measures+logs the term; the R0-B liveness lens is tasked to probe whether it stays bounded under the single writer (the external prompt's Lens A). Not banking a latency budget number — that's the R0-B + impl-measurement output, surfaced at plan-vs-impl.
