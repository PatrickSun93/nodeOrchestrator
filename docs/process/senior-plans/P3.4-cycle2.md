# Senior plan → junior: P3.4 cycle-2 (the runtime tool-executor)

> **Distinct from the cycle-1 plan** (`P3.4.md`). Cycle-1 built the MCP client + gating + the executor *function*. Cycle-2 builds the runtime stage that *consumes `TOOL_CALL` events and actually executes tools* — MCP **and** local. PR #48 (`claude/P3.4-impl`) accumulates; the whole P3.4 merges after cycle-2 + dual-lens clean.

## 1. Context

The impl-stage cross-family R0-B caught **Y2**: cycle-1's `execute_mcp_tool_call` + `interpret_mcp_tool_result` are correct and tested, but **nothing in the running app consumes the `TOOL_CALL` events the gate appends** — so an MCP tool gets *gated* (`AUTO_EXECUTE` → `TOOL_CALL` event) but never *executed* at runtime. The architect routed Y2 → **α wire-now**, scope = a **general runtime tool-executor**, and **ruled decision #1 = build-local-impls-now** (2026-06-03): cycle-2 builds the general framework, wires the MCP executor, **and** implements actual local-tool execution (NOT deferred). This is the system's **first component that actually runs a tool** — beyond ADR-013's envelope (it explicitly *"does not govern tool execution (P1.6+)"*) — so it earns **ADR-028** (the design; Proposed) + a **mandatory dual-lens R0-B**.

The design is inscribed in **ADR-028** (read it — D1 placement, D2 dispatch, D3 local set + trust boundary, D4 failure/no-re-dispatch, D5 single-writer liveness, D6 constitution). This plan turns it into atomic tasks. The **constitutional carry-forward is non-negotiable**: execution stays downstream of the gate (only a `TOOL_CALL` event triggers it); no LLM-judgment in the executor (the only LLM touch is the MCP content-gen interpret; no new `LLMPurpose`); the trust boundary holds (MCP allowlist/scoped-env/size-limit/fail-closed unchanged; local gets its own sandbox boundary).

**Key constraint that shapes the design (verified):** `tests/rooms/test_constitution.py::test_constitution_no_llm_calls_in_rooms_module` forbids LLM in `rooms/`, and `tests/mcp/test_constitution.py` c1 forbids upstream layers (incl. `rooms`/`agents`) from importing `orchestrator.mcp`. The executor imports both `orchestrator.mcp` and the LLM (for interpret) → it **cannot** live in `rooms/` or fold into `run_turn`. Hence the executor is a **new downstream leaf package `tools/`**, invoked as a **post-`run_turn` stage by the turn driver** (`api/app.py::_write_and_turn`). `run_turn`/`dispatch_turn`/`process_tool_calls` are **unchanged** (the empty gate diff from ADR-027 D2 stays empty).

## 2. Tasks

### P3.4-C2-1 — the general executor framework + MCP wiring
- **What:** Build `src/orchestrator/tools/executor.py` — `execute_pending_tool_calls(...)`: the post-dispatch stage that consumes a turn's `AUTO_EXECUTE` `TOOL_CALL` events and dispatches each by tool name. MCP (`mcp__*`) → `execute_mcp_tool_call(tool_call_event, session=mcp_sessions[server], …)` (server parsed via `to_mcp_call`), then on its `TOOL_RESULT` → `interpret_mcp_tool_result(...)`. Local-dispatch hook present (calls into the `local_tools` registry built in C2-2). Define the executor's inputs (the turn's `TOOL_CALL` events, `room_id`, `event_store`, `mcp_sessions: dict[str, MCPSession]`, `local_tools` registry, `llm_router`). **Double-execution guard**: skip a `TOOL_CALL` whose `call_id` already has a `TOOL_RESULT`/`TOOL_FAILED` in the room. **Per-call fail-closed isolation**: each call independent; one failure → `TOOL_FAILED` for that call, continue.
- **Where:** new `src/orchestrator/tools/__init__.py`, `src/orchestrator/tools/executor.py`. Imports: `orchestrator.mcp.execution`/`mcp.client`/`mcp.adapter`, `orchestrator.agents.mcp_interpret`, `orchestrator.core.event*`. No import of `decide_tier`/`emit_gate_decision`/`score`/`gate`.
- **Why:** ADR-028 D1 (placement), D2 (dispatch + session-retention + double-exec guard), D4 (per-call isolation); HR-carry-forward #1/#2.
- **Acceptance criteria:**
  - A `TOOL_CALL` event with `mcp__<server>__<tool>` → `execute_mcp_tool_call` called with the matching session → `TOOL_RESULT` appended → `interpret_mcp_tool_result` called → `OBSERVATION` appended (mocked session + mocked `llm_router`).
  - A non-`mcp__` `TOOL_CALL` routes to the local-dispatch hook (impls in C2-2; here: a hook with a test-injected registry suffices).
  - No `TOOL_CALL` event in the window → executor makes **zero** server/impl calls, appends nothing (the structural downstream-of-gate test — t4).
  - Double-execution guard: a `TOOL_CALL` whose `call_id` already has a result → **skipped** (executor does not call the tool again).
  - Per-call isolation: given two `TOOL_CALL`s where the first raises, the second still executes (its `TOOL_RESULT`/`TOOL_FAILED` is appended).
  - Local-result events are **not** interpreted (no `OBSERVATION` for non-`mcp__` results).
- **Out of scope:** the local *implementations* (C2-2); the bootstrap/driver wiring (C2-3); re-dispatch / agent-reaction (ADR-028 D4 deferred).

### P3.4-C2-2 — local tool implementations + the local trust boundary
- **What:** Build `src/orchestrator/tools/local.py` — the MVP local-tool implementations + a `LOCAL_TOOL_REGISTRY` (or a builder) keyed by tool name: `get_current_time` (pure), `read_file` + `list_files` (sandboxed). The **local trust boundary**: a configured **sandbox root**; every path is resolved (`Path.resolve()`) and **rejected if it escapes the root** (`..` / absolute / symlink-escape → raise → `TOOL_FAILED`); results **size-capped** (reuse the `MAX_RESULT_BYTES = 64 KiB` truncation pattern from `mcp/execution.py`, or import the constant). A local impl is a callable `(params: dict[str, Any]) -> str` (textual result). The executor's local-dispatch hook (C2-1): `local_tools.get(tool_name)` → run; **missing entry → `TOOL_FAILED` `error_class="not_implemented"`** (the deferred-tools fail-closed seam, ADR-028 D3).
- **Where:** new `src/orchestrator/tools/local.py`; wire the registry into the executor's local-dispatch path (C2-1). `config/tools.yaml` already classifies `get_current_time`/`read_file`/`list_files` at rev 10 (verified `config/tools.yaml:17-25`) → `AUTO_EXECUTE`; **no tools.yaml change needed** for these three. The sandbox root is a config/bootstrap value (C2-3 supplies it).
- **Why:** ADR-028 D3 (local MVP set + sandbox trust boundary; build-local-impls-now decision #1).
- **Acceptance criteria:**
  - `get_current_time` executes via the executor → `TOOL_RESULT(success=True)` with a time string; no I/O.
  - `read_file` inside the sandbox root → `TOOL_RESULT` with the file content; a path escaping the root (`../`, absolute outside, symlink to outside) → `TOOL_FAILED` (path rejected, no read).
  - `read_file` of an oversized file → content truncated at `MAX_RESULT_BYTES` with `output_truncated_at` set (no oversized content stored).
  - `list_files` of a dir inside the root → `TOOL_RESULT` with the listing; a dir outside the root → `TOOL_FAILED`.
  - A classified-but-unimplemented tool name (e.g. `web_search`) reaching the executor → `TOOL_FAILED` `error_class="not_implemented"` (no silent no-op, no crash).
- **Out of scope:** network tools (`web_search`/`web_fetch`), subprocess tools (`run_tests`/`run_lint`/`git_*`), code-intel (`search_*`/`find_*`), mutation tools (`propose_edit`/`apply_edit`/`send_email`/`git_push`) — deferred per ADR-028 D3; they remain classified (gate-able) but fail-closed `not_implemented` until their slices. **Do not** add write/move/delete local tools (mutation tier; gated-not-executed under the no-confirm-flow MVP).

### P3.4-C2-3 — runtime wiring (bootstrap sessions + turn-driver stage) + e2e + handoff de-claim
- **What:** Wire the executor into the running app.
  (a) **AppContext**: add `mcp_sessions: dict[str, MCPSession]` + `local_tools` registry + the local sandbox-root config. In `_build_context`, build `mcp_sessions` by **retaining** the sessions from the MCP discovery pass (fix the discard — ADR-028 D2; extend/replace `build_mcp_tool_registry_from_config` so it can also return the sessions, or add a sibling that returns both, keeping `skip_unavailable` graceful behavior). Build `local_tools` from `tools/local.py`.
  (b) **Turn driver**: in `_write_and_turn`, **after `run_turn` returns and before** the `new_events = get_room_events(rid)[pre_cursor:]` read, call `execute_pending_tool_calls(...)` passing the `TOOL_CALL` events appended this turn (the `[pre_cursor:]` window) + `mcp_sessions` + `local_tools` + `event_store=ctx.writer_store` + `ctx.llm_router`. (The post-stage `new_events` read then includes the `TOOL_RESULT`/`TOOL_FAILED`/`OBSERVATION` events → published to the WS bus.)
  (c) **e2e** (`tests/tools/test_e2e.py` + integration): a full runtime turn — agent emits a tool call → gate `AUTO_EXECUTE` → `TOOL_CALL` → executor runs → `TOOL_RESULT`. Two paths: a **local** tool (`get_current_time` → real result) and an **MCP** tool (`mcp__filesystem__read_file` → mocked session → `TOOL_RESULT` → interpret `OBSERVATION`). Plus a **HARD** tool (`mcp__filesystem__write_file` rev 2 → no `TOOL_CALL` → **not executed** — the constitutional demonstration carried from cycle-1).
  (d) **De-claim the handoff**: `handoff.md:954` ("MVP: AUTO_EXECUTE 执行, …") — reword so it reflects reality **after** this cycle (AUTO_EXECUTE now executes at runtime via the cycle-2 executor; before cycle-2 it executed only in tests). Update the P3.4 landing note to record the cycle-2 executor.
- **Where:** `src/orchestrator/api/app.py` (AppContext + `_build_context` + `_write_and_turn`); `src/orchestrator/mcp/adapter.py` (session-retaining builder) or a new helper; `handoff.md`; `tests/tools/test_e2e.py`, `tests/integration/` (full-turn).
- **Why:** ADR-028 D1 (driver-invoked stage), D2 (session-retention), D5 (inline-on-single-writer); the brief's "de-claim the handoff" deliverable.
- **Acceptance criteria:**
  - A runtime turn through `POST /rooms/{id}/intent` (test harness) with an agent that tool-calls a **local** AUTO tool → the response/stream includes a `TOOL_RESULT` (the tool actually ran).
  - The same for an **MCP** AUTO tool (mocked session) → `TOOL_RESULT` + `OBSERVATION` (interpret).
  - A **HARD** MCP tool → **no** `TOOL_CALL` event, **no** `TOOL_RESULT` (gated-not-executed; confirm-then-execute still deferred).
  - The bootstrap retains `mcp_sessions` (a connected server's session is reachable by the executor; an unavailable server is still skipped gracefully — `skip_unavailable` behavior preserved).
  - `handoff.md` no longer claims runtime AUTO-execution as true-pre-cycle-2; the wording reflects the executor landing in cycle-2.
- **Out of scope:** a separate execution lane (ADR-028 D5 deferred); any change to the gate decision logic or `process_tool_calls` (must stay an empty diff — verify).

### P3.4-C2-4 — executor constitution tests
- **What:** `tests/tools/test_constitution.py` mirroring `tests/mcp/test_constitution.py`: **t1** no upstream layer imports `orchestrator.tools`; **t2** `tools/` does not reference `decide_tier`/`emit_gate_decision`/`score`/`gate` (no autonomy decision in the executor); **t3** no new `LLMPurpose` (frozen set unchanged); **t4** execution keys on `TOOL_CALL` only (no path from a non-`TOOL_CALL` event to a server/impl — asserted via the C2-1 no-`TOOL_CALL`→no-execution behavior, plus an AST/structural check that the executor's entry requires `TOOL_CALL`).
- **Where:** new `tests/tools/__init__.py`, `tests/tools/test_constitution.py`.
- **Why:** ADR-028 D6 (the executor's constitutional invariants — the carry-forward spine, made load-bearing).
- **Acceptance criteria:** t1–t4 pass; t2/t3 would fail if a future edit added a decision call or a new purpose to `tools/`.
- **Out of scope:** re-testing the gate/MCP constitution (cycle-1 `tests/mcp/test_constitution.py` covers `mcp/`).

## 3. Execution order

**Sequential** (single-junior, tightly-coupled new infra — per the cycle-1 brief's "no within-slice parallelism" for the trust/autonomy surface):

`C2-1` (framework + MCP wiring) → `C2-2` (local impls + trust boundary; depends on C2-1's local-dispatch hook) → `C2-3` (bootstrap + driver wiring + e2e + handoff; depends on C2-1+C2-2) → `C2-4` (constitution tests; depends on the `tools/` package existing).

C2-4 may be authored alongside C2-1/C2-2 (it only needs the package to exist), but land it after C2-3 so the e2e + wiring are in place. **One atomic = one commit, one subject** (RC-17): `P3.4-C2-1: …`, `P3.4-C2-2: …`, `P3.4-C2-3: …`, `P3.4-C2-4: …` on `claude/P3.4-impl` (cycle-1's branch — PR #48 accumulates; do **not** open a new branch/PR).

## 5. Where you'd push back

1. **Local-tool MVP breadth — the surfaced architect call (decision #1 boundary).** Decision #1 ruled **build-local-impls-now** and delegated "the senior designs the local-tool set." I scoped the MVP to the **safe, AUTO-tier, low-trust-surface** subset `{get_current_time, read_file, list_files}` + a sandbox-root trust boundary (ADR-028 D3), and **deferred** network/subprocess/code-intel/mutation tools (each opens a distinct trust surface; mutation tools are *dead under the no-confirm-flow MVP* — `HARD`/`COUNTDOWN` → gated-not-executed — so implementing them now is dead code). **Architect: confirm this breadth, or broaden/narrow.** Narrowing to `get_current_time`-only (zero new trust surface, executor proven on the local path) is a defensible alternative if you want cycle-2 laser-focused on the executor framework and the local-FS sandbox deferred to its own slice. Broadening to network/subprocess would meaningfully expand the dual-lens surface. This is the one genuine scope/security dimension — flagged for an explicit beat.

2. **The `not_implemented` fail-closed seam is visible.** Deferred-but-classified AUTO tools (e.g. `web_search` rev 10) will get a `TOOL_CALL` event and then `TOOL_FAILED("not_implemented")` at runtime — honest + fail-closed, but the agent sees a failure for a "known" tool. The alternative (don't classify them until implemented) would change `tools.yaml` (out of this cycle's intent). I lean keep-classified-fail-closed (no `tools.yaml` churn; the gate still gates them correctly); flag in case you'd rather de-classify the deferred set.

3. **No-re-dispatch means the agent reacts to a tool result on the *next* turn, not in-turn (ADR-028 D4).** This is the conservative, terminating MVP and matches existing causality. If you want the agent to react in-turn (single-re-dispatch), that's a turn-loop extension (ADR-011 touch) with termination/loop-bounding + single-writer liveness implications — I deferred it. Confirm the deferral, or dispatch the re-dispatch design as part of this cycle (it would enlarge the ADR + the dual-lens).

4. **Inline-on-the-single-writer liveness (ADR-028 D5).** A slow MCP tool blocks **all** room writes for up to the bounded timeout (single `max_workers=1` writer). I accept this for the MVP (bounded + fail-closed; local tools are fast) and deferred a separate execution lane. This is the exact surface the dual-lens R0-B will probe — flagged so it's a known posture, not an accident.
