## Lens preamble

Cross-family Principle-11 constitutional + data-model-contract lens per `external-r0b-prompt.md` probes. This is the project's **first preference surface** — the constitutional check that matters most: *can an LLM-inferred preference become durable without an explicit user-confirm gate? does the create API make "inferred" un-representable, or is there a back door?* Also probed: the ProjectArchive persist-vs-derive decision (the headline design call), entity create discipline (where the confirm-gate lives), migration correctness, and the preference data model as a consumable contract for P2.5 re-entry. Over-correcting for Claude biases: sycophancy toward the senior's confidence ("verified"/"decisive"), the persist-vs-derive consensus (a Claude-family authored plan), and the assumption that behavioral tests + API contracts are sufficient for constitutional invariants when the project's own precedent (matcher/validation AST guards) says otherwise.

## Synthesis

Both R0-A yellows are independently confirmed by the cross-family lens. No net-new 🔴 or 🟡 beyond them — but the cross-family framing differs on Y2 in a way that matters for the architect's routing.

**Y1 (structural guard):** The cross-family lens confirms R0-A's finding but notes a nuance absent from the in-family review. The existing AST guards (matcher, validation) protect "must NOT actuate" invariants on pure-reader modules. The Principle-11 guard would protect "must NOT create PREFERENCE without user_id" — a different class of invariant (it's about the write path, not about preventing writes), but the structural-guard pattern fits equally well. The senior's ADR-020 D5 declines a guard on the grounds that there's "no actuation invariant to guard" — but that reasoning answers the wrong question. The invariant IS constitutional (Principle 11), it IS a "must not X," and the project's pattern IS to structurally guard those. Cross-family lean: α (add a lightweight structural guard — e.g., an AST check that `EntityType.PREFERENCE` is referenced only in `entity.py`'s pref functions — senior designs it).

**Y2 (upsert-vs-insert):** The cross-family lens independently confirms but reframes. R0-A frames this as brief-vs-plan divergence ("the brief said upsert"). The cross-family lens goes further: preferences-as-append-only-entity-log is the **wrong data model** for a key-value settings surface, regardless of what the brief said. The P2.5 consumer (and every future consumer) should not have to implement "latest-wins dedup" to answer "what is the current preference for key X?" Push the dedup into the write path — entity upsert-by-(user_id, key) for preferences — so the data model is a key-value map, not an append-only log with derived current-value semantics. Entities stay append-only (entities accumulate); preferences should upsert.

No 🔴. The design is sound on the major calls (persist-vs-derive, Principle-5 relocation, prefs-as-entity, entity create discipline, migration, reserve-fields). Both 🟡 are about enforcement strength (Y1) and data-model semantics (Y2) — resolvable at plan stage without re-design.

## What the architect needs to route

1. **Y1 (🟡):** R0-A Y1 confirmed — Principle-11 enforcement is by behavioral test only, not a structural guard. The project's precedent (matcher/validation AST guards) argues for consistency. Lean: **α** — add a lightweight structural guard (e.g., AST check that `EntityType.PREFERENCE` is referenced only in the preference functions within `entity.py`), senior designs the exact shape. Alternatively, **β** — defer to P2.6 (extraction producer), revisit the guard then.
2. **Y2 (🟡):** R0-A Y2 confirmed with stronger cross-family framing — preferences as plain-insert is the wrong data model for a key-value settings surface. Lean: **implement upsert for preferences** (upsert-by-(user_id, key, scope) gives exactly one row per preference key, deterministic current-value resolution), while keeping general entities as append-only. Alternatively, **accept plain-insert with explicit justification** that preferences are an append-only log and dedup is the consumer's job — but this leaves the non-deterministic tiebreak unresolved and pushes complexity onto every consumer.
3. **Greens** are cross-family confirmations; no action.
