## Lens preamble

Cross-family autonomy-bypass/subprocess-failure/env-leak/trust-boundary lens per `external-r0b-prompt.md` probes. P3.4 is **P3's heaviest constitutional/security slice**: a new stdio transport, **external untrusted third-party MCP servers**, **subprocess concurrency/failure**, and the **operation-gating constitutional surface** (the autonomy gate). This is exactly the class of surface the cross-family lens catches errors on — the P2.7-S3 precedent (c2 env-inheritance hole was a cross-family catch) and the P1.4 precedent (event_store failure-path) apply directly. The external prompt names the highest-value targets: autonomy-bypass (can a server reach execution without the gate? influence its tier? namespace-collide?), subprocess-liveness (does the timeout fire across the async↔sync bridge?), env-leak (the c2 pattern recurs, magnified — do the orchestrator's secrets leak to a third-party subprocess?), and untrusted-result handling. Over-correcting for Claude biases: sycophancy toward "structural"/"airtight"/"unchanged" claims without tracing the actual execution path through the bridge, and toward the config-classified classification without stress-testing the bridge timeout.

## Synthesis

The design is sound on the autonomy and security fronts. The autonomy-bypass surface is genuinely fail-closed: execution keys on the `TOOL_CALL` event (the gate's approval record — structural, not discipline), server hints never influence the tier, unclassified tools get no `ToolMeta` (discovery ≠ permission, no default-register path), and namespace collision is structurally prevented. The env-leak pattern — the P2.7-S3 c2 catch the cross-family lens caught — is explicitly addressed with the same structural fix (minimal scoped env, not inheritance). The gate's decision logic is unchanged — MCP tools feed the existing registry merge path.

One 🟡 on the subprocess-failure surface: the sync-over-async bridge timeout mechanism is underspecified. The P3.2 `llm_adapter` precedent's timeout is internal (HTTP client timeout), not bridge-enforced — a stdio subprocess hang doesn't have an HTTP-level timeout to fall back on. The plan should specify that the bridge enforces timeout via `asyncio.wait_for()` wrapping all SDK calls, and that a timed-out subprocess is killed (not abandoned as an orphan). This is the exact class of failure-mode detail the cross-family lens catches — the P1.4 precedent established the pattern.

## What the architect needs to route

1. **Y1 (🟡):** Sync-over-async bridge timeout — specify the timeout enforcement mechanism. Lean **α** — pin in ADR-027 D1: the bridge wraps all SDK calls in `asyncio.wait_for()` with a configurable timeout; on timeout, the subprocess is `.kill()`ed + `.wait()`ed; the timeout is tested with a deliberately-hanging mock server. This closes the bridge-liveness gap without changing the design.
2. **Greens** are cross-family confirmations; no action. The autonomy-bypass, env-leak, and untrusted-result surfaces are genuinely fail-closed. The gate feeds unchanged.

## Synthesis

The impl is faithful to the plan and ADR-027 on the **constitutional and security** fronts. The timeout mechanism is genuine — `asyncio.wait_for` wraps all SDK calls, the hanging-mock test verifies subprocess kill (no orphan), and the orchestrator thread is not blocked (HR#10 satisfied). The pre-classify allowlist is airtight — dual-intersection (config allowlist ∩ discovered tools), server hints ignored, no auto-register path, namespace parsing guards the execution entry point (HR#2/#3 satisfied). Env-leak prevention is structural — explicit safe-keys construction, no `os.environ` inheritance, tested with secret-injection (HR#10 satisfied — the c2 lesson applied). The gate feeds unchanged — diff empty, registry merge at bootstrap, no `mcp/` references to decision functions, constitution tests (c1–c5) all pass (HR#1/#5/#6 satisfied). Size-limit + untrusted-framing are structural in the executor (HR#9 satisfied).

One 🟡 on **runtime integration**: the execution and interpret functions are defined, tested (51 mcp tests pass, full-pipeline e2e with mocked transport works), and constitutionally correct — but they are not called from the runtime event loop. `app.py` merges the MCP registry at bootstrap but adds no consumer for `TOOL_CALL` events. The gate appends `TOOL_CALL` events for `AUTO_EXECUTE` MCP tools, but nothing reads them and calls `execute_mcp_tool_call`. The handoff claims "AUTO_EXECUTE 执行" — the *pipeline* exists and executes in tests; the *runtime* doesn't enter it. The sessions created at bootstrap for discovery are discarded (`adapter.py:115` — `session` is a local variable), so even if a consumer existed, it would need to create new transports (which `MCPTransport` supports — per-operation connections).

This is a **scope/completeness** finding, not a constitutional violation. The modules are correct and well-tested. The wiring is thin: an event-loop consumer that watches for `TOOL_CALL` events with `mcp__*` tool names, creates a transport (or reuses a cached session), and calls `execute_mcp_tool_call`. The `MCPSession` can be created per-call (the `MCPTransport` already supports per-operation subprocess connections). The interpret wiring (`interpret_mcp_tool_result`) would follow the same pattern — consume `TOOL_RESULT` events from MCP tools.

## What the architect needs to route

1. **Y2 (🟡):** Execution runtime wiring missing — `execute_mcp_tool_call` and `interpret_mcp_tool_result` are defined and tested but not called from the runtime event loop. The gate appends `TOOL_CALL` events for `AUTO_EXECUTE` MCP tools, but no consumer reads them. Lean **α** — add the thin event-loop consumer (iterate `TOOL_CALL` events → match `mcp__*` → create transport → `execute_mcp_tool_call`), or explicitly defer to a follow-up integration slice (and update the handoff to reflect the actual runtime state). Scope, not constitutional — the modules exist and are correct; the gap is the glue code that connects them to the event loop.
