## Architect-settled design decisions

### 1. Tool-call gating is code (handoff §3.1; not a new principle)

The decision "should this tool call proceed?" is `autonomy.gate(operation, tools, thresholds)`. Pure function (ADR-005 D4/D5); no LLM in the gating path. The LLM only produces the tool-call proposal in its response; code decides whether the proposal becomes a stream event.

**This is the first runtime exercise of the LLM-proposes-code-decides pattern that P1.2 inscribed.** Architecturally interesting (it's the proof the architecture works); architecturally trivial (the pattern was already inscribed; P1.5.5 just runs it).

### 2. Tier-to-event mapping is fixed by existing ADRs

Per ADR-005 D6 + ADR-007 D3, the mapping from `gate()` tier to event-stream emission is non-negotiable:

| Tier returned by `gate()` | Events emitted (in order) |
|---|---|
| `AUTO_EXECUTE` | `autonomy_decision` (per ADR-005 D6, synchronous); then `tool_call` (per `ToolCallMeta`). The `autonomy_decision` lands **before** `tool_call` in the stream (decision-then-action causality). |
| `COUNTDOWN_CONFIRM` | `autonomy_decision` only. The `tool_call` lands later via P2 UI countdown logic if the user doesn't intervene. |
| `HARD_CONFIRM` | `autonomy_decision` only. The `tool_call` lands only via P2 explicit user approval. |
| `gate()` raises `UnknownToolError` (ADR-006) | `autonomy_refusal` with `refusal_reason: "unknown_tool"` per ADR-007 D2. No `tool_call` event. The operator's LLM response is logged-as-dropped. |

**P1.5.5 implements this mapping; doesn't redesign it.** ADR-013 (if drafted) references the existing ADRs and inscribes the runtime contract for the call site.

### 3. operator's `llm_config` per handoff §5.5

```yaml
llm_config:
  default_model: deepseek_v4_flash
  fallback_chain: [qwen_mlx_30b]
  temperature: 0.3
  required_capabilities: [tools]
```

Per `handoff.md` §5.5 line 532 + ADR-003: operator MUST use an API-routable provider (not Claude Code CLI, which can't accept orchestrator tool definitions). The `required_capabilities: [tools]` is what `validate_consistency` already checks at config load — operator is the **first agent to exercise** this validation path against real config data (P1.4 R0-A G2 noted the validation was implemented but never run).

If `validate_consistency` surfaces a mismatch (e.g., a model in the fallback chain doesn't declare `tools` capability), it's a config-data issue (not a P1.1 code bug). Senior plan should specify how to surface this clearly during P1.5.5 dev.

### 4. Tool execution defer is strict scope discipline

P1.5.5 emits `tool_call` events; **does not execute the tools**. No `tool_result` events produced by P1.5.5.

This may feel artificial (the operator proposes; nothing happens; the event sits there). The justification:
- ADR-001: event store is single source of truth; events represent intent + outcome.
- Separating proposal (LLM output captured as `tool_call`) from outcome (execution captured as `tool_result`) keeps the event vocabulary clean.
- Future execution layer (P1.6+) can consume `tool_call` events from any source uniformly (operator, future user-explicit invocations, scheduled tasks).
- The state-of-the-world after P1.5.5: the *system can decide* to make tool calls; it just can't *execute* them yet. P1.6 closes that.
