**Subject:** Build P3.6 — **GUI completeness**: extend the read-mostly P3.3 MVP with **full interactivity + the remaining views** (richer event-stream rendering, room-management depth, read-only surfacing of the autonomy gate's pending decisions, the view-only §6.4 patterns, restrained polish). This is a **known-stack extension** (the `ui/` toolchain + gate + spine already exist) and the **frontend-track continuation**. It binds the **same frozen ADR-025 contract** — **adds zero Python** for the frontend-track scope. The one genuine fork is ⭐**D-B (confirm-then-execute)**, which — if ruled in — reshapes the slice into a cross-track build.

## What it binds (the frozen contract — no new backend, for the frontend-track scope)

Same as P3.3: the GUI is a **pure consumer** of the ADR-025 API — HTTP read/intent + WS live stream + the committed `openapi.json` (codegen) + `asyncapi.md` (WS semantics). **New data P3.6 can now bind (already on the wire, no contract change):** `Snapshot.tool_calls_pending_confirm: list[ToolCallRef]` (the gate's pending `COUNTDOWN`/`HARD` calls — P3.4's output) + the full 19-`EventType` stream the MVP already humanizes but renders flatly. **No backend change** for the frontend-track scope; if a remaining view needs a field the contract lacks → **surface a contract gap** (a separate backend decision), never backdoor.

## ⭐ The constitutional spine (NON-NEGOTIABLE — carried forward from ADR-026 HR#1–5; inscribe, not chosen)

Unchanged from P3.3 — the GUI is a **view + intent surface; backend-authoritative**:

1. **View + intent only; no decision surface.** Reads the stream + sends user intent; makes **no** state/routing/autonomy decision.
2. **Binds the API contract ONLY.** No `orchestrator` import, no DB/fs/sqlite access, no non-API network call. The HTTP/WS client modules stay the sole network surface (the eslint guard + constitutional test from ADR-026 D4 still hold).
3. **状态机不暴露 via `ui_strings`.** Never surface raw internal vocabulary. **P3.6 wrinkle (D-C):** the candidate "show agents / tools / skills / plugins / MCP" views must respect 不暴露 — see D-C.
4. **Partial-turn correctness.** `stage:"turn"`→reconcile via replay, no re-post; `stage:"append"`→safe retry.
5. **No forge attempt.** Send only allowlisted intent; the GUI cannot append events (incl. a `TOOL_CALL`) — only `POST /intent`.

**No new `LLMPurpose`** (the frontend calls no LLM — trivially holds; inscribed per the roadmap §9 watch-list). **No backend / API / gate / executor change** — unless ⭐D-B(c) is ruled in, and then via a *separate backend slice*, not a GUI backdoor.

## Scope (D-A surfaces the boundary; lean below — architect rules the MVP-of-completeness)

**Inventory — what the P3.3 MVP has vs what "completeness" adds** (deferred set = ADR-026 §Scope + handoff §6.4):

| Surface | P3.3 MVP has | P3.6 "completeness" candidate (architect rules in/out) |
|---|---|---|
| Event-stream rendering | all events → flat `MessageItem` (humanized author/type/content) | **type-appropriate rendering** of the 19 types: `tool_call`/`tool_result`/`tool_failed`, `decision`/`rejection`/`retraction`, `escalation`, `summary_snapshot`, `state_transition` — distinct affordances, not all-as-message |
| Autonomy gate decisions | not surfaced | **read-only** surfacing of `tool_calls_pending_confirm` + `autonomy_decision`/`autonomy_refusal` events ("等待确认"/"已拒绝执行" — humanized; **no confirm action** — that's ⭐D-B) |

**Lean (architect rules):** a coherent **view-only completeness set** = {richer event rendering, **read-only** pending-decision surfacing, room-management depth incl. leave/return, the view-only §6.4 patterns, restrained polish}. This keeps P3.6 a clean **frontend-track / backend-authoritative** slice. The architect sets the exact in-set + altitude (all five §6.4 patterns, or a subset).

## Decisions (surface for the architect — do not self-decide; ⭐ = the genuine fork)

**D-A. Completeness boundary (MVP-of-completeness).** Architect rules which rows above are in + the altitude. Lean: the view-only set (above). *Scope decision — architect's, not mine.*

**⭐ D-B. confirm-then-execute — the genuine decision (drives D-D + the track shape).** ADR-027 D6 / ADR-028 HR#1 defer the `COUNTDOWN`/`HARD` "确认后执行" flow as **GUI-coupled**. Three positions:
- **(a) AUTO-only, no surfacing** — status quo; P3.6 ignores pending calls. *(Lean: no — the gate's decisions staying invisible is an obvious completeness gap.)*
- **(b) surface pending calls READ-ONLY** — display `Snapshot.tool_calls_pending_confirm` + `autonomy_decision`/`autonomy_refusal` humanized ("等待确认"). **Pure frontend**: the data is **already on the frozen wire** (no contract change), it's **view-only** (backend-authoritative-safe), **no dual-lens**, folds into D-A. **← architect-partner lean for P3.6.**
- **(c) FULL confirm-then-execute** — the GUI **confirm action** → a backend confirm intent/endpoint **appends the gate-approval `TOOL_CALL`** → the existing executor runs it. **⭐ Critical surfaced nuance: (c) is GUI-coupled but NOT GUI-only.** The GUI **cannot** append a `TOOL_CALL` (that is exactly the forge/decision the spine forbids) — it needs a **new backend intent/endpoint** = **an ADR-025 frozen-contract change + a backend slice + a human-in-the-loop gating-approval trust surface** (idempotency — confirming twice must not double-execute; `COUNTDOWN` timer semantics; partial-turn on the confirm). So (c) **breaks "P3.6 = pure frontend track / no backend change,"** spans both tracks, and warrants **dual-lens + a new ADR** (see D-D).

**Lean: (b) for P3.6; (c) as its own future cross-track slice** if the architect wants the live approval loop now. **This is the call to rule before the senior plans** — it determines whether P3.6 is a frontend-only slice (a/b) or a cross-track build (c).

**D-C. 不暴露 reconciliation for the "show agents / capabilities" views (inscribe + one sub-call).** The candidate "present agent/skill/tool/plugin/MCP" views must pass through the humanization layer:
- **OK to present** (humanizable, already mapped): **agents** (助手 names via `AGENT_NAME_MAP`), **tool activity** (`tool_call`/`tool_result`/`tool_failed` → 工具调用/结果/失败).
- **不暴露** (the `uiStrings.ts` comment already marks these internal-only): **skill**, **state machine**, **autonomy level**, **dissent dimension** — and by extension **plugin** / **MCP-as-infrastructure** (internal distribution/transport vocabulary; the human-facing concept is "工具/能力", not "plugin"/"MCP server").

So "show more" ≠ "expose internal vocabulary." The architect rules **what human-facing projection (if any)** of the roster/capability surface is allowed — and any such view must bind **existing contract data** (surface a contract gap if not; no backdoor).

**D-D. ADR vehicle + `requires_cross_family_review` (downstream of ⭐D-B).**
- If **frontend-track** (D-B = a/b): **amend ADR-026** — its `Scope` already names "the rich §6.4 GUI patterns / `DECISION`/`RETRACTION` UX / theming (P3.6)" as P3.6's territory, so an amendment is the natural vehicle. `requires_cross_family_review: **false**` (view-only frontend, no security face). **← lean.**
- If **D-B = (c)**: a **new ADR** for the confirm/approval flow (it spans ADR-025 contract + ADR-027/028 gating + ADR-026 view — a cross-cutting confirm-flow decision) + `requires_cross_family_review: **true**` (the gating-approval trust surface = the dual-lens criterion, `dual-lens-r0b.md`).

Architect rules, **gated on D-B**. RC-23-safe either way (Proposed; no literal `Accepted` substring until accepted).

**D-E. Frontend gate (constraint — reaffirm, mostly).** Unchanged from ADR-026 D6: `npm run gate` = eslint + prettier --check + `tsc --noEmit` + vitest + **codegen:check**, in `ui/`. No gate change for the frontend-track scope (the codegen:check already covers `tool_calls_pending_confirm` — `schema.ts` is fresh). If D-B(c) adds a confirm intent type, the regenerated `schema.ts` flows through codegen:check automatically. **Test bar stays discriminating** (not "renders something"): each new view tested for the **不暴露 no-raw-leak** invariant + the **read-only / no-forge** invariant; the pending-decision view tested that it **displays-only** (no append, no confirm action under (b)).

## Frontend-track independence (carry forward — roadmap §5)
The `ui/` is a fully separate codebase/toolchain/gate binding **only the frozen contract** — so P3.6 runs **independently of the backend track**, exactly as P3.3 did. **The one exception is ⭐D-B(c):** a confirm flow couples to the backend (a contract change + a gating slice), collapsing the track independence for that feature. (b) preserves it. **Within P3.6:** single-junior serial (one FE codebase) — no within-slice parallelism.

## Constraints (do not violate)
- **The constitutional spine** (view+intent; backend-authoritative; **binds-API-only — no Python/DB backdoor**; 状态机不暴露 incl. the D-C 不暴露 set; partial-turn; no-forge; **no new `LLMPurpose`**).
- **No backend / API / gate / executor change** for the frontend-track scope — if a view needs data the contract lacks, **surface it**; a contract change is a separate decision (and *is* the ⭐D-B(c) fork).
- **Bind the frozen contract** — codegen tracks `openapi.json`; honor `asyncapi.md` exactly; the WS-type conformance + codegen-freshness guards (ADR-026 D2/D6) still apply.
- **Reuse the existing `ui/` patterns** — the store/component/hook shapes + `ui_strings` mapper exist; extend them, don't re-architect (the MVP's `applyEvent` dedup chokepoint, the `useRoomStream`/`useIntent` hooks).
