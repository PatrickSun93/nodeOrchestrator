## Background — what got designed in the previous cycle

P1.3 was the first task to exercise `awaiting_architect_accept` and the override path with a non-self-referential body of work. Two bugs surfaced:

**Sub-finding (a) — task→ADR mapping gap.** ADR-008 was accepted before W-001-impl ran its dogfood, so the dogfood never exercised the `awaiting_architect_accept` → `awaiting_junior_impl` auto-trigger that should fire when an ADR flips from Proposed to Accepted on `origin/main`. The state machine has no `task_id → adr_id` mapping in `TaskState`; `_read_adr_status(task_id, repo_root)` cannot identify which ADR belongs to which task. Workaround during P1.3: architect-partner `workflow override` (cfbf087) with audit-trail reason field.

**Sub-finding (b) — `record_override` cycle-counter bug.** Per ADR-008 Decision 11, `cycle` increments only on rework transitions. The P1.3 override I performed was `awaiting_architect_accept → awaiting_junior_impl` — categorically NOT a rework. Cycle should have stayed 1; it incremented to 2 anyway. The impl in `record_override` increments cycle on every override regardless of from-state semantics.

The P1.3 retro §8 recommendation #4 said: "State machine fixes from W-002 should land before P1.4 starts." This task IS those fixes.

## Architect-settled design decisions

### 1. Sub-finding (a) resolution path — three options, senior picks in plan §5

The P1.3-candidates.md capture surfaced three resolution paths. **Senior picks one in the plan**; architect-partner reviews via R0-A-on-plan if dispatched.

**Path α — Schema extension (preferred long-term):** add `adr_id: str | None = None` to `TaskState` Pydantic model. Plan-publish writes the field when drafting an ADR alongside. `_read_adr_status` consults the field. **Pro:** robust, typed, no markdown parsing. **Con:** schema evolution policy question — RC-6 from P1.2 still open. This would be the first additive field change to `TaskState` and would set precedent for that policy. The schema-evolution-policy intersection is a real ADR question.

**Path β — Plan frontmatter convention:** senior plan declares `adr: ADR-NNN` in YAML frontmatter when applicable; `_read_adr_status` parses the plan markdown to find it. **Pro:** no schema change; cheaper; aligns with the existing "review files have frontmatter" pattern. **Con:** regex / markdown parsing is fragile; senior plans don't currently have a frontmatter contract (only review files do per W-001-impl impl-3).

**Path γ — File-naming convention:** ADR filename includes task-id (e.g., `ADR-009-P1.3-skill-frontmatter-and-loading.md`). `_read_adr_status` parses the directory. **Pro:** no schema or frontmatter changes; "convention as data" is cheap. **Con:** breaks the existing ADR-NNN-slug pattern; would require renaming ADR-009; doesn't scale if a single ADR ever applies to two tasks.

**Architect-partner lean:** path β. The frontmatter pattern already exists (review files have it); extending it to plans is natural; the schema-evolution policy question is harder than this task's scope deserves. **Senior pushes back if α or γ is cleaner.**

If senior picks α, an ADR-010 for the schema-evolution-policy precedent is warranted (per senior-drafts-ADR rule). If β or γ, likely no new ADR needed — convention update to docs + impl + tests.

### 2. Sub-finding (b) resolution — single if-branch fix

The bug fix is narrow: `record_override` checks `from_state == "awaiting_architect_decision"` (or whatever the canonical rework-source state is) before incrementing cycle. Other overrides leave cycle unchanged.

**Test added:** one or two new unit tests in `tests/workflow/test_transitions.py` (or wherever `record_override` is tested) covering:
- Override from `awaiting_architect_decision` → `awaiting_junior_impl` increments cycle.
- Override from any other from-state → any to-state does NOT increment cycle.

No design surface; mechanical fix.

### 3. Sub-finding (c) optional — `verify-workspace` state-file divergence detection

If included, the implementation is:
- For each `.workflow/*.yaml` file locally, fetch the same path from `origin/main` and compare.
- If divergent, print a warning surfacing the divergence (without auto-resolving — divergence is information, not a state-correction signal).
- Exit code stays 0 (warning, not error) — the existing `verify-workspace` semantics warn-don't-block.

**If senior decides this is W-002 scope:** include in plan §3 atomic tasks.
**If senior decides it's W-003 territory:** explicitly defer in plan §2 out-of-scope.

### 4. Optional skills fix — graceful handling of non-skill `.md`

If included:
- `load_skills` skips files where YAML frontmatter parse fails OR returns non-dict.
- Logs at debug level (no stdout pollution).
- Does NOT raise `SkillFrontmatterError` for non-skill `.md` files.
- A real malformed skill (frontmatter present but invalid schema per Pydantic) still raises — the distinction is "no frontmatter at all" vs. "broken frontmatter."

**If included:** one test in `tests/skills/test_loader.py` adds a `config/skills/` fixture with a README.md and asserts it's skipped without raising. Sample skills still load correctly alongside.

**If excluded:** the constraint remains documented (P1.3 retro §5.2); future P1.4+ work can surface it again if relevant.
