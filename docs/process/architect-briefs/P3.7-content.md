**Subject:** Build P3.7-content — take the product to **完整 breadth** by adding **more agents, room templates, skills, local (stdio) MCP connectors, and local (Posture-A) plugins** on the **existing** loaders/registries. Every surface here already has a settled shape and a loader (P3.1/P3.4/P3.5); this slice is **additive content + established-pattern code**, the P3.1 class of work — *not* new infrastructure and *not* a new trust surface. (All remote/heavy-security work — Posture B subprocess isolation, remote MCP transport — is the **sibling slice P3.7-remote**, deliberately split out.)

## What this binds (the frozen substrate — reuse, don't reshape)

Each added unit slots into an existing loader, gated/allowlisted exactly as today:
- **agents** → `config/agents/*.yaml` (the ADR-024 role shape; activation stays **code** `should_agent_speak`; responses stay content-gen `AGENT_RESPONSE`);
- **skills** → `config/skills/{engineering,general}/*.md` (the ADR-009 frontmatter + loader);
- **room templates / rosters** → `rooms/templates.py` `ROOM_TEMPLATES` (the P3.1 shape);
- **local connectors** → `config/mcp_servers.yaml` stdio entries (the ADR-027 D3 pre-classify-allowlist — each tool a code-classified `ToolMeta`);
- **local plugins** → `plugins/<id>/` Posture-A bundles (the ADR-029 manifest + fail-closed loader).

If any added unit needs a loader/schema change → **surface it** (that would be a contract decision, possibly a different slice); content does not reshape the loaders.

## Constitutional carry-forward (NON-NEGOTIABLE — inscribe, not chosen; trivially held for content)

The roadmap §9 watch-list, all satisfied by construction for pure content:
1. **Routing = code.** A new agent/role/skill/connector/plugin brings **no** LLM routing/judgment decision; model-selection stays the code router + the P2.7 Layer-4 override; **no new routing/judgment `LLMPurpose`**.
2. **The gate stays the sole chokepoint.** A new local connector's / plugin's tools route through the **existing** code autonomy gate (classified → tier; unclassified → `UnknownToolError` → refused). Self-asserted reversibility is advisory-capped → host-authoritative-or-default-0 (ADR-027 HR#2 / ADR-029 D5).
3. **Local-only trust posture unchanged.** Connectors are stdio (user-launched); plugins are Posture-A operator-placed (presence = opt-in, curation IS trust — valid *because* it stays local). **Nothing here weakens that** — the moment provenance goes remote, it's the sibling P3.7-remote, not this slice.
4. **Backend-authoritative.** Content adds no GUI decision surface; the frontend remains a view.

## Scope
**In:** more **agents** (beyond the 6) + their **roster** placements in the room templates; more **skills** (beyond the 2); more **room templates** if warranted; more **local stdio MCP connectors** (each with its code-classified tool allowlist); more **local Posture-A plugins** — all reusing the frozen loaders, all gated/allowlisted as today; the **discriminating tests** each surface already has (a new agent activates via code; a new connector's unclassified tool is refused; a new plugin fails-closed on collision/bad-manifest).

**Out (defer):**
- **Anything remote** — remote MCP transport, Posture B subprocess isolation, fetched/registry plugins → **P3.7-remote** (the sibling slice).
- **The deferred local *tools*** (ADR-028 D3 — network `web_*` / subprocess `run_*`/`git_*` / mutation `*_edit`/`send_email`) → **each is its own trust-surfaced slice** (network trust / subprocess c2-env-leak / mutation tier), **not** lumped into "content" (§b). (Note: ADR-030 confirm-then-execute is now live, so mutation-tier tools *are* runnable post-confirm — but their trust-surface review is still per-slice, not here.)
- Any loader/schema/gate change (content **feeds** the registries; it doesn't reshape them).

## Decisions (surface for the architect — do not self-decide)

**(a) Breadth target — how much, and which domains?** How many more agents / skills / templates / local connectors / local plugins, and for which domains? **Lean:** round out the **existing room types' rosters + per-domain skill coverage** (a coherent "the 5 room types each have a credible agent+skill set" target) + 1–2 more local connectors/plugins to show breadth — *not* an open-ended content dump. *Scope/quantity is the architect's call.*

**(b) Are the deferred local *tools* in scope here?** ADR-028 D3 deferred network/subprocess/mutation tools, each "its own slice + classification review." **Lean: NO** — keep them out of "content"; each distinct tool trust-surface (network / subprocess / mutation) earns its own slice. Architect rules (if any are wanted now, that's a scope addition with its own classification review — arguably even part of P3.7-remote's heavier track, not this light one).

**(c) dual-lens R0-B? — the architect-asked evaluation. Lean: NO (single-lens R0-A).** Checking `dual-lens-r0b.md`'s 4 criteria — **zero hold**: (1) no new concurrency surface (load-time content); (2) no new cross-package layering edge (reuses existing loaders/merge points); (3) no new contract ≥5 future tasks bind (the manifest/connector contracts were *already* inscribed + bound in ADR-027/029 — content *consumes* them, adds none); (4) no first-runtime-exercise of a new pattern (every pattern is battle-tested in P3.1/P3.4/P3.5). This is **pattern-reuse, not novel design** — the explicit `dual-lens-r0b.md` skip case. So: **single-lens R0-A** (architect-partner — spine carry-forward + the discriminating per-surface tests). Architect confirms.

**(d) ADR vehicle? Lean: none / trivial.** Content reuses ADR-024 (role) / ADR-009 (skill) / ADR-027 (connector) / ADR-029 (plugin) — **no new architectural decision**. If a genuinely-new *role type* or *content pattern* with a contract emerges, surface it for a light ADR; otherwise **no ADR** (or a one-line note). Architect confirms.
