**Subject:** Implement P1.3 — **Skill loader**. Read `SKILL.md` files from `config/skills/` and provide a code-driven loading mechanism (which skills load for which agent / room / room-state). Per `handoff.md` §3.1 ("decision paths in code, LLMs generate content"), **the decision of which skills to load is code, not LLM-judgment**. The skill content itself (the markdown body) is LLM-consumed.

## Scope

**In scope (P1.3):**

- Define the `Skill` data structure: id, path, frontmatter metadata, body text.
- Implement `load_skills(directory: Path) -> dict[str, Skill]` — file-system scan of `config/skills/**/*.md`, frontmatter parse, body load. Pure-function loader; no I/O beyond reading the file system.
- Implement the **loading decision function** `decide_skills_for_context(...) -> list[Skill]` — takes (agent_id, room_type, room_state, optional event-type triggers) and returns the ordered subset of skills that should be in the agent's context window. Pure function; no LLM.
- Constitutional test analogous to autonomy / workflow modules: `test_constitution_no_llm_calls_in_skills_module`.
- Tests covering: skill discovery (including the `general/`, `engineering/`, `business/` subfolders from `handoff.md` §5.3); frontmatter parsing (id, applies-to fields per the skill spec to be drafted); the decision function across the 5 room-template scenarios.
- Skill SKILL.md frontmatter spec — what fields a SKILL.md must declare for the loader to consume it. Locked here as ADR-009 if needed (see Architect-settled design decisions below).
- 1-2 example `config/skills/general/*.md` files exercising the full schema, used by tests.

**Out of scope:**

- Loading skills into actual agent context windows (P1.4 agent runtime).
- Skill versioning / hash / etag (P2+).
- User-authored skill discovery beyond `config/skills/` (plugin system; P3).
- Cross-skill dependencies (one skill imports another) — P1.4+ if needed.
- LLM-readable skill format optimization (e.g., token budget pre-computation) — P2.
- The full 10 skills listed in `handoff.md` §5.3. **Land 1-2 sample skills demonstrating the format**; the full library is a separate content task downstream.

## Architect-settled design decisions

### 1. Skill format: SKILL.md with YAML frontmatter

Per `handoff.md` §3.3 ("Skills compatible with industry standard SKILL.md format"). The frontmatter declares loading-time metadata; the body is the LLM-readable instruction text.

**Senior decides the exact frontmatter schema in plan/ADR**. Architect-partner lean (open to senior pushback):

```yaml
---
id: research-decomposition           # unique within config/skills/
category: general                    # general | engineering | business
applies_to:
  agents: [prober, skeptic]          # which agents may receive this skill
  room_types: [research, idea_validation]  # which room types trigger consideration
  room_states: []                    # empty = all states; else specific states
priority: 50                         # ordering signal when multiple skills match
---

# Research decomposition

(markdown body — the actual skill instruction text consumed by the LLM)
```

Frontmatter fields are the **routing-decision substrate**; the loader reads them, the decision function matches them against agent + room context. **No LLM-judgment in matching** (Principle 11).

### 2. Loading decision is code, not LLM (handoff §3.1)

The function signature (illustrative; senior pins exact shape):

```python
def decide_skills_for_context(
    agent_id: str,
    room_type: RoomType,
    room_state: str,
    *,
    available_skills: dict[str, Skill],
    triggering_event_type: EventType | None = None,
) -> list[Skill]:
    """Pure function. Returns the ordered subset of `available_skills`
    whose frontmatter `applies_to` matches the given context. Order
    is by `priority` (higher = earlier). No LLM call. No I/O."""
```

The constitutional test forbids LLM imports in the entire `src/orchestrator/skills/` module.

## Constraints (do not violate)

- **No LLM imports in `src/orchestrator/skills/` module.** Constitutional test enforces. Skill content (markdown body) is LLM-consumed; loading and matching are code.
- **`decide_skills_for_context` returns a `decision_trace` analogue.** Per `contributing.md` Q2: any routing/gating/selection function returns enough information to explain *why* it selected what it did. For skills: which `applies_to` predicates matched. Senior decides exact trace shape.
- **Layering:** `orchestrator.skills` may import from `orchestrator.core` (`EventType`, `RoomType`, etc.) — **first such edge for skills**. Reverse direction (`core → skills`) forbidden per the same pattern as `core → autonomy` (locked by constitutional test in W-001-impl).
- **State-file dogfood:** every transition advances `.workflow/P1.3.yaml` per ADR-008 Decision 1.

## Places I expect you to push back

Address each in your plan §5:

- **Frontmatter schema specifics:** is `applies_to.agents` a list or a glob (`["*"]` for "all agents")? Is `priority` an int or a Literal of strings? Architect-partner has zero strong preference; senior picks based on extensibility cost.
- **ADR-009 yes/no:** see decision 3 above. Senior judgment.
- **Sample skills count:** brief says 1-2; senior may push back for more (e.g., 3-4 to exercise more matching scenarios) or fewer (e.g., 1 as proof of concept). Defend in plan.
- **Empty `applies_to.room_states` semantics:** lean is "empty = all states." Senior may prefer explicit `["*"]` or omitting the key entirely. Pick a default that matches Pydantic's natural shape.
- **Skill priority tie-breaking:** when two skills have the same priority, what's the deterministic order? Lean: alphabetical by `id`. Senior may prefer file-system order or undefined-with-test-that-explicit-order-is-set-when-it-matters.
- **Cross-file skill references:** out of scope per brief; but if senior reads the architecture and sees that a future skill might need to reference another skill (e.g., "use the assumption-audit workflow"), surface as a P1.4+ design question, don't try to solve in P1.3.
