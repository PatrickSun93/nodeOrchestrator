## RC-26 — `record_preference` upsert is a non-atomic read-modify-write (future-concurrency debt)

**Surfaced:** 2026-06-01, at P2.4 impl-stage routing (R0-A Y2 → β). Surface only — **deferred, not a fix this cycle** (architect routing: Y2 → β).

**Routing:** product (`src/orchestrator/memory/entity.py`). Future-concurrency retro candidate — revisit when a multi-connection surface arrives. NOT bundled into P2.4 (architect-deferral literal-reading: the defer is substantive; `record_preference` is untouched this cycle).

**Observation (architect's capture):** P2.4 R0-A Y2 — `record_preference` upsert is non-atomic read-modify-write + overwrites `created_at` on update; single-connection-safe today, revisit when a concurrency surface arrives (mirror R0-B G7a clearance).

**Detail:** the existence-`SELECT` (`entity.py:132–141`) sits **outside** the `with conn:` block; only the subsequent `UPDATE`/`INSERT` is transactional, and there is no DB-level `UNIQUE` backstop (the preference key lives inside the `attributes` JSON blob, so SQLite can't enforce a column constraint). Under the current single-connection sequential dispatch (ADR-011 D1) this is correct — two concurrent same-`(user_id, key, scope)` calls cannot interleave. Under a **future multi-connection surface**, both calls could `SELECT`-miss and both `INSERT`, duplicating a row the upsert is meant to keep singular (breaking ADR-020 D2's "exactly one row per `(user_id, key, scope)`"). Separately, the `UPDATE` sets `created_at = ts` (`entity.py:146`), so a re-declaration overwrites the original creation time — the field reads as "last-declared-at" after an upsert.

**Why it's a candidate, not a cycle fix:** **two independent lenses agree** it does not manifest today. R0-A Y2 tagged it 🟡-routable; R0-B **G7a** traced the same non-atomic read-modify-write and cleared it 🟢 ("correct under single-connection; a multi-connection future would need `SELECT … FOR UPDATE` or a `UNIQUE` constraint"). The architect routed **β (defer)** — the fix has no current-correctness value and the trigger (multi-connection access) does not yet exist.

**Candidate remedies (deferred — revisit at the concurrency surface):**
- **(a)** Wrap the `SELECT` + write in one transaction (`BEGIN IMMEDIATE`) so the read-modify-write is atomic per connection.
- **(b)** A real uniqueness mechanism — a materialized `(user_id, key, scope)` projection (e.g. a generated/normalized column) with a `UNIQUE` index + `INSERT … ON CONFLICT DO UPDATE`, which also closes the multi-connection race SQLite can't guard on a JSON field.
- **(c)** Decide `created_at`-on-upsert intent: preserve the original `created_at` and add a `last_declared_at` field, or rename intent in the docstring.

**Trigger to revisit:** the first task that introduces multi-connection / concurrent access to the memory store (none today; ADR-011 D1 is sequential).
