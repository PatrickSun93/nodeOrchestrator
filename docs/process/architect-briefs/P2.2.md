**Subject:** Implement P2.2 — the **cross-room hypothesis matcher (promotion rule (a))**: detect when the same claim (same canonical tag-set) is independently recorded across ≥N distinct rooms, and flip `Hypothesis.candidate_for_promotion = True` on those rows so the user is *shown* cross-room-corroborated candidates to (manually) promote. **Advisory only** — the matcher never promotes; `promote_hypothesis` (P1.6.5) remains the sole promotion path. This is the first cross-room memory *intelligence* surface, riding on the P2.1 registry.

## The rebase — what the merged registry changed (read this before reusing anything from the old plan)

The old matcher plan/ADR-017 (`58452bc`) was written **before** the registry existed and bundled the tag-vocabulary work. The registry (P2.1, now merged) shipped that. So:

1. **`Hypothesis.topic_tags` already exists** (`schema.py:94`, frozen + `extra="forbid"`) — and the `topic_tags TEXT NOT NULL DEFAULT '[]'` column + the `_ensure_hypothesis_topic_tags` ALTER migration are **on main** (`store.py`). **DROP the old plan's P2.1-2 atomic entirely** — there is no schema add, no ALTER migration to write. (Verified on `origin/main`.)
2. **`normalize_tag` exists** (`memory/tags.py`, `strip→lower→re.sub(r"\s+","-")`). The old ADR-017 D3 grouped on ad-hoc `frozenset(t.lower() for t in tags)`. **The matcher MUST reuse `normalize_tag`, not reinvent `.lower()`** — otherwise its canonical form silently diverges from the registry's (e.g. whitespace handling), and the matcher would group differently than the vocabulary the tags were registered under. This is the central rebase point.
3. **Stored Hypothesis tags are already canonical.** `record_hypothesis` now routes `topic_tags` through `resolve_tags` (canonical at write); pre-registry rows backfilled to `[]`. So in practice the matcher reads canonical-or-empty tags. This creates a real design fork (push-back #1): group on stored tags as-is (trusting write-time canonicalization) vs. re-normalize at read (defense-in-depth, mirroring the lookup Y1→α both-sides decision). **Lean: re-normalize at read** — cheap, and robust against any raw-tag insert path (tests, future bulk import) exactly as `lookup` chose both-sides.
4. **The matcher does NOT register tags.** It reads + groups + flags. No `resolve_tags` call, no registry write. Tags were registered at record-time. (The matcher's only write is the `candidate_for_promotion` UPDATE.)
5. **`candidate_for_promotion` column + `idx_hypothesis_status_candidate` index** are on main, still unused — the matcher activates them (its write target + the reader's index). (Verified.)

Everything else from the old ADR-017 (the predicate, distinct-room threshold, advisory-only orthogonality, determinism/idempotency/monotonicity, the reader, the new-ADR-vs-amend reasoning) **carries over** and was already architect-steered — reuse it.

## Scope

Pure code, no LLM. Deterministic, idempotent, monotonic (False→True only).

## Architect-settled decisions (carried from the steered old design + the rebase)

1. **Structural / code matching, reusing `normalize_tag`** — the grouping key is `frozenset(normalize_tag(t) for t in topic_tags)`, using the registry's function (NOT ad-hoc `.lower()`). No LLM in `memory/`.
2. **Advisory-only** — `run_matcher` flips `candidate_for_promotion`; never promotes, never gates `promote_hypothesis`. ADR-016 D3/D10 preserved. No canonical event on flag.
3. **N = ≥2 distinct rooms** (`min_rooms` param, default 2; distinct = distinct `room_id`; `min_rooms < 1` raises `ValueError`).
4. **Explicit on-demand batch trigger** `run_matcher(conn)` — not auto-on-record (mirrors `lookup`/`promote`/registry explicit-API pattern).
5. **Monotonic** (False→True only); idempotent; deterministic (stable regardless of SQLite scan order).
6. **Ship the reader** `list_promotion_candidates` so the flag is consumable end-to-end.
7. **Fresh ADR-017** (reserved number), Proposed → architect-accept gate. Inherits ADR-018's schema/migration (does not re-decide it).

## Constraints (do not violate)

- **No LLM in `memory/`** (`handoff.md` §3.1; `tests/memory/test_constitution.py` rglob covers `matcher.py`).
- **Reuse `normalize_tag`** — do not reinvent normalization; the matcher's canonical form must equal the registry's, or grouping diverges from the stored vocabulary.
- **No auto-promote** (ADR-016 D10): the matcher must not create a VK row or emit a promotion `decision` event. Orthogonality is load-bearing — e2e + the structural guard assert it.
- **Determinism** (Principle 11): same hypothesis set → same flagged set regardless of row/scan order. Sort before grouping; deterministic test (assert flag-set stable across shuffled input — note this is *correctness-by-construction* via set operations, the sort is for stable reporting; state which the test asserts).
- **Dependency direction** unchanged: `matcher.py` in `memory/`, imports `core/` + `memory/` (incl. `tags.normalize_tag`); `core/` MUST NOT import `memory/`. No new cross-package edge.
- **⚠️ RC-23** — when ADR-017 references ADR-016/ADR-018 status, **do not write the literal `Status: Accepted` / `Status: Proposed` substring in prose** (paraphrase: "ADR-018 is already accepted"). `_parse_adr_status` whole-file-scans; a quoted status line auto-passes ADR-017's own accept-gate while Proposed. Verify: `grep -i "status:.*\(accepted\|proposed\)" ADR-017` matches only ADR-017's own status line. (The registry's ADR-018 heeded this; do the same.)

Carried from the old ADR-017; confirm it still holds post-rebase. Lean: keep exact-equality; relaxation is a forward hook.

## RC-15 dual-lens R0-B dispatch recommendation

**Lean: DISPATCH dual-lens R0-B** (cross-family) — a genuine architect call, with the honest split below.

**Mechanical RC-15 read (leans NOT):** of the four criteria — (1) new concurrency/transaction surface: **no** (a single batched flag UPDATE, no multi-write atomic transaction like promotion); (2) new cross-package layering edge: **no** (matcher in `memory/`, imports `core/` + `memory/tags`); (3) contract referenced by ≥5 future tasks: **yes** (ADR-017 governs the matcher every downstream memory-intelligence + UI promotion-candidate surface relies on); (4) runtime/transaction-heavy / failure-mode-rich: **no** (read-scan + flag). That's ~1.5 of 4 — mechanically *below* the ≥3 bar, i.e. proxy-only / single-lens would be the default.

**Why I lean DISPATCH anyway (two reasons that override the mechanical read):**
- **(a) First cross-room *decision function*.** The matcher is the first piece of code that makes a cross-room determination (corroboration across rooms). Its correctness lives in subtle invariants — the partition/equivalence-relation property, the distinct-room (not distinct-row) count, determinism under scan-order, idempotency, monotonicity, and the `normalize_tag`-reuse equivalence. These are exactly the "trace the actual execution, not what the plan says" properties a cross-family lens checks well — and they're load-bearing for *every* downstream consumer of rule (a).
- **(b) Fresh, direct evidence from THIS task family.** The P2.1 R0-B (cross-family, deepseek) just **caught my R0-A false positive** — a finding that described a code path that didn't exist, resting on a probe that never executed. That is the RC-20 "correction mode" (cross-family corrects an in-family error, not just adds net-new), and it landed on the *immediately adjacent* slice. On a cycle where the in-family reviewer (me) recently made an empirical-claim error, a second lens is cheap insurance.

**The honest counter** (so you can rule against the lean): the matcher genuinely is low-runtime-surface, and RC-20's own observation is that external net-new co-varies with runtime surface — a low-runtime cycle may show high proxy/external overlap (external adds little). So a defensible lighter path is **proxy-only R0-B** (in-session contrarian Claude), reserving the external dispatch cost. If you take that, I'd still want the proxy lens to specifically trace determinism + the distinct-room count + the `normalize_tag` equivalence.

**My net:** DISPATCH dual-lens — the decision-function-correctness + the just-demonstrated correction-mode value outweigh the low mechanical surface. `requires_cross_family_review` left **false** in the bootstrap; flip to true if you accept the dispatch. **Your call.**
