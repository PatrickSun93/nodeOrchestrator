# Senior plan → P3.6: GUI completeness + confirm-then-execute (cross-track, D-B=(c))

## 1. Context

The architect ruled **⭐D-B = (c) full confirm-then-execute**. P3.6 is therefore **not** a frontend-only slice: it spans both tracks. The frontend half (D-A) extends the read-mostly P3.3 MVP to a **view-only completeness set** — richer per-type event rendering, read-only pending-decision presentation, room-management depth incl. leave/return symmetry, the view-only §6.4 patterns, restrained polish. The backend half (D-B=(c)) adds the **live gating-approval loop** the MVP deferred (ADR-027 D6 / ADR-028 D1): a GUI confirm → a **new backend confirm endpoint** validates a persisted pending call and appends the gate-approval `TOOL_CALL` → the **existing** executor (ADR-028) runs it. This is inscribed in **ADR-030** (Proposed, this cycle), which binds ADR-025 (contract change) + ADR-027/028 (gating/executor) + ADR-026 (view).

**The load-bearing finding (drives the whole backend half — see §5 push-back).** The brief frames (c) as "a new endpoint over data already on the frozen wire (`Snapshot.tool_calls_pending_confirm`)." **Against the live code that premise does not hold:** `process_tool_calls` appends a `TOOL_CALL` event **only** for `AUTO_EXECUTE` (`tool_dispatch.py:100,105` — the **sole** `TOOL_CALL` appender in `src/`, verified by grep), so the countdown/hard branch persists **nothing**, and the snapshot's correlate-`TOOL_CALL`-with-AD derivation (`snapshot.py:157-190`) makes `tool_calls_pending_confirm` **structurally empty in the running app**. The `AUTONOMY_DECISION` event that *is* appended (`emission.py:86-108`) carries `operation_tool_id`+`tier` but **not** `call_id` or `params`. So a pending gated call is **not confirmable from existing events** — (c) necessarily requires persisting the pending call's full payload at gate time. ADR-030 D1 resolves this with a new `TOOL_CALL_PENDING` event; this is a **recording** addition to the dispatch path, **not** a change to the gate's decision logic (`score`/`decide_tier`/`emit_gate_decision` stay untouched, per the architect's constraint). The whole backend atomic graph follows from this.

Constraints honored throughout: backend-authoritative (the GUI never forges a `TOOL_CALL` — it sends only `{pending_event_id, approve|cancel}`; the server reconstructs from the persisted record); idempotency (double-confirm never double-executes); no new `LLMPurpose`; 不暴露 (D-C); single-junior serial, no within-slice parallelism (one FE codebase + a sequential BE→FE contract dependency).

## 2. Tasks (atomic; six-field)

### Backend track (B1 → B2 → B3, sequential; must precede the FE confirm action)

---

**P3.6-B1 — Persist a `TOOL_CALL_PENDING` record on countdown/hard gating.**
- **What:** add `EventType.TOOL_CALL_PENDING` + `ToolCallPendingMeta{tool_name, call_id, params, tier, initiating_agent}` (frozen, `extra="forbid"`) to `core/event.py`; in `process_tool_calls`, the `COUNTDOWN_CONFIRM`/`HARD_CONFIRM` branch (today persists nothing) appends one `TOOL_CALL_PENDING` event. The `AUTO_EXECUTE` branch stays byte-for-byte unchanged.
- **Where:** `src/orchestrator/core/event.py` (new EventType + meta), `src/orchestrator/agents/tool_dispatch.py:125-134` (the else branch), `tests/agents/test_tool_dispatch.py`, `tests/core/` (meta validation), the EventType-exhaustiveness/metadata constitutional tests.
- **Why:** ADR-030 D1 (the representation fix). Without a persisted full-payload record there is nothing for the confirm endpoint to validate or reconstruct (§1 finding).
- **Acceptance:**
  - a countdown/hard tool call → exactly one `TOOL_CALL_PENDING` event with `{tool_name, call_id, params, tier, initiating_agent}` matching the `ToolCall` + the gate tier; **no `TOOL_CALL`** appended.
  - an `AUTO_EXECUTE` call → unchanged (a `TOOL_CALL`, **no** `TOOL_CALL_PENDING`); a test asserts `EventType.TOOL_CALL` still has exactly one appender (the AUTO branch) — ADR-028 D6 t4 preserved.
  - `emit_gate_decision`/`score`/`decide_tier` untouched (the gate decision-logic diff is empty; assert the `AUTONOMY_DECISION` shape is unchanged).
  - the metadata round-trips through `validate_metadata`; the EventType-exhaustiveness constitutional test covers the new type.
- **Out of scope:** the confirm endpoint (B3); snapshot derivation (B2); the executor (unchanged — it must NOT treat `TOOL_CALL_PENDING` as executable; assert it ignores the new type).

---

**P3.6-B2 — Re-point `tool_calls_pending_confirm` onto `TOOL_CALL_PENDING`.**
- **What:** change `derived/snapshot.py` D2.3 so `tool_calls_pending_confirm` lists each `TOOL_CALL_PENDING` whose `call_id` has **no** later resolving event (`TOOL_CALL` / `TOOL_RESULT` / `TOOL_FAILED` / `TOOL_CALL_CANCELLED`). `ToolCallRef` keeps its shape; `event_id` now points at the `TOOL_CALL_PENDING` (the confirm handle); `autonomy_tier` is sourced from the record's `tier`.
- **Where:** `src/orchestrator/derived/snapshot.py:157-190`, `tests/derived/test_snapshot.py`, `docs/decisions/ADR-014-*` (amendment note — the re-pointed predicate).
- **Why:** ADR-030 D2 — fixes the structurally-empty field so the GUI has a live, authoritative pending set; the "unknown" anomaly tier disappears (tier is carried explicitly).
- **Acceptance:**
  - a room with one un-confirmed countdown call → `tool_calls_pending_confirm` has one `ToolCallRef{event_id=<pending event>, tool_name, autonomy_tier="countdown_confirm"}`.
  - once that call is confirmed (a `TOOL_CALL`/result appears for the `call_id`) or cancelled → it drops out of the list.
  - an `AUTO_EXECUTE`-only room → the list is empty (no regression vs today's behavior).
  - the snapshot stays a pure function (no I/O); the derived-module constitutional test holds.
- **Out of scope:** the cancel event's producer (B3); any GUI.

---

**P3.6-B3 — The confirm endpoint `POST /rooms/{room_id}/confirm` + wire types + executor wiring.**
- **What:** add `ConfirmRequest{pending_event_id, decision: "approve"|"cancel"}`, `ConfirmResponse{appended_event, turn_events}`, `ConfirmError{stage, appended_event_id, reason}` to `api/wire.py`; regenerate `openapi.json`. Add the handler in `app.py` (on the **writer** executor — check→append→execute atomic): validate the pending record exists / right room / **still-pending** (idempotency layer 1) → on `cancel` append `TOOL_CALL_CANCELLED`; on `approve` append an `agent:<initiating_agent>`-authored `TOOL_CALL` (reconstructed from the record) + a `DECISION` recording the human approval, then call the **existing** `execute_pending_tool_calls` (idempotency layer 2 = its `call_id` guard) and publish via the bus. Partial-turn envelope (D5). Optional asyncapi.md note for confirm errors over WS.
- **Where:** `src/orchestrator/api/wire.py`, `src/orchestrator/api/app.py` (new route + exception handlers mirroring `_post_intent`/`_AppendFailedError`/`_TurnFailedError`), `src/orchestrator/api/openapi.json` (regenerated), `src/orchestrator/api/asyncapi.md`, `core/event.py` (`TOOL_CALL_CANCELLED` type + meta if new), `tests/api/`.
- **Why:** ADR-030 D3/D5 + HR#1-3 — the human-approval entry that produces the gate-approved `TOOL_CALL`; the existing executor runs it unchanged.
- **Acceptance:**
  - **happy path:** approve a pending call → one `agent:<id>`-authored `TOOL_CALL` (params from the record) → executor runs it → `TOOL_RESULT`; `ConfirmResponse.turn_events` contains them; the events publish to subscribers.
  - **idempotency:** a second approve of the same `pending_event_id` → **no** second `TOOL_CALL`, **no** double-execute (validated reject, `stage:"append"`, reason `already_resolved`). A test races two confirms (sequential on the single writer) and asserts exactly one `TOOL_CALL`/`TOOL_RESULT`.
  - **cancel:** `decision:"cancel"` → a `TOOL_CALL_CANCELLED`, **no** `TOOL_CALL`, no execution; the call drops from the snapshot pending set; a later approve of the same id → `already_resolved`.
  - **backend-authoritative / no-forge:** `tool_name`/`params`/`author` come from the persisted record; a `ConfirmRequest` carrying extra fields → `422` (`extra="forbid"`); a forged/unknown `pending_event_id`, a confirm on a closed/transitioned room, or a non-`TOOL_CALL_PENDING` target → fail closed (`stage:"append"`).
  - **partial-turn:** executor raises after the `TOOL_CALL` appended → `ConfirmError{stage:"execute", appended_event_id=<tool_call id>}` (do-not-re-confirm); pre-append failure → `stage:"append"` (safe retry).
  - the gate (`score`/`decide_tier`/`emit_gate_decision`) and the executor (`execute_pending_tool_calls`) are **not modified** (assert via the existing constitutional tests + an import/diff check).
  - `openapi.json` regenerated + committed (the frontend codegen source).
- **Out of scope:** auto-fire-on-timer (ADR-030 D4 deferred); agent re-dispatch on the result (ADR-028 D4); any GUI.

## 3. Execution order

```
B1 ─→ B2 ─→ B3 ─(contract lands; openapi.json committed)─→ F1 ─→ F2 ─→ F3 ─→ F4 ─→ F5
```

- **Backend sequential:** B1 (the pending record) → B2 (snapshot surfaces it) → B3 (the endpoint reconstructs + executes). Each its own atomic commit (`P3.6-B1: …`, etc.).
- **B3 gates the FE confirm action:** F1/F2 bind the new contract (codegen needs the committed `openapi.json`). The non-confirm FE views (F3/F4/F5) don't depend on the backend and could in principle precede it, **but** per the brief's **single-junior-serial** constraint (one FE codebase; no within-slice parallelism) they run sequentially after F1/F2. **No parallel-agent dispatch** this slice (the brief rules it out).
- One atomic = one commit, one subject (RC-17).

## 5. Where you'd push back

1. **The brief's `tool_calls_pending_confirm` premise is wrong against the live code — and this is the central design fact, not a nit.** The brief (and ADR-027/028's deferral prose) treat the field as "the read-only handle, already on the frozen wire." It is **structurally empty** in the running app: `TOOL_CALL`'s sole appender is the AUTO branch (`tool_dispatch.py:105`, grep-verified), so no countdown/hard `TOOL_CALL` ever exists for the snapshot to correlate, and the `AUTONOMY_DECISION` that *is* emitted lacks `call_id`+`params`. **Therefore (c) cannot be "a new endpoint over existing data"** — it requires persisting the pending call's full payload at gate time (ADR-030 D1, the new `TOOL_CALL_PENDING` event). I've drafted the plan + ADR around this (the minimal recording-only change; gate decision logic untouched), because it's the only way (c) is implementable and it respects the architect's "don't change `score`/`decide_tier`/`emit_gate_decision`" constraint. **Architect: please confirm** you're ratifying (a) the `TOOL_CALL_PENDING` recording addition to `process_tool_calls`'s countdown/hard branch (a narrow amendment to ADR-027 D2 / ADR-028's "process_tool_calls unchanged" claim — decision logic still untouched) and (b) the snapshot re-point (ADR-014 amendment). If instead you intended (c) to be implementable without any dispatch-path change, that is **not possible** given the current representation — surfacing rather than improvising.

2. **COUNTDOWN semantics — I designed explicit-confirm-MVP, auto-fire deferred (ADR-030 D4); confirm or override.** The brief asked the senior to *design* whether `COUNTDOWN_CONFIRM` auto-executes-in-window-unless-cancelled or requires explicit confirm. My call: **both tiers require explicit human approval; the tier is affordance only (countdown=low-friction, hard=high-friction); nothing auto-fires server-side.** Rationale: auto-fire needs a **durable backend scheduler** + a **headless-execution** posture (a gated op runs with no human in the loop) — a new concurrency/durability surface and the opposite of the trust surface we're building. The architect may rule auto-fire **in**, which pulls in a separate durable-timer slice (out of this P3.6). Flagging because it's a genuine design fork the brief left to me but that reshapes the trust surface.

3. **The `TOOL_CALL` appended on approve is `agent:<initiating_agent>`-authored, not `user`-authored (ADR-030 D3).** This broadens "agent events only arise from `run_turn`/`dispatch_turn`" (ADR-025 D4 prose) to a second backend origin (the confirm endpoint). The forge invariant still holds (the client never authors it; the server reconstructs from the persisted record). Inscribed in ADR-030 D3; flagging the broadening explicitly so the dual-lens reads a deliberate boundary, not an oversight.

4. **Plan length exceeds the brief's ~1200–1800-word frontend-only estimate.** That budget assumed (a/b) frontend-only; (c) is a cross-track build (a contract change + a dispatch-path record + a GUI trust surface). The added length is the backend half + the surfaced representation gap, not over-explanation. If you want the FE completeness (D-A) split into its own follow-up slice and P3.6 narrowed to the confirm loop, say so — the atomic graph already separates the BE (B1-B3) and FE (F1-F5) cleanly.
