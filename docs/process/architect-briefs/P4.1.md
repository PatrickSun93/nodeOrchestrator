**Subject:** Build P4.1 — (**B1**) an **agent turn-loop**: feed a turn's tool results back to the agent **within the same turn** so it can investigate → read-result → act → re-investigate, with an **inscribed, terminating loop bound** and a **bounded single-writer liveness cost**; and (**B2**) the **read-only code-intel local tools** (`search_text`/`search_code`/`find_references`/`find_definition`, + the in-or-out `log_event`) so an agent has something to chain. Together these make the flagship **bug-fix / code-review** scenario (handoff §toolset 第一/二层: `read_file` → `search_text` → `find_references` → … → re-investigate) **actually run** — today a tool result never feeds back in-turn, so multi-step investigation is impossible (ADR-028 D4). This is P4's **lowest-new-trust opener**: read-only + a bounded loop need **no sandbox-beyond-existing, no auth, no subprocess, no network** (P4-roadmap §7).

## The foundation P4.1 completes (verified — what's missing, precisely)

The executor runs tools but the loop is open at one end: `execute_pending_tool_calls` appends `TOOL_RESULT`/`TOOL_FAILED`/`OBSERVATION` and **returns** — the agent reacts only on the *next* real turn's snapshot (ADR-028 D4's no-re-dispatch MVP). So an agent **cannot** do "read file → see contents → now search for the symbol I found → see hits → open the reference" inside one turn. B1 closes that loop. B2 gives the loop read-only code-intel to chain (the 4 tools are classified-AUTO already; they just have no impl). **The whole value of B1 is unlocked only with B2 present** — a turn-loop with nothing to investigate is inert; read-only tools with no re-dispatch can't be chained. Hence one slice.

## ⭐⭐ Constitutional carry-forward (NON-NEGOTIABLE — inscribe in ADR-033/028; **not** decisions)

Per P4-roadmap §10 + the ADR-028/011 spine. The senior inscribes; the impl enforces; R0-A probes each:

1. **The turn-loop is CODE-driven — routing=code (P4-roadmap §10).** The loop condition — *"did this pass append new `TOOL_CALL` events **and** are we under the bound?"* — is **pure code**. The LLM only **generates content within each dispatched turn** (which may contain tool calls). **No LLM judges "should I loop again"**, no LLM decides when to stop. The re-dispatch trigger + the loop bound + the termination test are all code.
2. **No new `LLMPurpose`.** A re-dispatched turn reuses the existing `AGENT_RESPONSE`; the MCP interpret reuses the existing content-gen `TOOL_OUTPUT_INTERPRET`. The "agent reacts to a tool result" is **not** a new purpose — it is the existing turn primitive (`run_turn`/`dispatch_turn`) re-run against a snapshot that now **includes** the just-appended `TOOL_RESULT`/`OBSERVATION` events. (Reuse the snapshot mechanism; add no event type, no purpose.)
3. **Every pass still routes the gate — the loop NEVER bypasses or re-decides autonomy.** Each re-dispatched turn's new tool calls go through the **unchanged** `process_tool_calls`→`emit_gate_decision`→`AUTO_EXECUTE`-only-appends-`TOOL_CALL` path. The executor's `t4` (execute-on-`TOOL_CALL`-only) holds per pass. A `COUNTDOWN`/`HARD` call produced in a pass uses the **existing confirm-then-execute flow** (ADR-030) — it is **not** executed in-loop, and **the loop does NOT wait for human confirm** (stays synchronous + terminating; confirm-gated calls are out-of-band async, the agent reacts to their eventual result on a future real turn).
4. **Single-writer invariant preserved (ADR-028 D1/D5).** The re-dispatch stays **inline on the single-writer** (the D5 MVP posture); a separate execution lane stays **deferred** (D5). The loop multiplies the per-pass block by the bound N — that N× cost is the **named, inscribed** liveness surface (§(a)), not an accident.
5. **The loop TERMINATES and the single-writer block is absolutely BOUNDED.** Non-negotiable that it must; the *mechanism/shape* (single-re-dispatch vs bounded-loop, and the bound's value) is the surfaced §(a) decision. Termination via the bound N **and** early-exit when a pass appends zero new `TOOL_CALL`s; liveness via N × (the per-pass ADR-028 D5 bound).
6. **B2 = read-only, in-process, sandboxed, trusted-not-interpreted.** (i) **In-process only — NO subprocess** (see §(b): `search_*` via `os.walk`+`re`, **not** `grep`/`rg`/`git grep`; `find_*` via in-process regex/heuristic, **not** a language-server) — shelling out would smuggle in the **B3 subprocess surface (the c2 env-leak class) that P4.1 explicitly defers**. (ii) **Reuse the ADR-028 D3 trust boundary** — same sandbox root, `_check_path` resolve-then-containment, **bounded output** (`MAX_RESULT_BYTES`, the list_files cap pattern), **bounded traversal** (a file-count / deadline cap — the FS-walk liveness analog of read_file's bounded-read). (iii) **Local results are trusted → NOT interpreted** (ADR-028 D2: they stand in the next snapshot, no `OBSERVATION`).

## Decision points (surface — ⭐ = architect's genuine call; do not self-decide)

### ⭐ (a) B1 turn-loop **shape** — single-re-dispatch vs bounded-loop (the lead call)
- **single-re-dispatch** — after the executor appends results, re-run the turn **once** so the agent reacts; do not loop. *Terminates trivially; ~2× the LLM/writer cost of a no-loop turn.* **But:** it gives the agent **one** reaction — it can read→react, but a reaction that itself calls a tool (search→…) gets **no further** re-dispatch. **Too weak for the flagship multi-step investigation** (read→search→find_references→… is ≥3 chained steps).
- **bounded-loop (≤N)** — re-dispatch repeatedly until a pass appends **no new** `TOOL_CALL`s **or** N passes elapse. *Lets the agent chain N steps — this is what the flagship scenario needs.* **Cost:** up to N× the per-turn LLM calls **and** N× the ADR-028 D5 single-writer block; the bound N (a documented constant) + the per-pass D5 cap make the total **absolutely bounded**.
- **Architect-partner lean: bounded-loop (≤N), small conservative N (e.g. 3-5).** Single-re-dispatch does not deliver the capability the slice exists for; the bounded-loop is the terminating, liveness-bounded shape consistent with ADR-028 D5's "every inline dependency bounded." **But this is your call** — it is a product-semantics + liveness-cost decision (how many tool→react hops per turn; how much single-writer block you accept). The senior designs the chosen shape's mechanics (termination test, the N constant, the total liveness bound) within ADR-033; you accept via the ADR.

### (b) B2 **tool set + classification + `log_event` in-or-out**
- **The 4 code-intel tools — squarely in, already classified.** `search_text`/`search_code` (handoff 第一层) + `find_references`/`find_definition` (第二层), all **rev 10 → AUTO** in `config/tools.yaml` today. P4.1 builds the **in-process impls** (carry-forward #6) for these already-classified names. Confirm the set.
- **`log_event` — the one real sub-call (it is a *write*, not read-only).** `log_event(content, type)` is rev **8** → AUTO, but it **appends** (to the event log / a note) — it crosses the slice's "read-only" framing. *For:* trivially reversible (rev 8), writes only to our **own** store (no FS/network/subprocess surface), the natural "record what I observed" companion to the investigation tools (flagship: investigate→log finding). *Against:* it is a mutation; and **local tools have no per-turn cap** (ADR-028 D5 — the caps are MCP/Posture-B only), so inside the new **N-pass loop** an agent could emit many `log_event`s × N passes (minor event-store bloat). **Architect-partner lean: include `log_event`, but have the senior note the loop-interaction** (either a local-write cap, or accept the rev-8 triviality). **Your call: in or out.**
- **Classification:** all are **already** in `tools.yaml` at the right reversibility — B2 is **impl + wire**, not re-classification. The sandbox root is the **existing** ADR-028 D3 operator-configured workspace dir (no new sandbox).

### ⭐ (c) **Dual-lens R0-B? — lean single-lens R0-A** (per `dual-lens-r0b.md` — confirm or flip)
Mechanical ≥2-criteria read: **1 New concurrency surface?** — *No* (reuses the existing inline-single-writer posture; the loop is sequential bounded iteration, ADR-011 is sequential — the N× block is an *arithmetic extension of an already-cross-family-vetted bound*, P3.4 cycle-2). **2 New layering edge?** — *No* (the driver already invokes `run_turn`+`execute_pending_tool_calls`; the loop re-runs existing edges). **3 Contract ≥5 future tasks?** — *Partial-yes* (the loop bound is inscribe-before-producer; P4.2 B3/B4/B5 ride it). **4 First runtime exercise of an allowed pattern?** — *No* (re-dispatch was explicitly **deferred**, not allowed-unused; net-new). **→ below the dispatch bar → single-lens R0-A.**
- **Honest counter (RC-20 correction-mode):** the **liveness arithmetic** (is the N× single-writer block *truly* bounded?) is exactly the runtime-integration class the **true cross-family** lens catches and Claude under-weights (P1.4: DeepSeek caught the `event_store.append` + liveness-class findings). So there is a real argument to dispatch **on the liveness surface specifically**. Counter-counter: the underlying D5 bound was *already* dual-lens-vetted in P3.4; P4.1 opens **no new external/subprocess/network/auth** surface; cost-to-flip is cheap (~$2 + 40min) if you want it.
- **Architect-partner lean: single-lens R0-A, with R0-A explicitly tasked to probe the liveness bound + termination + no-gate-bypass** (since it carries the weight alone). **Confirm skip, or flip to dispatch** — set `requires_cross_family_review` accordingly (brief sets **false** pending your confirm).

### ⭐ (d) **ADR strategy — new ADR-033 + amend ADR-028/011, vs amend-in-place** (confirm)
- **Lean: a new `ADR-033` (agent turn-loop / tool-result re-dispatch + loop bound)** — because (i) the loop-bound/termination/liveness is a **new contract** that P4.2's heavier tools ride on (inscribe-before-producer, P4-roadmap §10); (ii) ADR-028 D4 deferred re-dispatch precisely as *"a follow-up that explicitly inscribes the loop bound"* — a follow-up ADR is its natural home; (iii) carrying a substantial new contract by amending two ADRs in place is messier than one new ADR that references both.
- **Plus light amendments:** **amend ADR-028** — **D3** (add the read-only code-intel tools to the local MVP set; per P4-roadmap §8 "B2 = classification; amend ADR-028") + **D4** (mark the re-dispatch deferral **resolved** → pointer to ADR-033); **light ADR-011 touch** (note the in-turn re-dispatch extension to the sequential snapshot-per-turn model — see the senior-design surface below).
- **Alternative:** amend ADR-028 D4 + ADR-011 in place, no new ADR. **Your call** (new ADR-033 vs amend-only). All RC-23-safe (Proposed; no `Status: Accepted` until accepted).

## Senior-design surface (within the architect's §(a) shape ruling — for the senior to address in ADR-033; **not** architect routes)

These are design questions the senior owns + the ADR inscribes (architect accepts via the ADR, not via routing):
- **What re-dispatches.** Lean: re-run the **full `dispatch_turn`** (all loaded agents re-evaluate `should_agent_speak` against the updated snapshot — ADR-011-consistent, multi-perspective, **no new dispatch primitive**) rather than a narrowed only-the-tool-calling-agent re-dispatch. **The ADR-011 touch:** non-tool-calling agents re-evaluating each pass must not cause a speak-loop — cooldown (ADR-010) + the zero-new-tool-calls early-exit + the bound N are the backstops; the senior shows the loop still terminates.
- **Per-turn-cap × loop reconciliation.** The existing `MAX_MCP_CALLS_PER_TURN` / `MAX_POSTURE_B_CALLS_PER_TURN` are **per-execution-stage-invocation**; a loop invokes the stage N times. The senior decides + inscribes **per-pass reset vs per-loop accumulate** (lean: per-pass, since the bound N already caps total passes → total ≤ N × cap, still bounded) so the "per turn" semantics are honest under a loop.
- **The total liveness bound** (the D5 claim, extended): worst-case single-writer block ≤ **N × (per-pass turn LLM time + the ADR-028 D5 per-pass execution bound)**; inscribe N + the total, as D5 inscribed its bound.
- **B2 bounded traversal** — the FS-walk liveness analog: `search_*` over a large sandbox tree blocks the single writer, so cap files-scanned / wall-time (the read_file bounded-read analog).
