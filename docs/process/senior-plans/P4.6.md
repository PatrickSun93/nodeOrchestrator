## 1. Context

The architect ratified all five DPs along the lean lines (commit `96a9a4d`). This plan implements them. The central verify-cited fact: **the COUNTDOWN "countdown" is today a name and a UI hint with no server timer** — `COUNTDOWN_CONFIRM` and `HARD_CONFIRM` share one `else` branch (`tool_dispatch.py:126-154`) and both wait forever for a human `POST /confirm`; if the user does nothing, a COUNTDOWN call stays pending **indefinitely, identical to HARD**. P4.6 is therefore **net-new actuation machinery**, not a tweak: a durable `expires_at` stamped at gate time + a single in-process asyncio sweeper that actuates expired-and-still-pending COUNTDOWN calls on the writer, bounded so an irreversible op never headless-fires, opt-in default OFF.

This **deliberately weakens** the human-in-the-loop posture for the COUNTDOWN tier — it conditionally inverts ADR-030 D7(c) (*"COUNTDOWN has no server-side auto-fire / no headless execution"*). That residual (**`RB-AUTOFIRE`**) is inscribed honestly in ADR-040 D8, not softened. The load-bearing framing that keeps "routing/gating = code" intact (roadmap §10): auto-fire is **a scheduler over an already-gated COUNTDOWN tier** — the gate decided the tier; the timer **only actuates** the operator's standing "approve-unless-cancelled." The gate's `score`/`decide_tier`/`emit_gate_decision` stay **byte-frozen**; **no new `LLMPurpose`**.

All design decisions are in **ADR-040** (read it alongside this plan — D1 durable expiry + sweeper, D2 the eligibility gate, D3 reuse the confirm closure, D4 provenance, D5 inherited idempotency, D6 boot re-arm, D7 opt-in OFF, D8 `RB-AUTOFIRE`, D9 the room-enumeration read API). Two plan-stage senior discoveries materially shaped the ADR; see §5.

### P4.6-1 — auto-fire config surface (opt-in, default OFF) + AppContext field + thread to dispatch
- **What:** a new server-level config carrying `enabled: bool = False`, `window_s`, `sweep_interval_s`, `reversibility_floor`; loaded once at bootstrap; absent ⇒ disabled. Threaded onto `AppContext` and into the dispatch path so `process_tool_calls` can read it (P4.6-2) and the sweeper can read it (P4.6-4).
- **Where:** lean config file `config/autonomy.yaml`, section `countdown_auto_fire` (matches the `tools.yaml`/`web_search.yaml`/`email.yaml`/`mcp_servers.yaml` convention; the exact filename is a §5 confirm item). A frozen Pydantic config model (`extra="forbid"`, `ge=0` bounds on the ints, `0 ≤ reversibility_floor ≤ 10`). Loaded in `_build_context` (`app.py:~324-340`, beside `load_tools_config`); stored on `AppContext` (`app.py:100-120`). Threaded through `run_turn`/`dispatch_turn` (`agents/dispatch.py:16-26,150-163`) to `process_tool_calls`.
- **Why:** DP4c / ADR-040 D7 (opt-in, fail-closed); the absent-file ⇒ disabled rule is the "zero regression when off" guarantee.
- **Acceptance:** (1) absent config file ⇒ `enabled=False`; (2) a malformed/partial config fails **closed** (refuse-startup or disabled — never silently enabled); (3) the config object reaches both `process_tool_calls` and the sweeper from a single bootstrap-resolved source; (4) `threshold_*`-style cross-field bounds validated at Pydantic time (`window_s ≥ 1`, `sweep_interval_s ≥ 1`, `0 ≤ reversibility_floor ≤ 10`); (5) ruff + mypy --strict + the new config-loader unit tests green.
- **Out of scope:** per-tool `auto_fire_eligible` flags (ADR-040 alternatives — deferred); per-agent auto-fire config (this is server-global).

### P4.6-2 — durable `expires_at` on `ToolCallPendingMeta` + stamp at gate time
- **What:** add `expires_at: TimestampMs | None = None` to `ToolCallPendingMeta`; in `process_tool_calls`, stamp `expires_at = current pending event timestamp + window_s*1000` **iff** `tier == COUNTDOWN_CONFIRM` **and** auto-fire enabled **and** `tools[tc.name].reversibility ≥ reversibility_floor`; else leave `None`.
- **Where:** `core/event.py:351-365` (the field; additive nullable — note the docstring "field set locked by the constitutional test" → the test is extended, not bypassed); `agents/tool_dispatch.py:126-154` (the stamp, in the COUNTDOWN/HARD `else`).
- **Why:** DP1′ / ADR-040 D1 (durable expiry on the pending record — the one site holding tier + `call_id`) + D2 (the eligibility gate: COUNTDOWN-only 4a, reversibility floor 4b, enabled 4c). `reversibility` is read from the `tools: dict[str, ToolMeta]` already passed to `process_tool_calls` (`tool_dispatch.py:65`) — no new data source.
- **Acceptance:** (1) HARD pending ⇒ `expires_at is None` (always); (2) disabled ⇒ `expires_at is None` (always); (3) COUNTDOWN with `reversibility < floor` ⇒ `expires_at is None` (degrades to explicit-confirm); (4) COUNTDOWN, enabled, `reversibility ≥ floor` ⇒ `expires_at == pending.timestamp + window_s*1000`; (5) `score`/`decide_tier`/`emit_gate_decision` **byte-unchanged** (diff them — the stamp runs *after* the tier decision, never alters it); (6) the `ToolCallPendingMeta` constitutional test extended to cover the new field's presence/absence per tier; (7) no new `LLMPurpose` (grep).
- **Out of scope:** the sweeper (P4.6-4); the human-confirm-path provenance marker (P4.6-3).

### P4.6-3 — `approval_source` provenance marker on `ToolCallMeta` + human-confirm path sets `"human"`
- **What:** add `approval_source: Literal["human", "auto_timer"] | None = None` to `ToolCallMeta`; the HTTP confirm approve path sets `"human"`.
- **Where:** `core/event.py:203-218` (the field; additive nullable); `api/app.py:830-843` (the approve-branch `ToolCallMeta(...)` construction sets `approval_source="human"`).
- **Why:** DP2b / ADR-040 D4 (the honesty crux — a positive marker so a `None` `approver_user_id` on an auto-fire reads "executed BY TIMER, no human approver," never an ambiguous null colliding with the pre-P4.5 legacy `None`).
- **Acceptance:** (1) a human approve appends `ToolCallMeta` with `approval_source="human"` (and `approver_user_id` from the principal, unchanged); (2) pre-existing/legacy events read `approval_source=None` (backward-compat — nothing on any existing read path inspects the field); (3) `approver_user_id` and the still-pending scan are **byte-unchanged** (the scan keys on type+call_id, never this field); (4) schema + confirm-handler tests green.
- **Out of scope:** the auto-fire path setting `"auto_timer"` (lands with the sweeper, P4.6-4, via the shared helper's parameter).

### P4.6-4 — extract the shared writer-approve helper + the durable sweeper
- **What:** (a) extract `_post_confirm`'s approve branch (still-pending check → reconstruct agent-authored `TOOL_CALL` from the persisted record → `execute_pending_tool_calls` → bus-publish) into a **shared helper** that runs on `writer_executor`, parameterized by `approval_source` + `approver_user_id`; the HTTP handler calls it with `("human", principal_user_id)`. (b) add the **single lifespan-started asyncio sweeper** that every `sweep_interval_s` discovers expired-and-still-pending COUNTDOWN pendings and calls the helper with `("auto_timer", None)`.
- **Where:** `api/app.py` — extract from `:826-865` into a module/closure helper; the sweeper started in `lifespan` (`:1054-1062`) after `_build_context`, cancelled cleanly in teardown (beside `ctx.shutdown()`); `server_start_ms = now_ms()` captured at lifespan start (D6). Discovery enumerates rooms via the new read API (P4.6-5) on the reader path; actuation submits the helper to `writer_executor` (the still-pending re-check inside the helper, on the writer, is the correctness guard — ADR-025 D6 reader-liveness: discovery never appends, never blocks the writer).
- **Why:** DP2a / ADR-040 D3 (reuse, don't rebuild — executor unchanged + tier-agnostic, idempotency layers 1+2 inherited, t4 appender-guard preserved: the auto-fire append reconstructs from the persisted gate-produced record, never invents a call) + D1 (the sweeper) + D6 (boot re-arm) + D4 (auto_timer provenance).
- **Acceptance:** (1) the HTTP confirm path is **behavior-identical** after extraction (the existing confirm test suite passes byte-for-byte at the response level); (2) the sweeper fires an enabled COUNTDOWN whose `effective_deadline` (D6) has passed and is still-pending → appends an `agent:<initiating_agent>`-authored `TOOL_CALL` with `approval_source="auto_timer"`, `approver_user_id=None`, runs the executor, publishes to the bus, lands a `TOOL_RESULT`; (3) the sweeper **never** fires a HARD pending (structurally `expires_at is None`, plus an explicit `tier == countdown_confirm` guard); (4) early human approve/cancel during the window ⇒ the later timer fire is `already_resolved` no-op (≤ one `TOOL_CALL`); (5) the simultaneity instant resolves to exactly one winner (both on the single writer); (6) **boot re-arm (D6):** a still-pending COUNTDOWN with `expires_at < server_start_ms` is re-armed to `server_start_ms + window_s*1000` and does **not** fire on the first post-boot sweep (never fires without a live cancel window having existed); one with `expires_at ≥ server_start_ms` past `now` fires; (7) the sweeper task is cancelled cleanly on shutdown (no pending-task warning, no fire-after-shutdown); (8) disabled ⇒ the sweeper either is not started or finds nothing (off ⇒ no fire); (9) a fire into a **closed** room is rejected (the ADR-030 D3 step-2 room-state gate, inherited via the helper).
- **Out of scope:** a new resolution event type / proactive expiry-clear (ADR-040 D5 — none; the still-pending predicate is the sole correctness guarantee under the append-only store); per-pending in-memory timers (rejected, D1).

## 5. Where you'd push back (senior pre-investigation findings)

Two plan-stage discoveries materially refine the brief's leans. Both are **verify-cited** and already folded into ADR-040 — surfaced here for architect awareness, not as open questions:

1. **The event store is append-only → DP1″ "re-arm a fresh window" and DP3 "clear the durable expiry on resolution" cannot be metadata rewrites.** Verified: `core/event_store.py:78-90` has `events_no_update` + `events_no_delete` triggers that `RAISE(ABORT)` on any UPDATE/DELETE. So `expires_at` is **immutable** once stamped. ADR-040 realizes:
   - **Re-arm (D6)** as a **read-time derivation** — `effective_deadline = expires_at if expires_at ≥ server_start_ms else server_start_ms + window_s*1000`. This honors the architect's ratified conservative semantics ("never fire without a live cancel window having existed") **without** mutating an event. Equivalent in posture to the brief's lean; cleaner in mechanism.
   - **Expiry-clear (D5)** is **dropped as moot** — there is no mutable field to clear; the position-anchored still-pending check (the brief's stated *correctness* guarantee) already skips a resolved pending on every future sweep. This is *simpler* than the lean, not a weakening. **Flagging because it diverges from the brief's literal "housekeeping clear" wording** — the architect-deferral literal-reading discipline cuts both ways: I did not silently keep the lean's wording where the store makes it impossible; I inscribed the honest mechanism in the ADR and surface it here.

2. **No room-enumeration API exists → the sweeper needs a new read method (P4.6-5).** Verified: `EventStore` has `get_room`/`get_room_events` *by id* only (`event_store.py:358-382`); nothing lists rooms, and no caller iterates rooms today (grep: only `memory/matcher.py` counts distinct room_ids *within a query*, not a room list). The sweeper cannot scan without enumeration — hence P4.6-5 as its own atomic. This is additive read-only plumbing (no spine impact), but it is **real new surface the "small" framing did not explicitly budget** — calling it out per the promotion-impact discipline. Not a scope concern (one read method), just an honest "this is needed and wasn't named in the brief."

If you want it folded into an existing config surface or env-driven instead, say so — I took the convention-matching lean and proceeded.
