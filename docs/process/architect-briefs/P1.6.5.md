## Background — why this brief exists and why now

P1.6 closed cycle 2 with snapshot mechanics + decision log landed (ADR-014 + ADR-015 Accepted; `src/orchestrator/derived/` live; Logger agent wired; e2e validates the Research room state chain through `snapshot_pending → closed`). **Why P1.6.5 now:**

1. **The §4.5 schemas have been declared since P0 but never persisted** — the longest-running "no orphan spec" debt in the project (5+ months schema-only). Slice B closes the loop for the 2 canonical promotion-path classes (Hypothesis + VerifiedKnowledge); Entity ships as a stub; ProjectArchive defers.

2. **A cross-room scenario is now articulable** (Scenario X). Per the P1.6 brief: "P1.6 doesn't add cross-room memory; that's deferred to P1.6.5 OR P1.7 when a real consumer scenario surfaces." Scenario X is not load-bearing for any *current* consumer (no cross-room agents, no UI), but it IS the validation-via-articulable-scenario the §4.5 design anticipated.

3. **Slice B sizing is tractable** (~4-5 days, 1 ADR, 1 new package, explicit promotion API + lookup API, e2e). Smaller than P1.6. Substrate maturity (7+ consecutive impl-drift-free cycles through P1.6) supports a substantive-but-bounded next cycle.

4. **The promotion-rule load-bearing complex part stays explicit-and-bounded.** (b) user-confirm is trivial API. (a) cross-N-rooms ships as a forward-compat column with no matcher — the brief deliberately punts the matcher because of unresolved code-vs-LLM tension (handoff §3.1 says promotion eligibility = code, but semantic similarity matching may not be expressible in code without LLM embeddings). Punting the matcher to a future cycle lets P1.6.5 ship the persistence contract without resolving the matcher design question.

5. **First cycle to share a SQLite file with the event store** — atomicity-by-shared-DB is a deliberate design choice (architect-settled #4); pins a migration strategy that future persistence work inherits.

## Architect-settled design decisions

### 1. Slice B: Hypothesis + VerifiedKnowledge primary; Entity stub; ProjectArchive defer

ProjectArchive is per-room (no cross-room search semantic) and its consumer (room re-entry) doesn't exist yet — defer. Entity ships as schema-only stub (table + Pydantic model with `attributes: dict`) — no producer/consumer beyond the schema — to avoid future migration. Hypothesis + VerifiedKnowledge is the canonical promotion path and the validation target.

ADR-016 D1 inscribes.

### 2. Promotion: (b) full; (a) candidate-flag column only; (c) deferred entirely

- **(b) user-confirm**: `promote_hypothesis(hyp_id, user_id) -> VerifiedKnowledge` is the full API. Creates VK row, updates Hypothesis.status="verified", emits `decision` event to event_store, single SQLite transaction.
- **(a) cross-N-rooms**: `Hypothesis.candidate_for_promotion: bool` column ships. P1.6.5 has no matcher; the column is written by future code (P1.7 or P2). The brief explicitly defers the matcher because of code-vs-LLM tension on semantic-similarity detection.
- **(c) external ground-truth**: no infrastructure exists; defer to P2+.

ADR-016 D2 inscribes promotion contract; D3 the candidate flag.

### 3. Hypothesis row creation: explicit API, not auto-mirrored from `hypothesis` events

`memory.record_hypothesis(content, room_id, source_event_ids, confidence) -> Hypothesis` is the producer. No automatic event-stream → memory-table sync.

Rationale: auto-mirroring couples persistence semantics to every `hypothesis` event (many of which may be transient, low-confidence, or non-canonical); explicit API keeps producer choice with the caller. Same intuition as ADR-014's "snapshot is producer-triggered, not event-triggered."

ADR-016 D4 inscribes.

### 4. Storage: same SQLite file as event_store

Per `handoff.md` §5.8 the event store is stdlib `sqlite3`. P1.6.5's 3 memory tables live in the same DB file:
- **Atomicity**: promotion = single transaction (VK insert + Hypothesis update + event append). Same DB = same connection = same transaction.
- **Operational simplicity**: 1 file, 1 backup, 1 migration path.
- **Migration**: extend the event-store init SQL with `CREATE TABLE IF NOT EXISTS` for the 3 new tables. Existing event-store DBs upgrade in place on next open.

ADR-016 D5 inscribes.

### 5. Single ADR (ADR-016)

All 6 decisions (schema, promotion, candidate flag, producer, storage, lookup) are tightly coupled — every decision references the others. Architect-partner lean: single ADR. Senior may push for split (push-back #1); defend if so.

### 6. Cross-room lookup contract

`lookup_verified_knowledge(topic_tags: list[str], scope: Literal["personal","team","global"]) -> list[VerifiedKnowledge]`:
- `scope` filtered first (per `VK.scope` column).
- `topic_tags` filtered as OR-semantics ("any input tag matches any row tag").
- Deterministic ordering by `last_validated` desc.
- No ranking / similarity.

ADR-016 D6 inscribes.

### 7. Promotion event type: reuse existing `decision` event

Promotion IS a user decision per `handoff.md` §4.5. Reuse the `decision` event type with a `promotion: True` metadata flag (or similar). No new EventType warranted. Senior may push for a dedicated `promotion` event type (push-back #6); defend if so.

### 8. e2e test: Scenario X (3-room promotion → query)

Architect-partner lean: full 3-room scenario (per "In scope" sequence). The cross-room semantic IS the load-bearing thing being validated; narrower scopes (2 rooms, synthetic event bypass) fail to exercise the cross-room semantic that justifies P1.6.5's existence.

## Constraints (do not violate)

- **`handoff.md` §3.1 + §4.5**: no LLM in `memory/` module. Promotion eligibility = code, not LLM. Constitutional test extends.
- **`handoff.md` §4.5 "不自动晋升"**: code must enforce that promotion only happens via explicit `promote_hypothesis(...)`; no path exists where an event triggers automatic promotion. ADR-016 D2 inscribes the invariant.
- **Principle 1 (event log is truth)**: promotion writes a `decision` event so the promotion act is in the canonical event stream. Memory tables are queryable convenience, not authoritative.
- **ADR-001 honored**: event stream remains canonical.
- **Storage atomicity**: promotion = single SQLite transaction. ADR-016 D5 pins.
- **Dependency direction**: `memory/` may import `core/`; `core/` MUST NOT import `memory/`. Constitutional test guards.
