# P3.5 senior plan — Plugin system (manifest + loader + code-trust model)

## 1. Context

P3.5 is the **Wave-2 backend-track closer** (roadmap §4/§5): a `plugins/` package — a **manifest schema** + a **loader** that discovers / validates / registers a **distribution unit** bundling **roles + skills + tool-classifications + executable tool code + MCP-server config** — merging each contribution into the **existing** agents/skills/tools/local-tools/MCP registries at the existing `_build_context` merge point (`api/app.py:142–158`), **reusing the four existing loaders** (`load_agents`, `load_skills`, `load_tools_config`, the MCP config/adapter). It is the *convergence* of P3.1 (roles/skills) + P3.4 (MCP config), not a new leaf.

The design is inscribed in **ADR-029** (Proposed — read it first; this plan implements it). The **constitutional spine + trust boundary** (gate-unbypassed plugin tools; allowlist-unbypassed plugin servers; load-is-code-not-LLM; no-new-`LLMPurpose`; fail-closed loading; opt-in / manifest-validated / credential-safe third-party bundle) are **non-negotiable** (ADR-029 HR#1–5).

**The architect ruled `admit-plugin-code-now`** (ADR-029 D4), overriding the brief's declarations-only lean: a plugin may carry **third-party executable tool code** (Python, *loaded = runs*). This is the project's largest security surface. **The code-trust / isolation posture (Posture A in-process vs B subprocess) is the single architect-Accept crux — surfaced in §5; it must be resolved before the code-loading atomic (P3.5-4) is implemented.** The rest of the plan is posture-independent up to that atomic.

**Substrate verified `origin/main`** (claims-with-cites per pre-investigation discipline):
- Two distinct tool registries: `tools: dict[str, ToolMeta]` (gate classification, `app.py:145,154`) and `local_tools: dict[str, LocalToolFn]` (executor impls, `app.py:158`). Verified `tools/executor.py:308` `local_tools.get(tool_name)` → `impl(params)` wrapped fail-closed `:326–331`.
- `build_local_tool_registry(sandbox_root)` (`tools/local.py:131`) is hard-coded to 3 builtins — **no third-party-impl loader exists** (the only genuinely-new mechanism — P3.5-4).
- All four loaders' models are frozen + `extra="forbid"` (Agent `agents/schema.py:95`; Skill `skills/schema.py:43`; ToolMeta `autonomy/scoring.py:36`; MCPServersConfig `mcp/config.py:63`) — verified.
- The loaders take a directory/path arg (`load_agents(directory, *, models)`, `load_skills(directory)`, `load_tools_config(path)`, `load_mcp_servers_config(path)`) → reusable pointed at plugin subpaths.
- ADR-027 D5 pre-committed the `mcp_servers` plugin-block shape; ADR-028 D6 + `tests/tools/test_constitution.py` is the constitution-test template.

## 2. Tasks (atomic)

### P3.5-1 — Manifest schema (`plugins/schema.py`)
- **What:** the `PluginManifest` Pydantic model (frozen, `extra="forbid"`) per ADR-029 D1 — `schema_version`, `id`, `name`, `version`, `contributions{roles, skills, tools, tool_impls, mcp_servers}`, `dependencies{model_ids, room_types, min_host_contract}`; the `tool_impls` value shape `"<module>:<callable>"`.
- **Where:** new `src/orchestrator/plugins/schema.py` + `plugins/__init__.py`.
- **Why:** ADR-029 D1; inscribe-before-producer (brief Constraints — P3.7 binds this).
- **Acceptance:** frozen + `extra="forbid"` (an unknown manifest key → `ValidationError`); `schema_version` present + validated; all `contributions`/`dependencies` fields optional with safe empty defaults; mirrors the existing loaders' model style (`mcp/config.py`).
- **Out of scope:** the loader; any I/O. Pure schema.

### P3.5-2 — Discover + validate + dependency-check (`plugins/loader.py`, part 1)
- **What:** `load_plugins(plugins_dir, *, models, host_room_types, host_contract_version, sandbox_root)` discovery + manifest-validation + dependency-check half (ADR-029 D2 steps 1–2, D6) — iterate subdirs, parse+validate each `plugin.yaml`, check `dependencies` against `models`/`host_room_types`/contract; **fail-closed + per-plugin isolation** (a bad/unparseable manifest, unknown `schema_version`, or unmet dependency → refuse THAT plugin, log, continue; never crash bootstrap, never half-register).
- **Where:** new `src/orchestrator/plugins/loader.py`.
- **Why:** ADR-029 D2 (steps 1–2) + D6 + HR#5.
- **Acceptance:** unknown `schema_version` → refused; unmet `model_id`/`room_type` dependency → refused; one bad plugin does not block a sibling valid plugin; returns a typed partial result for the merge half (P3.5-3).
- **Out of scope:** the four-loader reuse + merge (P3.5-3); code loading (P3.5-4).

### P3.5-3 — Reuse the four loaders + collision-check + reversibility-cap + merge (`plugins/loader.py`, part 2)
- **What:** for each valid plugin, call the **existing** `load_agents`/`load_skills`/`load_tools_config`/`build_mcp_tool_registry_and_sessions_from_config` pointed at the plugin's subpaths; **collision-check** every contributed name (role/skill/tool/server) against host registries + cross-plugin (**fail-closed on collision** → refuse that plugin, host registry unmodified, ADR-029 D6); **cap plugin-asserted reversibility** (host-authoritative-or-default-0, ADR-029 D5 — never accept a raise); produce the merged `PluginLoadResult` (agents, skills, tool ToolMetas, mcp ToolMetas+sessions; tool_impls deferred to P3.5-4).
- **Where:** `src/orchestrator/plugins/loader.py`.
- **Why:** ADR-029 D2 (steps 3–4), D5 (advisory-cap), D6 (collision); brief Constraints (reuse, don't reimplement).
- **Acceptance:** no loader reimplemented (greps confirm `plugins/` calls the existing loaders); a colliding role/tool/skill/server name → plugin refused, host registry unchanged; a plugin claiming `rev=10` on a tool whose host default is lower → capped (gate tier unchanged — a test asserts it); MCP block merges via the ADR-027 D5 path (sessions retained).
- **Out of scope:** executable code loading (P3.5-4); the `_build_context` wiring (P3.5-5).

### P3.5-4 — ⭐ Executable tool-code loading + the isolation posture (`plugins/code.py`) — **BLOCKED on §5 posture Accept**
- **What:** the **new** mechanism to load a plugin's `tool_impls` into the executor's `local_tools` registry, **per the architect-Accepted posture (ADR-029 D4 — A in-process import, or B subprocess)**. Posture A: `importlib` the plugin module, resolve `<module>:<callable>`, validate it is a `LocalToolFn`-shaped callable, register; **per-plugin load isolation** (import error → refuse plugin, never crash bootstrap) + per-call fail-closed inherited from the executor. Posture B: register a subprocess-runner `LocalToolFn` (scoped env, bounded-timeout, killable — the ADR-027 D4 pattern). The plugin tool's `ToolMeta` (classification, from P3.5-3) is what gates it.
- **Where:** new `src/orchestrator/plugins/code.py` (+ loader wiring).
- **Why:** ADR-029 D4 (the admit-code crux; the L1/L2 limits the posture resolves).
- **Acceptance:** a valid plugin executable tool loads → registered in `local_tools` → **gates** (classified ToolMeta → tier) → **executes** via the existing `tools/executor.py::_execute_local_call` (no executor edit) → `TOOL_RESULT`; a **broken** variant (import error / raises) → **fail-closed** (refused at load / `TOOL_FAILED` at call, never crashes); the posture's named limits (L1/L2) are honored exactly as ADR-029 D4 Accepts them (e.g. Posture B: a hanging tool is killed on timeout; Posture A: the limit is documented + the operator-curation trust model is the boundary).
- **Out of scope:** the OTHER posture (only the Accepted one is built); remote-provenance code (P3.7).

### P3.5-5 — Wire the plugin aggregation pass into `_build_context`
- **What:** add **one** aggregation pass in `api/app.py::_build_context` after the four loaders: call `load_plugins(...)`, merge the `PluginLoadResult` into `agents`/`skills`/`tools`/`local_tools`/`mcp_sessions` before `AppContext` construction. The gate, the executor, and the MCP client are **untouched** (empty-gate-diff + empty-executor-diff invariant).
- **Where:** `src/orchestrator/api/app.py` (`_build_context`, ~line 158).

- **Out of scope:** any gate/executor/MCP-client logic change.

## 5. Where you'd push back (decisions surfaced — architect must rule before the blocked atomic)

**⭐ (1) THE crux — the D4 code-trust / isolation posture (architect Accept, blocks P3.5-4).** The architect ruled admit-code-now but delegated the **isolation mechanism** to senior-design-and-surface. ADR-029 D4 lays out Posture **A** (in-process import, operator-curation-IS-trust) vs **B** (subprocess isolation), with two honest named limits on A: **L1** a malicious in-process plugin is NOT technically contained (Python in-process = full host privilege; security rests on operator-curation, a *policy* boundary, not a runtime one); **L2** in-process code cannot be safely timeout-bounded/killed → it **relaxes the ADR-028 D5 single-writer liveness bound** (a subprocess can be killed on timeout; in-process code cannot). Posture B resolves both — but at the cost that admit-code then converges with "bundle an MCP server" (which P3.4 already supports), so B's marginal value over the existing MCP path is thin. **The hinge question (ADR-029 D4): is an operator-placed local plugin a TRUSTED tier (→ A) or an UNTRUSTED third-party (→ B)?** The brief's fail-closed requirement *"恶意代码不能越权 host"* has two diverging readings — satisfied by A *only via curation*, by B *technically*. **Senior lean: Posture A for the operator-curated local-dir MVP (framed as extending the trusted-local-code boundary from `src/` to `plugins/`), with L1+L2 inscribed + fail-closed-against-breakage demo-proven, and Posture B reserved for untrusted provenance (P3.7 remote install).** Architect Accepts the posture (A / B / A-now-B-later) on ADR-029 — junior is blocked on P3.5-4 until then.

**(2) Demo collision posture (minor; confirm).** The demo reuses core names (`facilitator`, `research-decomposition`). Under D6 fail-closed-on-collision, a plugin re-declaring a *core* role/skill name would be **refused** — so the demo must either (a) ship its OWN copies under distinct names, or (b) the collision policy must distinguish "core re-export" from "cross-plugin clash." Lean: **(a)** the demo ships distinctly-named content (cleanest; no policy carve-out). Confirm, or rule a core-reexport carve-out.

**(3) `min_host_contract` definition (senior-design within ADR-029; nod).** The manifest declares `min_host_contract: int`; the host needs a contract-version constant to check against. Lean: introduce a `PLUGIN_HOST_CONTRACT_VERSION = 1` constant in `plugins/` (bumped when the manifest/merge contract changes). Confirm this is the right home (vs a project-wide version).

No other ambiguities: the constitutional spine + trust boundary are non-negotiable (inscribed, not decisions); collision=fail-closed, dependency=fail-closed, presence=opt-in, advisory-cap, reuse-the-four-loaders are architect-ruled (brief §Decisions + dispatch). ADR-029 binds ADR-027 D4/D5 + ADR-028 without restating.
