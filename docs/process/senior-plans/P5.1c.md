# Senior plan — P5.1c: headless pipeline email (the one authorized irreversible-actuation crossing)

## 1. Context

P5.1c is the third and final slice of the P5.1 analysis-pipeline wave and the honesty crux of P5. P5.1a (ADR-041) shipped the safe primitive (reversible output only); P5.1b (ADR-042) made it unattended on a timer but strictly reversible — a scheduled run could read/analyze/post a room summary headless, but any `send_email` it proposed just **waited**. P5.1c lets an **opted-in, promoted-to-live, scheduled** pipeline **send an irreversible external email with no human in the loop at any point**. This is the first headless *irreversible actuation* in the product — it steps past both the `RB-AUTOFIRE` reversibility floor (ADR-040) and the `RB-PIPELINE-SCHED` reversible envelope (ADR-042), and must do so **without touching either**.

The architect ratified the decision surface (C0–C8) on 2026-06-10 along the arch-partner leans, with **one strengthening: dry-run is the mandatory first state** (model the opt-in as 3-state OFF → dry-run → live). The ratified design is inscribed in **ADR-043** (drafted alongside this plan, Status: Proposed): scheduled-run-only (C0a); reuse `_writer_approve_helper` as a 3rd caller with `approval_source="auto_pipeline"` (C1a); owner-config-pinned recipient + LLM body (C2b); `send_email`-only literal-constant allowlist (C3a); schedule-level 3-state columns, default OFF fail-closed (C4a + C5); front-loaded owner-attributed audit + dry-run-first (C5); the `RB-PIPELINE-EMAIL` residual (C6).

**The whole crossing is a narrow actuation-authorization layer *after* the run.** The gate (`score`/`decide_tier`/`emit_gate_decision`), `_execute_local_call`, the COUNTDOWN spine (`_countdown_sweeper`/`_discover_expired_pendings`/the two `RB-AUTOFIRE` stamps), and `run_pipeline`'s `countdown_auto_fire=None` reversible envelope are all **byte-frozen**. Every task below is bounded by that.

**Verified seam (`origin/main` @ `dd5ced5`):** the actuator hooks into `_schedule_act_on_writer` step 5 (`api/app.py:678-727`), *after* `run_pipeline` returns — the run leaves a HARD `send_email` `TOOL_CALL_PENDING` waiting in the freshly-created run room (`result.room_id`); the actuator discovers it and, if eligible, actuates it via `_writer_approve_helper`. In the pipeline threshold config (`_PIPELINE_THRESHOLDS`, `runner.py:67`, `threshold_confirm=5`) `send_email` (reversibility=3 `<` 5) tiers **HARD_CONFIRM** — so the actuator actuates a HARD pending, mirroring a human `/confirm` exactly.

### P5.1c-3 — Pipeline-email actuator: discovery + eligibility gate + live actuation, wired post-run

- **What:** Add the post-run actuator that discovers waiting `send_email` pendings in a scheduled run's room and, for eligible ones in **live** mode, actuates them via `_writer_approve_helper` with `approval_source="auto_pipeline"`.
- **Where:** `src/orchestrator/api/app.py` (new `_actuate_pipeline_emails(...)` near the sweeper; widen the `Literal` annotation at `_writer_approve_helper` `:383`; add a **keyword** `loop` param to `_schedule_act_on_writer` `:600` + pass it in the `functools.partial` call `:758`; fix the `_schedule_act_on_writer` docstring `:618-619`; add the post-run call in step 5 after `create_pipeline_run`); `src/orchestrator/core/event.py` (widen the `ToolCallMeta.approval_source` `Literal` annotation `:224`).
- **Why:** ADR-043 D2 (mechanism), D3 (recipient pin), D4 (single-tool guard). The seam: `_writer_approve_helper` `:379-471` (reconstruct-from-record, not byte-frozen) called from `_schedule_act_on_writer` which already runs on the writer executor.
- **Acceptance criteria:**
  - A module-level literal constant `_PIPELINE_EMAIL_TOOL = "send_email"` is the **sole** tool the actuator will ever actuate.
  - `_actuate_pipeline_emails(ctx, schedule, run_room_id, loop)`: returns immediately if `not schedule.email_enabled` (OFF never touches pendings). Otherwise it **discovers** candidate pendings with a **new, dedicated scan** of the run room's events — `TOOL_CALL_PENDING` whose `ToolCallPendingMeta.tool_name == _PIPELINE_EMAIL_TOOL` and not yet resolved. **Do NOT reuse `_discover_expired_pendings`** (byte-frozen, keys on `expires_at`); the new scan never reads/writes `expires_at`.
  - **Eligibility gate** (all must hold to actuate): `tool_name == _PIPELINE_EMAIL_TOOL`; `schedule.email_mode == 'live'`; `schedule.email_recipient` non-empty **and** equals the pending's `params['to']` by a **case-insensitive match — lowercase both sides before comparing** (R0B-Y1; RFC 5321 semantics, so a benign casing difference does not silently fail-closed). Ineligible pendings are **left waiting** (no actuation, no mutation); a recipient-mismatch in live mode logs a debug note and leaves the pending waiting.
  - Eligible pendings are actuated via `_writer_approve_helper(ctx, run_room_id, pending_event_id, approval_source="auto_pipeline", approver_user_id=schedule.owner_user_id, loop=loop)`. The actuator **never** mutates the pending record (`params`/`to` come from the record inside the helper, never the caller — ADR-043 D2).
  - **Value-set widening, not field-set change (R0A-Y2):** the **only** production edits are the **two type annotations** — `_writer_approve_helper`'s param `Literal` (`app.py:383`) and `ToolCallMeta.approval_source`'s `Literal` (`event.py:224`) → `["human", "auto_timer", "auto_pipeline"]`. P5.1c adds **no field** to `ToolCallMeta`, so the field-set constitutional pin `test_constitution_tool_call_meta_field_set_pin` (`test_constitution.py:281-287`, which enumerates the five field **names**, not the `Literal` values) stays **byte-unchanged**. The new `"auto_pipeline"` value is exercised by this task's actuator tests, not by the field-set pin.
  - `_schedule_act_on_writer` gains a **keyword** `loop` param (existing positional call-sites in `tests/api/test_schedule_sweeper.py` `:273,301,328,333,385,428` then need **no change** — R0A-Y3) and calls `_actuate_pipeline_emails(ctx, schedule, result.room_id, loop=loop)` as a **step 6, after** `run_pipeline` + `create_pipeline_run` succeed, guarded so a run with `email_enabled=0` skips it. `loop` is passed from `_schedule_sweeper` (`:756-759`).
  - **Docstring honesty (R0A-Y1):** rewrite the `_schedule_act_on_writer` docstring (`:618-619`) which currently states "Never calls … `_writer_approve_helper`" — it must truthfully state the crossing: the act now reaches `_writer_approve_helper` **only** via the narrow `_actuate_pipeline_emails` email path (`send_email`-only), while the COUNTDOWN spine (`_countdown_sweeper`/`_discover_expired_pendings`) stays uncalled.
  - **Idempotency:** integration test asserts sweeping the same run twice (or re-invoking the actuator) actuates the `send_email` pending **at most once** (inherited still-pending check, `_writer_approve_helper:422-429`).
  - `ruff` + `mypy --strict` + full `pytest` clean.
- **Out of scope:** the dry-run record path (P5.1c-4); changing `run_pipeline` (byte-frozen); any change to the gate/executor/COUNTDOWN spine.

### P5.1c-4 — Dry-run posture (mandatory first state)

- **What:** Implement the dry-run branch of the actuator: when enabled but `email_mode == 'dry_run'`, record what *would* be sent and do **not** actuate or call the transport.
- **Where:** `src/orchestrator/core/event.py` (new typed metadata class + `TYPED_METADATA` registration `:394`); `src/orchestrator/api/app.py` (the dry-run branch inside `_actuate_pipeline_emails`); `tests/core/`, `tests/integration/`.
- **Why:** ADR-043 D6 — dry-run is the mandatory first state for the first irreversible crossing; the preview is the owner's load-bearing promote-to-live evidence, so it is **structurally typed** (R0B-Y2).
- **Acceptance criteria:**
  - New typed metadata class **`PipelineEmailDryRunMeta`** with fields `recipient`, `subject`, `would_actuate` (bool), `owner_user_id`, `approval_source`, **registered in `TYPED_METADATA`** (`event.py:394`) keyed to the existing **`OBSERVATION`** event type — **no new `EventType`** (the scope-narrowing stands; only the metadata gains a schema).
  - When `schedule.email_enabled` and `email_mode == 'dry_run'`: for each discovered `send_email` pending, the actuator appends an `OBSERVATION` carrying a `PipelineEmailDryRunMeta` recording the **decision the live path would take** — `recipient` = the pending's `to`, `subject`, `would_actuate` = (`to` case-insensitively == `email_recipient`), `owner_user_id`, `approval_source="auto_pipeline"`. It does **NOT** call `_writer_approve_helper`, does **NOT** append a `TOOL_CALL`, does **NOT** call the transport; the pending **stays waiting**.
  - Test asserts: in dry-run, zero `TOOL_CALL`/`TOOL_RESULT` for the `send_email` call is appended, no transport is invoked (mock/fake send asserts not-called), the pending remains unresolved, and exactly one preview `OBSERVATION` carrying a schema-valid `PipelineEmailDryRunMeta` per discovered pending is recorded.
  - Test asserts the **3-state transition**: a freshly opted-in schedule is in dry-run (P5.1c-1/2); only after `promote_schedule_email_live` does the same run actuate (P5.1c-3).
  - `ruff` + `mypy --strict` + `pytest` clean.
- **Out of scope:** a runtime cancel window (rejected, ADR-043 D6); promoting to live automatically.

### P5.1c-5 — Constitutional + dual-lens no-regression tests

- **What:** Add the cross-cutting tests that pin the crossing's bounds (Lens A) and the spine no-regression (Lens B).
- **Where:** `tests/integration/`, `tests/pipeline/`, `tests/core/` as appropriate.
- **Why:** ADR-043 D4 (constitutional-test-pinned) + the C8 Lens contract. Mirror ADR-040 Decision 2's `HARD-never` test.
- **Acceptance criteria (Lens A):**
  - **HARD-never-generalize:** a scheduled run that leaves a **non-`send_email`** HARD pending (e.g. a `git_push`/`apply_edit` pending, even with `email_enabled` + `email_mode='live'`) is **never** auto-actuated by the pipeline-email path — it stays waiting. (This is the structural guard against "any HARD tool headless.")
  - **Recipient-pin:** a `send_email` pending whose `to` ≠ pinned `email_recipient` is **not** actuated in live mode (stays waiting), even when its domain is within `allowed_domains`.
  - **Default-OFF / dry-run-first:** an absent/`email_enabled=0` schedule never actuates; a freshly enabled schedule is in dry-run and does not send.
  - **Idempotency:** no double-send across re-sweep/restart (at-most-once).
  - **Owner-attribution:** the actuated `TOOL_CALL`/`TOOL_RESULT` carry `approval_source="auto_pipeline"` + `approver_user_id=owner_user_id`.
- **Acceptance criteria (Lens B):**
  - **Honest rewrite of the ADR-042 D1 isolation test (R0A-Y1 — the headline).** `test_schedule_act_on_writer_does_not_call_countdown_spine` (`tests/api/test_schedule_sweeper.py:492-516`) currently AST-checks `_schedule_act_on_writer`'s own source against `forbidden_calls = {_countdown_sweeper, _discover_expired_pendings, _writer_approve_helper}`. Because the email path reaches the helper through the **separate** `_actuate_pipeline_emails` fn, that one-hop test would keep passing while the invariant it names is (now legitimately) violated — a **silent-vacuous** pass at the honesty crux (the P5.1b cyc3 failure theme). Rewrite it honestly: **(1)** drop `_writer_approve_helper` from `_schedule_act_on_writer`'s forbidden set (now legitimately reachable, *only* via the narrow email path); **(2)** **keep `_countdown_sweeper` + `_discover_expired_pendings` forbidden** for both `_schedule_act_on_writer` **and** `_actuate_pipeline_emails` (the COUNTDOWN spine is genuinely untouched — Lens B); **(3)** add a **positive pin**: assert `_schedule_act_on_writer`'s sole new actuation reach is `_actuate_pipeline_emails`, and that `_actuate_pipeline_emails` is the **only** function in the scheduled path that calls `_writer_approve_helper`. (`test_schedule_sweeper_does_not_call_countdown_spine` at `:463-489` for `_schedule_sweeper` is unaffected — it stays as-is.)
  - **Field-set pin byte-unchanged (R0A-Y2):** `test_constitution_tool_call_meta_field_set_pin` (`:281-287`) is **not** edited — P5.1c widens a `Literal` value set, adds no field. (Confirm it still passes unchanged.)
  - **Byte-frozen guards:** assert `countdown_auto_fire=None` still present at `runner.py:153,223`; the two `RB-AUTOFIRE` stamps at `tool_dispatch.py:137-145` unchanged; `_execute_local_call` + `score`/`decide_tier`/`emit_gate_decision` unchanged (the project's existing byte-frozen/constitutional assertions still pass).
  - **No new `LLMPurpose`:** the only pipeline LLM purpose stays `AGENT_RESPONSE` (analyze/reduce); the recipient is config, not an LLM judgment. (Existing no-new-LLMPurpose constitutional test still passes.)
  - **Existing callers behavior-identical:** the `human`/`auto_timer` `_writer_approve_helper` paths + the COUNTDOWN sweeper + interactive `/confirm` are unaffected by the `Literal` widening (existing tests green).
  - `ruff` + `mypy --strict` + full `pytest` clean.
- **Out of scope:** new product behavior — this task only pins existing behavior.

## 5. Where you'd push back

- **Column model (D5) is a pinned proposal, not a fork.** The architect ratified "`email_enabled bool=False`, `email_recipient`, + the dry-run state" and "model as 3-state OFF→dry-run→live." I render that as **two flags + recipient** (`email_enabled` on/off + `email_mode` dry_run/live + `email_recipient`) because it (a) matches the literal `email_enabled bool` wording, (b) is fail-closed in *both* dimensions (the dangerous `live` state needs both flags explicitly set; `email_mode` defaults to the safe `dry_run` even if `email_enabled` flips), and (c) maps the 3 states cleanly. A single `email_mode` enum (`off|dry_run|live`) is the only real alternative; if the architect prefers it, that is a one-column swap confined to P5.1c-1. **Verified** against `memory/store.py:107-118` (the guarded-ALTER precedent) and `pipeline/store.py:44-58` (the DDL).
- **Dry-run preview shape.** I specified the dry-run record as an `OBSERVATION` in the run room (reuses the existing reversible-output channel — no new EventType, consistent with ADR-041 Decision 6). If the architect wants a structured/queryable dry-run log table instead, that is a scope addition to flag now rather than bundle.
- **No `/run` change confirmed.** Per C0a, the manual `POST /pipelines/{id}/run` path is untouched (a `send_email` it produces still waits for interactive `/confirm`). The plan deliberately adds **zero** code there. Flag if the architect later wants manual-run parity — it is explicitly *not* in this slice.
- **Amendment authorship boundary.** ADR-043 is drafted (Proposed) alongside this plan; the cross-ADR amendment *text* is authored in ADR-043 D8 and merely **applied** by the junior in P5.1c-6. I did not edit the five accepted ADRs at plan-stage (keeps the impl diff and the dual-lens focused on code; the doc edits land in the impl branch). RC-3: I do **not** self-accept ADR-043.
