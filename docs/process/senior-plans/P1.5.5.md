### P1.5.5-3: New module `src/orchestrator/agents/tool_dispatch.py`

**What**: sibling module that processes `LLMResponse.tool_calls` after a dispatch_turn LLM call. Per ADR-013 D1, dispatch site lives in this sibling (not inline in `dispatch_turn`; not in `RoomRuntime.run_turn` — option (b) is structurally impossible since `dispatch_turn` discards `response.tool_calls` before returning).

**Where**:
- `src/orchestrator/agents/tool_dispatch.py` (new)
- `tests/agents/test_tool_dispatch.py` (new)

**Module surface** (signature freeze — junior implements body):

```python
def process_tool_calls(
    tool_calls: list[ToolCall],
    *,
    agent_id: str,
    room_id: RoomId,
    current_event: Event,
    event_store: EventStore,
    tools: dict[str, ToolMeta],
    thresholds: ThresholdConfig,
) -> ToolDispatchResult:
    """For each tool call: build Operation, call emit_gate_decision,
    and for AUTO_EXECUTE only, append a tool_call event. See ADR-013."""
```

`ToolDispatchResult` is a frozen Pydantic model (per `feedback_physical_over_logical` + project pattern):

```python
class ToolDispatchResult(BaseModel):
    model_config = ConfigDict(frozen=True, extra="forbid")
    decisions: list[ToolDispatchDecision]  # one per processed tool_call

class ToolDispatchDecision(BaseModel):
    model_config = ConfigDict(frozen=True, extra="forbid")
    call_id: str
    tool_name: str
    tier: AutonomyTier | None  # None when UnknownToolError raised
    tool_call_event_appended: bool  # True only when tier == AUTO_EXECUTE
    refusal_reason: Literal["unknown_tool"] | None
```

**Why**: ADR-013 D1 decision. Sibling module keeps `dispatch_turn` shape lean (one extra call site, not a buried sub-loop); makes the tool-call path independently testable (tests don't need `dispatch_turn`'s full fixture); enables future executor agents (P1.6+) to reuse the function.

**Acceptance**:
- Function signature matches above (frozen via `interface freeze` discipline — see [[feedback_interface_freeze]]: ToolDispatchResult + ToolDispatchDecision shipped this commit; body in same commit since the function is short; **freeze-then-implement gap not required** for a function this small per interface-freeze rule's "for new modules with multiple coupled functions" scoping).
- Per `ToolCall`: build `Operation(tool_id=tc.name, initiating_agent=agent_id, user_explicit_intent=(current_event.type == EventType.USER_INPUT), params=tc.arguments)`. **`user_explicit_intent` derivation pinned per ADR-013 D3.**
- Call `emit_gate_decision(operation, tools, thresholds, event_store, room_id=room_id, author=build_author(agent_id))`.
- `emit_gate_decision` appends `autonomy_decision` event synchronously (already implemented; reused as-is).
- On `UnknownToolError`: `emit_gate_decision` appends `autonomy_refusal` + raises. `process_tool_calls` catches, records `ToolDispatchDecision(tier=None, refusal_reason="unknown_tool")`, continues to next call (one bad tool_call doesn't poison the rest).
- On success: read `result.tier`. If `AUTO_EXECUTE`, append `Event(type=TOOL_CALL, metadata=ToolCallMeta(tool_name=tc.name, call_id=tc.id, params=tc.arguments).model_dump())`. If `COUNTDOWN_CONFIRM` or `HARD_CONFIRM`, **do NOT append `tool_call` event** (P2 UI work emits later) — record `tool_call_event_appended=False`.
- **Causal ordering**: `autonomy_decision` event lands **before** `tool_call` event in event-stream timestamp order (emit_gate_decision appends first; `process_tool_calls` appends `tool_call` after). Pin in ADR-013 D2.
- Tests (§1 cross-module integration; ≥6 tests):
  - AUTO_EXECUTE path: 1 tool_call → 1 autonomy_decision event + 1 tool_call event in stream, timestamps in order.
  - COUNTDOWN_CONFIRM path: 1 tool_call → 1 autonomy_decision event, NO tool_call event.
  - HARD_CONFIRM path: 1 tool_call → 1 autonomy_decision event, NO tool_call event.
  - UnknownToolError path: 1 tool_call (unknown) → 1 autonomy_refusal event, NO tool_call event, decision records `refusal_reason: "unknown_tool"`.
  - Mixed batch: 3 tool_calls (1 known/AUTO + 1 known/HARD + 1 unknown) → 3 ToolDispatchDecision; expected event counts per tier.
  - `user_explicit_intent` derivation: same tool, same tier-config, USER_INPUT trigger → effective threshold lowered per ADR-005 D5; non-USER_INPUT trigger → raw thresholds.
- Tests (§3 cleanup): event_store.append exception during tool_call append propagates unwrapped per ADR-011 D7-b precedent. Tests assert the exception type (no swallowing).
- Tests (§6 schema invariants): ToolDispatchResult / ToolDispatchDecision frozen + extra="forbid" (4 tests covering: frozen, extra="forbid", required-field-absent, wrong-type).
- No new error class (`ToolCallParseError` was speculatively named in brief §"Tests" — pre-investigated: not needed, since `ToolCall` parsing already happened in P1.1 LLM layer and raises `PermanentProviderError` there if malformed).
- **No LLM imports** (`agents/tool_dispatch.py` imports from `autonomy/emission`, `core/event`, `agents/schema` only). Constitutional test `test_constitution_no_llm_calls_in_autonomy_module` stays green; the new module lives in `agents/` which is allowed to import `autonomy/`, but tool_dispatch itself touches no LLM call site (it consumes pre-parsed `ToolCall` instances).

**Out of scope**: tool execution itself (P1.6+); P2 UI countdown loop; per-tool cost estimation; new constitutional test (`agents → autonomy` direction already allowed per P1.4; the existing constitutional surface covers).

### Brief push-backs

**#1 ADR-013 yes/no — lean YES; senior pin: YES.**
First runtime exercise of `agents → autonomy` edge that P1.4 only allowed. ADR-013 D1 (dispatch site) is non-trivial after pre-investigation — option (b) is structurally impossible; the choice between (a) and (c) has lasting refactor cost. Pattern-locking value: every future tool-using agent (operator-style or otherwise) inherits the dispatch contract.

**#2 Dispatch site — pre-investigated; senior pin: option (c) SIBLING MODULE called from dispatch_turn.**
Brief listed 3 options. Pre-investigation result:
- **Option (b) — RoomRuntime.run_turn post-dispatch: STRUCTURALLY IMPOSSIBLE.** `dispatch_turn` discards `response.tool_calls` after extracting `response.content` (see `agents/dispatch.py:117-127`). By the time `dispatch_turn` returns, tool_calls are gone unless `TurnResult` is extended to carry per-agent tool_calls. Extending TurnResult breaks the reviewer-validated P1.4/P1.5 contract — added cost > separation benefit.
- **Option (a) — inline in dispatch_turn: viable but bloats.** dispatch_turn becomes responsible for tool-call gating, event ordering, error handling. Reviewer-validated shape (lean per-agent loop with one LLM call + one event append) is compromised.
- **Option (c) — sibling `agents/tool_dispatch.py` called from dispatch_turn: senior pick.** dispatch_turn gains exactly one new call site (`if response.tool_calls: process_tool_calls(...)`). The sibling owns the gating logic + event emission ordering + error handling. Mirrors ADR-011 D4's "separate concern" pattern (dispatch vs context-builder; here dispatch vs tool-call-handling). TurnResult contract unchanged.

**#3 LLM-tool-call parsing shim — pre-investigated; refuted.**
