**Subject:** Build P3.3 — a **read-mostly GUI MVP** (React/TS) that **reads** a room's event/room stream (HTTP snapshot + WS live) and **sends user intent** (`POST /intent`), binding the **frozen ADR-025 API contract**. This is a **new stack** (React/TS/node — nothing shared with the Python product) and the **frontend-track opener** (roadmap §5's biggest parallelism win). It makes the product **visible/demo-able** to non-CLI users: type a message → watch the agents respond live.

## What it binds (the frozen contract — no new backend)

The GUI is a **pure consumer** of the P3.2 API (ADR-025). It binds: the HTTP read/intent endpoints + the WS live stream + the committed `openapi.json` (HTTP types) + `asyncapi.md` (WS semantics: replay→`replay_complete`→live, dedup by `event.id`, `StreamErrorMessage` `stage:"turn"`→reconcile-via-replay). **No backend change** — P3.3 adds zero Python; the API is the sole boundary.

## ⭐ The constitutional spine (NON-NEGOTIABLE — inscribe in ADR-026; not a choice)

The GUI is a **view + intent surface; backend-authoritative** (handoff §747/§898). The spine — most of it is *structurally enforced* by the API, but the senior/ADR must inscribe and the GUI must honor:

1. **View + intent only; no decision surface.** The GUI **reads** the stream + **sends** user intent; it makes **no** state/routing/autonomy decision. (The API already prevents forging — the GUI POSTs `IntentRequest{type,content,…}`; the server stamps `author:"user"`. The GUI **cannot** and **must not** decide state.)
2. **Binds the API contract ONLY.** The GUI must **not** reach into the Python product — no `orchestrator` import, no direct event-store/sqlite access, no backdoor. The HTTP/WS API is the **sole** boundary. (This is what keeps backend-authoritative true.)
3. **状态机不暴露 — the GUI's UNIQUE constitutional duty (§6.2/§748).** The wire is **raw** (raw `state`/event-type names). The GUI maps internal vocabulary to human terms (`agent→助手`, `snapshot→进展`, `memory→经验`, `skill→不暴露`, `autonomy level→工具调用`, `dissent dimension→挑战`, `state machine→不暴露`, …) and **never surfaces raw internal vocabulary to the user**. (Where the mapping lives + how a node GUI reads it is a decision — §Decisions(a).)
4. **Partial-turn correctness.** Handle `IntentError`/`StreamErrorMessage`: `stage:"turn"` → intent landed, **reconcile via replay, do NOT re-post**; `stage:"append"` → safe to retry.
5. **No forge attempt.** Send only allowlisted intent types (`USER_INPUT` for the MVP; the contract omits `author`/`id`/`timestamp` — don't try to set them).

## Scope (decision g — surface; lean below)

**In scope (P3.3 MVP — lean):**
- **Read view**: load a room (HTTP `GET /snapshot` or `/events`) + a **live event stream** (WS `/stream` — replay→`replay_complete`→live, with dedup + reconnect-replay). Render the conversation (events → messages, mapped via ui_strings).
- **Send user intent**: a compose/send box → `POST /rooms/{id}/intent` `{type:"user_input", content}` → watch the agents' responses arrive on the WS. The core demonstrable loop.
- **Room create/list**: minimal (`POST /rooms`, pick a room type) to have somewhere to talk.
- **The human-term mapping** (`ui_strings`) for the vocabulary the MVP surfaces.

**Out of scope (defer to P3.6 GUI completeness):**
- `DECISION`/`RETRACTION` confirm/retract UX; the rich §6.4 patterns (the 280px progress panel, decision 3-stage, AI-multi-perspective ✨, leave/return symmetry); full L2–L4 complexity layers; theming/polish; multi-room navigation depth; auth (localhost-trust MVP, ADR-025 D7).
- Any backend/API change (if the GUI needs a field the contract lacks → surface; don't add a backdoor).

## Decisions (surface for the architect — do not self-decide; ⭐ = new-stack-specific)

**⭐ (a) Frontend stack + scaffold + `ui/` location.**
- **Stack — lean:** **React + TypeScript + Vite** (handoff §11 says React+TS; Vite = the standard fast scaffold/HMR). **State: Zustand** (handoff §11: "Zustand 或 Jotai,不要 Redux" — lean Zustand, simplest). **UI: restrained** per §6.1 (no gradients/shadows/neon; **Tabler Icons** outline) — lean Tailwind **or** plain CSS modules over a heavy component lib. Architect rules stack + state lib + UI approach.
- **`ui/` location — lean: top-level `ui/`** (repo-root sibling of `src/`/`tests/`/`docs/`; its own `package.json`/`node_modules`/gate). *(Handoff §10 sketched `src/orchestrator/ui/`, but nesting a node/TS app inside the Python package is awkward — surface the tension; architect rules.)*
- **`ui_strings` home + consumption (sub-decision, ties to spine #3):** `config/ui_strings/` (handoff canon) **served via an API endpoint**, **or** GUI-owned (`ui/`, a TS module), **or** a build-step copy? A node GUI can't cleanly read a Python `config/` dir at runtime. Lean: **GUI-owned for the MVP** (simplest; the GUI is the only consumer) **or** API-served if the `config/ui_strings/` canon matters. Architect rules.

**⭐ (b) Frontend gate + `contributing.md`.** The Python gate (ruff/mypy/pytest) does **not** apply to TS. The frontend needs its **own** gate: **eslint** (lint) + **tsc --noEmit** (typecheck) + **vitest** (unit/component tests) + **prettier** (format) — run in `ui/` (node), separate from the Python gates. `contributing.md`: add a **frontend-gate section** (the `ui/` gate command) **separate** from the Python gates (mirror the P3.2 `[api]`-extra note pattern — a clearly-scoped sub-gate). The PR template's Q1–Q5 are Python-product-specific; lean a **frontend-adapted checklist** (view-only? binds-API-only? ui_strings-maps-no-raw-vocab? partial-turn handled?). Architect rules the exact tools + the contributing.md split.

**⭐ (c) node environment setup.** The junior + reviewers need **node/npm** to run the frontend gate. Surface: **pin a node version** (`.nvmrc` / `package.json engines`), choose a **package manager** (lean **npm** — ubiquitous; or pnpm), document setup in `ui/README.md` + `contributing.md` (node X → `npm install` → `npm run dev`/`gate`). **How do the junior/reviewer sessions get node?** (is it installed in those environments? a session-setup step?) Architect rules node version + package manager + the env-provisioning answer.

**⭐ (d) ROLE arrangement — the key new-stack question.**
- **Sonnet junior for frontend?** **Lean: OK** — React/TS is well within Sonnet's range. Caveat: there's **no existing frontend to pattern-match** (unlike Python, where the junior mirrors existing modules), so the **plan must be explicit** about the FE patterns (component structure, the API client, the WS hook, the store shape).
- **Frontend review — who, and what does R0-A mean for React/TS?** **Lean:** I (architect-partner) R0-A the **spine** (view-only? binds-API-only? ui_strings-no-raw-vocab? partial-turn handling?) + the **contract-binding correctness** (types match `openapi.json`; WS replay/`replay_complete`/dedup/reconnect/`StreamError` handled) + general code quality — I can review React/TS. The FE-idiom/a11y/render-perf lens is a different expertise.
- **dual-lens R0-B for frontend?** **Lean: SKIP for the MVP** (per `dual-lens-r0b.md` — a read-mostly **consumer of a frozen contract** is lower runtime risk than the API server; only the WS-client robustness is a real integration surface, which R0-A focuses on). Architect rules whether a **frontend-specialized 2nd lens** (or a cross-family TS lens) adds value here. **This is the most genuinely-architect call of the slice.**

**⭐ (e) API integration — codegen vs hand-written; WS client.**
- **HTTP client — lean: codegen the types** from the committed, drift-tested `openapi.json` (e.g. `openapi-typescript`) so the GUI types track the contract automatically (a contract change regenerates) + a thin typed `fetch` wrapper. (Alt: hand-written typed client — more control, drifts.) Architect rules.
- **WS client — hand-written** (AsyncAPI is a markdown note, not codegen-able): a typed client over the `StreamMessage` envelope handling connect → replay → `replay_complete` (switch UI "loading"→"live") → live (dedup by `event.id`) → `StreamErrorMessage` (`stage:"turn"`→reconcile) → ping keepalive → **reconnect-replay**. Confirm.

## Frontend-track independence (explicit assessment — roadmap §5's biggest win)
- The frontend is a **fully separate codebase + toolchain + gate**, binding **only the frozen API contract** (no shared code, no Python import). So the **frontend track (P3.3 → P3.6) runs independently of the backend track (P3.4 MCP → P3.5 plugin)** — distinct stack + skillset (React/TS vs Python). The **only** coupling is contract evolution (a backend slice adding an endpoint/field → additive; codegen catches it). This is the cleanest parallel track in P3.
- **Within P3.3:** single-junior serial (one FE codebase, coupled MVP) — no within-slice parallelism (consistent with the serial-junior principle).

## Constraints (do not violate)
- **The constitutional spine above** (view+intent; backend-authoritative; **binds-API-only — no Python/DB backdoor**; 状态机不暴露 via ui_strings; partial-turn correctness; no forge attempt).
- **No backend/API change** — P3.3 is frontend-only; if the GUI needs something the contract lacks, **surface it** (a contract change is a separate decision), don't reach around the API.
- **Bind the frozen contract** — generate/track types from `openapi.json`; honor `asyncapi.md`'s WS semantics exactly.
- **RC-23-safe** ADR-026 (if ruled) — Proposed; no literal `Status: Accepted` substring until accepted.
