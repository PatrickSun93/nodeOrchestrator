**Subject:** Build P3.7-remote — the two deferred **remote** surfaces: **(B1)** a **Posture B subprocess-isolated plugin executor** (replacing the in-process `importlib` path with a killable, scoped-env, bounded-timeout subprocess) and **(B2)** a **remote MCP transport** (SSE/streamable-http over the stdio-only client). This is the **heaviest constitutional/security slice of P3** — it crosses the trust boundary P3.4/P3.5 leaned on: from **operator-curated/local** (where curation *is* the trust) to **untrusted/remote provenance** (where it is not).

## The substrate + the deferred triggers (verified)

P3.7-remote invents **no** gate, executor, MCP client, or plugin loader — all exist. It absorbs three deferrals:

| Trigger | Source | Piece |
|---|---|---|
| Posture B subprocess isolation for plugin tool code | ADR-029 **D4** ("REQUIRED once provenance untrusted; reserved for P3.7 remote") + the itemized A→B migration | **B1** |
| Remote install / registry / fetch-from-network + the discovered-but-not-activated consent | ADR-029 scope + **D5** ("a P3.7 concern when provenance becomes untrusted") | **B1-coupled (§a)** |
| SSE / streamable-http remote MCP transport | ADR-027 **D1** ("remote = larger trust surface; deferred to P3.7") | **B2** |

## ⭐⭐ The constitutional spine (NON-NEGOTIABLE — inscribe; the remote/untrusted case changes the *trust premise*, never the spine)

Per Principle 5 + roadmap §9 — the senior/ADR(s) must inscribe and the impl must enforce:

1. **The gate stays the sole chokepoint — unchanged.** A remote MCP tool **and** a Posture-B/remote plugin tool route through the **same** code autonomy gate (`process_tool_calls → emit_gate_decision`); tier from code-classified reversibility; **unregistered/unclassified → `UnknownToolError` → refused** (fail-closed). B2 is a **transport** change, not a gating change — ADR-027 D2 "feed-the-gate-unchanged" holds **verbatim** (the gate empty-diff invariant must survive).
2. **Remote does NOT bypass the allowlist; routing = code.** A remote MCP server is **still** an allowlist entry; remote/fetched plugin code is **still** opt-in (the *consent granularity changes* — §a — but never to "auto-trust on fetch"). **Discovery ≠ permission, one level up: *fetching* ≠ *trusting*.** No remote infra brings an LLM routing/judgment decision; model-selection stays the code router + the P2.7 Layer-4 override; **no new routing/judgment `LLMPurpose`**.
3. **Self-asserted tier is never authoritative.** A remote server's protocol hints + a fetched plugin's claimed reversibility are **advisory-capped → host-authoritative-or-default-0** (ADR-027 HR#2 / ADR-029 D5) — a remote source cannot self-classify a write tool to dodge `HARD_CONFIRM`.
4. **Untrusted results — *more* untrusted, not less.** A remote MCP server is **not** a user-launched local subprocess → results stay size-limited, content-gen-interpreted (`TOOL_OUTPUT_INTERPRET`), untrusted-framed, no auto-action; **no tool-result drives a routing/autonomy decision**.
5. **Credential safety + scoped env carry forward — and become REAL.** Remote transports need credentials (auth tokens / TLS) → **`api_key_env` indirection only**, no plaintext. Posture-B subprocesses get a **minimal scoped env** (the c2 env-leak lesson) — and Posture B is exactly what makes the env boundary **real** for plugin code (it is **zero** under Posture A — ADR-029 D4 **L1**).
6. **Fail-closed everywhere.** TLS failure / unverified provenance / unreachable remote / fetch failure / subprocess crash-hang-timeout-orphan → **refuse / `TOOL_FAILED`**, never degrade-open, never crash/hang the orchestrator.

### ⭐ The crux to inscribe (the heart of this slice): remote provenance VOIDS the operator-curation premise

ADR-029 D4 accepted **Posture A only because plugins are operator-placed — curation IS the trust boundary.** A **fetched/remote** plugin is **not operator-placed**, so **curation no longer holds**, so **Posture A is constitutionally invalid for remote provenance** → **Posture B (killable subprocess, scoped env, bounded-timeout, fail-closed) is REQUIRED, not optional** (the architect already ruled this in ADR-029 D4). **You cannot ship remote-fetch on the in-process executor** — that is the inscribed **L1** (full host privilege + every secret), **L1b** (import-time code ungated), and **L2** (server-wide DoS — the voided ADR-028 D5 bound) exposures with **no curation backstop** = a real vulnerability, not an accepted MVP posture. **B1 is therefore the enabling precondition for any remote-plugin capability** — the two are coupled (§a).

## Scope

**In:**
- **B1 — Posture B subprocess-isolated plugin executor.** Replace the in-process `importlib`/`exec_module` path (`plugins/code.py`) with a **killable subprocess** (minimal scoped env, bounded-timeout, kill-no-orphan, fail-closed → `TOOL_FAILED`) — the ADR-029-D4-itemized A→B migration (`importlib`→subprocess launch; `LocalToolFn`→a subprocess-runner adapter; `plugins/code.py` substantially reworked). This **restores the ADR-028 D5 per-turn liveness bound** (a subprocess is killable; in-process was not — resolves **L2**) **and** gives a **real isolation/env boundary** (resolves **L1**). Plus the **remote-provenance / consent** surface it gates (§a): fetched code runs **only** under Posture B; presence=opt-in (valid for operator-placed) is **replaced** for fetched code by an explicit activation/allowlist (ADR-029 D5 "discovered-but-not-activated").
- **B2 — remote MCP transport.** SSE and/or streamable-http (ADR-027 D1) over the stdio-only client, with the **remote trust knobs** (the new surface vs stdio — a remote server is *not* a user-launched local process): **TLS verification** (reject plaintext/unverified), **server-URL allowlist** (the remote analog of the stdio command allowlist), **auth/credential via `api_key_env`**, **bounded network timeouts**, **fail-closed**, **untrusted-result handling**. The **gating spine is unchanged** — a remote MCP tool gates exactly like a stdio one (the pre-classify-allowlist, ADR-027 D3).
- **One remote demo each** (the P3.4/P3.5 one-demo discipline): one remote MCP connector (a real `https://` endpoint) + one remote/Posture-B plugin demo — end-to-end, proving each loop, incl. the fail-closed paths (TLS/auth/subprocess failure → `TOOL_FAILED`/refused).

**Out (defer — likely P4):** a full plugin *registry/marketplace*; remote plugin *upgrade / version-coexistence / uninstall* lifecycle; auth beyond the MVP token/TLS; GUI surfacing of remote infra (frontend track); any change to the gate/executor **decision logic** (`score`/`decide_tier`/`emit_gate_decision`/`process_tool_calls` — unchanged).

## Decisions (surface for the architect — do not self-decide; ⭐ = constitutional/security/scope)

**⭐ (a) B1 — Posture B execution model + the remote-provenance coupling.**
- **Execution-model design (senior-design + architect breadth-confirm):** the A→B migration is itemized (ADR-029 D4 Reversibility / R0-B Y6): `plugins/code.py` (`importlib` + `LocalToolFn`) → a subprocess protocol (scoped env, bounded-timeout, kill-on-timeout, fail-closed); `LocalToolFn` → a subprocess-runner adapter. **The convergence to surface:** ADR-029 D4 itself observed *"a Posture-B plugin executable tool ≈ a bundled MCP server."* So **does Posture B REUSE the MCP-server subprocess mechanism** (a plugin tool ≈ a local stdio MCP server — **one** subprocess trust boundary, maximal reuse of ADR-027 D4's scoped-env/kill-no-orphan/bounded-timeout/fail-closed) **or build a distinct plugin-subprocess protocol?** **Lean: converge on the MCP-subprocess pattern** (don't build a second parallel subprocess surface; the security machinery already exists + is dual-lens-vetted). Architect confirms breadth.
- **⭐ Scope coupling (the genuine call):** does B1 land **with** the actual remote-fetch/registry capability, or is **Posture B built + tested standalone first**?
  - **B-coupled** — remote-fetch/registry + its required Posture-B executor together (the full untrusted-remote-plugin story end-to-end).
  - **B-executor-first** *(lean)* — build + test the **Posture B executor migration** demonstrated on a **local** plugin (so the execution-model change is verified in isolation, the D5 bound re-proven, the env boundary tested), then **defer remote-fetch/registry** to a further slice. Lower-risk: the migration is the hard, testable part; remote-fetch is additive once the safe executor exists. Architect rules.

**⭐ (b) B2 — remote MCP transport + the remote trust surface.** Architect rules:
- **Transport:** SSE / streamable-http (the two the MCP SDK offers). **Lean: streamable-http** (the current MCP standard; SSE is the legacy variant) — confirm which (one or both).
- **Remote trust knobs** (the new surface — the senior designs within the ADR; the *posture* wants the architect's nod, like ADR-027 D4's allowlist ruling): **TLS verification** + **server-URL allowlist** (`https://` endpoints; the remote analog of the stdio command allowlist) + **auth via `api_key_env`** + **bounded network timeouts** + **fail-closed** + **untrusted-result limits**. Confirm the posture (the local allowlist/credential pattern, lifted to remote endpoints — and *stricter*, because a remote server is more untrusted than a user-launched one).

**⭐ (c) ADR vehicle(s).** Both B1 + B2 are new heavy trust surfaces:
- **B1** (Posture B + remote provenance) is an **execution-model change + a trust-premise shift** → **lean: a new ADR** (e.g. **ADR-031**, *Posture-B executor / remote-plugin provenance*) rather than a mere ADR-029 amendment (the change is too substantial for an amendment).
- **B2** (remote transport) → **a new ADR** (e.g. **ADR-032**, *remote MCP transport*) **or** an **ADR-027 D1 amendment** (D1 scoped remote as "additive/deferred", so an amendment is defensible). Architect rules vehicle + numbering. **RC-23-safe** (Proposed; no literal `Accepted` substring until accepted).

**⭐ (d) dual-lens R0-B — MANDATORY (confirmed; `requires_cross_family_review: true` already set).** ≥2 criteria hold decisively (all 4, in fact): **(1)** new concurrency surface (the Posture-B subprocess executor — kill/timeout/orphan; the ADR-027/028 dual-lens class); **(2)** new cross-package edge (remote-fetch/provenance; the subprocess executor replacing in-process `plugins/code.py`); **(3)** a contract ≥5 future tasks bind (the remote-plugin/registry + remote-transport config = the P4 extensibility story); **(4)** **first runtime exercise of untrusted-remote-provenance code execution** — the largest trust surface to date, **exceeding** P3.4/P3.5 (those were *local/operator-curated*; this is *fetched/untrusted*). The trust-premise shift (curation no longer holds) is exactly the cross-family failure-mode lens (malicious fetched code, subprocess escape, TLS bypass, provenance spoofing, env-leak — recall the c2 env-leak catch was a cross-family find). The senior authors `docs/process/reviews/P3.7-remote/external-r0b-prompt.md`.

**(e) MVP scope.** **Lean: one remote MCP demo connector** (a real `https://` MCP endpoint) **+ one remote/Posture-B plugin demo** — the one-demo-per-surface discipline (P3.4/P3.5), each proving the loop + the fail-closed paths. Architect rules the demo scope (e.g. whether B-executor-first means the "remote plugin demo" is instead a *local* plugin run under Posture B to prove the migration, with the remote-fetch demo deferred).

## Parallelism
- **P3.7-remote runs ∥ P3.7-content** — disjoint footprints (`mcp/transport.py` + `plugins/code.py` rework + new provenance/consent code here; `config/` + `plugins/<new>/` there) + disjoint risk/review. Independent of the frontend track.
- **Within P3.7-remote:** **single-junior serial** — the subprocess/trust surface wants one careful hand + the dual-lens, not fan-out (the P3.4/P3.5 posture). (B1 and B2 are two surfaces, but tightly coupled to the one trust boundary; serial.)

## Constraints (do not violate)
- **The constitutional spine + the remote-provenance-voids-curation crux above.** Fetched/remote plugin code **must never** run in-process (Posture A); Posture B is required off-local (ADR-029 D4).
- **Feed the gate/executor/MCP-client; don't change their decision logic** — B2 is a transport addition; B1 is an executor-mechanism swap (in-process → subprocess). Neither touches `score`/`decide_tier`/`emit_gate_decision`/`process_tool_calls`. The empty-gate-diff invariant (ADR-027 D2 / ADR-028 D6 / ADR-029 D3) holds; B1 extends it to an **empty-gate-diff-with-a-new-executor-mechanism**.
- **Restore the ADR-028 D5 liveness bound** — the killable subprocess must re-establish the absolute per-turn bound that Posture A voided (L2); a Posture-B tool call is bounded-timeout + killable.
- **Bind ADR-027 D4 / ADR-029 D4-D5, don't restate** — the remote trust knobs ARE the lifted stdio/local posture; the new ADR(s) compose them for the remote/untrusted case.
- **Inscribe-before-producer** — the remote-transport config + the remote-plugin/provenance contract are bound by P4; pin them in the ADR(s) before producers bind. **RC-23-safe** ADR(s).
