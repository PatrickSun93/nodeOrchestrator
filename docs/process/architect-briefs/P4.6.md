# Architect brief — P4.6: COUNTDOWN auto-fire-on-timer — the first human-out-of-loop execution (decision-surface)

**Task:** P4.6 (C1) — give the `COUNTDOWN_CONFIRM` tier its **auto-fire-on-timer** semantics: after a configured window with no human action, the system **executes the gated call itself**. P4-roadmap §3.C / the ADR-030 **D4** forward hook ("auto-fire is a clean follow-up slice … the architect may rule it in"). The **Wave-3 completeness/polish** slice (roadmap §4: `P4.6 autonomy auto-fire-on-timer [small; rides ADR-030 confirm machinery]`); independent of every other open slice.

**Class:** **lean dual-lens** (roadmap §8: "C1 auto-fire … introduces a **human-out-of-loop** execution — the *opposite* of the trust surface ADR-030 established; must be inscribed as honestly as `RB-FS/NET`"). `requires_cross_family_review: true` (set in `.workflow/P4.6.yaml`). **New ADR-040** (next unused; ADR-039 is the highest existing).

**Status of this doc:** a **DECISION-SURFACE**, not a plan and not a set of decisions. Five decision points carry **architect-ratifiable leans + tradeoffs**; the architect-partner does **not** decide. **The core tension** — and the reason this small slice is dual-lens — is that auto-fire is a **deliberate weakening of the human-in-the-loop posture** the whole confirm machinery (ADR-030) was built to establish: ADR-030 **D7(c)** lists *"COUNTDOWN has no server-side auto-fire (no headless execution)"* as a **probed trust invariant**, and P4.6 **conditionally inverts it** for the COUNTDOWN tier. That inversion must be inscribed honestly, not softened (roadmap §177). The load-bearing pair is **DP1 (timer mechanism + durability)** and **DP4 (the human-out-of-loop boundary)** — *decide them together: the mechanism and the boundary it actuates.* **DP2's provenance** sub-call is the honesty crux. No plan / ADR-040 is drafted until the architect ratifies (≥ DP1, DP4).

## 0. What exists today + what C1 adds (verify-cited `origin/main` @ 408e568)

**The "countdown" in `COUNTDOWN_CONFIRM` is, today, a name and a UI hint — there is no timer anywhere.** The tier is decided by pure code; both confirm tiers then take the **identical** wait-for-human path.

| Surface | What exists **today** (verified) | The gap C1 closes | Src |
|---|---|---|---|
| **The tier** | `AutonomyTier{AUTO_EXECUTE, COUNTDOWN_CONFIRM, HARD_CONFIRM}`; `decide_tier` purely maps `eff_confirm ≤ score < eff_auto → COUNTDOWN` — **reversibility-only, no timer concept**. | The tier gains a *timer*; the **gate decision logic stays byte-frozen** (the timer adds no new autonomy decision — DP2/Lens B). | `autonomy/scoring.py:11-16,165-207`; ADR-005 D4 |
| **COUNTDOWN == HARD today** | `process_tool_calls`'s countdown/hard branch is **one `else`**: both append a `TOOL_CALL_PENDING` (tier recorded in `ToolCallPendingMeta`) and then **wait forever** for a human `POST /confirm`. If the user does nothing the call **stays pending indefinitely — identical to HARD**. ADR-030 D4: *"the countdown is a UI hint, not a server timer."* | COUNTDOWN diverges from HARD: it acquires a server-side expiry that **actuates** on its own. HARD must **never** acquire one (DP4a). | `agents/tool_dispatch.py:126-145`; ADR-030 D4 |
| **The confirm-actuate path** | `_post_confirm` (`POST /confirm`) runs on the **single writer** (`writer_executor`, `max_workers=1`): position-anchored **still-pending check** (idempotency layer 1) → on approve, **reconstruct an agent-authored `TOOL_CALL` from the persisted record** → `execute_pending_tool_calls` (executor `call_id` guard = layer 2). `check→append→execute` atomic, no TOCTOU. | Auto-fire is **a third caller of this exact closure** (DP2a) — same atomicity, same idempotency, executor unchanged. | `api/app.py:734-867`; ADR-030 D3 |

The approve site is the **"D5 checkpoint seam #1: authenticated ⇒ allowed; role check would gate here."** | Auto-fire has **NO human approver at all** — a step *beyond* `RB-AUTHZ` (which still required an *authenticated* operator). How the no-approver fact is recorded is the honesty crux (DP2b). | `app.py:753,759,814,841`; `core/event.py:351-380`; ADR-039 D6 |

The server *has* an asyncio loop (lifespan), the single `writer_executor`, the per-thread reader pool, and the `RoomEventBus` — but **zero background-task infrastructure**. Auto-fire arguably *needs* the boot scan ADR-030 left open. | ADR-030 Consequences L104-106 |

**Framing the boundary P4.6 turns on (the spine that keeps this constitutional).** ADR-030 **D4** deferred auto-fire and named the *exact* surfaces this brief must resolve: *"which thread fires it vs the single writer; what survives a server restart mid-window; how the timer interacts with a concurrent cancel"* + *"a posture where the system executes a gated operation with no human in the loop."* Roadmap **§10** gives the framing that keeps "routing/gating = code" intact: **auto-fire must NOT become an external/timer-decided autonomy** — *"it is a scheduler **over an already-gated** COUNTDOWN tier (the gate decided the tier; the timer only **actuates** the operator's standing 'approve-unless-cancelled')."* The gate still decides; the timer only actuates a standing posture. Hold that line and the slice is a *recording/actuation* addition, not a new decision surface — exactly as ADR-030 D1 was for the pending record.

## 1. ⭐⭐ DP1 — Timer mechanism + restart durability (load-bearing — the architecture)

Where does the expiry live, who fires it, and what survives a restart mid-window?

| Option | What it builds | Trade-off / honest residual |
|---|---|---|
| **(a) In-process asyncio timer per pending** | On each COUNTDOWN `TOOL_CALL_PENDING`, schedule a `call_later`/task that fires the auto-confirm on the writer after `window_s`. | Simplest, no new storage, precise. **But the timer lives only in event-loop memory** — a restart mid-window **loses it silently** (the COUNTDOWN never fires, or needs a recovery scan anyway). And `process_tool_calls` runs on the **writer thread**, so arming the timer needs `loop.call_soon_threadsafe` — a thread-boundary wrinkle. Re-opens the **exact durability hole** ADR-030 D4 named as a reason to defer. |
| **(b) Durable expiry + in-process sweep** (lean) | Persist `expires_at` at gate time (DP1′); a **single lifespan-started asyncio sweeper** wakes every *K*s, scans for COUNTDOWN pendings past `expires_at` that are **still-pending** (the existing position-anchored predicate), and dispatches the fire **to the writer executor**. | **Event-sourced-native + survives restart** (the expiry is in a durable event → the sweeper picks it up on boot — directly answers D4's "what survives a restart"). Reuses the still-pending predicate; stays **single-process** (no new infra — matches the roadmap's "small" framing). Cost: fire latency is rounded up to the sweep tick (negligible for a seconds-to-minutes window); a new, bounded background-task surface beside the single writer (ADR-025 D6 note). |
| **(c) External scheduler** (cron / APScheduler / job queue / separate process) | Offload timing to an external scheduler. | Heavyweight: new dependency + deployment surface, breaks the single-process localhost posture, and over-builds what roadmap §3.C frames as "small; rides ADR-030 confirm machinery." **Lean: reject** unless the architect foresees a distributed deployment. |

**Lean: (b)** — durable expiry + in-process sweep. It is the only option that satisfies ADR-030 D4's restart-survival concern *and* stays single-process, and its thread story (sweeper → writer executor) is cleaner than (a)'s cross-thread arming. *(A hybrid — (a)'s precise timer for the live path + (b)'s durable sweep as the restart backstop — is possible but runs two mechanisms; surface only if the architect wants sub-second fire precision.)*

**Embedded sub-decisions (surface with DP1):**
- **DP1′ — where `expires_at` is stored.** Lean: a field on the gate-produced pending record (`process_tool_calls` is the one site holding tier + `call_id`, mirroring ADR-030 D1's "the pending record holds everything to reconstruct"). **But that adds a field to `ToolCallPendingMeta`, a constitutional-test-locked schema** — inscribe it (the ADR-030 D1 / ADR-039 D6 precedent for additive metadata fields). Alternative: a sidecar table — rejected-lean (duplicates state, breaks "the event stream is the truth").
- **DP1″ — expired-during-downtime semantics.** A COUNTDOWN whose `expires_at` passed *while the server was down*: **(i) fire immediately on the next sweep** (the standing approve-unless-cancelled posture remained valid), **(ii) re-arm a fresh window** (give the operator the cancel window they "lost"), or **(iii) leave-for-explicit-human** (downtime voids the auto-posture). This is a genuine **safety-vs-liveness** sub-call — lean **(ii) re-arm** as the conservative default (no call fires *without a live cancel window having existed*), but it is the architect's posture call. *(Whichever is chosen, C1 effectively builds the bounded boot-recovery scan ADR-030 left open — for COUNTDOWN only.)*

## 2. DP2 — Auto-fire execution path (⭐ lean) + provenance (⭐⭐ the honesty crux)

**(2a) ⭐ Execution path — reuse the confirm-actuate closure, don't build a new one.**

| Option | Trade-off |
|---|---|
| **(a) Reuse** (lean) | Extract `_post_confirm`'s approve branch (still-pending check → reconstruct agent-authored `TOOL_CALL` from the persisted record → `execute_pending_tool_calls` → publish to bus) into a **shared helper** called by both the HTTP handler and the sweeper, **both on the writer executor**. Executor **unchanged + tier-agnostic** (ADR-028 carry-forward); idempotency layers 1+2 **inherited** (→ DP3 falls out free); `TOOL_CALL` appenders stay at **two** (HTTP-confirm + timer-confirm), keeping the ADR-028 D6 **t4 appender-guard** at "each downstream-of-gate." |
| **(b) New path** | A second actuation surface re-opens the t4-appender invariant and duplicates the idempotency reasoning. **Lean: reject.** |

The auto-fire append is **downstream-of-gate** by the same logic as the human-confirm append: it reconstructs `{tool_name, call_id, params}` from a **persisted, gate-produced COUNTDOWN record**, never inventing a call — Lens B re-probes this (the t4-guard-adjacent property). Reuse also gives bus-publish for free (the GUI sees the live `TOOL_CALL`/`TOOL_RESULT` stream).

**(2b) ⭐⭐ Provenance — who authorized an execution no human approved?** This is the honesty crux where C1 meets P4.5. The `TOOL_CALL` stays `agent:<initiating_agent>`-authored (unchanged — the gate approved *that agent's* op). The open call is **what goes in the approver slot**:

| Option | Trade-off |
|---|---|
| **(i) `approver_user_id = None` + an explicit positive auto-fire marker** (lean) | A dedicated field — e.g. `approval_source: Literal["human","auto_timer"]` or `auto_fired: bool` on the confirm metadata — so the audit reads **"executed BY TIMER, no human approver,"** not an ambiguous null (which collides with the pre-P4.5 legacy `None`). **Silence under-records the single most security-relevant fact of this slice.** |
| **(ii) A sentinel principal** (e.g. `approver_user_id = "system:countdown-timer"`) | Rejected-lean: `approver_user_id` is a **bare `<user_id>`** field (ADR-039 D1 namespace); a non-user sentinel pollutes it and could confuse any future role/authz consumer. Keep the marker in a **distinct** field. |

**The deeper inscription (DP4d):** the real answer to "who authorized this" is **not an actor at fire time** — it is the **operator's standing, config-time decision** to enable auto-fire with window *N* (+ the cancel window that elapsed unused). **The human-in-the-loop moment moves *earlier*** — from per-action approval to the configuration act. That is precisely the residual to inscribe honestly. **Interaction with P4.5:** auto-fire is a step **beyond `RB-AUTHZ`** — `RB-AUTHZ` left *any authenticated account* a full actuator; auto-fire lets **no account at all** actuate within the window. Surface that this is qualitatively new, not a tightening of `RB-AUTHZ`.

## 3. ⭐ DP3 — Cancel / preempt race (mostly *inherited*, not newly built)

The reassuring result of DP2a: **the single writer already serializes the race, and the position-anchored still-pending predicate already resolves it — with zero new mechanism.**

- **Early human approve / cancel during the window** → appends a `TOOL_CALL` / `TOOL_CALL_CANCELLED`; when the timer later fires, its **still-pending check fails (`already_resolved`) → no-op.** ✓
- **The simultaneity instant** (human approves *exactly* as the timer fires) → both land on `writer_executor` (`max_workers=1`); **exactly one wins**, the other no-ops. The predicate is already in `PENDING_RESOLUTION_TYPES` (`core/event.py:401-408`). ✓
- **Deliberate non-change:** the timer appends an **ordinary `TOOL_CALL`** (same as human-approve), so it is *already* a resolution — **do NOT add a new resolution event type** (that would ripple into the idempotency scan + snapshot derivation, which ADR-030 D7 / ADR-039 D6 require unchanged). ✓

**Embedded sub-decision:** on cancel/approve, should the system **proactively cancel the timer** (drop the durable expiry / cancel the asyncio task)? **Optimization, not correctness** — under DP1b the sweeper simply skips an already-resolved pending. Lean: clear the durable expiry on resolution as housekeeping, but the still-pending check is the *correctness* guarantee. **The genuinely new race is timer-vs-restart (DP1″), not timer-vs-human** — DP3 is largely "confirm the existing serialization covers it," which it does.

## 4. ⭐⭐ DP4 — The human-out-of-loop boundary (load-bearing — the core honesty point)

Where, exactly, is the boundary of "the system acts without a human" drawn — and how is the residual inscribed? Four sub-calls, all load-bearing:

**(4a) ⭐⭐ COUNTDOWN-only; HARD *never* auto-fires.** A hard invariant enforced in code (the sweeper only ever arms/scans `tier == countdown_confirm`; a `hard_confirm` pending is structurally unreachable by the timer) and **pinned by a constitutional test**. ADR-030 D4/D7 framed HARD as "high-friction, explicit, no pre-selection"; a HARD auto-fire would be a spine violation. **Non-negotiable** — surfaced only to be ratified as the invariant, with the test, that Lens A probes.

**(4b) ⭐⭐ Is auto-fire reversibility-capped — or does *any* COUNTDOWN call fire?** The subtle trap: **COUNTDOWN ≠ reversible.** ADR-005 §5(c)'s own worked example puts `git_push` (reversibility=1) on **COUNTDOWN** when `operator` calls it with `user_explicit_intent` (the user-intent modifier shifts the band). So "auto-fire all COUNTDOWN" can headless-execute an **irreversible** op.

| Option | Trade-off |
|---|---|
| **(b1) No extra cap** | Any COUNTDOWN auto-fires; the gate already chose COUNTDOWN, the timer honors it. Simplest, most faithful to "the timer doesn't re-decide" — **but** lets an irreversible op execute with no human ever in the loop. The sharpest edge of the residual. |
| **(b2) Reversibility floor** | Auto-fire only fires COUNTDOWN calls with `reversibility ≥ R_floor`; below it, the call **degrades to explicit-confirm** (stays pending for a human). Bounds the blast radius; **but** adds a second threshold and a "COUNTDOWN that doesn't auto-fire" sub-state (muddies the tier's mental model + the UI affordance). The floor is **code/config, not LLM** — so it stays on the right side of "routing = code." |
| **(b3) Per-tool opt-in** | A `tools.yaml` flag (`auto_fire_eligible: bool`) — the operator declares which tools may headless-fire. Most explicit, most config surface; composes with (b2). |

**Lean: (b2) or (b3) over (b1)** — bound the headless blast radius so the *irreversible* tail can't fire with no human ever involved, while still delivering the convenience for genuinely routine ops. **But this is the architect's posture call** — it is *the* place the human-out-of-loop boundary is physically drawn, a `RB-FS/NET`-class Accept. ⭐⭐

**(4c) ⭐⭐ Opt-in, default OFF.** A config flag (e.g. `autonomy.countdown_auto_fire.enabled`, default **false**, + `window_s`). With it **off, COUNTDOWN behaves exactly as today** (explicit-confirm) — **zero regression**, and the ADR-030/P4.5 human-in-every-loop trust surface is **preserved unless an operator deliberately turns it off**. The opt-in default **is** the honesty mechanism (roadmap §10 "opt-in, fail-closed"): the system never silently goes human-out-of-loop. ⭐⭐ — lean strongly, surface only to ratify.

**(4d) Residual inscription — Accept the real surface, don't soften.** Inscribe a named residual (proposed **`RB-AUTOFIRE`**, the `RB-FS/NET`/`RB-AUTHZ` convention): *"When COUNTDOWN auto-fire is enabled, a gated operation executes with **no human in the loop at fire time**. The human-in-the-loop moment moves to the **config-time** decision to enable auto-fire (+ the unused cancel window); within the window a human may still preempt (approve early / cancel), after it the operator's standing 'approve-unless-cancelled' posture actuates the call. Bounded by: COUNTDOWN-only (4a), [the reversibility cap / per-tool opt-in of 4b], and opt-in-default-off (4c)."* This must read as honestly as `RB-FS/NET` did (roadmap §177).

## 5. ⭐ DP5 — New ADR-040 + amendments + the lean dual-lens two-lens design

**ADR-040 (new contract — the durable auto-fire scheduler + the human-out-of-loop posture):** the timer mechanism (DP1), the reuse-the-confirm-closure actuation + provenance (DP2), the inherited idempotency (DP3), and the boundary + residual (DP4). Expensive-to-change (the durable-expiry field shape + the posture bind future consumers) → **inscribe-before-producer**.

**Amendments this slice carries:**
- **ADR-030 D4** — the deferral *lands* (auto-fire was "a clean follow-up slice"); amend from deferred → realized.
- **ADR-030 D7(c)** — the probed invariant *"COUNTDOWN has no server-side auto-fire (no headless execution)"* is **conditionally inverted** for the COUNTDOWN tier when opt-in is on; this is **the** honest-inscription amendment.
- **ADR-005** (annotation) — the COUNTDOWN tier's semantics gain a timer (the tier-decision logic is unchanged; the *consequence* of landing on COUNTDOWN now differs).
- **ADR-025 D6** (note) — a new bounded background-task surface (the sweeper) beside the single writer.

**Lean dual-lens — `external-r0b-prompt.md`, two orthogonal failure-family lenses** (matches the architect's proposed split):
- **Lens A — auto-fire safety / over-authorization / race (the "headless execution done wrong" adversary).** Can the timer ever fire a **HARD** call (must be impossible — 4a)? Fire when **disabled**, or **outside** the window? Fire an **already-cancelled / already-approved** call (idempotency)? Fire into a **closed room** (the ADR-030 D3 step 2 room-state gate)? Honor the **reversibility cap / per-tool opt-in** (4b)? Is the **no-human-approver fact recorded honestly** (not a silent null — 2b)? Does the restart path (DP1″) ever fire **without a live cancel window having existed**? Does the boundary ever **escalate** beyond the configured one?
- **Lens B — spine no-regression (the "did the timer break the existing constitution" adversary).** Is the **gate decision logic byte-frozen** (`score`/`decide_tier`/`emit_gate_decision` — the timer **actuates, never decides**; **no new `LLMPurpose`**)? Is **confirm idempotency** intact (position-anchored still-pending; double-fire ≤ one `TOOL_CALL`; the writer-serialized human-vs-timer race)? Is the **executor unchanged + tier-agnostic**? Does the **t4 appender-guard** still hold (auto-fire appends only by reconstructing a persisted gate-produced record)? `PENDING_RESOLUTION_TYPES` + the snapshot derivation **unchanged**? **Backward-compat:** opt-in-off ⇒ behavior byte-identical to today (the additive metadata field never inspected on any existing path)?

*(The two are genuinely orthogonal — "auto-fire is unsafe / over-authorized" vs "auto-fire regressed ADR-005/028/030" — the dual-lens design goal, `dual-lens-r0b.md`.)*

## 6. Constitutional carry-forward watch-list (carry into the plan + ADR-040)

- **Routing/gating = code (the load-bearing framing).** Auto-fire is a **scheduler over an already-gated COUNTDOWN tier** — the gate decided the tier; the timer **only actuates** the operator's standing "approve-unless-cancelled" (roadmap §10). It must **NOT** become an external/timer-*decided* autonomy, and adds **no new `LLMPurpose`** — the timer is pure code.
- **No new decision surface.** The gate's `score`/`decide_tier`/`emit_gate_decision` stay **byte-frozen** (the ADR-027 D2 / ADR-030 D1 discipline — a *recording/actuation* addition, not a decision).
- **Backend-authoritative.** The auto-fired `TOOL_CALL` is reconstructed from the **persisted, gate-produced** pending record — never invented; the t4 appender-guard generalises to "the timer is a downstream-of-gate appender."
- **Confirm idempotency + crash-window (ADR-030 D7) preserved.** The timer is a third caller of the writer-atomic still-pending closure; it must not regress position-anchored idempotency / partial-turn / the (inherited) crash-window posture.
- **Opt-in, fail-closed, posture-ratified** (the P2.7-S3 → P3.5 → P4.5 trust-boundary discipline) — default OFF; COUNTDOWN-only; HARD never; the reversibility boundary ratified, not assumed.
- **Honest-residual inscription.** Accept the *real* human-out-of-loop surface (`RB-AUTOFIRE`), exactly as `RB-FS/NET` / `RB-AUTHZ` modelled — never a softened one (roadmap §177).
