## Background — what got designed in the architect-partner session

Architect-partner enumerated three automation shapes during the session that produced this brief:

- **Option A (status-visible, manual trigger):** state file documents current state; sessions read on start, write on end; architect manually trigger every transition. Minimal friction-reduction.
- **Option B (auto-trigger for low-risk segments only):** like A, plus auto-trigger on transitions that are verifications, not decisions — specifically (a) senior plan-vs-impl → architect-partner R0-A; (b) clean R0-A (0 🔴 / 0 🟡) → auto-open PR. **Any 🟡 or architect-decision point blocks for manual ack.**
- **Option C (full automation with 24h delays):** state machine progresses automatically, each state has 24h minimum dwell time.

**Architect chose Option B.** Architect-partner's pre-decision push-back surfaced four concerns (distance test conflict, bypassed intervention points, self-loop risk on same-family chain, ADR-008 itself needing distance test); architect heard them and explicitly chose B with full awareness.

The route to ADR-008-via-senior (this task) was the architect's chosen mitigation of the "architect-partner self-loops on workflow design" concern — senior reads context fresh, drafts ADR independently, architect-partner reviews.

## Architect-settled decisions

These do not need to be re-litigated in your ADR-008 draft (but state them as Decisions, with rationale):

### 1. Option B shape — gated vs auto-triggered transitions

**Gated** (architect intervention REQUIRED; state machine blocks until architect acks):

- Brief → senior plan start.
- Senior plan + ADR draft → architect Accept (status Proposed → Accepted).
- R0-A 🟡 finding → architect picks routing (which option / who fixes).
- PR merge to main.

**Auto-triggered** (state machine advances automatically when prior session pushes the required artifact):

- Senior plan-vs-impl review file (`docs/process/reviews/{task-id}/plan-vs-impl.md`) appears → fire architect-partner R0-A.
- Clean R0-A (0 🔴, 0 🟡 in `R0-A.md`) AND clean gates AND merge conflict-free → auto-open PR to main.

ANY 🔴 or 🟡 in a review file blocks the chain unconditionally.

### 2. State machine in code, not LLM

Per Principle 3.1 ("decision paths in code"). The state transitions are deterministic functions of (a) current state, (b) artifacts present in git, (c) gate status. No LLM call in the transition logic. Sessions consume LLM for their natural work (writing plans, reviewing, coding), but the orchestration layer is pure code.

### 3. Distance test preserved at architect-intervention points

The brief → senior plan transition is gated by architect; if architect wants 24h before ADR Accept, they hold the state and don't ack. The state machine respects whatever delay architect imposes. Auto-triggered transitions (plan-vs-impl → R0-A; clean R0-A → PR) intentionally do not have a delay — they are verification steps, not architectural inscribing.

### 4. Override capability at every state

Architect can force-advance any state, force-revert to any prior state, or halt the machine entirely. The state file is git-tracked so override actions are auditable.

### 5. Bootstrap exception is closed after this ADR

ADR-005 was the documented workflow-bootstrap exception (architect self-drafted because senior-planner role doc was being established alongside). Architect-partner proposed this very W-001 as a second bootstrap exception during the session; **architect rejected that path**, electing (ii) instead: senior drafts ADR-008. ADR-008 reinforces RC-3's senior-drafts rule by **not** extending the bootstrap exception. Document this in ADR-008's Considered Alternatives section: "architect-partner self-drafts ADR-008 (rejected — would extend the bootstrap exception beyond its stated one-time scope)."

## Constraints (do not violate)

- **No code in this task.** The ADR is a design artifact; the follow-up plan stub is a planning artifact. Both are docs.
- **No LLM proposals inside the state machine.** Per Principle 3.1, transitions are code. If your ADR draft proposes any LLM-based judgement in the state machine (e.g., "LLM determines if R0-A is clean enough to auto-PR"), reject it and document why.
- **Honor the role boundaries you helped codify in `senior-planner.md`.** ADR-008 must not propose architecture that would let architect-partner self-drive without architect intervention at the four gated transitions above.
- **Synchronous state transitions.** The state file is the truth; transitions are atomic file writes. No async / eventual-consistency / "fire and forget" semantics.

## Places I expect you to push back

Address each in your ADR-008's Considered Alternatives section (or as a separate Plan §5 push-back if the disagreement is about the brief itself, not the ADR design):

- **State file location**: `.workflow/state.yaml` vs `docs/process/.workflow/state.yaml` vs `docs/process/state.yaml` (no hidden dir). Architect-partner lean: `.workflow/state.yaml` at repo root (precedent: `.github/`, `.claude/` for tool-level config — `.workflow/` is the same kind of project-level harness directory).
- **State file shape**: single global file vs per-task file (`.workflow/{task-id}.yaml`). Lean: per-task, so multiple tasks can be in different states concurrently (e.g., P1.3 in `awaiting_review`, W-002 in `awaiting_plan`).
- **"Clean R0-A" detection**: grep R0-A.md for emoji markers vs structured frontmatter vs parsing the findings table vs explicit YAML field at top of R0-A.md. Lean: explicit YAML frontmatter field `verdict: clean | blocking | needs_architect`, written by the R0-A author. Grep-on-emoji is fragile to formatting.
- **Trigger mechanism**: GitHub Actions firing on push vs Claude Code session start checking state vs manual command (`go senior`, `go review`). Lean: session-start check (every session reads state on launch, knows what it should do; transitions still happen on push but the trigger is "next session launched" not "auto-CI-fire"). This avoids needing GitHub Actions integration and keeps human-in-the-loop on session spawning. **Push back on this** if you find a cleaner alternative.
- **Error-state semantics**: what happens if a session crashes mid-state? Lean: each state transition is its own commit; partial work is not committed; state file is updated atomically with the artifact. A crashed session leaves state at the prior committed snapshot. Push back if this misses a failure mode.
- **State vocabulary**: what are the canonical states? Lean (≤8 states total): `awaiting_brief`, `awaiting_senior_plan`, `awaiting_architect_accept`, `awaiting_junior_impl`, `awaiting_senior_plan_vs_impl`, `awaiting_R0A`, `awaiting_architect_decision` (on 🟡 routing), `awaiting_PR_merge`. Final state: `closed`. Push back if there's a missing or redundant state.
