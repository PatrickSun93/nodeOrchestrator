## RC-20 — Dual-lens R0-B independent-confirmation rate: 4 of 6 (first clean measurement)

**Surfaced:** 2026-05-29, at the close of P1.6.5 plan-stage dual-lens R0-B (after both lenses' findings were routed).

**Observation:** P1.6.5 ran both R0-B lenses at **plan stage against the same baseline** — the post-R0-A-absorption plan + ADR-016 (architect chose current-state parallel dispatch over wait-for-2nd-revision). Proxy lens first (`R0-B-cross-family.md`, in-session Claude contrarian, 6🟡/4🟢), then true cross-family external (`R0-B-cross-family-external.md`, DeepSeek V4 Pro, 5🟡/7🟢). **This is the first time in project history both lenses reviewed the same artifact and the overlap is directly measurable.**

### The numbers

External independently re-derived **4 of the proxy's 6** findings, without being told them (the external prompt steered probe directions but did not disclose proxy findings):

| Proxy finding | External | Class |
|---|---|---|
| Y2 — `append_in_transaction` bare-call footgun | 🟢-confirm | runtime |
| Y3 — FK-timing acceptance error ("CREATE raises") | Y8 (re-derived) | factual/test |
| Y4 — layering-guard set incomplete | Y10 (re-derived) | completeness |
| Y5 — `DecisionMeta` ID prefix gap | 🟢-confirm | schema |
| Y1 — append-caller grep miscount (5 vs 6) | **not re-raised** | cite/process |
| Y6 — keep `contradictions` (vs defer) | **not re-raised** (explicitly agreed deferred) | judgment |

The external added **3 net-new** the proxy missed, all runtime/schema-correctness:
- **Y7** — `conn ≠ event_store.conn` silent atomicity loss (unasserted invariant).
- **Y9** — no UNIQUE on `verified_knowledge.promoted_from_hypothesis_id`.
- **Y11** — shared-DB migration path untested (all tests `:memory:`).

So: **4/6 proxy findings confirmed (67%)**; the 2 not re-raised are both **non-runtime** (one cite/process, one already-agreed deferral) — neither a false positive; **3 net-new from the external**, all in the operational/runtime dimension the Claude family structurally under-weights.

### Why it matters — RC-15 dual-lens economics

[[RC-15]] (`dual-lens-r0b.md`) codified **when** to dispatch dual-lens (≥3 of 4 criteria) but left open the **economic** question: *is the in-session proxy lens trustworthy enough to lean on alone, or does the true cross-family external add enough to justify its dispatch cost?* P1.6.5 is the first cycle with a clean controlled measurement (same artifact, both lenses), and it answers both halves:

- **The proxy lens is TRUSTWORTHY.** 4 of its 6 findings were independently re-derived by a different model family. The 2 the external didn't re-raise are both non-runtime (cite-recount + agreed-deferral), not false positives. The proxy is not a throwaway "Claude reviewing Claude" — it caught real issues an external family confirmed.
- **The external lens is NOT redundant.** It added 3 net-new findings, every one runtime/schema-correctness (Y7 atomicity, Y9 schema constraint, Y11 test gap) — exactly the dimension the stated cross-family rationale targets. Y7 in particular is the **canonical cross-family catch**: a silent invariant (`conn is event_store.conn`) that *both* same-family reviewers (R0-A G2 + proxy G1) accepted as obvious — they praised D11 atomicity but stopped at "same connection = obvious." Textbook validation of *why* a different family is dispatched, not just *that* it found things.

**Conclusion this cycle: both lenses paid for themselves; neither dominates.**

### Sub-observation — the second lens also corrected an architect-partner routing over-reach

The external Y10 (+ architect-partner verification) corrected the proxy-Y4 routing: the proxy routing had said "add 4 guards incl `workflow/`"; the external flagged `workflow/` as dev-harness (zero product imports) → refined to 3 product-only guards. So the cross-family lens benefits the **routing synthesis**, not just the senior plan — a data point that architect-partner routing leans are themselves improved by the second lens.

### Status

**Open — single clean measurement (n=1 cycle).** P1.6.5 establishes the baseline (4/6 confirm + 3 net-new). Codification (e.g., "proxy sufficient for low-runtime-surface cycles; external mandatory for runtime/transaction-heavy contracts") needs 2–3 cross-cycle measurements of the confirmation rate. Per the project's RC-4 precedent (one instance ≠ codify), this stays a tracked candidate, not a graduated rule.

**Open question for the retro:** does 4/6 generalize, or is it an artifact of P1.6.5's particular shape? P1.6.5 is persistence + transaction-atomicity — a lot of runtime surface for an external family to find net-new in. A lower-runtime-surface cycle (e.g., a doc/process or pure-schema cycle) might show *higher* proxy/external overlap (external adds less net-new) — which would tilt the economics toward "proxy alone suffices for non-runtime cycles." The confirmation rate likely **co-varies with runtime-surface area**; the codification, when it comes, should be conditioned on cycle shape, not a flat rule.

## RC-21 — Impl-stage state reconcile-after-merge breaks the branch-ahead detection (merge-fragile vs plan-stage's merge-durable)

**Surfaced:** 2026-05-29, reconciling `.workflow/P1.6.5.yaml` after PR #26 (impl branch) merged.

**Observation:** at plan stage I reconciled the state file **after** merging PR #25 and `workflow advance` cascaded cleanly (`awaiting_senior_plan → awaiting_architect_accept → awaiting_junior_impl`) — because the plan-stage transitions key off **file presence on main** (`senior_plan_exists`, `adr_status == accepted`), which survives a merge. At impl stage I did the same thing (reconcile after merging PR #26) and `workflow advance` **stalled at `awaiting_junior_impl`** — "no transition fires." Root cause: `awaiting_junior_impl → awaiting_senior_plan_vs_impl` requires `artifacts.junior_impl_commit_present`, computed by `_has_junior_impl_commits` (cli.py) as *"`origin/claude/{task_id}-impl` exists AND is ahead of `origin/main` since `last_transition_at`."* The PR #26 merge put the impl branch's commits **onto** main, so the branch is no longer ahead (verified: `git log origin/main..origin/claude/P1.6.5-impl` empty; impl tip is an ancestor of main). **The merge destroys the exact signal the impl-stage cascade depends on.**

**The asymmetry (the real finding):** plan-stage detection is **merge-durable** (files on main); impl-stage detection is **merge-fragile** (branch-ahead). So the "reconcile after merge" workflow — which is correct + dogfooded at plan stage — silently breaks at impl stage. There is no warning; `advance` just reports "no transition fires," which reads like "nothing to do" rather than "the signal I need was destroyed."

**Why it matters:** this recurs on **every** impl cycle reconciled after merge. The plan-stage success trains the "reconcile after merge" habit; the impl stage punishes it. Without a fix, every impl-stage close needs an architect override — which inflates `override_history` with non-substantive entries (defeating the audit-signal value of overrides) and burns an architect decision on a harness gap.

**This instance's unblock:** architect override `awaiting_junior_impl → closed` (architect-only; reason cites this merge-fragility). Cycle stays 1 (override target is not `awaiting_junior_impl`, so no rework increment). P1.6.5 is genuinely complete (impl merged `9f13861`; plan-vs-impl + R0-A + R0-B all clean; gates green 896; zero substantive overrides).

**Candidate remedies (deferred — retro/W-series decides; this is an observation, not a graduated rule):**
- **(a) Make impl detection merge-durable** (mirror plan stage): `_has_junior_impl_commits` also returns True if impl commits are *merged into* main since `last_transition_at` (e.g., a merge commit referencing `claude/{task_id}-impl`, or the impl tip being an ancestor of main with commits after `since`). Then reconcile-after-merge cascades `awaiting_junior_impl → … → awaiting_PR_merge → closed` like plan stage. Cleanest; removes the asymmetry.
- **(b) Convention: advance impl-stage states before merge** (while the branch is ahead), then merge fires `awaiting_PR_merge → closed`. Requires advancing main's state file against an open branch — awkward, and contradicts the plan-stage habit.
- **(c) Make `advance` warn** when it stalls at `awaiting_junior_impl` while a merged-but-not-ahead `{task_id}-impl` branch exists ("impl branch appears merged; if reconciling post-merge, override to closed") — turns the silent "no transition fires" into an actionable signal.

Lean for the retro: **(a)** (merge-durable detection) as the structural fix + **(c)** (warn) as the cheap guardrail. Related: this is W-005-family (the cycle-boundary filter + Route B were the prior state-machine refinements); RC-21 is the next state-machine gap in the same area.

**Cross-references:**

- `src/orchestrator/workflow/transitions.py:158` (`AWAITING_JUNIOR_IMPL` gated transition requires `junior_impl_commit_present`).

## RC-22 — Cycle-boundary filter (Decision 14) blocks post-merge reconcile cascade

**✅ GRADUATED — fixed in W-006 (2026-05-31), ADR-008 Decision 16 (Accepted).** Remedy (a) cycle-relative boundary: `TaskState.cycle_started_at` stamped only at cycle-boundary events (init / rework override), with both the Decision 14 review filter and Decision 15 impl detection unified onto it. Hit twice (P2.1 + P2.2 close overrides) before the fix. Do NOT re-open. See `docs/decisions/ADR-008-workflow-state-machine.md` Amendments § + commit 3b9f984.

**Surfaced:** 2026-05-29, while fixing RC-21 (merge-durable impl detection, ADR-008 Decision 15).

**Observation:** RC-21's fix (Decision 15) made `_has_junior_impl_commits` merge-durable, so `workflow advance` on a post-merge P1.6.5 correctly fired the *first* step `awaiting_junior_impl → awaiting_senior_plan_vs_impl`. But the cascade then **re-stalled** at the next step. Root cause: `cmd_advance` sets `last_transition_at = datetime.now(UTC)` on every transition, and the W-005 Decision 14 cycle-boundary filter (`_safe_load_verdict_cycle_filtered`) only counts a review file as present if it was committed *after* `last_transition_at`. Reconciling a fully-merged cycle replays transitions whose review artifacts are all in the past (P1.6.5 `plan-vs-impl.md` + `R0-A.md` committed `12:30`); each advance bumps the timestamp to *now* (`20:10`), so the very next step's verdict reads as `'absent'` and Route B can't fire.

**The interaction (the real finding):** Decision 14 (cycle-boundary filter) and post-merge reconcile are at odds. Decision 14 keys "in cycle" off `last_transition_at`, which advance mutates per micro-transition. For a *live* cycle this is correct (artifacts arrive after each transition). For a *post-hoc reconcile* (replaying a merged cycle), every advance's `now()` bump hides the next step's pre-merge artifact. RC-21 fixed the entry stall; RC-22 is the same merge-fragility one layer deeper — the *whole* impl-review cascade is timestamp-fragile under reconcile, not just the junior_impl entry.

**This instance's resolution:** architect override `awaiting_senior_plan_vs_impl → closed` (cycle stays 1; substantive, reason cites RC-21 + this Decision-14 interaction). P1.6.5 is genuinely complete (impl merged `9f13861`; all reviews clean; gates green 904).

**Candidate remedies (deferred — retro/W-series decides):**
- **(a) Cycle-relative boundary:** track a `cycle_started_at` (or use the cycle's first `awaiting_junior_impl` entry) separate from `last_transition_at`, and have Decision 14 filter relative to *that*. Then a reconcile cascade sees all in-cycle artifacts regardless of per-micro-transition timestamp bumps. Cleanest; removes the reconcile fragility.
- **(b) Reconcile mode:** a `workflow advance --reconcile` flag that does not bump `last_transition_at` between cascaded micro-transitions (or bumps once at the end). Scoped to the post-merge-reconcile use case.
- **(c) Accept override-on-reconcile:** treat post-merge reconcile-to-closed as an expected architect override (document it as the supported path, stop trying to auto-cascade). Lowest effort; keeps a substantive override per impl close.

Lean for the retro: **(a)** (cycle-relative boundary) as the structural fix — it makes both the live path and the reconcile path correct without a special mode. Related: RC-21 (Decision 15) + W-005 Decision 14 are the same state-machine area; RC-22 is the next gap in it.
