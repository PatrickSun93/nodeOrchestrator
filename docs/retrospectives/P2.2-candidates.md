## RC-24 — Whole-file substring scan is a recurring harness failure mode (RC-23 widening candidate): 3rd instance

**Surfaced:** 2026-05-31, at P2.2 plan-stage routing (B → α). Surface only — **not a decision this cycle**.

**Routing:** dev-harness (test infrastructure + workflow CLI). Architect-deferral literal-reading: **not bundled into P2.2's product scope** (P2.2 fixes only its own new guard, per B → α). This RC is the record for a future W-series / retro decision on whether to widen.

**Observation:** the "scan the *whole file* for a substring" pattern has now misfired (or would have misfired) **three times**, each in a different part of the harness:

1. **[[RC-23]] — `_parse_adr_status`** (`src/orchestrator/workflow/cli.py`): whole-file `if "status: accepted" in content.lower()` → an ADR that *quotes another ADR's* status line auto-passes its own accept-gate while Proposed. Caught on ADR-017 (P2.1 matcher draft).
2. **The constitutional no-LLM test** (`tests/memory/test_constitution.py:46`): whole-file `if pattern in content` over `memory/*.py`. Works **today** only because no `memory/` module legitimately mentions `"import anthropic"` etc. in prose — but it is the same brittle mechanism (a module docstring explaining "we deliberately do NOT import anthropic here" would false-positive).
3. **The P2.2 structural orthogonality guard** (planned, P2.2-4): modeled on #2, so it inherited the same scan — and *would* have false-positived on the matcher's own orthogonality docstring ("advisory only — never calls `promote_hypothesis`"). Caught at plan-stage R0-A/R0-B (both lenses); routed B → α to implement it as a real call/import check instead.

**The pattern (the real finding):** whole-file substring scanning conflates **code** with **prose about code**. Every instance is a check that means "does the *code* do X?" implemented as "does the *file text* contain the string X?" — so documenting the very property the check enforces trips the check. The failure mode is self-reinforcing: #3 exists because a contributor correctly modeled a new guard on the existing #2, propagating the brittleness. Left alone, the next harness check that needs "does the code reference Y?" will copy #2 or #3 and inherit it again.

**Why it matters:** these are **forcing-function** mechanisms (accept-gate, constitutional guards) — the project's safety rails. A brittle safety rail is worse than a known-absent one: it gives false confidence (#2 "passes" but doesn't really guarantee no-LLM against a documented exception) and it actively penalizes good documentation (#1, #3 punish prose that describes the enforced property). RC-23 scoped the fix to `_parse_adr_status` alone; the 3rd instance suggests the *class* — not the single function — is the real debt.

**Candidate remedies (deferred — W-series / retro decides; surface only):**
- **(a) Audit + fix the class:** enumerate whole-file substring scans in the harness (`_parse_adr_status`, the constitutional tests, any future guards); convert each to either (i) line-scoped/anchored matching (for the status-line parser — already RC-23's lean (a)) or (ii) AST/import-graph checks that inspect code, not text (for the "does the code reference Y?" guards). Strip comments/docstrings where a text scan is genuinely the right tool.
- **(b) A shared helper** — a small "does this module's *code* (AST) call/import X?" utility the constitutional guards + orthogonality guards share, so the pattern is written once correctly and copied safely.
- **(c) Leave RC-23 scoped** (parser only) + fix each guard ad-hoc as it's written (P2.2 B → α does exactly this for its own guard). Lowest effort; accepts that the next copy re-inherits the brittleness.

Lean for the retro: **(a) + (b)** — the 3rd instance is the signal that this is a class, not a one-off; a shared AST helper (b) is the forcing function that stops instance #4. But per RC-4 discipline (one instance ≠ codify; here it's three, which is *why* this is now worth surfacing as a widening candidate rather than leaving RC-23 scoped), the actual decision is the architect's at a W-series dispatch or the P2.2 retro — this is the observation, not the graduated rule.

**Relationship to RC-23:** RC-23 is the specific bug (`_parse_adr_status`); RC-24 is the **class** (whole-file substring scans generally). If the architect widens, RC-23's fix folds into RC-24's audit; if not, RC-23 stays the scoped parser fix and RC-24 records that the class was observed and consciously left scoped.

## RC-25 — `run_matcher` operational/concurrency posture: a future ADR-017-amendment candidate (surface only)

**Surfaced:** 2026-05-31, at P2.2 impl-stage routing — the three forward-notes from the cross-family R0-B (G6). Architect routed Y1 → α and recorded these as **surfaced-not-routed** (no action this cycle).

**Routing:** **surface only — not a decision this cycle.** All three are 🟢 forward-compatibility observations from R0-B's line-by-line execution trace; none affects P2.2 correctness under the current **single-connection sequential** model (ADR-011 D1). They graduate to an **ADR-017 amendment** only *if* the concurrency model changes. Recorded so they are not lost.

**Observation (the three notes, verbatim intent from R0-B G6):**
1. **`run_matcher` self-commits** — `matcher.py:104` calls `conn.commit()`, unlike the registry's transaction-neutral `resolve_tags` (which never commits — caller owns the transaction). This is correct for a standalone advisory batch API and is the right default for current usage, but it is **not documented in ADR-017 D4**. If a future caller ever composed `run_matcher` inside a larger write transaction, the internal `commit()` would prematurely commit the caller's uncommitted writes. (Contrast: `resolve_tags` was deliberately made transaction-neutral in P2.1 precisely so it could compose inside `promote_hypothesis`'s D11 transaction.)
2. **COUNT-then-UPDATE are separate implicit transactions** — `matcher.py:94-103` runs a COUNT (for `rows_newly_flagged`) then an UPDATE as two statements in autocommit mode; a concurrent writer could change rows between them. **Moot under single-connection sequential** (ADR-011 D1); the defensive `AND candidate_for_promotion = 0 AND status = 'pending'` guard on both is insurance. Would matter under a multi-connection / concurrent-writer model.
3. **Reader imports private `store._row_to_hypothesis`** — `matcher.py:20` forward-couples to an internal helper's signature. The plan explicitly accepted this reuse (P2.2-3); a `_row_to_hypothesis` signature change would require a matcher update.

**Why it matters (deferred):** these are the seams that would need attention if/when the matcher stops being a standalone single-connection batch — e.g. a runtime that composes matching inside a larger transaction, or a concurrent dispatch model (the same "async/concurrency reshape" deferred across ADR-011 D1 / ADR-016 D11 forward hooks). Inscribing #1 (the self-commit contract) into ADR-017 D4 is the cheapest pre-emption; #2 and #3 are reshape-time concerns.

**Candidate remedies (deferred — future ADR-017 amendment decides):**
- **(a) Document the self-commit contract in ADR-017 D4** now (one sentence: "`run_matcher` self-commits; it is a standalone batch and must NOT be composed inside a caller transaction — unlike `resolve_tags`"). Cheapest; pre-empts a future composition footgun. Could even be a small in-cycle docstring touch if the architect later wants it, but **not routed this cycle**.
- **(b) Make `run_matcher` transaction-neutral** (mirror `resolve_tags`: drop the internal `commit()`, caller owns the transaction) — only warranted if a composing caller materializes.
- **(c) Leave as-is** — correct under the current model; revisit at the concurrency reshape.

Lean for the retro/amendment: **(a)** as a cheap documentation pre-emption when ADR-017 is next touched; **(b)/(c)** are reshape-time. Per RC-4 discipline, this is an observation, not a graduated rule — the actual decision is a future ADR-017 amendment or the P2.2 retro.
