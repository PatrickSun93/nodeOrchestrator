# Architect brief — P5.1c: headless pipeline email — the first **authorized irreversible-actuation** crossing (decision-surface)

**Task:** P5.1c — the **third and final slice** of the P5.1 analysis-pipeline wave, and the **honesty crux of all of P5**. P5.1a (ADR-041) shipped the *safe* primitive (reversible output only); P5.1b (ADR-042) made it *unattended on a timer* but **strictly reversible** — a scheduled run can read, analyze, and post a room summary headless, but any irreversible op it proposes (e.g. `send_email`) just **waits**. P5.1c crosses the line P5.1a/b were built around: it lets an opted-in scheduled pipeline **send an irreversible external email with no human in the loop at any point**.

**Class:** **the heaviest slice of the wave**; `requires_cross_family_review: true` (already set in `.workflow/P5.1c.yaml`); **likely new ADR-043** (ADR-041 D10 named it as the vehicle: "Extends this ADR (or ADR-043)"). Isolated dual-lens. This is **not** a new initiation surface (P5.1b was) — it is the **first headless *irreversible actuation*** in the product. `RB-AUTOFIRE` (ADR-040) explicitly *refused* this with its reversibility floor; `RB-PIPELINE-SCHED` (ADR-042) explicitly stayed inside the reversible envelope. P5.1c steps past **both** guards — and must do so **without touching either**.

**Status of this doc:** a **DECISION-SURFACE**, not a plan and not a set of decisions. Each point carries an **architect-ratifiable lean + tradeoff**; the architect-partner does **not** decide — **routing is the architect's**. DP6 (opt-in headless email = (b2)) is already ratified at the wave level; this brief refines the *mechanism, bounding, and honesty* of that crossing into concrete decision points (local numbering **C0–C8**) and surfaces the sub-decisions they fan out into. No plan / ADR-043 is drafted until the architect ratifies the load-bearing set (C1 mechanism, C2 recipient-authorship, C3 boundary-guard, C6 the honest residual).

**Pre-inscription note (read first).** ADR-041 **D10** already inscribed a strong steer for this slice: *"Opt-in, per-schedule, recipient-allowlisted, owner-attributed, reusing `_writer_approve_helper` as a third caller with a new `approval_source="auto_pipeline"` marker; inscribes the `RB-PIPELINE-EMAIL` residual honestly."* The leans below **mostly track D10**. The **one genuinely-open refinement D10 did not resolve** is **C2 (recipient authorship)** — "recipient-allowlisted" is necessary but, with a broad domain allowlist, still leaves the **LLM choosing *who* gets an irreversible email**. C2 is where the real architect honesty call lives.

## 0. What is already inscribed + the verified seam P5.1c plugs into (verify-cited `origin/main` @ `2087e5c`)

**The crossing, structurally.** A pipeline analyze-branch that proposes `send_email` today produces a HARD `TOOL_CALL_PENDING` that **waits forever**, by **three** independent locks:
1. **`countdown_auto_fire=None` in the runner** (`pipeline/runner.py:153,223`) → the pending is never stamped `expires_at` → the COUNTDOWN sweeper's discovery (`expires_at is not None`) **cannot find it** (ADR-041 D5, the load-bearing guard).
2. **Gate guard #1 — tier** (`agents/tool_dispatch.py:137-138`): `expires_at` is stamped **iff `tier == COUNTDOWN_CONFIRM`**. `send_email` is **HARD_CONFIRM** (reversibility=3 → HARD), so it is structurally excluded.
3. **Gate guard #2 — reversibility floor** (`tool_dispatch.py:143-144`): stamp iff `reversibility ≥ reversibility_floor`. `send_email` reversibility = **3** (`config/tools.yaml:48`) `<` floor **5** (`config/autonomy.yaml:14`) — excluded again, independently.

`RB-AUTOFIRE` installed guards #2/#3; ADR-041 D5 added #1. **Headless email inverts all three.** The constitutional requirement: **invert them for `send_email` in a pipeline context WITHOUT relaxing any of the three on the interactive path, and WITHOUT editing the byte-frozen gate** (`score`/`decide_tier`/`emit_gate_decision`) or `_execute_local_call`.

**The actuation seam already exists (ADR-040 D3).** `_writer_approve_helper` (`api/app.py:379-468`) actuates a gated `TOOL_CALL_PENDING` on the writer: room-state gate → position-anchored still-pending check → **reconstruct the `TOOL_CALL` from the persisted record** (`tool_name`/`params`/`author` from `ToolCallPendingMeta`, **never from the caller**, `:434`) → `execute_pending_tool_calls` → bus-publish. It returns a discriminated outcome (`_ApproveOk`/`_ApproveSkipped`/`_ApproveFailed`); callers map it (HTTP confirm → 422/500; sweeper → log+skip). **Two callers today:** the HTTP `/confirm` handler (`:1453`, `approval_source="human"`) and the countdown sweeper (`:549,553`, `"auto_timer"`). Its signature already carries `approval_source: Literal["human", "auto_timer"]` (`:383`). **This helper is NOT in the byte-frozen set** — the byte-frozen set is `_execute_local_call` + the gate (`score`/`decide_tier`/`emit_gate_decision`). `_writer_approve_helper` is the *designed actuation-reuse seam* (ADR-040 D3/D4 built it to be called by multiple actuators), and ADR-040 D4 anticipated additive `approval_source` markers exactly like a third one.

**`send_email` exists and is config-driven (verified).** `_make_send_email` (`tools/network_tools.py:409-563`) is a local tool dispatched through `_execute_local_call` → the `local_tools` registry (`:563`). Transport = **config-driven HTTP** (Resend/Mailgun/SendGrid-style), configured in **`config/email.yaml`** (**gitignored**; `email.yaml.example` is committed); the API key is read from an **env var**, sent only in the `Authorization` header. Recipient bounding (ADR-036): a **mandatory** `allowed_domains` allowlist + an **optional** explicit `recipients` list; unconfigured ⇒ **fail-closed** (`:472-476`); the `to`/`subject`/`body` come from **`params`** — i.e. **the analyze branch (LLM) composes them** (`:458-460`), bounded only by the domain/recipient allowlist (`:478-495`). `send_email` runs **UNSANDBOXED by design** (ADR-037 R9 DLP tail), logging a per-call transparency WARNING.

**Persistence + opt-in homes (verified).** `pipeline_schedules` (`pipeline/store.py:44-57`: `schedule_id, pipeline_id, owner_user_id, kind, expr, next_fire, enabled, created_at`) — **no email/opt-in column yet**. `PipelineDefinition`/`OutputConfig` (`pipeline/schema.py:13-35`, both `frozen=True`) — `OutputConfig` carries only `room_prefix` today. Either is a candidate opt-in home (C4).

**What P5.1c adds:** (i) a **narrow `send_email`-only actuation authorization** layered *after* the run (C1/C3); (ii) the **opt-in surface** (per-schedule, default OFF, owner-config-pinned recipient — C2/C4); (iii) **audit + the `auto_pipeline` provenance marker** (C5); (iv) the honest **`RB-PIPELINE-EMAIL`** residual (C6); (v) **ADR-043** + amendments + isolated dual-lens (C7/C8). The runner, gate, executor, COUNTDOWN spine, and the reversible-output envelope are all **byte-frozen** — the crossing is an **actuation-authorization layer**, never a gate/tier/floor change.

## C0. ⭐ Scope — scheduled-run-only, or also the manual `/run` path? (decide first)

The opt-in could authorize headless email for **scheduled** runs only, or for **any** opted-in run (manual `/run` too).

| Option | Trade-off |
|---|---|
| **(a) Scheduled-run-only (lean)** — the opt-in attaches to a **schedule** (the headless initiator); a manual `POST /pipelines/{id}/run` keeps the P5.1a/b posture (the `send_email` pending waits for an interactive `/confirm`). | Tightest first crossing: the headless-irreversible authorization exists **only** where there is genuinely no human (the scheduled fire). A manual run has the owner *right there* — they can confirm interactively, so no headless authorization is needed. Matches D10's "per-schedule" wording exactly. |
| **(b) Any opted-in run (manual + scheduled)** — the opt-in attaches to the **pipeline definition**; both callers auto-actuate. | One uniform path. **But** a manual run already has a human at trigger time, so auto-actuating its email skips a confirm the owner *could* trivially give — widening the headless-irreversible surface to a case that doesn't need it, and conflating "what the pipeline is" (definition) with "is headless email authorized." |

**Lean: (a) scheduled-run-only.** The crossing should exist *only* where the human is genuinely absent. **Architect's scope call** — it determines where the opt-in lives (C4) and whether `/run` is in the crossing's blast radius at all. *Decide first.*

## C1. ⭐ The actuation mechanism — reuse `_writer_approve_helper` (3rd caller) vs separate channel vs deterministic delivery (load-bearing)

How does the `send_email` pending get actuated headless, given the gate/spine/runner are byte-frozen?

| Option | What it builds | Trade-off / residual |
|---|---|---|
| **(a) Reuse `_writer_approve_helper` as a 3rd caller (lean — D10's steer)** — a pipeline-email actuator discovers `send_email` `TOOL_CALL_PENDING`s left by the run and, for eligible ones (C3), calls `_writer_approve_helper(…, approval_source="auto_pipeline")` on the writer — exactly as a human `/confirm` actuates a HARD pending, but headless. New code = the eligibility gate (C3) + discovery + widening the `Literal` to `["human","auto_timer","auto_pipeline"]` + the marker. | **Reuses the proven reconstruct + still-pending + executor-idempotency + bus-publish machinery** — no second actuation path, no re-derived idempotency. The gate stays byte-frozen (`send_email` is still tiered HARD; nothing re-tiered/floor-lowered); the COUNTDOWN spine stays byte-frozen (this is **not** a second COUNTDOWN consumer — it never touches `expires_at`/the sweeper). Honest framing: *the owner's config-time standing authorization actuates the pending, in place of a live human click.* **Mirrors ADR-040 D3's "no second actuation path" discipline.** |
| **(b) A separate, independent pipeline-email channel** — a new actuation function not reusing the helper. | More visual isolation from the countdown path — **but** duplicates the reconstruct + still-pending + idempotency + bus-publish reasoning, the exact duplication **ADR-040 D3 rejected** ("a second actuation path re-opens the t4-appender invariant and duplicates the idempotency reasoning"). **Reject** for the same reason. |
| **(c) Deterministic config-delivery (NOT actuate-a-pending)** — the email is not an LLM tool-call at all; `output_config` declares "deliver the reduce summary to recipient R" and a deterministic step sends it (recipient = config, content = the deterministic reduce summary). | **Most constitutional** on the "orchestration = code, not LLM" axis (no LLM judges *whether/what/whom* — see C2). **But** it reshapes email from *an actuated gated tool-call* into *a pipeline output*, does **not** reuse the gate/actuation machinery, and discards the gate's record of "an agent proposed this HARD op." It also answers C2 by construction (recipient is config), so it really competes with **C2(c)**, not just C1. |

**Lean: (a) reuse `_writer_approve_helper` as a 3rd caller** — honors D10, reuses the constitution-critical actuation machinery verbatim, keeps the gate/spine/runner byte-frozen. The crossing is an **actuation-authorization layer**, not a gate change. **Load-bearing.** *Note the deep interaction with C2:* (a) actuates the LLM-composed pending **as-is** (the helper reconstructs `params` from the record, never the caller), so under (a) the recipient is whatever the LLM put in `to` — which is exactly why **C2** must decide whether that is acceptable or must be config-pinned. (c) is the "make the recipient config by construction" answer and lives in C2.

## C2. ⭐ Recipient + content authorship — LLM-composed-within-allowlist vs **owner-config-pinned recipient** (the honesty sub-crux; load-bearing)

D10 said "recipient-allowlisted." The existing `allowed_domains` allowlist (ADR-036) satisfies that literally — but a domain allowlist (`yourdomain.com`) can be **broad**, and within it the **LLM still chooses the exact `to:` address** and the full body. Headless, that is *an LLM judgment about who receives an irreversible external message, with no human backstop* — the sharpest edge of this slice. Three postures:

| Option | Trade-off |
|---|---|
| **(a) LLM-composed, allowlist-bounded only** (today's `send_email` contract, unchanged) — actuate whatever the analyze branch composed, bounded by `allowed_domains`/`recipients`. | **Maximum reuse** (`send_email` byte-unchanged; actuate the pending as-is). **But** the "within `allowed_domains` exfil is still possible" honest residual (ADR-036 D3-ii) now has **no human backstop** — the LLM picks the recipient (within domain) *and* the content, and it goes out unreviewed. The heaviest reading of `RB-PIPELINE-EMAIL`. |
| **(b) Owner-config-pinned recipient, LLM content (lean)** — the schedule's opt-in carries an explicit **`email_recipient`** (set by the owner at opt-in time); the eligibility gate (C3) actuates the pending **iff its `to` matches the pinned recipient**, else it stays waiting. Content stays the LLM analysis summary. | The minimal tightening that **removes the LLM-chooses-irreversible-recipient hazard** while keeping C1(a)'s reuse: the owner config-pins **who**, the LLM only composes **what**. Cleanly compatible with the helper (validate `to` *before* calling it — the helper still actuates the record unchanged, honoring "never from the caller"). The honest "human-in-the-loop moves to config-time" posture (ADR-040 D4/D8) done **right**: config pins the recipient, not just enables a domain. |
| **(c) Fully deterministic** — recipient config-pinned **and** content = the deterministic reduce summary (= C1(c)); no free LLM `send_email` composition at all. | Most conservative; smallest LLM surface over an irreversible op. **But** reshapes the mechanism (C1(c)) and loses the gate's "an agent proposed this" record; over-tight if the value is "email the *analysis* the agents wrote." |

**Lean: (b) owner-config-pinned recipient (+ LLM content, allowlist still enforced).** It is the honest reading of "the authorizing decision is the operator's, at config-time" — the owner pins **who**, so the LLM cannot redirect the headless email even within the domain allowlist; the body remains the analysis (the point of the feature). **This is THE architect honesty call** — (a) is more reuse but leaves an LLM judging an irreversible recipient with no backstop; (b)/(c) move "who" to owner config. **Load-bearing.** (The "never soften a residual" discipline applies: if (a) is chosen, `RB-PIPELINE-EMAIL` must name "the LLM chooses the recipient within the domain allowlist, headless" plainly.)

## C3. ⭐ The crossing boundary guard — what stops it becoming "any HARD tool headless"? (load-bearing)

The eligibility gate for the pipeline-email actuator must be **structurally narrow**, or the crossing generalizes.

| Option | Trade-off |
|---|---|
| **(a) `send_email`-only allowlist + opt-in + owner + recipient-match (lean)** — actuate a pending **iff all hold**: `tool_name == "send_email"` (a **single-tool** allowlist, ideally a literal constant — not "any HARD tool", not "any tool below floor"); the schedule opted in (C4, default OFF); the schedule **owner** stands behind it (`owner_user_id`); the `to` matches the config-pinned recipient (C2b); the existing `send_email` allowlist passes. Any other HARD pending (`git_push`, …) stays waiting **forever**, exactly as today. | The structural guard against generalization: the crossing is **one named tool**, not a class. **Constitutional-test-pinned** (mirror ADR-040 D2's `HARD-never` test: a test asserts no non-`send_email` pending is ever auto-actuated). |
| **(b) A reversibility-band gate** (allow headless actuation for reversibility ≥ some lower band, e.g. ≥3). | **Reject** — this *is* the "generalize to any sufficiently-reversible tool" path; it sweeps in every other rev≥3 tool and re-introduces a class-level judgment. P5.1c is **one** crossing, not a band. |
| **(c) Per-tool `auto_pipeline_eligible` flag in `tools.yaml`** (the deferred ADR-040 "per-tool opt-in" idea). | More general/config-driven — **but** invites exactly the "just flip it on for tool X" generalization the slice must resist. For the **first** irreversible crossing, an explicit single-tool allowlist is tighter and more auditable; the flag can be a later, separately-scrutinized generalization. |

**Lean: (a) a `send_email`-only allowlist** (literal constant preferred over config list), gated by opt-in + owner + recipient-match. The boundary is a **single named tool**, constitutional-test-pinned — **not** a reversibility band, **not** a generic flag. **Load-bearing.** **Architect's call** on literal-constant (tightest) vs a config allowlist (flexible, looser).

## C4. Where the opt-in lives + its shape

Given C0(a) (scheduled-only) + C2(b) (config-pinned recipient), the opt-in carries at least `{email_enabled: bool = False, email_recipient: str}`.

| Option | Trade-off |
|---|---|
| **(a) Columns on `pipeline_schedules` (lean if C0=a)** — add `email_enabled`/`email_recipient` to the schedule row. | The opt-in lives **with the headless initiator** (the schedule). Default OFF (absent ⇒ disabled). One join already feeds the sweeper. Migration: a guarded `ALTER TABLE ADD COLUMN DEFAULT` (precedent `memory/store.py:116-130`) since `pipeline_schedules` may pre-exist; or a sibling `pipeline_email_optin` table keyed by `schedule_id` for cleaner separation. |

| **(c) A dedicated opt-in side table** keyed by `schedule_id` (or `pipeline_id`). | Cleanest separation (mirrors the `pipeline_schedules` side-table discipline); one more table + join. |

**Lean: (a) schedule-level columns** (or (c) a dedicated table if the architect prefers isolating the irreversible-authorization state from ordinary schedule state). **Modeling call**, gated by C0/C2. Whatever the home: **default OFF, fail-closed, absent ⇒ disabled.**

## C5. Audit + compensability — the irreversibility-specific safeguards

Email is fire-and-forget: once sent, **no recall**. `RB-AUTOFIRE` had a runtime *cancel window* (the COUNTDOWN timer) as its compensation; this crossing has no equivalent unless one is built.

| Option | Trade-off |
|---|---|
| **(a) Front-loaded safeguards + send-record audit (lean baseline)** — the compensation is *front-loaded* (opt-in OFF by default + owner-config-pinned recipient C2b + the `send_email` allowlist), not a runtime window. Every headless send appends the ordinary `TOOL_CALL`/`TOOL_RESULT` carrying `approval_source="auto_pipeline"` + the owner — **the event trail IS the audit** ("sent BY PIPELINE, no human approver, owner=X, recipient=Y"). | Simplest; reuses the existing audit. Honest residual: once fired, no recall — **named explicitly in `RB-PIPELINE-EMAIL`** (C6). |
| **(b) + a dry-run / preview posture (lean addition)** — a per-schedule (or global) **`dry_run`** mode where the actuator **logs/records what it *would* send** (recipient + subject) and does **not** call the transport. | Cheap and high-value for a **first** irreversible crossing: the owner validates recipient/content shape on a live schedule before enabling real sends. Could even be the **mandatory first state** (opt-in to dry-run → then opt-in to live). **Lean: include**, architect decides in-scope vs follow-on. |
| **(c) + a runtime cancel window** (delay the send, let the owner cancel). | The closest analog to `RB-AUTOFIRE`'s window — **but** it requires either routing email through the COUNTDOWN sweeper (impossible without relaxing the byte-frozen gate — `send_email` is HARD + below floor) or a **new** pipeline-email delay-timer surface (a second sweeper-like mechanism). Heavy for an infrequent scheduled send. **Lean against for the first crossing** — front-loaded opt-in + dry-run is simpler and the human-in-the-loop moment is honestly at config-time, not a runtime window. |

**Lean: (a) front-loaded + send-record audit, plus (b) a dry-run/preview posture.** Lean **against (c)** a runtime cancel window (re-introduces a timer surface and tangles with the frozen gate). **Architect's call** on whether dry-run is P5.1c-scope or a follow-on, and whether dry-run is the mandatory first state.

## C6. ⭐ `RB-PIPELINE-EMAIL` — the honest residual (load-bearing honesty)

This is the **heaviest residual in the chain** and must read that way. The lineage:

> `RB-FS`/`RB-NET` (sandboxed I/O) → `RB-ADMIT` (plugin admission) → `RB-AUTHZ` (any *authenticated* account is a full actuator, ADR-039) → `RB-AUTOFIRE` (no account actuates a *gated, COUNTDOWN-tier, **reversible-floored*** pending, ADR-040) → `RB-PIPELINE-SCHED` (no account *initiates* a **reversible** run, ADR-042) → **`RB-PIPELINE-EMAIL`** (no account *actuates* an **irreversible** external send, P5.1c).

The honest inscription must say plainly: **a configured pipeline, when its schedule opts in, sends an irreversible external email with no human in the loop at any point** — the human-in-the-loop moment is **entirely at config-time** (enable the feature + opt the schedule in + pin the recipient). It is **qualitatively heavier than `RB-AUTOFIRE` and `RB-PIPELINE-SCHED`**: `RB-AUTOFIRE` *refused* irreversibility (its reversibility floor); `RB-PIPELINE-SCHED` *stayed* reversible (`countdown_auto_fire=None`). `RB-PIPELINE-EMAIL` is the **one place in the product allowed to cross the reversible boundary** — and only because it is bounded by: **`send_email`-only** (C3), **opt-in default OFF** (C4), **owner-config-pinned recipient** (C2b), the **`send_email` allowlist** (ADR-036), [**dry-run** first if C5b], and **owner-attributed audit** (C5a). **Once sent, no recall** — named, never softened (roadmap §177 / the "never soften a residual" discipline).

This point is **a ratify-the-framing, not a routing fork** — there is no honest alternative to naming it. The only sub-choice: how strongly the bounding clauses are stated (which is just the union of C1–C5). **Load-bearing** because under-naming or over-claiming here is the single most likely way this slice fails its honesty bar.

## C7. ADR-043 (new) + amendment set

| Option | Trade-off |

| **(b) Amend ADR-041/042 in place** | One pipeline document. **But** ADR-041 scoped itself "P5.1a only" and ADR-042 "the scheduler"; bundling the irreversible crossing dilutes both records and the focused review. **Reject.** |

## C8. Isolated dual-lens (`requires_cross_family_review: true`)

Two orthogonal failure-family lenses (`dual-lens-r0b.md`):

- **Lens A — the crossing done wrong / over-actuation + irreversible-send safety** ("the headless email actuator misfires"): fires **only** `send_email` (never another HARD tool — the C3 constitutional test); **only** opted-in schedules (default OFF honored; absent config ⇒ no send); **only** the **config-pinned recipient** (C2 — the LLM cannot redirect even within the domain allowlist); the `send_email` allowlist still enforced; **idempotent** (no double-send across sweep ticks or restart — the still-pending check + claim-then-run discipline from ADR-040 D5 / ADR-042 D4); **owner-attributed** (`approval_source="auto_pipeline"` + `owner_user_id`); **fail-closed** unconfigured; **dry-run actually does not send** (if C5b).
- **Lens B — spine + reversible-envelope no-regression** ("the crossing regressed the constitution"): the gate (`score`/`decide_tier`/`emit_gate_decision`) + `_execute_local_call` **byte-frozen**; the interactive `/confirm` path + COUNTDOWN sweeper + the `RB-AUTOFIRE` eligibility guards (the two `tool_dispatch.py` stamps) **byte-untouched**; `run_pipeline`'s `countdown_auto_fire=None` **preserved** (the email actuator is layered **after** the run, **not** a relaxation of the run's reversible envelope — a scheduled run still stamps no `expires_at`); **no new routing `LLMPurpose`** (the only LLM stays analyze/reduce content-gen; the recipient is **config**, not an LLM judgment, per C2b); `_writer_approve_helper`'s existing two callers (`human`/`auto_timer`) **behavior-identical** after the `Literal` widening; `send_email`'s allowlist + unsandboxed transparency-warning intact.

*(Genuinely orthogonal: "the actuator over-fires / sends to the wrong place / double-sends" vs "the crossing regressed the gate / the reversible-pipeline envelope / the countdown spine.")*

## Constitutional carry-forward watch-list (carry into the plan + ADR-043)

- **Orchestration = code/config, never LLM.** The crossing decision (which tool, which schedule, which recipient) is **all code/config** — `send_email`-only allowlist (C3), opt-in flag (C4), config-pinned recipient (C2b). **No new routing `LLMPurpose`**; the only LLM stays the analyze + reduce content-gen.
- **The actuator actuates, never decides.** Like the human `/confirm` and the countdown timer, it actuates a **gate-produced** HARD pending; it never re-tiers, never lowers the floor, never invents a call (the helper reconstructs from the record, never the caller).
- **Gate + executor byte-frozen.** `_execute_local_call` + `score`/`decide_tier`/`emit_gate_decision` **zero-diff**. `send_email` stays tiered HARD. The crossing is an **actuation-authorization layer**, not a gate change.
- **COUNTDOWN spine byte-frozen.** `_countdown_sweeper`/`_discover_expired_pendings`/the two `RB-AUTOFIRE` stamp guards untouched. This is **not** a second COUNTDOWN consumer — it never touches `expires_at`/the sweeper.
- **`run_pipeline` + the reversible-output envelope preserved (`countdown_auto_fire=None` holds).** The email actuator is layered **after** the run; a scheduled run still stamps no `expires_at`. The reversible summary stays **ungated** (P5.1a/b unchanged).
- **The ONE authorized reversible-boundary crossing.** P5.1c is the **only** place allowed to actuate an irreversible op headless, and **only** as: **opt-in + default-OFF fail-closed + owner-authorized + recipient-config-pinned + `send_email`-only + honestly marked**.
