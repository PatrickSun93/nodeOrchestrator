**Subject:** Build P3.4 — an **MCP client** (transport + a generic tool-adapter) that connects external MCP servers (e.g. filesystem/git/GitHub) and exposes their tools to agents, with **every MCP tool-call routed through the existing code autonomy gate** and external servers treated as a **trust boundary**. This is the Wave-2 extensibility opener (real external tools), and **the heaviest constitutional/security surface in P3** — the operation-gating spine + the third-party-trust boundary both land here.

## The substrate the gate already gives us (verified — this is what MCP must reuse, not reinvent)

A clean finding: the autonomy gate is **tool-source-agnostic**. `process_tool_calls` takes any `ToolCall(name, arguments)`, builds an `Operation`, and calls `emit_gate_decision(operation, tools, thresholds, …)`. The tier comes **only** from `tools[name].reversibility` (a code/config classification) + the agent's thresholds. So an MCP tool-call is **just a `ToolCall`** — if its `ToolMeta` is in the `tools` registry, it gates **identically** to a local tool; if not, `UnknownToolError` → **refused** (ADR-006, fail-closed). P3.4 plugs MCP into this path; it does **not** build a second decision surface.

## ⭐⭐ The constitutional spine (NON-NEGOTIABLE — inscribe ADR-027; not a choice)

This is the most important section. Per Principle 5 + roadmap §9, the senior/ADR must inscribe and the impl must enforce:

1. **MCP tool-calls route through the existing CODE autonomy gate** — via the existing `process_tool_calls` → `emit_gate_decision` path. An MCP tool-call is a `ToolCall`; it gets a tier from `score`+`decide_tier` (code). **No MCP-server-decided autonomy.** The MCP client never auto-executes a tool the gate didn't approve.
2. **MCP tool reversibility is CODE/config-classified, not server-provided.** Each MCP tool gets a `ToolMeta.reversibility` in config (the orchestrator's classification). The MCP protocol's own tool hints (`readOnlyHint`/`destructiveHint`/annotations) are **advisory at most** — the **authoritative** reversibility is the code classification. Unclassified → **default 0 (irreversible → HARD_CONFIRM)**.
3. **Unregistered MCP tool → fail-closed** (`UnknownToolError` → refused). **Discovery ≠ permission**: a tool the server advertises but that isn't classified/allowlisted **cannot auto-execute**.
4. **Execution is downstream of gate approval.** The MCP client sends a call to the server **only** for a tool-call the gate approved (`AUTO_EXECUTE`) or the user confirmed (`COUNTDOWN`/`HARD`). It never executes a gated-but-unconfirmed call; the gate is the chokepoint *before* the server is contacted.
5. **Tool-result interpretation = content-gen** (reuse `TOOL_OUTPUT_INTERPRET`; **no new routing/judgment `LLMPurpose`**). The LLM **describes** the result; it never routes/gates/executes based on it. (And the result is untrusted — §trust boundary.)
6. **No routing/judgment in `mcp/`** — the client is transport + adapter only; model-selection/state/activation stay the existing code.

## ⭐ The trust boundary (NON-NEGOTIABLE — inscribe; the P2.7-S3 pattern, magnified)

External MCP servers are **third-party** (opaque code/processes). The S3 alt-backend security pattern recurs, larger:

- **Server allowlist** — only explicitly-declared, opt-in MCP servers (command/URL) are connectable; a non-allowlisted server is refused (like S3's `trusted_base_urls`).
- **Credential safety** — servers needing secrets (a GitHub token) use the **`api_key_env` indirection** (no plaintext secrets in config; env-var reference), scoped to that server.
- **Untrusted tool-results** — a malicious/compromised server can return arbitrary content (prompt-injection, oversized payloads). Mitigations: **size limits** on results; the result is content-gen-*interpreted* (described, not executed); the interpreting prompt treats it as **untrusted external data** (no auto-action); **no tool-result drives a routing/autonomy decision**.
- **Subprocess isolation + fail-closed** (stdio) — a server subprocess crash/hang/malformed-protocol must **fail the tool-call closed** (refuse/error), never crash or hang the orchestrator; **do not inherit the full environment** into the subprocess (the P2.7-S3 **c2 env-inheritance** lesson — scope the subprocess env, don't leak the orchestrator's secrets).
- **The server cannot escalate autonomy** — the worst a malicious server does is return bad results (mitigated above) or expose a dangerous tool; *calling* it still requires passing the code gate (unclassified → HARD_CONFIRM → user confirms). Allowlist + conservative-default + user-confirm are the layered defense.

## Scope

**In scope (P3.4):**
- A new **`mcp/` package**: an MCP **client + transport** (connect, `tools/list` discovery, `tools/call` execution) + a **generic tool-adapter** (MCP tool → a `ToolCall`-compatible namespaced tool + its `ToolMeta`).
- **Autonomy-gating wiring**: MCP tools' `ToolMeta` merged into the `tools` registry (namespaced, e.g. `mcp__<server>__<tool>`) so `process_tool_calls`/`emit_gate_decision` gate them; **execution downstream of gate approval**; `TOOL_RESULT` appended + interpreted via `TOOL_OUTPUT_INTERPRET`.
- **The trust boundary**: server allowlist + credential indirection + untrusted-result handling + subprocess isolation/fail-closed (§above), at the **ruled MVP posture** (§Decisions d).
- **One demo connector** end-to-end (a low-risk server — e.g. filesystem-read or git — to prove the loop), via the ruled transport (§Decisions a).
- **Config**: the MCP server config (`config/mcp_servers.yaml` or similar) + the MCP-tool reversibility classification — shaped to **anticipate plugin-delivery** (P3.5; §Decisions e).

**Out of scope (defer):**
- The **plugin packaging** of MCP config (P3.5 — "MCP as a plugin", handoff §3.3) — P3.4 builds the **client** + direct config; P3.5 wraps it.
- **Many connectors / remote transports beyond the ruled MVP** (P3.7 content depth); the GUI's MCP surfacing (frontend track).
- Any change to the autonomy gate's **decision logic** (`score`/`decide_tier`/`emit_gate_decision`) — P3.4 **feeds** it, doesn't change it.

## Decisions (surface for the architect — do not self-decide; ⭐ = constitutional/security)

**(a) MCP transport + scope.**
- **Transport — lean: stdio** (local subprocess servers — e.g. official filesystem/git/github MCP servers via `npx`/`uvx`) for the MVP: most-trusted (a local process the user launched), simplest, consistent with the `claude_code_cli` subprocess pattern. **Defer** SSE/streamable-http (remote servers = a bigger trust surface) to later. Architect rules.
- **Scope — lean: a generic MCP client + ONE demo connector** (a low-risk filesystem/git server, reversibility-high tools) to prove the loop; not many connectors (P3.7). Architect rules.

**⭐ (b) dual-lens R0-B? — lean: DISPATCH** (per `dual-lens-r0b.md`). New transport + **external I/O** + a new cross-package edge (`mcp/ → autonomy/agents/llm`) + **first runtime exercise of external-tool execution through the gate** + the **trust/autonomy boundary** (S3 magnified). The cross-family lens is exactly for these failure modes (malicious server, subprocess crash/hang, transport-protocol errors, autonomy-bypass attempts, env-leak — recall the S3 **c2 env-inheritance** catch was a cross-family find). Architect confirms (if yes, senior authors `reviews/P3.4/external-r0b-prompt.md`).

**⭐ (c) The autonomy-gating mechanism (how MCP tools map into the gate — the constitutional crux).** Architect rules the classification model:
- **How does a discovered MCP tool get its `ToolMeta.reversibility`?** Lean: **pre-classify in config** (an allowlist of `mcp__<server>__<tool>` → reversibility) — only classified+allowlisted MCP tools are callable; a discovered-but-unclassified tool → `UnknownToolError` → **refused** (fail-closed). **Or** auto-register discovered tools at **reversibility 0 (HARD_CONFIRM)** so they're callable but always user-confirmed until classified. (The two compose: allowlist-to-call + conservative-default-tier.) **The server's own hints are never authoritative.** Architect rules.
- **Namespacing** — MCP tool names need a namespace (`mcp__<server>__<tool>`) to avoid collision with local tools + to key the classification. Confirm.

**⭐ (d) Trust-boundary posture (the knobs around the non-negotiable boundary).** Architect rules, like S3's allowlist:
- **Server allowlist** shape (config-declared commands/URLs; opt-in).
- **Credential handling** (`api_key_env` indirection; per-server scoping).
- **Untrusted-result limits** (max result size; the untrusted-input framing for the interpret prompt).
- **Subprocess env scoping** (what env the stdio subprocess inherits — lean: a minimal scoped env, not the full orchestrator env; the c2 lesson).

**(e) MCP-as-plugin relation to P3.5.** handoff §3.3: MCP is "**作为插件不是核心**" (config plugin-delivered); Plugins package "skills + tools + **MCP 配置** + roles". But the roadmap sequences **P3.4 (MCP client) before P3.5 (Plugin)** (P3.5 depends on P3.4). **Lean:** P3.4 builds the **MCP client as core infra** (`mcp/`) + a **direct config** (`config/mcp_servers.yaml`) for the demo connector; P3.5 later **packages that config into plugins** ("as plugin" is the P3.5 end-state). The config shape should **anticipate plugin-delivery** so P3.5 wraps it without re-architecting the client. Architect confirms (client-now + config-anticipates-plugin), or rules to defer/reshape.

| Field | Value |

| ADR | `ADR-028` (Proposed) — the runtime tool-executor (new; ADR-013 explicitly "does not govern tool execution itself (P1.6+)", so this is *beyond* the existing envelope, not within it) |

**Subject:** Cycle-1 shipped the MCP client + the autonomy-gating wiring + the MCP executor *function* (`execute_mcp_tool_call`) + the interpret wiring — but **nothing in the runtime consumes `TOOL_CALL` events and executes them** (Y2). Cycle-2 builds the **general runtime tool-executor**: the event-loop consumer that, for each gate-approved `TOOL_CALL` event, executes the tool (MCP via the existing `execute_mcp_tool_call`; local via a framework hook) → appends `TOOL_RESULT`/`TOOL_FAILED` → (for MCP) interprets via the existing content-gen `TOOL_OUTPUT_INTERPRET`. This is the **first time the orchestrator actually runs a tool** — so it is more than glue.

## Constitutional carry-forward (NON-NEGOTIABLE — unchanged from cycle-1; the executor must preserve)
- **Execution stays DOWNSTREAM of the gate** — the consumer runs **only** for a `TOOL_CALL` event (the gate's AUTO-approval record; already structural in `execute_mcp_tool_call`). It never executes a gated-but-unapproved call. **confirm-then-execute stays deferred** (cycle-1 plan §5; `COUNTDOWN`/`HARD` remain gated-not-executed until a confirm flow lands with the GUI).
- **No LLM-judgment in the executor** — execution is code; the only LLM touch is the content-gen interpret (`TOOL_OUTPUT_INTERPRET`, untrusted-framed); **no new `LLMPurpose`**; no routing/judgment in the executor path.
- **The trust boundary holds** — MCP execution keeps the allowlist + scoped-env + size-limit + fail-closed (cycle-1; unchanged).

## Decision points (surface for the architect — ⭐ = architect's genuine call)
1. **⭐ MCP-wired-vs-local scope (the key call).** The MCP executor exists (`execute_mcp_tool_call`); **local tools have NO executor and NO implementations** (verified — and ADR-013 deferred execution to "P1.6+"; ADR-003 makes the orchestrator the intended tool-execution layer for `openai_compatible` providers, but it's **unbuilt**). **Lean:** build the **general executor framework + wire the MCP executor now**; local-tool *dispatch* is framework-ready (the consumer routes `mcp__*` → `execute_mcp_tool_call`; non-`mcp__` → a local-executor hook), but local-tool **implementations stay deferred** (they don't exist + are a large separate scope — likely P3.7 / a dedicated tools slice). Architect confirms (general-framework-MCP-wired-local-deferred vs build-local-impls-now).
2. **Failure / re-dispatch semantics.** `TOOL_FAILED` → does the turn continue? Does the agent **react** to the `TOOL_RESULT`/`TOOL_FAILED` (a re-dispatch so the agent responds to what the tool returned)? This is a **turn-loop extension** (event-model / ADR-011 territory) — surface the options (no-re-dispatch MVP / single-re-dispatch / bounded-loop); the senior designs, the architect accepts via ADR-028.
3. **sync/async + P3.2 single-writer liveness.** The executor runs inside the turn path, which (in the API server, P3.2) runs on the **single-writer executor** — a tool call (MCP subprocess, bounded-timeout; or local) **blocks that thread** while running. Surface: inline-on-the-writer (simple; a slow tool blocks the turn, bounded by the MCP timeout) vs a separate execution lane. Senior designs; flag the P3.2-liveness interaction (the same surface R0-B probes).
4. **Event-model / ADR-011 interaction.** Where the execution stage sits relative to `run_turn`/`dispatch_turn` (a post-dispatch executor pass? a new runtime stage?) + the `TOOL_RESULT` → agent-reaction loop. Senior designs within ADR-028 (+ any ADR-011 touch noted).
5. **ADR-028 scope.** A new ADR inscribing: the execution-stage placement, the MCP-wired/local-deferred dispatch (#1), the failure/re-dispatch semantics (#2), the sync/async + liveness (#3), the event-loop placement (#4), and the relationship to ADR-013 (deferred execution) / ADR-027 (MCP exec) / ADR-003 (orchestrator-tool-layer) / ADR-011 (turn loop). RC-23-safe (Proposed).
