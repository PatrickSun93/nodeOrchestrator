**Subject:** Build P2.6 — **feed the dormant promotion rules**. Three blocks: **(B1)** a **rule-a tagging producer** (agent-layer content-gen that populates `Hypothesis.topic_tags` so `run_matcher` can group + flag candidates); **(B2)** **rule-c external connectors** (integration code that produces `external_validation` events with externally-grounded verdicts, feeding `list_externally_validated_candidates`); **(B3)** **refuted/inconclusive verdict handling** (the ADR-019 push-back #4 forward hook). The rules (a, c) **already exist + work** — P2.6 ships the producers that feed them; it does **not** modify the rule readers (except B3 may *add* a sibling reader).

## The crux — Principle 5 + Principle 11 (the lead constitutional check; decision c)

P2.6 is the first time LLM/external producers feed the promotion rules, so it's the sharpest test yet of *where content-gen ends and judgment begins*. Two distinct boundary questions, both for the architect to rule (c):

- **(B1) Is LLM-tagging content-gen or judgment?** The tagging producer reads a hypothesis (+ its source events) and emits candidate `topic_tags`. Generating descriptive tag strings is **content-gen** (keyword extraction — like `HYPOTHESIS_CANDIDATE` / `TERM_DEFINITION_PROPOSAL`: LLM proposes, code/human disposes). It would **cross into judgment** if the LLM decided *which hypotheses match/promote*, *ranked* them, or chose tags *to make a hypothesis promotable* (selection). The intended boundary: LLM emits **descriptive** tags → deterministic `resolve_tags` normalizes/registers (ADR-018) → `run_matcher`'s deterministic grouping → **advisory** `candidate_for_promotion` (ADR-016 D3/D10: not a promotion precondition) → **rule-b user-confirmed** promotion. So the LLM never makes the durable-knowledge decision (generalized D10). **Architect: confirm the line — tags are descriptive content-gen, the LLM must not select/rank/gate.** (Needs a new content-gen `LLMPurpose`, e.g. `HYPOTHESIS_TAG_PROPOSAL` — ADR-022-gated.)
- **(B2) How is the connector verdict guaranteed external-ground-truth, not LLM judgment?** ADR-019's whole premise is that rule-c's verdict is produced **outside** `memory/` by a connector — and ADR-019 line 13 **explicitly permits "even an LLM-in-a-connector interpreting a tool result."** So the boundary is **not** "no LLM in connectors" — it's **interprets-external-evidence (grounded) vs judges-the-hypothesis-from-nothing (drift, Principle 11)**. The guarantee anchor is `evidence_ref`: every verdict must trace to real external evidence (a CI result, a DOI, a benchmark, a dataset, a price feed, or an LLM reading *that* evidence). **Architect: rule the guarantee mechanism** — e.g. `evidence_ref` required + non-empty + pointing to an external source; the verdict derives from the evidence; if an LLM is used it interprets the **evidence**, not the bare hypothesis. (How hard to enforce structurally — connectors aren't in `memory/` — is part of the call.)

The recurring rule, a **fifth time**: code/external-ground-truth decides; the LLM only generates content / interprets external evidence; nothing inferred becomes durable without code-derivation-from-canonical-facts or user-confirm.

## Scope — three blocks

**In scope (P2.6):**
- **(B1) rule-a tagging producer** — agent-layer, content-gen LLM → candidate `topic_tags` → the existing tag write path (`record_hypothesis(topic_tags=...)` at creation, **or** a new `memory/` retro-tag-update routing through `resolve_tags` — senior pins which; see forks). Feeds `run_matcher` (unchanged).
- **(B2) rule-c external connector(s)** — integration code producing `external_validation` events (verdict from external evidence; `evidence_ref` populated) via `EventStore.append`. At least one concrete connector to demo (senior picks a tractable external source — a deterministic one is the cleanest demo). Feeds `list_externally_validated_candidates` (unchanged).
- **(B3) refuted/inconclusive handling** — the ADR-019 push-back #4 forward hook. **Hard constraint (ADR-019): must NOT mutate `status`** (status is `promote_hypothesis`/user territory; conflating external-refutation into the lifecycle breaks rule-b). So a refuted-handler is **advisory** (e.g. a `list_refuted_candidates` reader in `memory/`, badged by provenance) — unless the architect rules a **user-confirmed** reject path (the only way a refuted verdict could touch status). Decision surfaced.
- **ADR-022** — pins the producer/connector contracts, the content-gen-vs-judgment boundary (c1), the connector-verdict-external-grounding guarantee (c2), the new `LLMPurpose`(s), and the refuted/inconclusive handling [or amend ADR-019 for the latter].
- **e2e** — per block: B1 (tag a hypothesis → `run_matcher` flags it cross-room), B2 (connector produces `external_validation` → `list_externally_validated_candidates` surfaces it), B3 (refuted/inconclusive → the chosen handling). Source ≠ sink (producer → store → rule reader).

**Out of scope (defer):**
- **Multi-source aggregation / trust-weighting** (ADR-019 forward hook).
- **P2.7** (platform / state-machine evolution / LLM Layer 4 / startup polish).
- Modifying the rule readers (`matcher.py` / `list_externally_validated_candidates`) — they work; P2.6 feeds them.

## Constraints (do not violate)
- **No LLM in `memory/`** (rglob) — producers/connectors live **outside** `memory/`; the rule readers stay pure code.
- **No LLM-judgment-without-ground-truth** (Principle 11) — B1 tags are descriptive content-gen; B2 verdicts are `evidence_ref`-grounded; **no auto-durable from LLM inference** (candidacy advisory, promotion user-confirmed).
- **rule-c must NOT mutate `status`** (ADR-019 push-back #4) — B3 is advisory unless a user-confirm path is ruled.
- **Rule readers unchanged** — `run_matcher` / `list_externally_validated_candidates` are not modified (B3 *adds* a reader, doesn't change the confirmed-path one).
- **Adding `LLMPurpose` requires an ADR** (purposes.py) — content-gen purposes only; **no routing/judgment purpose** (CLAUDE.md "never LLM-judge").
- **`external_validation` events go through `EventStore.append`** (validate_metadata + `ExternalValidationMeta` extra="forbid") — connectors never raw-INSERT (the fail-loud canary in `validation.py` depends on it).
- **Determinism** — the rules stay deterministic over produced data; discriminating tests (RC-25).
