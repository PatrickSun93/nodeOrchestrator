**Subject:** Implement P1.5.5 — **operator agent + autonomy-aware tool dispatch + content agents (divergence_mapper, logger)**. Close the last big deferred-from-P1.4-and-P1.5 item: the agent that calls orchestrator tools, with the autonomy gate as the safety layer between LLM-proposed tool calls and event-stream `tool_call` emission.

This task is **mostly integration**, not new architecture: the autonomy gate exists (ADR-005); `tool_call` events have a typed metadata schema (ToolCallMeta from P0); `dispatch_turn` exists (ADR-011); the operator's `llm_config.required_capabilities: [tools]` is honored by the existing LLMRouter (ADR-002 + ADR-003). What's new is the **wiring**: an agent that proposes a tool call → the gate evaluates reversibility → tier outcome decides whether the tool_call event lands.

**Tool execution itself (running `read_file`, `web_search`, etc.) is OUT of scope.** P1.5.5 lands the gating + event emission; the execution layer (consuming `tool_call` events and producing `tool_result` events) is P1.6 or later.

## Architect-settled design decisions

### 1. Tool-call gating is code, not LLM (handoff §3.1)

The decision "should this tool call proceed?" is `autonomy.gate(operation, tools, thresholds)` — already a pure function (ADR-005). The LLM only produces the tool-call proposal in its response; the gate decides whether the proposal becomes a stream event. No LLM in the gating path.

This is the **first runtime exercise of the architecture P1.2 inscribed**. The pattern: LLM proposes → code decides → event emits.

### 2. Tier-to-event mapping

The mapping from gate tier to event-stream emission is fixed per ADR-005 D4/D5 + ADR-005 D6 + ADR-007:

| Tier returned by `gate()` | Events emitted (in order) |
|---|---|
| `AUTO_EXECUTE` | `autonomy_decision` (per ADR-005 D6, synchronous before tool dispatch); `tool_call` (per ToolCallMeta from P0) |
| `COUNTDOWN_CONFIRM` | `autonomy_decision` only (tool_call deferred to UI countdown loop in P2; if user doesn't intervene, P2 logic re-emits the tool_call) |
| `HARD_CONFIRM` | `autonomy_decision` only (tool_call requires explicit user approval; P2 territory) |
| `gate()` raises `UnknownToolError` (ADR-006) | `autonomy_refusal` with `refusal_reason: "unknown_tool"` per ADR-007 |

**This is non-negotiable per the ADRs that already exist.** P1.5.5 implements; doesn't redesign.

### 3. operator's `llm_config` per handoff §5.5

```yaml
llm_config:
  default_model: deepseek_v4_flash
  fallback_chain: [qwen_mlx_30b]
  temperature: 0.3
  required_capabilities: [tools]
```

Per handoff §5.5: operator MUST use API (not Claude Code per ADR-003) because Claude Code can't accept orchestrator tool definitions. The `required_capabilities: [tools]` is what the LLMRouter validates against the model_profile's capabilities (`deepseek_v4_flash` has `[tools]`; `claude_code_*` doesn't). Fail-fast at config load if no fallback model satisfies.

`operator.autonomy_thresholds`: per handoff §5.5 example or per ADR-005 D3 placeholder values. Senior pins.

### 4. Tool execution deferred — strict event-only scope

P1.5.5 emits `tool_call` events; **does not execute the tools**. There is no `tool_result` event produced by P1.5.5. The architectural reason: `tool_call` is the LLM's proposal; `tool_result` is execution. Separating them lets the execution layer (P1.6 or P1.7+) consume `tool_call` events from any source (operator, future user-explicit invocations, scheduled tasks) uniformly.

This may feel artificial in P1.5.5 (the operator proposes; nothing happens). The justification: ADR-001's event store is the single source of truth; events represent intent + outcome; separating proposal (LLM output) from outcome (execution) keeps the event vocabulary clean.
