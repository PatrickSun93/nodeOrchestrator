## H1 — the 🔴: stream-bound both readers (verify-cited)

### Why it's the OOM `_stream_bounded` was built to prevent
`_stream_bounded` (`network_tools.py:98`) exists precisely so a response is **never** buffered whole: it iterates `response.iter_bytes()`, stops at `MAX_RESULT_BYTES` (= `65_536`, 64 KiB, `mcp/execution.py:37`), returns `(content, truncated_at)`. `_inprocess_web_fetch` uses it correctly: `client.send(build_request("GET", …), stream=True)` then `_stream_bounded(response)` (`:243-248`).

The two source readers **bypass** it: `client.get()` materialises `response.content` (the entire body) *before* the `[:max_bytes]` slice ever runs. The slice caps the *kept* string; it does nothing to stop a multi-GB body from hitting RAM first. That is the exact `ADR-028/035 D2/D3` OOM vector — re-opened, and now on the **single writer thread**, so the blast radius is every room (HoL), not one request.

### The seam (the load-bearing detail)
`_stream_bounded` hardcodes its cap at `MAX_RESULT_BYTES` (64 KiB). But sources honour `source.options.max_bytes` (default **512 KiB**, `sources/schema.py:15`) — a *different, larger* cap. **Naive reuse would silently shrink every source read from 512 KiB → 64 KiB** (a regression: legitimate feeds/pages that fit in 512 KiB but not 64 KiB would truncate). So:

1. **Parametrize** `_stream_bounded(response, max_bytes: int = MAX_RESULT_BYTES)` — replace the two `MAX_RESULT_BYTES` uses inside with the param. The existing `_inprocess_web_fetch` caller passes nothing → 64 KiB → **`web_fetch` byte-identical** (matters if a constitutional/AST test freezes it).
2. Source readers pass `max_bytes = min(source.options.max_bytes, _SOURCE_MAX_BYTES_CEILING)` (the H2-c ceiling — defense-in-depth even if a stored definition predates the H2-c validator).
3. Mirror `_inprocess_web_fetch`'s idiom exactly (`with client:` → `client.send(req, stream=True)` → `raise_for_status()` → `_stream_bounded`). `raise_for_status()` is valid in stream mode (status is read before the body); the existing `HTTPStatusError` handlers (`web.py:31`, `rss.py:125`) are preserved. Reuse of the `_`-private `_stream_bounded` across modules matches the existing precedent of `file.py:8` importing `_check_path` from `tools/local`.

### RSS-specific seam — "can it still parse after streaming + bound?" (the architect's explicit question)
**Yes — and the failure mode is already handled.** Streaming + bound is *not* about parsing partial XML; it is about never reading more than `max_bytes` into RAM. Then:
- **Feed within the bound** (normal case): the bounded buffer *is* the whole feed → `_parse_feed` (`rss.py:65`) parses it identically. No behavior change.
- **Feed exceeding the bound**: the raw XML is truncated → `defusedxml.fromstring` raises `ET.ParseError` → `_parse_feed` raises `SourceReadError("rss_parse_failed: …")` (`rss.py:77-78`) → the runner's per-source `try/except` (`runner.py:292`) records an OBSERVATION error event and **continues**. Fail-closed: an over-cap feed is *skipped with an error*, never OOM'd, never crashes the writer. We do **not** attempt lenient partial-XML parsing.

One intentional **semantic shift to flag for R0-A**: today `rss.py`'s `truncated` means "the *rendered* output exceeded max_bytes" (post-parse, `:150-152`); after the fix it means "the *raw XML fetch* hit the cap" (the OOM-relevant place). The post-render truncation block is subsumed by the fetch-stage bound. (H2-c also caps the parse-*input* size, so the `defusedxml` DOM is bounded too — the full-`.content` parse was itself a second amplifier.)

### Fail-on-revert tests (H1 — the must-haves)
`tests/sources/` (web + rss):
- **OOM/stream**: a mock `httpx.Response` whose `iter_bytes()` yields chunks summing **past** the cap (or a generator that raises if fully drained) → reader returns content bounded to `max_bytes` **and stops iterating at the cap** (assert via chunk-counter / the would-raise generator). Revert to `.content` → test fails (full drain). **This is the 🔴's revert-gate.**
- **stream idiom (HoL proxy)**: assert the reader takes the `send(stream=True)` path, not `.get().content` (timing-based HoL is impractical to unit-test; the structural assertion is the practical revert-gate).
- **RSS over-cap fail-closed**: feed XML > `max_bytes`, truncated mid-document → `read_rss_source` raises `SourceReadError` (no OOM, no crash). Revert → full buffer + full parse, no size fail-close.
- **cap honoured**: a 300 KiB body with default options → not truncated (proves the param carries `source.options.max_bytes`, not the 64 KiB default). Revert the parametrization → truncates at 64 KiB.

## H2 — ingress caps (bundle): the 4 ceilings + lean values

All four are **hardcoded constants**, matching the established floor pattern (`MAX_RESULT_BYTES`, `_PIPELINE_MAX_PASSES=4` are hardcoded). **Not config** — these are *safety floors*; making them operator-tunable re-opens the very misconfiguration vector (owner sets count = 10 000 → OOM/HoL is back). The one existing operator knob (`SourceOptions.max_bytes`, 512 KiB default) **stays tunable** but gains the (c) ceiling.

| Bound | Where enforced | **Lean value** | Reasoning |
|---|---|---|---|
| **(a)** source count / run | `max_length` on `PipelineDefinition.sources` (`pipeline/schema.py:33`) — rejects at `POST /pipelines`, fail-closed before any run | **`_MAX_SOURCES_PER_RUN = 16`** | Bounds worst-case memory (16 × 5 MiB ceiling = 80 MiB) **and** writer occupancy. ⚠ see fetch-wall-clock sibling below — count alone does not bound *time*. |
| **(b)** RSS entries / feed | slice `entries[:_MAX_FEED_ENTRIES]` after extract (`rss.py:~133`) | **`_MAX_FEED_ENTRIES = 256`** | Caps the render explosion (a 100k-item feed → 100k lines). 256 ≫ anything an analyze step meaningfully uses. |
| **(c)** per-source max_bytes ceiling | `le=_SOURCE_MAX_BYTES_CEILING` on `SourceOptions.max_bytes` (`sources/schema.py:15`) **+** the `min(...)` clamp in H1's stream call (belt-and-suspenders) | **`_SOURCE_MAX_BYTES_CEILING = 5 * 1024 * 1024`** (5 MiB) | 10× the 512 KiB default; bounds single-source buffer **and** parse-input. Owner can no longer raise max_bytes above it. |
| **(d)** aggregate analyze context | truncate joined `fetched_context` + visible marker (`runner.py:308`) | **`_MAX_FETCHED_CONTEXT_BYTES = 1 * 1024 * 1024`** (1 MiB) | ≈ 250k tokens — already large for a context window; fed to **every** branch, so it bounds LLM cost + memory. Truncate (don't reject) with a `[context truncated at N bytes]` marker, consistent with existing `truncated` semantics. |

### Contract analysis — routine or upgrade?
(a) and (c) touch the ADR-041 **D4 / D8** model contracts (`Source`/`SourceOptions`/`PipelineDefinition`). They are **narrowing validators** (hardening), squarely within D4's stated *"bounded size (ADR-035/037)"* intent and the writer-occupancy risk **already inscribed** in ADR-041's risks ("A manual run occupies the single writer … can delay interactive turns"). They add **no new field, no new decision, reverse nothing**.

→ **Determination: routine. Amend ADR-041 in place** (D4 + risks: pin the per-source ceiling and the source-count cap that D4's generic "bounded size" left unpinned). **No new ADR; `plan_has_adr=False`.** Precedent: P6.9 #109 narrowed a HARD write tool's containment contract and still landed as an in-place ADR-036 amendment with `plan_has_adr=False`. This is lighter (config-schema validators on a 5-day-old feature).

**Migration note (fail-on-revert test point):** existing stored definitions with `max_bytes > 5 MiB` or `> 16` sources would now fail validation on load. The feature shipped 2026-06-10 (~5 days) and the default is 512 KiB, so no realistic stored row is affected — but the plan must include a test that a **default-options** definition still validates, and the senior should confirm no fixture/seed exceeds the ceilings.

### ⚠ Sibling to surface — fetch-stage wall-clock (the *time* dimension of HoL)
The analyze stage has a wall-clock budget (`_PIPELINE_MAX_WALL_CLOCK_S = 120`, `runner.py:58`); the **fetch loop has none** (`runner.py:287-306`) — only per-source `timeout_s` (default 15 s). So source-count caps *memory* but worst-case fetch occupancy = `16 × 15 s = 240 s` of single-writer hog. Two ways to bound the *time*: lower (a), **or** add a fetch-stage wall-clock budget mirroring the analyze one. **This is a genuine product-policy call (feature reach vs interactive-turn latency — the exact tension ADR-041's risks name), so it's yours.** My lean: keep (a)=16 for this cycle and **defer** a fetch wall-clock budget as an inscribed sibling (don't bundle it under H2 unless you want it in-cycle).

### Fail-on-revert tests (H2)
- (a) `PipelineDefinition(sources=[17 …])` → `ValidationError`; `[16 …]` → accepted (boundary). Revert → accepts 17.
- (b) feed with 300 entries → rendered output has exactly 256. Revert → all 300.
- (c) `SourceOptions(max_bytes=6 MiB)` → `ValidationError`; `= 5 MiB` exactly → accepted. Revert → accepts 6 MiB. Plus the default-options-still-valid migration test.
- (d) sources whose joined content > 1 MiB → analyze receives ≤ 1 MiB + the marker. Revert → full context.

## H3 — confirm + inscribe

**Confirmed as-designed.** Pipeline source reads go through the **in-process SSRF floor** (`build_ssrf_client` / `_resolve_and_validate`: scheme allowlist, IP denylist, resolve-then-pin DNS-rebind defense, redirect re-validation), **not** the ADR-037 D3 egress-sandbox container. That container is the **tool-call path's** defense for **agent-chosen** URLs (`_sandbox_web_fetch`, gated by `posture_resolver`, which the `sources/` readers never reference). Pipeline sources are **owner-configured, deterministic** reads (ADR-041 D4: "no LLM chooses what to fetch") — a different trust path, for which the SSRF floor is the designed floor. Not a gap.

**Inscription (one line, in ADR-041 D4):** e.g. *"Source reads use the in-process SSRF floor (`build_ssrf_client`), not the ADR-037 D3 egress-sandbox container — the container defends the tool-call path's agent-chosen URLs; pipeline sources are owner-configured deterministic reads for which the SSRF floor (scheme/IP/DNS-rebind/redirect) is the designed floor. As-designed."* (ADR-037 is the alternative home; D4 is the better fit — that's where a reader asks "how do sources fetch?".)
