second look). The disagreement on the find side is high (large
marginal value of a second look). The cost-benefit lives almost
entirely in the second column.

## 2. Three drift forms named

Each form is a category of failure mode that previously had no
project-level countermeasure. Each round of review surfaced one,
named it, and produced a `forcing function` (a test, a process
rule, or a doc artifact) that catches future instances of the same
form before merge.

### Round 1 — `reverse drift` on past arguments

**Symptom:** A previous review reached a decision (e.g., "prefer
async over sync"). The implementer's commit re-justifies the OLD
position with arguments the prior review had already weighed and
ruled out. The familiarity of the language ("we already discussed
async — sync is fine because of ergonomics") hides the silent
re-derivation.

**Forcing function:** Every review-followup commit message must
lead with a tracking table — one row per review item, with explicit
`Status: Done | Skipped (reason) | Disagreed (proposing X)`. The
table makes a re-derivation visible: a `Done` row that re-states
the old position is obviously not Done.

**Lives at:** `feedback_review_followup_tracking.md` (memory).

### Round 2 — `doc-spec drift` on flipped schema

**Symptom:** A schema flips in code (e.g., `fallback_chain` no
longer requires the default model at index 0). The example yaml
follows. The ADR establishing the schema, the architecture doc
explaining the schema, and the project narrative referencing the
schema all retain the *old* shape. The change is locally consistent
but globally split.

**Forcing function:** `contributing.md` PR template Q3. Schema
changes must scan five surfaces:

1. Main code (`src/orchestrator/**/*.py`).
2. Example YAML (`config/**/*.yaml.example`).
3. ADRs (`docs/decisions/*.md`).
4. Architecture docs (`docs/architecture/*.md`).
5. Project narrative (`handoff.md`, `chat-history.md`).

A `Status: Done` row in the followup tracking table is not
legitimately checked until all five are consistent.

**Lives at:** `feedback_doc_spec_drift_5_surfaces.md` (memory) +
`docs/contributing.md` Q3.

### Round 3 — `freeze-vs-impl drift`

**Symptom:** An interface frozen in commit 1 changes during commit 2
implementation. The change is correct (e.g., adding a parameter
that closes a data-flow bug) but is not flagged in the commit
message tracking table, not synced to the architecture doc, and
not backed by a signature-consistency test. Future readers see the
new shape in code but the old shape in the freeze-period docs.

**Forcing function (two-part):**

- `contributing.md` Q3 layer-crossing rule: schema changes that
  flow across module boundaries (e.g., a field added on `RouteResult`
  meant to populate `LLMResponse.model_id_requested`) must be traced
  end-to-end with source ≠ sink in a unit test. The static 5-surface
  scan does not catch missing plumbing because each surface is locally
  consistent.
- `test_constitution_provider_call_signature_consistency`: pins the
  `Protocol.call` parameter set across all implementations. Future
  silent additions to the Protocol fail this test until every provider
  is updated and the expected set in the test is bumped.

**Lives at:** `feedback_interface_freeze.md` (memory, "Freeze-vs-impl
drift" section) + `docs/contributing.md` Q3 + the constitutional
test.

### Generalization

All three forms share a structural cause: **changes that are locally
consistent but skip a boundary**. Different boundaries:

- Round 1: the conversational boundary (something already discussed
  needs explicit re-handling, not silent re-derivation).
- Round 2: the document-surface boundary (schemas live in five
  parallel surfaces; flipping one without others is asymmetric).
- Round 3: the interface boundary (frozen contract changes need
  disclosure, not silent bumping).

Each forcing function names the boundary explicitly so contributors
have a chance to notice it.

## 3. Constitutional tests — load-bearing verification

The project ships seven tests with the `test_constitution_` prefix.
Each is meant to catch a specific class of regression that the
type system, the documentation, and code review collectively miss.
This table separates "would have caught (theoretical)" from "did
catch (actual)" so future test additions are evaluated on real
yield, not aspiration.

| Test | Module | What it actually caught |
|---|---|---|
| `test_constitution_append_only_at_schema_level` | `tests/core/test_constitution.py` | Nothing yet — preventive. Locks the SQLite TRIGGER guarantees against any future `UPDATE events` or `DELETE events`. |
| `test_constitution_round_robin_uses_matched_key` | `tests/llm/test_mock_provider.py` | Nothing yet. Locks `MockProvider`'s "cursor per matched key" semantic against silent refactors that introduce a global cursor or fall-through-on-exhaust. |
| `test_constitution_model_id_requested_flows_distinct_from_used` | `tests/llm/test_mock_provider.py` | The data-flow bug in round 3. Lockable only because the test uses `requested ≠ used`; a "test it returns model.id" test would have passed with the bug present. |
| `test_constitution_no_hardcoded_model_names` | `tests/llm/test_constitution.py` | **3 real catches at first run** — model name strings (`claude-opus-4-7`, `claude_code_sonnet_46`, `deepseek-v4-flash`) leaking into `types.py` docstrings. The only test in P1.1 that has paid for itself with concrete hits. |
| `test_constitution_no_llm_calls_in_autonomy_module` | `tests/llm/test_constitution.py` | Nothing (autonomy module not yet built). Pre-locks the rule before P1.2 starts. |
| `test_constitution_provider_call_signature_consistency` | `tests/llm/test_constitution.py` | Would have caught the silent `Protocol.call` change in round 3. Now standing guard. |
| `test_constitution_no_provider_class_accepts_kwargs` | `tests/llm/test_constitution.py` | Nothing (no current provider uses `**kwargs`). Pre-locks the schema-level enforcement preference against future "convenience" additions. |

### Honest read

- **One test paid for itself in P1.1**: `no_hardcoded_model_names`.
- **Three are preventive backstops** for the freeze-vs-impl,
  doc-vocabulary, and schema-level disciplines.
- **Two are pre-locks** for modules not yet built (autonomy, future
  provider classes).
- **One is data-flow-specific** and was added because the bug it
  catches was just demonstrated.

The total cost of these seven tests is well under 200 lines, plus
the discipline cost of writing one when a new failure mode is named.
Cheap insurance — and pre-locking known failure modes before they
land has obvious dividends, even when no specific bug is caught
during the prevention period.

The shape of a "good" constitutional test, observed across the
seven: it checks a property the type system **cannot** check
(string content, file-level patterns, structural conformance to a
Protocol, data-flow with source ≠ sink). When a test only checks
something a type would catch, it is duplicate.

## 4. Two-reviewer workflow — empirical observations

The PR was reviewed by two independent sessions across rounds 1–4:
a Claude session (call it Reviewer A) and a separate session
running on a different model family (Reviewer B). Notes:

### Cross-family pairing > same-family pairing

When both reviewers ran on the same model family, their outputs
correlated more — they tended to find the same things or miss the
same things. Different families gave more independent signal.

### Reviewer roles stabilized by round 3

Without prompting, the two reviewers differentiated:

- **Reviewer A** (Claude session): documentation drift, vocabulary
  consistency, narrative-vs-code mismatches, file-level patterns.
- **Reviewer B** (other family): data-flow contracts, behavior
  edges, layer-crossing, signature semantics, error-class precision.

This was reproducible across rounds 2–4. The two lenses are
near-orthogonal; running both is the empirical justification for
the cost.

### "Verify checklist" agreement vs "find new issues" disagreement

The numerical pattern in section 1: ~100% verify-overlap, <10%
find-overlap. Verifying the prior round's followup is a high-overlap
task (one set of explicit asks, two sessions agree). Finding new
issues is a low-overlap task (each session brings its lens).

Practical implication: if the budget is for one reviewer, the
verify pass is the lower-value one — most of the value is in the
find-new pass, where lens diversity matters.

### Cost / when to use

Cost: ~2x review time. Recommended for:

- Interface freezes (catching design-time issues before impl
  amortizes them).
- Module completions (catching cross-cutting drift before merge).
- Decision changes that span multiple ADRs.

Not recommended for:

- Routine bugfix commits.
- Mechanical refactors.
- Doc-only changes within a single file.

## 5. Recommendations for P1.2 (autonomy) and beyond

### Process recommendations

1. **Interface freeze** as a separate commit remains the cheapest
   review surface. P1.2 should follow the same pattern as P1.1.
2. **Two-reviewer at the freeze and at module completion**. Skip
   for in-between fix commits unless the previous review surfaced
   `必修` items.
3. **The four memory rules + contributing.md Q3 are now baseline.**
   P1.2 should produce zero regressions in the named drift forms
   if the process is followed; if a regression appears, the
   forcing function for that form needs strengthening.
4. **Constitutional tests added by need, not by quota.** Each new
   one should answer: what real failure mode am I locking? If the
   answer is theoretical, defer.

### Specific predictions to test

- P1.2 autonomy module starts with the constitutional test
  `test_constitution_no_llm_calls_in_autonomy_module` already in
  place (vacuous in P1.1, becomes load-bearing in P1.2).
- The autonomy module has zero LLM calls by spec — if any sneak
  in, that test fires immediately.
- The freeze-vs-impl drift rule applies to the autonomy module's
  scoring functions: any signature change between freeze and impl
  must surface in the commit tracking table.

### Anti-recommendations (things that worked but shouldn't be over-applied)

- Don't write retrospectives for every commit. Write one per
  module/PR. P1.1 is the first; P1.2 will be the second.
- Don't treat every drift form discovery as warranting a new ADR.
  Memory + contributing.md is enough for most. Reserve ADRs for
  changes that will outlive the current contributors' memory.
- Don't double-review trivial commits.

## 6. Meta-lesson

> **Architecture review is not a one-time activity. It's a layered
> pipeline of forcing functions, each catching what the previous
> layer missed.**

The four-layer pipeline P1.1 ended with:

1. **Type system** (mypy strict, Pydantic frozen, `extra="forbid"`)
   catches structural type errors.
2. **Constitutional tests** catch what types can't (string content,
   structural Protocol conformance, file-level patterns, data-flow
   with source ≠ sink).
3. **Doc-spec discipline** (`contributing.md` Q3 5-surface scan +
   layer-crossing rule) catches what tests can't (drift between
   parallel documentation surfaces).
4. **Process discipline** (commit tracking tables, freeze-vs-impl
   disclosure) catches what docs can't (decisions changed silently
   between rounds, interfaces modified without flagging).

Each layer is small in isolation. Together, they form a system
where most drift is caught before merge, and the drift that ships
is named explicitly for the next round to act on. None of the
layers is sufficient alone; that's the point.

P1.1 demonstrated this pipeline working. P1.2 should test whether
the pipeline catches what its rules predict it will, with no further
forcing functions needed unless a new failure mode appears.
