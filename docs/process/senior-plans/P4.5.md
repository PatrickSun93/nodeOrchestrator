## 1. Context

Everything before P4.5 assumed **one trusted operator on localhost** (ADR-025 D7: "Auth: none"). There is **zero** human authentication or identity in the product: all 7 HTTP routes + the 1 WS stream are unauthenticated (no middleware, no `Depends`, no principal); every human event is `author="user"` hardcoded server-side (`app.py:486`); the confirm approver is anonymous (the `TOOL_CALL` is agent-authored, ADR-030 N1 dropped `user_id` "until auth lands"); the gate scores actions not actors. P4.5 adds the **orthogonal** boundary the spine never had: *proving which human is on the other end* (DP1b — a per-request authenticated principal), and *what they may do* (DP3a — all-or-nothing authenticated-operator). The constitutional spine is **unchanged** (no new principle); this is the first slice where "the operator" becomes a modeled, authenticated primitive.

The architect ratified all five DPs along the **lean** lines (commit `9356bea`):

- **DP1 = (b)** real multi-user seam — per-request authenticated `Principal`; `author="user"` → `user:<id>`; simplest credential now; OAuth/OIDC (c) additive behind the same primitive. **The do-not-reverse call** (the principal shape binds D2/D3 + the P4.7 GUI).
- **DP3 = (a)** all-or-nothing authenticated-operator (members assumed fully trusted) — **no** speculative RBAC; **pin** the permission checkpoints (confirm-approve / plugin-admit / config-write) so a role model is additive; **inscribe `RB-AUTHZ`**.
- **DP2** cookie-session (GUI) + optional per-user static token (programmatic); `auth + multi-user + remote-bind` IN; **TLS at the deployment/reverse-proxy layer** (documented, not in-app); rate-limiting thin-on-write-chokepoints or named residual; **D2 (remote-MCP OAuth) deferred** to a follow-on.
- **DP4** gate stays identity-blind; confirm gains authenticated approver `user_id` provenance (amend ADR-030), executed `TOOL_CALL` stays agent-authored; forge-guard generalises (principal **server-derived** from the verified session, never the request body); **pin** the ADR-038 D5 management-endpoint authz dimension (build no endpoint code).
- **DP5** new ADR-039 + amend ADR-025 / ADR-026 / ADR-030 (+ ADR-038 D5); the dual-lens two-lens prompt (A=identity trust boundary, B=spine-preservation).

The expensive-to-change surfaces (the principal shape / `author` format / the checkpoint seams / the management-endpoint authz dimension) are **inscribed in ADR-039 before any producer binds them** (roadmap §10, inscribe-before-producer).

### P4.5-1 — User store + credential model + first-account bootstrap CLI (the identity primitive's storage)

- **What:** A new `users` SQLite table (co-located, the ADR-020/025 idiom) + a frozen `User` model + a credential layer. Schema: `user_id` (PK, `[a-zA-Z0-9_-]+`), `password_hash`, `password_salt` (+ KDF params), `created_at`, `disabled` (bool default false). Credential = password hashed with **`hashlib.scrypt`** (stdlib, no new dep); verify via `hmac.compare_digest`. The hash/salt is **never** logged / wired / evented (the `mcp/transport.py:107` secret-never-inlined discipline). Add an **admin CLI** (`python -m orchestrator.api.admin create-user <id>`, password from stdin/env) that writes directly to the `users` table — the out-of-band first-account bootstrap (the operator's filesystem/DB access IS the pre-auth trust root; D2).
- **Where:** a new `src/orchestrator/api/auth/` module (e.g. `users.py` + the schema migration alongside `core/event_store.py`'s schema-init) + `src/orchestrator/api/admin.py` (+ `tests/api/auth/test_users.py`).
- **Why:** DP1b; ADR-039 D2. The user store is the floor the principal (D1) + sessions (P4.5-2) + authz (D5) stand on.
- **Acceptance:** `User` frozen; `create_user`/`get_user`/`verify_password` round-trip; a wrong password fails closed; `hashlib.scrypt` used with a per-user random salt; `hmac.compare_digest` for the comparison; the hash never appears in any return value / log / event (test-asserted); the admin CLI creates a user readable by `get_user`; `disabled=true` blocks verify. Pure storage + credential — no HTTP wiring yet.
- **Out of scope:** sessions/tokens (P4.5-2); the auth boundary (P4.5-3).

### P4.5-2 — Session store + per-user static token (the credential-carrying mechanisms)

- **What:** A new `sessions` SQLite table: `session_id` (opaque, `secrets.token_urlsafe`), `user_id`, `created_at`, `expires_at`, `revoked` (bool). `create_session(user_id)` / `validate_session(session_id) -> Principal | None` (rejects expired/revoked) / `revoke_session`. Sessions are **created/revoked on the writer connection, validated on the reader connection** (the ADR-025 D6 two-connection model). Plus an **optional per-user static bearer token** (server-issued, stored **hashed**, revocable) for programmatic clients — `validate_token(token) -> Principal | None`. Define the frozen **`Principal{user_id}`** model here (the D1 primitive both mechanisms resolve to).
- **Where:** `src/orchestrator/api/auth/session.py` + `.../token.py` + `.../principal.py` (+ `tests/api/auth/`).
- **Why:** DP2a; ADR-039 D3. Two credential carriers (cookie-session for humans, token for programs) resolving to **one** principal behind the D4 interface.
- **Acceptance:** a session round-trips create→validate→revoke; an expired session validates to `None`; a revoked session validates to `None`; the opaque `session_id` is cryptographically random (`secrets`); the bearer token is stored **hashed** (not plaintext) and round-trips; `validate_session`/`validate_token` both return the **same** `Principal` shape; session create/revoke run on the writer executor, validate on the reader (no cross-thread sqlite misuse — the `check_same_thread` discipline). Persistence survives a store re-open (restart-safe).
- **Out of scope:** the cookie wiring + login/logout endpoints (P4.5-3); CSRF beyond `SameSite` (named in ADR-039 D3).

### P4.5-3 — The fail-closed auth boundary + login/logout endpoints (the security crux)

- **What:** (a) `POST /login {user_id, password}` → verify (P4.5-1) → `create_session` (P4.5-2) → set an **`HttpOnly`, `Secure`, `SameSite=Strict`** cookie carrying only the `session_id`; `POST /logout` → `revoke_session` + clear cookie. (b) **The fail-closed gate (lean: middleware-with-explicit-public-allowlist):** a middleware that, for any path **not** in the public allowlist (`/login`, `/logout`-handling, `/health` if present, the bootstrap), requires a valid session cookie **or** `Authorization: Bearer <token>` → else **`401` before the route runs**; the resolved `Principal` is attached to the request scope. **Fail-closed by default** — a new route is protected unless allow-listed. (c) **WS auth at handshake:** `/rooms/{id}/stream` validates the cookie/token at connect → reject the upgrade if unauthenticated (WS stays read-only push, ADR-025 D2 unchanged).
- **Where:** `src/orchestrator/api/app.py` (`create_app` `:839-859` — register the middleware; `_register_routes` `:379` — `/login`·`/logout` + the WS-connect check `:781`) + `src/orchestrator/api/auth/middleware.py` (+ `tests/api/auth/test_boundary.py`).
- **Why:** DP2a; ADR-039 D4 (HR#2 fail-closed). The single server-side gate that derives the principal **before** any handler; the boundary the whole slice protects.
- **Acceptance:** an unauthenticated request to **every** non-public route → `401` before any append/`run_turn` (parametrize over all 7 HTTP routes); a valid cookie / valid bearer → the route runs with the resolved principal; an **expired/revoked** session → `401`; login sets an `HttpOnly`+`Secure`+`SameSite=Strict` cookie; logout revokes + clears; an unauthenticated WS upgrade is **rejected at connect** (no stream); a newly-added dummy route is protected **without** being explicitly listed (fail-closed-by-default, test-asserted); the gate makes **no LLM call / no routing decision** (mechanical verify only).
- **Out of scope:** the principal *threading into events* (P4.5-4); confirm provenance (P4.5-5).

### P4.5-4 — Principal threading: `author="user"` → `user:<id>` + `is_valid_author` generalisation (the do-not-reverse stamp)

- **What:** Generalise `is_valid_author` (`core/event.py:405`) regex to `^(user|user:[a-zA-Z0-9_-]+|system|agent:[a-zA-Z0-9_-]+)$` (**bare `user` stays valid** — backward-compat for stored events + the system-of-record default) + add `build_user_author(user_id)` (the single-point-of-truth factory mirroring `build_author`, raises on empty id). Replace the hardcoded `author="user"` at `app.py:486` with `build_user_author(request_principal.user_id)` — stamped **from the principal (P4.5-3), never the request body** (the ADR-025 D4 forge-guard, generalised — D7). Authenticate the audit `user_id` namespace: `DecisionMeta.user_id` / `record_preference` `user_id` now carry the **principal's** id (no new field — the existing free string becomes authenticated).
- **(promotion-impact grep — forcing function)** Grep **all** binders of the literal `author == "user"` / `"user"` author assumption before the regex locks: the t4 appender guards, `is_valid_author` tests, snapshot derivation, any test fixture asserting `author=="user"`, and the GUI author-label (`ui/src/uiStrings.ts` `authorLabel` — **frontend-track ripple**, named not built: `user:<id>` falls back to the generic until the FE follow-on maps it, same as `agent:<id>`'s sub-map). Record the grep result + update in-scope (Python) callers in this atomic.
- **Where:** `src/orchestrator/core/event.py:405` (+ `build_user_author`) + `src/orchestrator/api/app.py:486` (+ `tests/core/` author-validation tests, `tests/api/` intent tests).
- **Why:** DP1b/DP4c; ADR-039 D1/D7. The `author` format is the do-not-reverse primitive producers bind.
- **Acceptance:** `is_valid_author("user")` **and** `is_valid_author("user:alice")` both true; `is_valid_author("user:")` / `is_valid_author("user:bad space")` false; an authenticated intent stamps `author="user:<principal.user_id>"` (test-asserted, derived from the session — not the body); a request **cannot** influence the stamped author (forge test — no body field reaches `author`); the promotion-impact grep result is recorded; existing `author=="user"` Python assertions are reconciled; the GUI author-label ripple is **named** (frontend follow-on, not built this slice).
- **Out of scope:** the React author-label mapping (frontend track); confirm provenance (P4.5-5).

### P4.5-5 — Confirm approver provenance (the ADR-030 N1 hook landed)

- **What:** `POST /confirm` records the **authenticated approver `user_id`** (the principal from P4.5-3, **not** the request body) as approver provenance in the confirm flow (the cleanest landing: a `user_id` on the appended approval/confirm event's metadata, mirroring `DecisionMeta.user_id`'s shape). **The executed `TOOL_CALL` stays `author=build_author(pending_meta.initiating_agent)`** (`app.py:699`, byte-unchanged — agent-authored; the human supplied approval, not authorship). The cancel path (`app.py:677`) likewise stays agent-authored, gaining the approver provenance. The D5 checkpoint seam #1 (who-may-approve) is marked here as a **named no-op comment** ("authenticated ⇒ allowed; role check would gate here" — DP3a/D5), built no further.
- **Where:** `src/orchestrator/api/app.py:611-731` (the `_post_confirm` handler) + `core/event.py` (the confirm/approval metadata shape, if a field is added) (+ `tests/api/` confirm tests).
- **Why:** DP4b; ADR-039 D6 (amends ADR-030 D3 step 5 / N1). The audit trail finally records which human approved a HARD/COUNTDOWN action.
- **Acceptance:** an approved confirm records the authenticated `user_id` provenance, **derived from the session not the body** (forge test); the executed `TOOL_CALL` is still `agent:<initiating_agent>` (empty-diff on the author of the executed call — test-asserted); idempotency / position-anchored still-pending / partial-turn (ADR-030 D3/D5/D7) are **unchanged** (regression-asserted); the who-may-approve seam is a named no-op (DP3a). Confirm stays human-in-the-loop + idempotent (HR#4).
- **Out of scope:** a role check (DP3b, `RB-AUTHZ`); the executed-call authorship change (forbidden — ADR-030 unchanged).

### P4.5-6 — Remote-bind + transport posture (fail-closed bind, CORS, TLS/rate-limit disposition)

- **What:** (a) **Fail-closed remote-bind:** `api/__main__.py` / startup refuses (loud, at startup) a bind beyond `127.0.0.1` when **no users are provisioned** (or auth is disabled) — a remote bind must have the auth boundary armed; localhost stays permissive. (b) **CORS:** add the never-built ADR-025 D7 CORS middleware — restrict origins to a configured GUI origin (default local), allow credentials (the session cookie). (c) **TLS:** documented as a deployment/reverse-proxy requirement + the `TLS-at-deployment` residual (the `Secure` cookie requires it remotely) — **no in-app code**. (d) **Rate-limiting:** a thin per-identity limiter on `/login` (brute-force — the one with a real security argument) + optionally `/intent`·`/confirm`, **OR** a named residual (the §5 call).
- **Where:** `src/orchestrator/api/__main__.py` (the bind guard) + `src/orchestrator/api/app.py` `create_app` (CORS middleware) + `docs/` deployment note (TLS) (+ `tests/api/` bind-guard + CORS tests).
- **Why:** DP2b; ADR-039 D8. Remote-bind unblocks networked deployment without re-architecting the invariants (ADR-025 D7).
- **Acceptance:** a non-localhost `--host` with zero users → startup **refused** (loud); localhost bind unaffected; CORS restricts to the configured origin + allows the credentialed cookie; the TLS deployment requirement + residual are documented (not coded); rate-limiting is either implemented thin (test-asserted on `/login`) or a named residual in ADR-039 D10 (per §5).
- **Out of scope:** in-app TLS termination (deployment layer); a full rate-limit framework.

## 5. Where you'd push back (architect sub-decisions surfaced — I drafted a choice, confirm or redirect)

These are genuine forks the ratified leans did not nail to the field level. I drafted the **conservative, spine-preserving** option for each so the junior can execute; **each is the architect's to confirm** (none is mine to decide):

1. **⭐ The auth-boundary shape: fail-closed middleware vs per-route `Depends` (P4.5-3 / ADR-039 D4).** I chose **middleware-with-explicit-public-allowlist** because it is **fail-closed-by-default** — a newly-added route is protected unless explicitly allow-listed, so the boundary cannot be defeated by a forgotten `Depends`. The cost: middleware sees every request (incl. static/health) and the allowlist must be maintained. Alternative: per-route `Depends(get_principal)` — idiomatic FastAPI, but **fail-open-by-omission** (a route without the dependency is unprotected — the exact class of bug Lens A hunts). **Confirm middleware-fail-closed**, or redirect to per-route Depends (changes P4.5-3 + needs a "every route has the dependency" test as the fail-closed compensator).

2. **Password KDF: stdlib `hashlib.scrypt` vs an argon2/bcrypt dependency (P4.5-1 / ADR-039 D2).** I chose **stdlib scrypt** (memory-hard, since 3.6, **no new dep**) — the honest MVP, swappable behind the verify interface. Alternative: add `argon2-cffi` (the current OWASP-preferred KDF) — stronger defaults, but a new dependency on the security-critical path. **Confirm scrypt**, or rule argon2 in (adds a dep to `pyproject.toml`).

3. **Rate-limiting: thin-on-`/login` vs named-residual (P4.5-6 / ADR-039 D8/D10).** I drafted **thin on `/login`** (the brute-force surface with a real argument) as the in-scope minimum, with `/intent`·`/confirm` optional. Alternative: **defer all rate-limiting as a named residual** (keep the slice to the identity core). **Confirm thin-on-`/login`**, or defer-all (the chokepoints are then unthrottled — `RB`-named in D10).

4. **GUI login surface: contract-only vs minimal React login this slice.** I read DP2 + the ADR-026 amendment as "**pin** the cookie/login integration contract in ADR-039/ADR-026, build **no `ui/` code** this slice" (the P4.4 mgmt-endpoint-contract-only / P4.7-GUI precedent) — so P4.5 ships the backend auth + the optional bearer token (fully testable via `TestClient`) but **no** React login form (a frontend-track follow-on). The cost: the **browser GUI cannot authenticate until the FE follow-on lands** (the product is reachable programmatically via the token in the interim). Alternative: add a minimal React login form as a final frontend atomic now. **Confirm contract-only**, or pull the FE login into this slice (adds a `ui/`-track atomic + the FE gate, breaks the single-junior backend focus).
