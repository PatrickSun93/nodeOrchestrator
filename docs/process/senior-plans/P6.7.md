# P6.7 — senior plan (cron evaluation for pipeline schedules)

## 1. Context

P5.1b shipped the recurring scheduler **interval-only**: `ScheduleKind = Literal["interval",
"cron"]` is on the wire (ADR-042 D2) and every seam — the four `compute_next_fire` call sites,
the sweeper, boot re-arm, the endpoints — is **kind-agnostic**, but `validate_schedule_expr(
"cron", …)` raises `ValueError` (so create rejects `kind=cron` with **422**) and
`compute_next_fire("cron", …)` raises `NotImplementedError`. ADR-042 **D3** deferred cron
evaluation to *this* focused follow-on "with a dedicated greenfield-correctness review" (the
architect-routed Y1 = (c) interval-only). P6.7 implements the cron evaluator in the one isolated
pure module (`pipeline/schedule.py`), un-gates the 422 for *valid* cron (malformed cron still
422s — the gate **narrows**, it is not removed), adds the mandated adversarial correctness
suite, and amends ADR-042 D3 in place.

The risk profile is **inverted** from P5.1b. P5.1b's risk was the *scheduler spine* (a second
background task near the auto-fire neighborhood); P6.7 touches **none** of that. Its entire risk
is **greenfield arithmetic correctness** inside one ~pure module. The architect ratified
(2026-06-14, brief §"Ratification"): **mechanism = (a) hand-rolled 5-field subset, no
`croniter`** (preserves the 4-runtime-dep posture, ADR-040 D1); **all calendar arithmetic is
delegated to stdlib `datetime` + `timezone.utc`** (leap years, month lengths, rollover,
year-wrap — *not* hand-written); the hand-rolled surface is only (1) field-parse into
allowed-value sets, (2) a per-minute match predicate, (3) a **bounded** forward-search. The
greenfield-correctness floor D3 deferred this slice to enforce **is** the C5 adversarial suite +
the never-match bound; those are the deliverable, not optional hardening.

**This is a product slice, cross-family** (`requires_cross_family_review: true`) → full-impl
**dual-lens** (R0-A ∥ R0-B; R0-B's exhaustiveness lens is well-aimed at a greenfield evaluator).
No new ADR (amends ADR-042 D3 in place, no Accept gate — the dual-lens reviews the cron
correctness + the contract inscription). **Spine byte-frozen, no new `LLMPurpose`, no new
dependency (`pyproject.toml` untouched).**

**Interpretation note (push-back if wrong).** I read the ratified scope as: the hand-rolled
parser owns *only* token expansion + range checks; every wall-calendar question (does Feb have a
29th this year, what weekday is this date, does adding a minute roll the hour/day/month/year) is
answered by constructing/iterating `datetime(..., tzinfo=timezone.utc)` objects. If the architect
intended any calendar logic to be hand-rolled, stop — that materially widens Lens A.

### P6.7-1 — cron parse + validate (`validate_schedule_expr` cron branch + parser)

- **What:** Replace the cron `raise ValueError("…deferred…")` branch in
  `validate_schedule_expr` with a real 5-field parser that expands each field into an
  allowed-value set and **rejects malformed cron** (raising `ValueError`, which the create
  endpoint already maps to 422). Expose a parse helper the next-fire matcher (P6.7-2) reuses —
  parse-once, no re-parse in the search loop.
- **Where:** `src/orchestrator/pipeline/schedule.py:36-39` (the cron branch in
  `validate_schedule_expr`) + a new module-private parser (e.g. `_parse_cron(expr) ->
  <5 frozensets + the two "is-DOM/DOW-restricted" flags>`). Update the module docstring
  (`:1-19`) from "interval-only" to the implemented subset. `_SUPPORTED_KINDS` already contains
  `"cron"` — no change.
- **Why:** ADR-042 D3 (cron deferred → implemented); the ratified subset contract (brief C2/C5).
  `validate` raising is the *emergent* 422 gate (brief §0); narrowing it to malformed-only is the
  un-gate.
- **Subset contract to implement (ratified, brief C2 + Ratification):**
  - **5 fields**, whitespace-separated: `minute hour DOM month DOW`. Exactly 5 → else reject
    (4 or 6 fields are the malformed cases).
  - **Domains:** minute `0-59`, hour `0-23`, DOM `1-31`, month `1-12`, DOW `0-6` with **`7`
    accepted as an alias for `0` (Sunday)** — normalize 7→0 at parse time.
  - **Tokens (compositional)** per field — a comma-list of terms, each term one of: `*`
    (full domain), `a` (single value), `a-b` (inclusive range, `a ≤ b`), `*/n` (full domain
    stepped by `n`), `a-b/n` (range stepped by `n`). `n ≥ 1`. Names (`JAN`/`MON`) **excluded**
    — numbers only.
  - **Restricted-flag capture:** record, per the DOM and DOW fields, whether the field is the
    **literal `*`** (not restricted) vs anything else (restricted) — this drives the P6.7-2
    union and is the standard Vixie trigger (a `*/n`/range/list counts as *restricted* even if
    it spans the full domain). Capture it here at parse time.
- **Acceptance criteria:**
  - `validate_schedule_expr("cron", expr)` returns `None` for every well-formed expr in the
    suite (P6.7-3) and raises `ValueError` for every malformed one.
  - **≥6 malformed-reject classes**, each its own test (brief C5.6): wrong field count (4 **and**
    6); out-of-range each field (`60` min / `24` hr / `32` DOM / `0` or `13` month / `8` DOW);
    **`*/0`** (step-zero); inverted range `5-2`; non-numeric step `*/x` and value `a-b` with
    `a`/`b` non-numeric; empty / whitespace-only expr.
  - `7` in DOW accepted and treated identically to `0` (alias test).
  - The interval branch of `validate_schedule_expr` is **byte-unchanged**.
- **Out of scope:** the next-fire search (P6.7-2); 6-field/seconds, `@hourly`/`@daily`/`@reboot`
  macros, `L`/`W`/`#` specials, timezone tokens, name tokens (each a future opt-in, **not**
  P6.7 — do not gold-plate, brief C2 exclude-list).

### P6.7-2 — cron `compute_next_fire` (stdlib-datetime matcher + DOM/DOW union + bounded search)

- **What:** Replace the cron `raise NotImplementedError` branch in `compute_next_fire` with a
  bounded forward minute-by-minute search over UTC `datetime` that returns the epoch-ms of the
  first minute **strictly after** `after_ms` matching the parsed expr; raise `ValueError` if no
  match within the search horizon.
- **Where:** `src/orchestrator/pipeline/schedule.py:62-65` (the cron branch in
  `compute_next_fire`), reusing the P6.7-1 parser.
- **Why:** ADR-042 D3 (cron `compute_next_fire`); brief C3 (DOM-vs-DOW union), C4 (bounded
  never-match guard).
- **Arithmetic contract to implement (ratified):**
  - **All calendar math via stdlib** `datetime` + `timezone.utc` — construct
    `datetime.fromtimestamp(after_ms/1000, tz=timezone.utc)`, floor to the minute, **step
    `+timedelta(minutes=1)`** each iteration (stdlib owns every rollover: minute→hour→day→month
    →year, month lengths, leap days, year-wrap). **No hand-written calendar arithmetic.**
  - Start at the **first whole minute strictly greater than `after_ms`** (consistent with
    interval's strictly-later semantics: `after_ms + interval_s*1000`); return `int` epoch-ms
    at `second=0, microsecond=0` (i.e. a multiple of 60000).
  - **Match predicate** for a candidate UTC `datetime` `dt`: `dt.minute ∈ minute-set` **and**
    `dt.hour ∈ hour-set` **and** `dt.month ∈ month-set` **and** `day_match`.
  - **Weekday conversion (off-by-one footgun — explicit + tested):** Python `dt.weekday()` is
    Mon=0…Sun=6; **cron DOW is Sun=0…Sat=6**, so `cron_dow = (dt.weekday() + 1) % 7`.
  - **`day_match` (DOM-vs-DOW union — the load-bearing semantic, brief C3):** using the
    P6.7-1 restricted-flags:
    - DOM `*` **and** DOW `*` → `True` (day unconstrained).
    - DOM restricted, DOW `*` → `dt.day ∈ dom-set`.
    - DOM `*`, DOW restricted → `cron_dow ∈ dow-set`.
    - **both restricted → `dt.day ∈ dom-set` OR `cron_dow ∈ dow-set`** (standard Vixie
      **union**, *never* intersection — this is the single most likely correctness bug in the
      slice; explicit + dedicated test).
  - **Bounded never-match guard (brief C4):** cap the forward search at a horizon that comfortably
    covers a legitimate `0 0 29 2 *` (Feb-29-only, next match up to ~4 years out) — **cap ≈ 4
    years of minutes** (define a named module constant, e.g. `_CRON_SEARCH_HORIZON_MIN`, sized to
    ≥ 4×366×24×60). On cap exhaustion **raise `ValueError`** (fail-closed) — **never** loop
    forever. Malformed exprs cannot reach the search (rejected at validate, P6.7-1), so the loop
    only ever runs on a well-formed expr.
- **Acceptance criteria:**
  - The full C5 next-fire suite passes (P6.7-3): boundary rollover, month-end/leap, `*/n`
    alignment, DOM-vs-DOW union, year-wrap.
  - An unsatisfiable expr (`0 0 31 2 *` — Feb 31 never exists; `0 0 30 2 *`) raises `ValueError`
    via the horizon cap — **does not hang**.
  - Every test passes `after_ms` explicitly — **wall clock never read** (the existing
    `test_schedule.py` discipline; brief C5).
  - The interval branch of `compute_next_fire` is **byte-unchanged**.
- **Out of scope:** a smarter field-advance search (the per-minute step is an acceptable guard,
  not a hot path; the optimization is explicitly deferrable per brief C4 — do **not** build it).

### P6.7-3 — adversarial correctness suite (Lens A; replaces the cron-deferred tests)

- **What:** Replace the three cron-deferred tests in `tests/pipeline/test_schedule.py` with the
  mandated adversarial suite; **delete** the now-false deferred assertions.
- **Where:** `tests/pipeline/test_schedule.py:65-73` (`test_validate_cron_raises_valueerror`,
  `test_validate_cron_raises_even_empty_expr`) + `:116-118`
  (`test_compute_cron_raises_not_implemented`) — these get **replaced** (the cron path no longer
  raises). Update the module docstring's Lens-A invariant list (`:1-13`). The interval +
  unknown-kind tests stay untouched.
- **Why:** brief C5 — "if (a), the correctness suite **is** the mitigation"; each test must
  **FAIL if its guard is removed** (the project's fail-on-revert discipline).
- **Required classes (each a distinct test; brief C5.1-6 + Ratification adversarial suite):**
  1. **Boundary rollover** — `59 23 * * *` crosses minute→hour→day; `59 23 31 12 *` crosses the
     **year boundary** (Dec 31 23:59 → next year). Assert exact computed epoch-ms.
  2. **Month-end / leap** — `0 0 31 * *` skips 30-day months + Feb; **`0 0 29 2 *` matches only
     leap-year Feb 29** (exercises the C4 ~4y horizon, must resolve, not raise); an end-of-month
     range.
  3. **`*/n` alignment** — `*/15` fires at :00/:15/:30/:45 (**aligned to 0, not "15 min from an
     arbitrary start"** — pin the misconception); `*/7` over 0-59 (ragged: 0,7,…,56 then resets
     at 0); `*/90`-style step>range collapsing to only the field minimum.
  4. **DOM-vs-DOW union** — `0 0 13 * 5` = 13th **OR** Friday (**union**, assert a date that is
     Friday-but-not-13th AND a date that is 13th-but-not-Friday both match); `0 0 * * 1`
     (DOW-only); `0 0 1 * *` (DOM-only); the both-restricted union case explicitly. Include a
     **weekday-conversion** assertion pinning Sun=0 (e.g. `0 0 * * 0` lands on a Sunday).
  5. **Year-wrap** — `0 0 1 1 *` from mid-December → next Jan 1, year increments.
  6. **Malformed-reject (≥6)** + **never-match raise** — the P6.7-1 reject classes asserted at
     this level too, plus `0 0 31 2 *` / `0 0 30 2 *` raising `ValueError` via the horizon cap.
  7. **DST-irrelevance (UTC-only)** — a cron crossing a wall-clock DST instant (e.g. a March
     02:30 local) computes purely in UTC with **no** hour skip/repeat — assert the UTC arithmetic
     is unaffected (brief Ratification adversarial suite; documents the no-timezone-surface
     contract).
- **Acceptance criteria:** suite green; removing the union OR-branch, the weekday `+1` offset, the
  `*/n` alignment-to-0, or the horizon cap each turns ≥1 test red (fail-on-revert, self-audit by
  the junior before commit).
- **Out of scope:** endpoint-level integration tests (P6.7-4); property-based/fuzz testing (the
  enumerated adversarial classes are the ratified surface).

## 5. Where you'd push back

- **Calendar-arithmetic boundary (the one real interpretation risk).** The ratified scope delegates
  **all** wall-calendar math to stdlib `datetime`/`timezone.utc` and hand-rolls **only** field-parse
  + match-predicate + bounded search. P6.7-1/-2 are written to that line. If the junior finds an
  edge that seems to need hand-rolled calendar logic (e.g. computing "the next Feb 29" directly
  instead of stepping minutes until stdlib lands on it), **stop + surface** — the per-minute step
  over stdlib `datetime` is the ratified mechanism precisely so we hand-write **zero** calendar
  math (brief C1 narrowing note). Do not optimize into hand-rolled calendar arithmetic.
- **"Restricted" = literal-`*` test, not full-domain-coverage.** The DOM/DOW union triggers on
  whether the field is the **literal `*`**, not on whether its expanded set spans the domain. A
  DOW of `*/1` or `0-6` is **restricted** (triggers the union) even though it covers every day —
  standard Vixie. I have specified capturing the flag at parse time (P6.7-1) rather than inferring
  it from the expanded set; if R0-A/R0-B reads the ratification as full-domain-coverage semantics
  instead, that is an architect call, not a junior re-interpretation.
- **Horizon constant sizing.** I specified ≥ 4×366×24×60 minutes (~2.1M) to cover `0 0 29 2 *`.
  This is a guard, not a hot path (brief C4 accepts the worst-case iteration count). If the
  architect wants a different horizon (or a smarter field-advance to shrink it), that is a tuning
  call — the named constant makes it a one-line change, but I am **not** building the field-advance
  optimization this slice (explicitly deferred, brief C4).
- **No new ADR is correct here.** I confirm the ADR-042-D3-in-place amendment (no Accept gate) per
  the architect's 2026-06-14 ratification — same weight as the P6.x annotation notes. If the
  architect later decides the cron contract deserves its own ADR, that is a re-route; I am
  inscribing per the ratified instruction. (`plan_has_adr: false`, no `adr:` key — confirmed.)
