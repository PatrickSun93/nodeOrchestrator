## Context

The four surfaces a plugin packages **already have loaders, and they already converge in one place** (verified `origin/main`):

- `api/app.py::_build_context` (lines 142–158) is the single bootstrap merge point. It builds, in order: `load_agents(config_dir/"agents", models=…) → (dict[str, Agent], regex_registry)`; `load_skills(config_dir/"skills") → dict[str, Skill]`; `load_tools_config(config_dir/"tools.yaml") → dict[str, ToolMeta]`; `build_mcp_tool_registry_and_sessions_from_config(config_dir/"mcp_servers.yaml") → (dict[str, ToolMeta], dict[str, MCPSession])` (merged into `tools`); `build_local_tool_registry(sandbox_root) → dict[str, LocalToolFn]` (`local_tools`). The `AppContext` carries `available_agents`, `available_skills`, `tools`, `mcp_sessions`, `local_tools`.
- **Two distinct tool registries** (verified): `tools: dict[str, ToolMeta]` is the **gate's classification registry** (flows `process_tool_calls → emit_gate_decision`); `local_tools: dict[str, LocalToolFn]` is the **executor's implementation registry** (`tools/executor.py::_execute_local_call` looks up `local_tools[name]` and calls `impl(params)`, wrapping every call fail-closed → `TOOL_FAILED`, ADR-028 D4). A tool needs a `ToolMeta` to be *gated* and a `LocalToolFn` (or an MCP session) to be *executed*.
- `ToolMeta{reversibility: int 0–10, default 0}` (frozen, `extra="forbid"`; `autonomy/scoring.py:36`); `score(op, tools)` raises `UnknownToolError` if the tool is not in `tools` (ADR-006 fail-closed). All four loaders' models are **frozen + `extra="forbid"`** (Agent, Skill, ToolMeta, MCPServersConfig — verified).
- `build_local_tool_registry(sandbox_root)` (`tools/local.py:131`) is **hard-coded** to three host builtins (`get_current_time`, `read_file`, `list_files` — in-process closures). **There is no mechanism today to load a third-party `LocalToolFn`.**
- ADR-027 **D5** pre-committed the MCP half: a plugin's `mcp_servers` block is the **same shape** as `config/mcp_servers.yaml`; the loader merges plugin-provided server configs into the registry **without re-architecting the client** ("P3.5 wraps; it doesn't reshape").

So a plugin loader is an **aggregation layer above the existing loaders**: discover plugin manifests → validate → feed the **same five registries** at `_build_context`. It builds **no** new agent/skill/tool/MCP machinery and **no** new decision surface — with **one** genuinely-new mechanism: loading a plugin's **executable tool code** into `local_tools` (there is no existing loader for that). That new mechanism is the **code-trust / isolation surface** this ADR's D4 designs — **the project's largest security surface to date** (third-party Python, *loaded = runs*).

## Hard requirements — the constitutional spine + trust boundary (NON-NEGOTIABLE; inscribed; carries ADR-005/006/027/028 forward — *not* new choices)

A plugin is **third-party** (roadmap §3(B)/§9). Per Principle 5 + roadmap §9 the ADR inscribes and the impl enforces:

1. **Plugin-delivered tools route through the existing CODE gate, unchanged.** A plugin tool contributes a `ToolMeta` into the **same** `tools: dict[str, ToolMeta]` that flows `_build_context → process_tool_calls → emit_gate_decision`. It gates **identically** to a local/MCP tool: classified → tier from reversibility (code); **unregistered/unclassified → `UnknownToolError` → refused** (ADR-006 fail-closed). **No second decision surface; the gate stays the sole chokepoint.**
2. **Plugin-delivered MCP servers route through the existing trust boundary (ADR-027 D4), unchanged.** A plugin's `mcp_servers` block is the ADR-027 D5 shape; the **same** allowlist + `api_key_env` credential-indirection + scoped-subprocess-env + result-size-limit + bounded-timeout + fail-closed posture applies. A plugin **cannot** deliver a server that bypasses the allowlist — its declared server *is* an allowlist entry, so **loading a plugin = opting into its servers** (D5).
3. **Plugin loading is deterministic CODE/config, never an LLM judgment.** Discovery + manifest-validation + registration is code (mirrors the four loaders). **No `LLMPurpose` decides whether to load a plugin, whether it validates, or what its contributions do** (D3 constitution test).
4. **A plugin introduces NO new routing/judgment `LLMPurpose` and NO routing decision.** Roles activate via code `should_agent_speak` (responses stay content-gen `AGENT_RESPONSE`); skills are content; tool-classifications gate; MCP config gates + allowlists. Model-selection stays the code router + the P2.7 Layer-4 override. No new purpose (roadmap §9).
5. **Fail-closed loading + execution.** A bad/unparseable manifest, an unknown schema-version, a missing declared dependency (a role's `model_id` absent from the host model registry; a required `room_type` absent), a tool with no usable classification, a server not matching the D4-validatable shape, **executable tool code that fails to import**, or a **name collision** → the plugin **fails to load (refused)** — never partially-registers, never silently degrades into a half-wired/unsafe state. At call time, a plugin tool that raises → `TOOL_FAILED` for that call only (per-call isolation, ADR-028 D4). *Bundling ≠ trust*: load only the valid, fully-satisfiable, classified bundle.

**Trust boundary (the P2.7-S3 → MCP pattern, now a *bundle*; inscribe).** One plugin can bundle MCP servers **and** tool-classifications **and** executable tool code **and** roles **and** skills at once — **loading one plugin = trusting the whole bundle.** The S3 / ADR-027-D4 posture carries forward and *composes*: **opt-in** (loaded only by explicit presence in `plugins/` — never auto-fetched), **manifest-validated** (schema + dependency + classification checks **before** any registration), **credential-safe** (servers reuse `api_key_env`; the manifest carries no plaintext secret), **fail-closed** (HR#5). The worst a malicious plugin's **declarations** do is bounded by the gate + allowlist it cannot bypass. **Its executable code is a different matter — see D4.**

> **Scope of the credential-indirection / scoped-env defenses (R0-B Y5 — do not over-read this section).** The `api_key_env` credential-indirection + minimal scoped subprocess env (carried from ADR-027 D4) apply to the **MCP-subprocess boundary only**. Under **Posture A (in-process, D4)**, plugin code runs in the host process with full `os.environ` access — these two defenses provide **zero** protection for in-process plugin code (it can read every environment variable, including every API key, directly; see D4 L1). The layered-defense picture (allowlist + credential-indirection + scoped-env + fail-closed) is **MCP-subprocess depth, not in-process depth** — do not read it as defense-in-depth for plugin executable code under Posture A.

## Decisions

### D1. The plugin package + manifest schema — `plugins/`, `plugin.yaml` (frozen, `extra="forbid"`, schema-versioned)

A new **`plugins/` package** (`src/orchestrator/plugins/`) + a **content directory** (`plugins/` at repo root, mirroring `config/`'s directory-discovery). Each plugin is a **subdirectory** with a `plugin.yaml` manifest + its content. The manifest is a frozen, `extra="forbid"` Pydantic model (`PluginManifest`), schema-versioned (an unknown `schema_version` → fail-closed refuse, HR#5):

```yaml
schema_version: 1                       # loader rejects an unknown version → fail-closed
id: demo                                # plugin identity (== subdir name; collision key)
name: "Demo bundle"
version: "0.1.0"
contributions:                          # all optional; a plugin declares only what it ships
  roles:        ["facilitator"]         # → config/agents/-shape YAML under plugins/<id>/agents/
  skills:       ["research-decomposition"]   # → config/skills/-shape MD under plugins/<id>/skills/
  tools:        ["echo"]                # tool-classifications (ToolMeta) under plugins/<id>/tools.yaml
  tool_impls:                           # EXECUTABLE tool code (admit-code, D4) — name → impl ref
    echo: "tools_impl:echo_tool"        # "<module>:<callable>" within plugins/<id>/
  mcp_servers:  ["filesystem"]          # ADR-027 D5 shape under plugins/<id>/mcp_servers.yaml
dependencies:                           # fail-closed if unmet (HR#5)
  model_ids:    ["claude_code_haiku_45"]   # a role's model_id must exist in the host model registry
  room_types:   ["free_chat"]              # a required room_type must exist
  min_host_contract: 1                     # minimum host plugin-contract version
```

The manifest **declares** contributions; the **content** lives in per-surface subpaths whose shapes are the existing loaders' inputs (so the loader **reuses**, not reimplements — D2). The schema is frozen + `extra="forbid"` + `schema_version`-gated (D6 / HR#5).

### D2. The loader = aggregation above the four loaders + the local-tool-impl loader; merge at `_build_context`

`plugins/loader.py::load_plugins(plugins_dir, *, models, host_room_types, host_local_tool_names, sandbox_root) → PluginLoadResult` (a typed bundle of the merged contributions). It is an **aggregation layer**. **Step ordering is security-load-bearing — collision-check precedes any plugin code import (R0-B R1; the fail-closed gauntlet must run before import-time arbitrary-code execution):**

1. **Discover** — iterate `plugins/` subdirs; each with a `plugin.yaml` is a candidate. (Presence = opt-in, D5; no auto-fetch.)
2. **Validate** — parse + validate each manifest (frozen/`extra="forbid"`/`schema_version`); check declared **dependencies** against the host (`models`, `host_room_types`, contract version). A failure → that plugin is **refused, isolated** (logged + skipped; never crashes the bootstrap; never half-registers — HR#5).
3. **Collision-check ALL declared contribution names — BEFORE any code import** — every declared name (`roles`, `skills`, `tools`, **`tool_impls`**, `mcp_servers`) is checked against the host registries **and** across plugins; **fail-closed on any clash** (D6). For `tool_impls` this means checking the declared tool name against (i) the host `local_tools` keys (`host_local_tool_names`), ~~(ii) the host `tools` registry,~~ and (iii) cross-plugin `tool_impls` (D6 — closes the shadow-bypass, R0-A Y1). **[Amendment 1: leg (ii) is intentionally OMITTED — it contradicted D5/D7 (host-pre-classification). `tool_impls` ↔ host `local_tools` + cross-plugin only; the host-`tools` leg is the separate `contributions.tools` check. See "## Amendment 1".]** This check runs on **names from the manifest** — *no module import is needed* — so it **precedes and gates** the import-time code execution in step 5: a then-refused plugin's code **never runs**.
4. **Load non-code surfaces by reusing the existing loaders, pointed at the plugin's subpaths** (pure data parse — no arbitrary code): `load_agents(plugin_dir/"agents", models=models)`; `load_skills(plugin_dir/"skills")`; `load_tools_config(plugin_dir/"tools.yaml")`; `load_mcp_servers_config` / `build_mcp_tool_registry_and_sessions_from_config(plugin_dir/"mcp_servers.yaml")`. **No loader is reimplemented or forked.**
5. **Load code — only now, after validation + collision-check cleared** — the **new** D4 mechanism `importlib`s the plugin's `tool_impls` modules (Posture A: import-time top-level code runs **here**, after the full fail-closed gauntlet — **never before** a collision/dependency refusal). An import failure → refuse that plugin, isolated (HR#5).
6. **Reversibility-cap** — cap plugin-asserted reversibility (host-authoritative-or-default-0, D5).
7. **Atomic merge (HR#5; R0-B Y4)** — steps 2–6 accumulate a plugin's contributions into a **per-plugin intermediate** `PluginLoadResult`; the merge into the live host registries (at `_build_context`, P3.5-5) happens **only after every stage succeeds**. A failure at **any** stage discards the **entire** per-plugin intermediate — **host registries are never mutated by a partially-loaded plugin** (never half-registers). The merge is atomic per-plugin.

**Merge points (verified, unchanged downstream):** plugin roles → the `agents` dict; skills → `skills`; tool-classifications + MCP `ToolMeta`s → the gate's `tools` dict; **executable tool impls → the executor's `local_tools` dict** (so `tools/executor.py::_execute_local_call` runs them via the existing path — **no executor edit**); MCP sessions → `mcp_sessions`. `_build_context` gains **one aggregation pass** after the four loaders; the gate, the executor, and the MCP client are **untouched** (the empty-gate-diff invariant, ADR-027 D2 / ADR-028 D6, holds — and extends to an empty-executor-diff invariant).

### D3. The constitutional spine — feed the existing surfaces unchanged (HR#1–4); the `plugins/` constitution test

`plugins/` makes **no** autonomy/routing/model decision. A constitution test (`tests/plugins/test_constitution.py`, the ADR-027 D2 / ADR-028 D6 analog) forbids `plugins/` referencing `decide_tier` / `emit_gate_decision` / `score` / `gate` / `select_model_and_provider`, forbids any `llm/` provider call, and asserts the frozen `LLMPurpose` set is unchanged (no new purpose, HR#4). Plugin loading is discovery + validation + registration — code, not judgment (HR#3). This ADR **binds** ADR-005/006 (gate + fail-closed), ADR-027 D2 (feed-the-gate-unchanged), ADR-028 D6 (the executor invariants) — it does **not** restate them.

### D4. ⭐ The code-trust / isolation model for plugin-delivered executable tool code — **the architect-ruled security crux**

**The architect ruled `admit-plugin-code-now`, overriding the brief's declarations-only lean (brief §Decisions(b)).** A plugin may carry **third-party executable tool code** (Python): a `tool_impls` entry binds a tool name to a `<module>:<callable>` within the plugin, which becomes a `LocalToolFn` in the executor's `local_tools` registry. This is *loaded = runs* — code executes both at **import time** (the module's top level runs when the loader imports it) and at **call time** (the executor calls `impl(params)` when the gate `AUTO_EXECUTE`s the tool). **This is the project's largest security surface to date** and is **explicitly recorded here as the admit-code override of the brief's declarations-only lean.**

The brief delegated the **isolation mechanism** to senior-design-and-surface-for-architect-Accept. Three postures (the architect's three named options), with their honest threat models:

- **Posture A — in-process import, operator-curation-IS-trust (ARCHITECT-ACCEPTED — A-now-B-later; architect ruling 2026-06-03 via orchestrator routing).** The loader `importlib`s the plugin's tool module and registers the declared callable as a `LocalToolFn`, running **in-process**, like today's `build_local_tool_registry` builtins. **Trust model — operator-accepted-third-party-trust (NOT "as trusted as self-written code"; R0-B Y1 / R0-A §3).** Placing a plugin in `plugins/` = the operator accepts it as trusted third-party code. This is **distinct from `src/`'s trust model, not equivalent to it**: `src/` code passes brief → plan → ADR → R0-A/R0-B → CI gates → merge (commit-time multi-role review); `plugins/` code has no mandatory review, no CI gate, no authorship provenance. Posture A **relocates the trust gate from commit-time multi-role review to deploy-time operator curation** — the operator assumes the review burden that CI + R0-A/R0-B provide for `src/`. The "same privilege as a file in `src/`" is true on *privilege* (both in-process, full host) but a **category error on *path*** (review surface differs); the analogy is therefore retired from this ADR. **Fail-closed-against-breakage is fully delivered**: a bad import / bad manifest / collision / unmet dependency → that plugin refused at load (per-plugin isolation, HR#5); a raise at call → `TOOL_FAILED` for that call (per-call isolation, ADR-028 D4). **Three honest, fully-inscribed exposures** (stated, not implicit — the ADR-028 D3 discipline; the architect Accepts the *real* surface):
  - **(L1) No technical isolation + zero credential/env protection.** A malicious in-process plugin is **NOT technically contained** — Python in-process has no privilege boundary; its code runs with full host privilege (FS, network, **and full `os.environ`** — every API key/secret). The ADR-027 D4 credential-indirection + scoped-env defenses are **MCP-subprocess-only and provide ZERO protection** for in-process plugin code (it reads all env directly). Security rests **entirely on operator-curation**, not a runtime sandbox.
  - **(L1b) Import-time code is ungated by construction.** The gate is a tool-**call** chokepoint; `importlib`-ing a plugin module (step 5 / bootstrap) runs its top-level code **before any gate/room/turn exists**. Presence = opt-in (D5) therefore means **every** plugin in `plugins/` runs its import-time code at boot, full host privilege, **with no gate covering it** — curation is the *only* control. (Not a gap to fix — a property disclosed at Accept; the D2 step ordering ensures it runs only after the validate+collision gauntlet, never before a refusal.)
  - **(L2) Posture A VOIDS (does not merely "relax") ADR-028 D5's absolute per-turn liveness bound for the plugin-local path — server-wide blast radius (R0-A Y2 / R0-B Y3).** D5's *absolute* per-turn bound is real **only because it excludes local tools on the premise they are "fast, no inline block"** — a premise the host's **3 builtins** satisfy *by construction* (hard-coded closures: no network, no subprocess, no infinite-loop surface, sub-ms to ms; `read_file` is bounded specifically to avoid OOM-ing the single writer). **Arbitrary third-party code has none of these guarantees** — an accidental `while True`, a `time.sleep(3600)`, a synchronous `requests.get` blocks the `max_workers=1` writer = **every room's writes, not its own** — indefinitely, with **no cap** (the per-turn cap excludes local tools, ADR-028 D5) and **no kill** (in-process is unkillable; CPython has no safe thread-kill; `signal.alarm` is main-thread/Unix-only). **One buggy (not even malicious) curated tool = a server-wide DoS.** The risk delta is **categorical** ("3 known-bounded closures" → "arbitrary third-party code"), not continuous; the earlier "host's own local tools already run unbounded" framing is *true of the mechanism* but elided that D5's *bound* leaned on those tools being fast-by-construction — that elision is corrected here. **Mitigation under A is the trust model + documentation only** (in-process is unkillable). **Posture B restores the bound** (a killable subprocess) — the operative reason B is the required posture once provenance is untrusted (P3.7).
- **Posture B — subprocess isolation (the ADR-027 MCP-server pattern, applied to plugin tool code).** Plugin tool code is **never imported in-process**; it runs as a **subprocess** with a **minimal scoped env** (ADR-027 D4 / the P2.7-S3 c2 env-leak lesson), **bounded-timeout + killable + fail-closed** → `TOOL_FAILED`. This delivers a **real technical boundary** against malicious code (L1) **and restores the D5 liveness bound** (L2) — both limits resolved. Cost: plugin tool code must speak a subprocess protocol, at which point a "plugin executable tool" ≈ a **bundled MCP server** — which the plugin's `mcp_servers` block (HR#2) **already supports**. So Posture B's marginal value over "bundle an MCP server" is thin; the *distinctive* value of admit-code (in-process convenience) is exactly what Posture B removes.
- **Posture C — in-process import isolation (RestrictedPython / audit hooks).** **Rejected as a live option** (recorded as a considered alternative): in-process Python restriction is **not a real security boundary** (well-documented escapes) — it gives a false sense of isolation (the worst of both: restriction complexity + no real guarantee).

**The hinge question (the Accept crux): is an operator-placed local plugin a TRUSTED tier or an UNTRUSTED third-party?** **Architect ruling (2026-06-03, via orchestrator routing): TRUSTED-tier-via-operator-curation → Posture A, A-now-B-later.** An operator-placed local plugin is accepted as trusted third-party code (the operator assumes the review burden); the brief's *"恶意代码不能越权 host"* is met **by curation** (a policy boundary — malicious code does not enter the operator-curated dir), explicitly **NOT** by a runtime sandbox. The Accept is informed by the **fully-inscribed exposure above (L1 no technical isolation + zero env protection; L1b import-time ungated; L2 D5-bound voided / server-wide DoS)** — the dual-lens (R0-B) + R0-A surfaced these and the architect Accepts the *real* surface, not a softened one. **Posture B is reserved as the REQUIRED posture once provenance becomes untrusted (P3.7 remote install / registry — a fetched plugin is not operator-placed, so curation no longer holds; B's killable-subprocess restores the D5 bound + a real isolation/env boundary).** This parallels ADR-027's "stdio local = most-trusted tier; remote deferred." The A→B migration surface is itemized in the Reversibility table.

### D5. The trust / consent posture (the knobs around the boundary; ADR-027 D4 carried forward — bind, not restate)

- **Consent / opt-in = presence.** A plugin's presence in the `plugins/` directory **is** the opt-in (the dir IS the host's curation, mirroring `config/`); loading a plugin = opting into its bundled servers + tool-classifications + (per D4) code. No separate per-plugin allowlist entry for the local-dir MVP (a discovered-but-not-activated registry is a P3.7 concern when provenance becomes untrusted). Per-surface guards (gate / allowlist) still apply unconditionally. **[Annotated P4.4 → ADR-038, Accepted 2026-06-05: presence=opt-in is preserved (ADR-038 D2, narrowed-not-reversed). A `config/plugins.yaml` registry entry can additionally carry `enabled: false` to declare-but-disable a plugin without removing it; absent entry → still enabled by presence. The per-plugin enabled-state is evaluated at boot (boot-only lifecycle, ADR-038 D2).]**
- **Plugin-asserted reversibility is advisory-capped → host-authoritative-or-default-0** (the ADR-027 HR#2 analog — a third-party self-claim is **never** authoritative for the tier). A plugin **cannot** claim `rev=10` on a write tool to dodge `HARD_CONFIRM`: the host may only *lower* trust (cap), never accept a raise. **Default-0 semantics, made explicit (R0-B Y2):** for a tool the **host has never classified** (every genuinely-new plugin tool), there is **no host-authoritative value** → it defaults to **reversibility 0** (conservative-low, ADR-005 D2) → `HARD_CONFIRM` → **it does NOT `AUTO_EXECUTE`**. The plugin's *own* claimed reversibility is **not** used as the value — it is only ever a ceiling-candidate that is capped against a host classification, and absent one the result is 0. **Consequence the operator must know:** a brand-new plugin executable tool will **never reach the executor (AUTO)** until the **operator adds a host-side classification** (a `config/tools.yaml` entry — the host-authoritative source) raising it above the auto threshold. (This is the intended friction — discovery ≠ permission, one level up: bundling a tool ≠ auto-trusting its tier.) A test asserts a plugin-claimed high reversibility on an unclassified tool does **not** change the gate tier (stays default-0 → `HARD_CONFIRM`).
- **Credential + scoped-env** for plugin-delivered servers **reuse ADR-027 D4 verbatim** (`api_key_env`, minimal scoped subprocess env) — **bound, not restated**. The manifest carries no plaintext secret.

### D6. Dependency model + collision policy — fail-closed (HR#5)

- **Dependencies** (manifest `dependencies`): a role's `model_id`s must exist in the host model registry; required `room_type`s must exist; `min_host_contract` ≤ the host contract version. **Any unmet dependency → the plugin is refused** (fail-closed; never half-registers).
- **Collision policy = fail-closed on collision** (architect-ruled lean; loudest, safest for the MVP). The collision namespace covers **all five contribution surfaces** — a role id / a skill id / a tool name (ToolMeta) / a server name / **and a `tool_impls` name (→ `local_tools`)** — checked against the host registries **and** across plugins; any clash → the colliding plugin **fails to load (refused)**, host registries unmodified.
  - **The `tool_impls → local_tools` shadow-bypass this closes (R0-A Y1; HR#5).** A plugin could declare **only** `tool_impls: {read_file: "evil:read_file"}` and **no** `tools` ToolMeta. Without checking the `tool_impls` namespace, the ToolMeta-only collision check finds no clash; the impl merges into `local_tools` and **shadows the host's sandboxed `read_file`**; at call time the gate scores `read_file` via the **host's** ToolMeta (`tools.yaml` rev=10 → `AUTO_EXECUTE`) and `_execute_local_call` runs the **plugin's** impl — **bypassing the host path-sandbox + OOM-guard entirely**. Both merge directions are unsafe (plugin-wins → host shadowed = bypass; host-wins → plugin silently dropped = silent degrade, violating HR#5). The fix is a **collision-check, not a merge-order choice**: check `tool_impls` names against (i) host `local_tools` keys, ~~(ii) host `tools` registry,~~ (iii) cross-plugin `tool_impls` → fail-closed on any clash (D2 step 3). **[Amendment 1: leg (ii) is intentionally OMITTED — see "## Amendment 1". The shadow-bypass is closed by leg (i) alone (it covers every tool with a host *implementation* to shadow); a host `tools` ToolMeta-*only* entry is a pre-classification to *adopt* (D5/D7), not an impl to shadow.]** A discriminating test: a plugin `tool_impl` named `read_file` → refused, host impl unchanged.
  - (Considered alternative: namespacing `<plugin>__<id>`, the MCP-namespacing analog — deferred; fail-closed is the MVP posture.) **[Annotated P4.4 → ADR-038, Accepted 2026-06-05: cross-plugin namespacing has LANDED (ADR-038 D4). Cross-plugin collision now resolves to deterministic `<plugin_id>__<name>` prefix, not refusal. Host-collision (incl. shadow-bypass) and within-plugin dup remain fail-closed on the bare name.]** A test asserts a colliding plugin (each surface, incl. `tool_impls`) is refused and the host registry is unmodified.
- **Per-plugin load isolation:** one plugin's validation/collision/dependency/import failure refuses **only that plugin**; other valid plugins load (mirrors ADR-028 D4 per-call isolation, at load granularity).

### D7. The demo plugin — one bundle exercising all surfaces end-to-end (incl. admit-code)

ONE demo plugin (`plugins/demo/`, mirroring P3.4's one demo connector) bundling all five surfaces. **The demo ships DISTINCTLY-NAMED content, not core re-exports (R0-A Y3 — resolves the D7-vs-D6 self-collision):** under D6 fail-closed-on-collision a plugin re-declaring a *core* name (`facilitator`, `research-decomposition`) would be **refused** — so the demo ships its own ids (e.g. a `demo_facilitator` role modeled on the facilitator shape, a `demo-research` skill), an **MCP-server config** (the ADR-027 filesystem demo), a **tool-classification**, **and one executable tool** (admit-code, D4 — a trivial *pure, no-I/O, deterministic* function, e.g. `word_count`). **Host-side classification for the demo tool (R0-B Y2):** per D5's default-0 semantics, the demo's executable tool needs a **host-side `config/tools.yaml` classification** (operator-accepted) raising it above the auto threshold for the demo to show the AUTO_EXECUTE path end-to-end — without it the tool defaults to 0 → `HARD_CONFIRM` → not executed. The demo proves the merged plugin tool **gates** (host-classified → tier), **executes** (via the existing executor), and **fails closed** (a deliberately-broken variant — import error / raise — refused/`TOOL_FAILED`, in tests). The demo's value *is* the bundle merging across every surface, including the new code surface.

## Amendment 1 — `tool_impls` collision is two-way; name-adoption is the D5/D7 mechanism (clarification, no behavior change)

**Status:** Accepted — 2026-06-03 (architect Peidong, P3.5 impl-stage; ruled via orchestrator routing; `reviews/P3.5/architect-routing-on-impl.md`). This is a **clarification amendment** — it corrects the *as-Accepted prose* of D2 step 3 + D6 to match the *correct-by-design* implementation; **it changes no behavior** (the impl on `claude/P3.5-impl` was already two-way, and the gate/executor/empty-diff invariants are unchanged). ADR-029 **remains Accepted** (an amendment does not downgrade the decision).

**Why.** The as-Accepted D2 step 3 + D6 specified a **three-way** `tool_impls` collision check — against (i) host `local_tools`, (ii) host `tools` (ToolMeta), (iii) cross-plugin. Leg (ii) **contradicts D5/D7**: D5/D7 require a plugin's executable tool to be **host-pre-classified** in `config/tools.yaml` (so it clears default-0 and `AUTO_EXECUTE`s) while the plugin supplies only the impl via `tool_impls`. Under leg (ii), that pre-classified name would be in host `tools`, so the plugin's own `tool_impl` would **collide with the very classification it depends on → refused**. Leg (ii) and the D5/D7 mechanism are **mutually exclusive**; the as-Accepted ADR specified both. The plan-vs-impl review (`plan-vs-impl.md` Y1) + the impl-stage R0-A independently judged the **two-way** implementation **correct-by-design**.

**The corrected, authoritative collision rule (supersedes D2 step 3 + D6 leg-(ii) wording):**

| Declared surface | Collision-checked against | Purpose |
|---|---|---|
| `roles` / `skills` / `mcp_servers` | host registry + cross-plugin | namespace integrity |
| **`contributions.tools`** (a ToolMeta *classification*) | **host `tools`** + cross-plugin | a plugin **cannot re-declare** an existing classification (fail-closed) |
| **`tool_impls`** (an executable *implementation* name) | **host `local_tools`** + cross-plugin — **NOT host `tools`** | closes the **shadow-bypass** (no shadowing a host *impl* like `read_file`); host `tools` is deliberately excluded so the D5/D7 **host-pre-classification** path works |

**Name-adoption is the intended D5/D7 mechanism, not a hole.** A plugin `tool_impl` whose name matches a host **ToolMeta-only** classification (one with no host `local_tools` impl) **adopts that gate tier** — this is exactly how the operator grants a plugin tool a tier above default-0: the operator **pre-classifies the name in `config/tools.yaml`** (the authoritative, operator-curated source) and the plugin supplies the impl via `tool_impls`. Under **Posture A**, the operator curates **both** `plugins/` and `config/tools.yaml`, so this is **operator-controlled**, consistent with the accepted trust model: *classifying a tool name in `config/tools.yaml` accepts that gate tier for whatever implements that name — host builtin or operator-curated plugin.* The gate remains the sole chokepoint (an `AUTO_EXECUTE` plugin tool still ran through `score`/`decide_tier`); name-adoption affects only **which tier** a curated plugin tool gets, and that tier is set by the operator, not the plugin (the plugin's self-asserted reversibility is still advisory-capped, D5). The **shadow-bypass** (overriding a host *implementation* to escape its sandbox) remains closed by the host-`local_tools` leg.

**Demo (P3.5-7) exercises both paths** (`plugins/demo/`): `text_stats` is the **plugin-classify path** (`contributions.tools` + the demo `tools.yaml` rev-5 → capped to 0 → `HARD_CONFIRM`, no host pre-classification); `word_count` is the **host-pre-classify + plugin-impl path** (`config/tools.yaml` rev-10 authoritative + `tool_impls` → `AUTO_EXECUTE`).

**Net:** D2/D6 prose corrected to the two-way `tool_impls` check + the separate `contributions.tools`↔host-`tools` check; name-adoption inscribed as the D5/D7 operator-controlled mechanism. No invariant weakened; the empty-diff + gate-sole-chokepoint + fail-closed-loading guarantees hold unchanged.
