# Architect brief — P4.4: plugin registry + lifecycle + signature (decision-surface)

**Task:** P4.4 (A2 + A3 + A4 + A5) — formalise **how plugins are declared, enabled, version-managed, and admitted** now that P4.3 (ADR-037) put a **real per-call container sandbox under the Posture-B fetched-plugin EXECUTION path**. The **Wave-2 trust-hardening middle slice** (P4-roadmap §4: capability → **trust hardening** → completeness); depends on P4.3 (roadmap §4 `P4.3 → P4.4` — registry/lifecycle ride the sandbox).

**Class:** heavy trust slice. `requires_cross_family_review: true` (set in `.workflow/P4.4.yaml`; mandatory dual-lens for A2/A3/A4, roadmap §8). **New ADR-038.**

**Status of this doc:** a **DECISION-SURFACE**, not a plan and not a set of decisions. Five decision points below carry **architect-ratifiable leans + tradeoffs**; the architect-partner does **not** decide. The load-bearing call is **DP3 (A4 admission/signature)** — an architect-weight trust call, not a lean to bank. No plan/ADR-038 is drafted until the architect ratifies (≥ DP1, DP2, DP3).

---

## 0. What exists today + what each ledger item extends (verify-cited `origin/main`)

P4.3 sandboxes a fetched plugin's **execution** (per-call OS container, deny-default net, killed-in-finally — ADR-037 D1/D2/D3, wired through `_PostureBFn`). **P4.4 is the orthogonal half: how code gets *admitted, declared, and managed* in the first place.** The current state is deliberately minimal (ADR-029/031 both scoped registry/lifecycle/signature **out**, to P4):

| # | Item | What exists **today** (verified) | The gap P4.4 weighs | Src | Sec / lens |
|---|---|---|---|---|---|
| **A2** | **Registry** | **No registry object.** Operator-placed = **directory presence** in `plugins/` (boot-read, no entry). Fetched = the **activation allowlist YAML** (`provenance.py::load_activation_registry`: `plugin_id → {source_url, sha256 digest, plugin_subprocess_env}`) — a **proto-registry for fetched only**. Both are **boot-time-immutable** (`load_plugins` runs once in `_build_context`, `app.py:255`). Fetched path is built+tested but **not even bootstrap-wired** (`load_plugins` called with **no** `fetched_plugins_dir`/`activation_registry_path`). | Is there **one** declared registry (covering operator-placed *and* fetched)? Config-file vs runtime-store vs both. What an entry holds. | ADR-031 D5; ADR-029 D5 considered-alt + scope | **Heavy** / dual-lens |
| **A3** | **Lifecycle** | **None.** Install = place dir / `fetch.py`. Enable = presence. Disable = delete. Update = re-fetch (`fetch.py` rmtree+rename idempotence; **no** version-coexistence/upgrade). No enable/disable toggle, no state machine, no runtime mutation. | The ops (install/enable/disable/update/remove) + a per-plugin state machine + **hot vs boot-time** + the **confirm posture for admitting untrusted code**. | ADR-031 D5; ADR-029 scope | **Heavy** / dual-lens |
| **A4** | **Signature / provenance** ⭐⭐ | **Operator-pinned source + digest** (options b+c, **shipped**): `fetch.py` verifies sha256 of the **compressed bundle bytes before extraction** (TLS-only, traversal-guarded); the **operator** authors the activation entry = the trust anchor. **No crypto signature, no signer, no keyring, no trust-root.** | Do we **add** a signature/keyring model (a) on top, or keep pinned-digest (b+c) and only widen remote-fetch? The honest residual either way. | ADR-031 D4 considered-alt + Reversibility; brief §Out | **Heavy** / dual-lens |
| **A5** | **Namespacing** | **Fail-closed on collision** (`loader.py::_collision_check`): two plugins both declaring `echo` → the second is **refused**. No namespacing. | Move to auto-namespace `<plugin>__<id>` so contributions **coexist**. (Name-collision only — **distinct** from runtime isolation; see DP4.) | ADR-029 D6 considered-alt | **Light** / single-lens |

**Framing the trust split P4.4 turns on:** P4.3 answered *"what can admitted code DO"* (container-bounded). P4.4 answers *"what gets admitted, and how is admission expressed and revised over time."* The sandbox lowers the cost of being **wrong** about admission (bounded blast radius) — but does **not** decide admission. A4 is still the load-bearing trust call.

## 1. ⭐ DP1 (A2) — Registry shape: where plugins are declared + enabled

**Backend-authoritative (ADR-026 HR#2): the registry is the source of truth; the GUI (P4.7) sends intent, never decides.** Two sub-calls:

**(1a) Storage model — config-file vs runtime-store vs both.**

| Option | What | Trade-off |
|---|---|---|
| **Config-file registry** (lean) | One operator-authored YAML (generalise today's activation allowlist to cover **both** roots), boot-read like every other `config/` surface. | Matches `config/`-curation + boot-time-immutable reality; **lowest new trust surface** (no runtime mutation of the largest boundary). **But** no live enable/disable — a change needs a restart (couples to DP2-hot). |
| **Runtime store** | A mutable backend-owned store (sqlite/event-store) the management API writes; load merges from it. | Enables GUI-driven **live** enable/disable (E2/P4.7) — **but** introduces a **runtime-mutation path on the plugin trust boundary** + a registry-rebuild-on-running-system liveness problem (DP2). Heaviest. |
| **Both** | Config seeds the declared set; a thin runtime overlay carries enabled-state only. | The GUI ambition without a full mutable code-admission store; more moving parts to keep fail-closed. |

**Lean: config-file registry for the MVP** (it *is* today's posture, generalised — the activation allowlist already proves the shape), with the runtime-overlay reserved as the additive step **if** the architect wants live enable/disable in P4.4 rather than deferring it to P4.7's backend endpoints. *(This couples tightly to DP2-hot — decide them together.)*

**(1b) What a registry entry holds (the inscribe-before-producer contract).** Candidate fields, each a verify-grounded need: **id/name** (identity, today's subdir name); **provenance** (`operator_placed | fetched` — already host-set-by-origin, ADR-031 D3, *un-spoofable*); **posture** (A/B — today derived from provenance, ADR-031 D3; does the registry record it or keep deriving it?); **enabled state** (the genuinely-**new** field — nothing carries it today); **version** (the manifest already has `version: str`, unused — A3 makes it load-bearing); **admission proof** (today: `source_url` + digest for fetched; A4 decides whether a signature joins). This entry shape is **expensive-to-change** (every future producer binds it, the ADR-029-D1 manifest-schema lesson) → **inscribe before producers** (roadmap §10).

## 2. ⭐ DP2 (A3) — Lifecycle: the ops, the state machine, hot-vs-boot, and the admit-confirm posture

**(2a) The operations + a per-plugin state machine.** install/fetch → enable ⇄ disable → update → remove. A candidate machine: `fetched/placed → (activated/admitted) → enabled ⇄ disabled → removed`, with **update** = re-admit a new version (digest/signature re-checked, A4). Today only the endpoints exist (place/fetch, delete); the **toggle** and the **machine** are new. Note two **distinct code-lifetimes** already in the system that lifecycle must not flatten: a plugin's **bundled MCP server** is a **persistent** `MCPSession`; its **`tool_impls`** run **per-call** (fresh container, ADR-037 D3). "Update/disable a plugin" means different things for each.

**(2b) ⭐ Hot vs boot-time (the load-bearing lifecycle call).**

| Option | What | Trade-off |
|---|---|---|
| **Boot-time-only** (lean) | enable/disable/update edit the registry; effect at next restart. | Matches the boot-immutable reality (`_build_context` runs once); **zero new runtime-mutation surface**; trivially fail-closed. **But** no live management (GUI shows intent that lands on restart). |
| **Hot** | Changes take effect live: re-run the merge + atomically swap the AppContext registries. | True live management — **but** mutating `agents/tools/local_tools/mcp_sessions` under the `max_workers=1` writer with in-flight rooms is a real **liveness + consistency** surface (ADR-028 D5 territory); tearing down a persistent plugin MCP session mid-turn; re-entrancy. Heavy, dual-lens-worthy on its own. |

**Lean: boot-time-only for P4.4**; hot-reload deferred (named residual) unless the architect rules live-management in-scope now. *(If DP1 = config-file, this is nearly forced; if DP1 = runtime-store, hot becomes tempting — hence "decide DP1+DP2 together.")*

**(2c) The admit-confirm posture (surface, don't conflate with the gate).** Installing/enabling a plugin **admits code-execution capability** — but it is an **operator** action, **not** an agent tool-call, so it does **not** route through the autonomy gate (the gate scores *agent* operations; ADR-029 HR#1 / D3 keep loading code-not-judgment). The honest question for the architect: should plugin **admission** itself carry an explicit confirm step (a deliberate "you are admitting third-party code" acknowledgement, the ADR-031-D4 activation-entry discipline made interactive), or stay pure config-authoring (presence/entry = consent, as today)? **Lean: keep admission = operator-authored registry entry** (consent-by-authoring, consistent with ADR-029 D5 presence=opt-in + ADR-031 D4 activation=opt-in); a GUI confirm is a **P4.7 frontend** concern over the same backend intent, not new backend trust.

## 3. ⭐⭐ DP3 (A4) — Admission / signature: THE load-bearing trust call

**The threat (unchanged): untrusted fetched plugin code. P4.3 bounds what it can DO; A4 decides what gets ADMITTED.** What ships today is **operator-pinned source+digest** (b+c): the operator obtains a digest out-of-band and pins it; `fetch.py` guarantees you get **exactly those bytes** (integrity) before any extraction. The four options (ADR-031 D4 named the signature one and **deferred it to here**):

| Option | Trust model | What it buys over today | Honest residual |
|---|---|---|---|
| **(a) Signature / keyring** | A signer (plugin author? a registry authority?) signs the bundle; operator pins a **public key / trust-root**; verify-on-admit. | **Author identity + update-trust** (new versions signed by the same key verify without re-pinning each digest) — the thing pinned-digest cannot give. | Only as strong as **key distribution / rotation / revocation**; TOFU on first key; a compromised/coerced signer signs malware. Adds keyring machinery. |
| **(b) Provenance-pinning** (digest/lockfile) | sha256 of the bundle, operator-pinned (**shipped**). Extend = a lockfile over multiple plugins / per-version digests. | Strong **integrity**; zero key infra; already vetted (ADR-031 D5, R0-B Y5 ordering). | **No author identity / no revocation**; the operator must re-pin every version by hand (no update-trust); trust = "the operator vetted these exact bytes." |
| **(c) Operator-admit-only** (no crypto) | The operator explicitly admits (the ADR-029 admit-code / ADR-031 activation model). | Simplest; the operator **is** the trust root. | Pure curation — no integrity against a tampered mirror unless combined with (b). |
| **(d) Combination** (lean) | **(c) operator-admit + (b) digest = exactly today**; optionally **add (a) signature as an upgrade path** for an author-identity / update-trust story. | Keeps the shipped, vetted floor; signature is **additive** when key infra is justified (ADR-031 Reversibility: "moving to signature is a consent-granularity change, P4"). | Whatever of (a)'s residual you opt into; if signature is **not** added, the no-author-identity/no-revocation residual of (b) **persists past P4.4** and must be inscribed. |

**Lean: (d) — keep the operator-admit + pinned-digest floor; treat signature/keyring as an additive, separately-justified layer, NOT a default.** Rationale: (i) the shipped digest model already gives cryptographic **integrity** — A4's real *new* value is **author-identity + update-trust**, which only matters once there is a multi-author *distribution* story (a registry/marketplace, explicitly still deferred); (ii) a keyring's trust collapses to **key management**, a heavier and easy-to-get-wrong surface than the threat (a single operator vetting bundles) currently needs; (iii) the sandbox (P4.3) already bounds the blast radius of an admission mistake. **But this is an architect-weight call, not a lean to bank** (the same weight as Accepting a residual): if a near-term **third-party plugin distribution** story is the goal, signature-now is legitimate. **Whatever is chosen, the residual must be inscribed exactly as `RB-FS/NET` was** (ADR-031 D1a discipline) — "what A4 does NOT prove about the code's author/provenance."

## 4. ⭐ DP4 (A5 + inter-plugin isolation) — two *different* axes the dispatch conflated

The dispatch's "namespacing / isolation between plugins" is **two distinct decisions** — surfaced separately so neither hides the other:

**(4a) A5 — name-collision namespacing (the actual ledger item, Light).** Today fail-closed-on-collision **refuses** a second plugin that re-declares a name (`loader.py::_collision_check`). A5 = auto-namespace `<plugin>__<id>` so they **coexist** (ADR-029 D6 considered-alt; the MCP-namespacing analog). **Lean: ship namespacing as the multi-plugin-coexistence relaxation** (amend ADR-029 D6) — it is purely a **registry/dispatch naming** concern, single-lens. *(Caveat to weigh: namespacing changes the tool **names** agents see — a content/UX ripple, not a trust one.)*

**(4b) Runtime inter-plugin isolation — a sandbox-LIFETIME axis, not A5.** "One container per plugin? shared? per-call vs persistent for a long-lived MCP-stdio plugin?" is **not** name-collision — it is how lifecycle (A3) sits on the P4.3 sandbox. The honest state: **ADR-037 D3 already ratified per-call** (fresh container per `tool_impls` call, isolation>latency) — so per-call **already gives per-call inter-plugin isolation for free** (no two plugins share a container). The genuinely-open question is the **persistent long-lived** case: a plugin that wants a warm sandboxed process (e.g. an in-sandbox stdio MCP server) would be a **persistent-container** model — a **reversal/extension of ADR-037 D3**, with its own cross-call state-leak + lifecycle surface. **Lean: keep per-call (inherit ADR-037 D3); name "persistent sandboxed plugin process" as an out-of-scope forward-watch** unless the architect rules a long-lived-plugin capability into P4.4 (it would re-open the ADR-037 D3 per-call call).

**(4c) Backend-authoritative GUI surface (trails P4.7).** A2/A3 define the **management-endpoint contract** (list/enable/disable/admit/remove) that E2 (plugin-management UI, roadmap §E2) binds in P4.7. P4.4 owns the **backend contract**; the config UI **sends intent, never decides** (ADR-026 HR#2; roadmap §10). **Lean: pin the management-endpoint shape in ADR-038 so P4.7 plans against it rather than discovers it** (inscribe-before-producer) — but build no UI here (frontend track).

## 5. ⭐ DP5 — New ADR-038 + the dual-lens external-r0b-prompt

**New residuals P4.4 will leave — inscribe, don't soften (roadmap §10):** the A4-residual (DP3 — no author-identity/revocation if signature not added); the **hot-reload deferral** (if DP2 = boot-only); the **persistent-plugin deferral** (DP4b); and the registry being **only as fail-closed as its parser** (a malformed/over-broad registry entry must refuse, not admit — the ADR-031-D4 fail-closed discipline at registry granularity).

**ADR-038 (new contract):** the registry-entry schema (DP1b) + the lifecycle state machine (DP2) + the admission/signature model (DP3) + the namespacing rule (DP4a) + the management-endpoint contract (DP4c) + the residual inscription (DP5). Expensive-to-change (every plugin + the P4.7 GUI bind it) → **inscribe-before-producer** (roadmap §10, RC-23-safe). **Annotates** ADR-029 (D5 presence→registry; D6 collision→namespacing) + ADR-031 (D4 activation→registry-entry; D5 registry/lifecycle "deferred P4" → landed) — mark them narrowed/resolved at impl, the ADR-037 precedent.

**Review posture:** `requires_cross_family_review: true` → **mandatory dual-lens** (roadmap §8: A2/A3/A4 heavy; A5 single-lens). Plan-stage writes `docs/process/reviews/P4.4/external-r0b-prompt.md` (the P4.3/ADR-037 precedent) with two lenses: **(a) the plugin-admission trust boundary** — can a fetched/registered plugin get admitted/enabled without passing the full activation+integrity (+signature) gauntlet? does a registry-entry forge provenance/posture/enabled-state? does update/re-admit re-verify? is the admit path fail-closed on a malformed entry? **(b) the registry/lifecycle state-machine correctness** — enable/disable/update/remove transitions (incl. hot-swap if DP2=hot) for consistency under the single writer, state-leak across a persistent plugin, partial-failure atomicity (the ADR-029-D2 atomic-merge analog at lifecycle granularity), and the namespacing collision-resolution (DP4a) staying fail-safe.

## 6. Constitutional carry-forward watch-list (carry into the plan + ADR-038)

- **Trust boundary** (P2.7-S3 → P3.5 → P3.7-remote → P4.3, now the *admission* half) — opt-in, fail-closed, credential-safe, posture-ratified. The registry/lifecycle **must not** become a path to admit code that skips activation+integrity (DP5 lens a).
- **Backend-authoritative** (ADR-026 HR#2) — the registry is the source of truth; the P4.7 GUI sends intent. The management endpoints are a backend contract, **not** a decision surface.
- **Gate unchanged / no LLM-judgment** — admission/lifecycle is **deterministic operator config**, never an LLM decision (ADR-029 D3 / ADR-031 D7); no new `LLMPurpose`. Plugin admission is an **operator** action, not a gated **agent** op (DP2c) — don't accidentally route it through the autonomy gate.
- **Inscribe-before-producer** — the registry-entry schema + management-endpoint contract are expensive-to-change; pin them in ADR-038 before plugins + the P4.7 GUI bind (roadmap §10; the ADR-029-D1 manifest-schema discipline).
- **Honest-residual inscription** — Accept the *real* post-P4.4 admission surface (DP3/DP5), never a softened one. The discipline that governed `RB-FS/NET` governs A4's residual.
- **Sandbox is the floor, not the admission decision** — P4.3 bounds execution; it does **not** lower the admission bar. "It's sandboxed" is not a reason to admit unverified code (DP3).

## 7. What the architect ratifies (the routing surface)

1. **DP1 (A2) — registry shape** (lean: config-file MVP generalising the activation allowlist; runtime-overlay reserved). *Decide with DP2.*
2. **DP2 (A3) — lifecycle** (lean: ops + state machine; **boot-time-only**, hot-reload deferred; admission = operator-authored entry, no gate). *The hot-vs-boot call is the load-bearing lifecycle decision.*
3. **DP3 (A4) — admission/signature** (lean: **(d)** keep operator-admit+digest floor, signature additive-not-default — **but an architect-weight trust call**, signature-now legitimate if a distribution story is near-term). *Ratify the trust model + the inscribed residual.*
4. **DP4 (A5 + isolation) — namespacing** (lean: ship `<plugin>__<id>`; **keep per-call sandbox per ADR-037 D3**, persistent-plugin deferred; pin management-endpoint contract for P4.7, build no UI).
5. **DP5 — ADR-038 + dual-lens prompt** (confirm the two lenses + the residual/annotation set).

Plus the mechanical confirm: **new ADR-038**, `requires_cross_family_review: true` (already set in `.workflow/P4.4.yaml`); A5 single-lens, A2/A3/A4 dual-lens (roadmap §8).

Once ratified, P4.4 gets the senior plan → ADR-038 → impl → mandatory dual-lens (R0-A ∥ R0-B) → plan-vs-impl → merge.
