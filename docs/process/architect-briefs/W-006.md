## Scope

**W-006-1 — RC-22: cycle-relative boundary (the real fix).**
The W-005 Decision 14 cycle-boundary filter (`_safe_load_verdict_cycle_filtered` / `_review_file_in_cycle`) decides a review file is "in cycle" iff it has a commit since `state.last_transition_at`. But `cmd_advance` bumps `last_transition_at` to `now()` on **every** transition. So when `advance` runs late or cascades multiple steps, each bump pushes the boundary past already-committed reviews → the next step reads their verdict as `absent` → the cascade stalls → architect must override. **Hit twice** (P2.1 + P2.2 close), each time inflating `override_history` with a non-substantive entry — exactly what overrides were meant NOT to be (ADR-008 Decision 10 audit-signal value).

The boundary that's actually correct is the **cycle's review-phase start**, which is stable across the cascade — not the per-micro-transition `last_transition_at`. **Remedy options (RC-22 candidate, for arch to evaluate + architect to pick):**
- **(a) cycle-relative boundary** [candidate lean]: filter reviews against a stable per-cycle timestamp (e.g. when the task entered the impl phase of the current cycle), not `last_transition_at`. Needs a way to know cycle-start — a new `cycle_started_at` field, or derive from `override_history` / the junior-impl commit time.
- **(b) reconcile mode**: `advance --reconcile` that doesn't bump `last_transition_at` between cascaded steps (or bumps once at the end).
- **(c) accept override-on-reconcile**: document override-to-advance as the supported path; stop trying to auto-cascade. Lowest effort, keeps a substantive override per close.

Acceptance: a delayed/multi-step `advance` over a completed review cycle cascades to the correct state with **no override**. ADR-008 amendment (Decision 16). Tests: synthetic repo where reviews are committed well before the advance timestamp; assert the cascade fires (the exact P2.1/P2.2 failure as a regression test).
