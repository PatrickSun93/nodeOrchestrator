# Architect brief — P5.1b: recurring pipeline scheduler + schedule persistence + restart re-arm (decision-surface)

**Task:** P5.1b — the **second slice** of the P5.1 analysis-pipeline wave. P5.1a shipped the *safe* primitive (deterministic `fetch → fan-out(analyze×N) → reduce`, `sources/` read abstraction, reversible-only room output, owner-private `/pipelines*` CRUD + **manual** `POST /pipelines/{id}/run`, owner-scoped `pipelines`/`pipeline_runs` side tables with **deliberately zero schedule columns**) under **ADR-041**. P5.1b adds the **recurring loop scheduler** + **schedule-definition persistence** + **restart re-arm** — making the headless pipeline *unattended on a timer*, not just unattended on a manual click.

**Class:** **heavy-ish**; `requires_cross_family_review: true` (already set in `.workflow/P5.1b.yaml`); **likely new ADR-042** (ADR-041 D10 named it as the extension vehicle). Dual-lens (two orthogonal failure-family lenses, §B6). The risky surface is **not** a new irreversible actuator (that is P5.1c) — it is the **first headless *initiation* surface** (nothing in the product yet *starts* a multi-stage run with no human at start time; P4.6's sweeper only *actuates a pre-gated pending*).

**Status of this doc:** a **DECISION-SURFACE**, not a plan and not a set of decisions. Each point carries an **architect-ratifiable lean + tradeoff**; the architect-partner does **not** decide — **routing is the architect's**. No plan / ADR-042 is drafted until the architect ratifies (≥ B0 scope, B1 mechanism, B4 the honesty/autonomy face).

The wave-level leans for this slice already exist in `docs/process/architect-briefs/P5.1.md` **DP2** (scheduling: *sibling* scheduler on the ADR-040 *pattern*, not a generalization of the spine-critical countdown sweeper) and **DP7** (persistence: schedule defs → side table; restart → lifespan re-arm). This brief **refines those wave-leans into P5.1b's concrete decision points** (local numbering **B0–B6**) and surfaces the sub-decisions they fan out into.

## 0. What is already inscribed + the verified seam P5.1b plugs into (verify-cited `origin/main` @ `40740c6`)

ADR-041 was written **inscribe-before-producer** specifically so P5.1b extends a written contract. The relevant already-decided seams:

- **One run path, the scheduler is its *second caller* (ADR-041 D7).** P5.1a's `POST /pipelines/{id}/run` is the first caller; the scheduler is the second — *a caller, not a parallel execution model*. **Verified wiring** (correcting the dispatch's shorthand — the senior must plan against the real seam): `run_pipeline(pipeline_id, definition, *, deps, owner_user_id)` **generates its own** `run_id` internally (`runner.py:263`) and returns it on `PipelineRunResult.run_id`; the **store** function `create_pipeline_run(..., run_id=...)` is the one that **accepts a caller-supplied `run_id`** (`store.py:141-149`); the endpoint threads `result.run_id` into the store row so the index id == the run-anchor event id (`app.py:1687-1692`, "F-runid"). The scheduler replicates *exactly this*: on the `writer_executor`, call `run_pipeline(...)` → take `result.run_id` → `create_pipeline_run(run_id=result.run_id, …)`. It does **not** pass a run_id *into* `run_pipeline`. (cyc2 "真正使用 owner_user_id" **is** accurate: `owner_user_id` is a required kwarg, stamped via `build_user_author` at `runner.py:281` — for a scheduled run it comes from the **stored schedule owner**, not a live principal.)
- **Reversible-only output, no headless actuation (ADR-041 D5 — the load-bearing safety invariant P5.1b inherits).** The runner calls `process_tool_calls(..., countdown_auto_fire=None)` (`runner.py:153,223`), so **no** `TOOL_CALL_PENDING` the pipeline produces is ever stamped `expires_at` → the COUNTDOWN sweeper **cannot** auto-fire any pipeline pending. A HARD tool an analyze branch proposes (e.g. `send_email`) just **waits**. **P5.1b MUST preserve this** — a *scheduled* run is still reversible-only; it can **never** escalate to headless-actuating an irreversible op. That escalation is **P5.1c** (the `RB-PIPELINE-EMAIL` crossing), explicitly out of P5.1b.
- **The scheduler PATTERN already exists, fully (ADR-040).** P4.6's `_countdown_sweeper` (`app.py:476-539`) + `_discover_expired_pendings` (`:430-473`) + lifespan start-when-enabled + clean teardown (`:1743-1759`) + `CountdownAutoFireConfig` opt-in (`autonomy/config.py:17-30`, default OFF, fail-closed) is a **near-perfect template**. P5.1b reuses the *pattern*; the *unit* differs (a standing recurring schedule vs a one-shot deadline).
- **Persistence precedents.** Mutable side tables: `users`/`sessions` (P4.5/ADR-039) and the P5.1a `pipelines` table itself. In-place **schema migration** has an in-repo precedent: guarded `ALTER TABLE … ADD COLUMN … DEFAULT` (`memory/store.py:116-130`, ADR-016) — so *either* "ALTER `pipelines`" *or* "new table" is mechanically supported (B2).

**What P5.1b adds:** (i) a **sibling** background scheduler (recurring cron/interval → due-discovery → `run_pipeline` on the writer); (ii) **schedule persistence** (cron/interval, `next_fire`, `enabled`) — schema home is B2; (iii) **boot re-arm** of schedules + catch-up semantics (B3); (iv) the **honest residual** for headless *reversible-pipeline initiation* (B4); (v) an **opt-in config** posture (B5); (vi) **ADR-042** + amendments + dual-lens (B6). Manual trigger is **done** (P5.1a) — not re-built here.

## B0. ⭐ Scope — is incremental feed state IN P5.1b, or deferred again? (decide first)

ADR-041 **D4** parked incremental **last-seen feed state** "with the scheduler (P5.1b), where 'what changed since last run' first becomes meaningful." But the dispatch scopes P5.1b to **scheduling + persistence + re-arm only**. These are separable: the scheduler works fine re-reading the full feed each run; incrementality is a *per-source cursor* feature with its own state design.

| Option | Trade-off |
|---|---|
| **(a) Defer incrementality (lean)** — P5.1b = scheduler + persistence + re-arm; each scheduled run reads the full current feed (P5.1a behavior). | Keeps the slice tight around the *one* new spine concern (a second background task near the auto-fire neighborhood). Incrementality lands as a separable later add (P5.1b′ / P5.2) with its own last-seen-cursor design. Matches the dispatch's explicit scope. |
| **(b) Pull incrementality in** — add per-source `last_seen` state + "only-new-items" fetch alongside the scheduler. | Realizes ADR-041 D4's "with the scheduler" parenthetical in one slice; one fewer future slice. **But** widens P5.1b into *two* greenfield surfaces (scheduler **and** feed-cursor state) under one dual-lens, diluting scrutiny of the scheduler crux. |

**Lean: (a) defer incrementality** — keep P5.1b the *scheduler* slice. **Architect's scope call** — D4's "with the scheduler" can be read as "no earlier than," not "must be in P5.1b."

## B1. ⭐ Scheduler mechanism — sibling sweeper, not a generalization (load-bearing)

The wave DP2 leaned **sibling**. Refined options:

| Option | What it builds | Trade-off / residual |
|---|---|---|
| **(a) Generalize the ADR-040 sweeper** into one shared scheduler both COUNTDOWN auto-fire and pipeline schedules ride. | One `Scheduler` over "things with a next-fire." | DRY — but **couples two unlike concerns onto spine-critical code**. `_countdown_sweeper` + `_writer_approve_helper` are the `RB-AUTOFIRE` security crux (still-pending predicate + writer-atomic actuation, ADR-040 D3/D5). A recurring cron schedule (re-arm-after-fire, catch-up, CRUD) shares *shape*, not *invariants*. Generalizing risks **regressing the auto-fire spine under a refactor** — a Lens-B hazard. **Reject.** |
| **(b) A sibling `_schedule_sweeper` (lean)** — parallel to `_countdown_sweeper`: same lifespan-asyncio shape (start-when-enabled, sleep-loop, discover-on-reader, act-on-writer, clean teardown), **independent logic** (discover *due schedules* not *expired pendings*; act = `run_pipeline` + `create_pipeline_run`, **not** `_writer_approve_helper`). | **Reuses the proven pattern, not the spine-critical code** — the two sweepers stay fully decoupled; a bug in schedule logic *cannot* regress auto-fire idempotency, because the sibling **shares nothing** with the countdown actuation path. The ~10-line `while True: sleep / try-discover-act / except CancelledError: raise / except: log` skeleton is duplicated, **consistent with ADR-041 D2's own precedent** (duplicate trivial scaffolding to keep the load-bearing path byte-untouched). Cost: a **second** bounded background task in the lifespan (ADR-025 D6 note — must shut down cleanly, must never block the writer; discovery on the reader path). |
| **(c) External scheduler** (cron / APScheduler / separate process). | Offload timing outside the process. | Already **rejected by ADR-040 D1** (new dependency + deployment surface; breaks single-process localhost). **Reject** unless distributed deployment is foreseen. |

**Lean: (b).** The discover→act split mirrors ADR-040 exactly: **discover due schedules on the reader** (`SELECT … WHERE enabled=1 AND next_fire <= now`, approximate — stale reader OK), **act on the writer** (`run_pipeline` + `create_pipeline_run` + re-arm `next_fire`, atomic on `writer_executor`, serializing behind any in-flight run or countdown fire). **Embedded sub-decision:** does the sibling share *any* helper with the countdown sweeper (e.g. a generic loop-skeleton)? **Lean: share nothing that touches the countdown actuation invariants** — duplicate the trivial skeleton (the ADR-041 D2 line: spine-untouched > DRY for ~10 trivial lines).

## B2. ⭐ Schedule persistence — where do `cron/interval/next_fire/enabled` live?

P5.1a's `pipelines` table is *deliberately* schedule-free (`store.py:6-7,25-42`). Three homes:

| Option | What | Trade-off |
|---|---|---|
| **(a) `ALTER pipelines` — add schedule columns** (`schedule_kind`, `schedule_expr`, `next_fire`). 1 pipeline : 1 schedule. | Guarded `ALTER TABLE ADD COLUMN DEFAULT` (precedent: `memory/store.py:116-130`). | Simplest; one row already carries `enabled`/`owner_user_id`. **But** (i) **1:1** — a pipeline can be scheduled at most one way (no "hourly weekday + daily weekend"); (ii) **collides the two `enabled` meanings** — `pipelines.enabled` (is this pipeline active) vs schedule-armed (is the timer firing) become one column; (iii) mixes **hot mutable timer state** (`next_fire`, UPDATEd every fire) into the *definition* table. |
| **(b) New `pipeline_schedules` side table (lean)** — `schedule_id` PK, `pipeline_id` FK, `owner_user_id`, `kind` (cron/interval), `expr`, `next_fire`, `enabled`, `created_at`. 1 pipeline : N schedules. | New table + a join. | Cleanly separates **when** (schedule) from **what** (P5.1a frozen `definition`); isolates `next_fire` churn from definitions; **distinct** `schedule.enabled` vs `pipeline.enabled`; gives the sweeper an **indexable** `WHERE enabled=1 AND next_fire <= now` discovery (vs a JSON-blob scan); supports N schedules/pipeline. Matches DP7's "schedule defs → side table" with the cleaner shape. |
| **(c) In the JSON `definition` blob** — add a `schedule` field to `PipelineDefinition`. | Zero migration. | **Reject for `next_fire`**: `PipelineDefinition` is `frozen=True` + the JSON column is non-queryable, so every fire would rewrite the whole definition and the sweeper couldn't index due-ness. (A *static* cron spec could ride the blob, but `next_fire` still needs a column — so this collapses into (a)/(b) anyway.) |

**Lean: (b) a new `pipeline_schedules` side table** — `next_fire` is hot, queryable, mutable runtime state that wants its own indexable column; separating *when* from *what* keeps the frozen `definition` frozen and the two `enabled` meanings distinct. **Note (a) is mechanically supported** (the ALTER precedent) and is the lighter build if the architect wants **strict 1:1** pipeline:schedule and accepts the `enabled`-overload — that is the real modeling call (**1:1 vs 1:N**, and *definition table* vs *dedicated timer table*).

## B3. Boot re-arm + catch-up semantics

**Re-arm contract** (the ADR-040 D6 analog): at lifespan boot, the sibling reloads **enabled** schedules and re-computes `next_fire`. Crucial **difference from ADR-040**: ADR-040 had to derive re-arm at *read time* because `expires_at` lived on an **immutable event** (append-only store invariant #1). P5.1b's `next_fire` lives on a **mutable side table** (B2) → **re-arm-after-fire and boot-recompute are a plain `UPDATE`** (`UPDATE pipeline_schedules SET next_fire = ? …`), sidestepping ADR-040's append-only friction entirely. The side-table choice (B2) *buys* this simplicity.

**Catch-up** — a schedule whose `next_fire` elapsed during downtime (the recurring analog of ADR-040 DP1″):

| Option | Trade-off |
|---|---|
| **(i) Run-once-immediately on boot**, then re-arm next interval. | "Catch up the one missed run." Risk: a thundering boot-time run; the missed-window data may be stale. |
| **(ii) Skip-to-next (lean)** — recompute `next_fire` forward from now; the missed fire is dropped. | A missed 9am analysis is usually stale by noon; the conservative-*for-this-context* choice is **don't do stale work**. Matches the wave DP2 lean. |
| **(iii) Run-all-missed** — backfill every missed interval. | Almost never wanted for analysis (a restart-gap thundering herd of stale runs). **Reject.** |

**Lean: (ii) skip-to-next.** Worth making explicit to the senior + Lens-A: the *conservative direction differs* from ADR-040. ADR-040's conservatism was "never fire an *irreversible actuation* without a *fresh human cancel window*" (safety-over-liveness for an irreversible op). P5.1b's run is **reversible + safe**, so the conservatism inverts to "**don't run a stale/wasteful analysis**" → skip, not run-immediately. Same word ("conservative"), opposite default, *because the blast radius differs*. **Posture call** — the architect may prefer (i) if "never silently skip a scheduled run" matters more than staleness.

## B4. ⭐ The honesty / autonomy face — does headless *reversible-pipeline triggering* fall under `RB-AUTOFIRE`, or need a new residual? (THE call)

The dispatch foregrounds this, correctly. The precise distinction:

- **`RB-AUTOFIRE` (ADR-040 D8)** = *actuating an already-gated `TOOL_CALL_PENDING`* (a HARD/COUNTDOWN op that went through the gate and is waiting) **with no human at fire time** — bounded COUNTDOWN-only / reversibility-floored / opt-in.
- **P5.1b's scheduler** = *initiating a whole **reversible** run* with no human **at start time**. It does **not** actuate any gated pending; the run's output is the **ungated, reversible** room summary (ADR-041 D5), and any HARD tool a branch proposes still just **waits** (`countdown_auto_fire=None` preserved). **Different mechanism, strictly milder blast radius.**

So `RB-AUTOFIRE` does **not literally cover** it (different surface), **but** the scheduler IS a genuinely new posture: the **first thing in the product that *starts work* with no human at start time** (P4.6 only *actuated a pre-gated pending*). Two honest readings:

| Option | Trade-off |
|---|---|
| **(a) A new, explicitly *milder* residual `RB-PIPELINE-SCHED` (lean)** — name the first headless-*initiation* surface honestly, per the RB-* discipline (RB-FS/NET, RB-AUTHZ, RB-AUTOFIRE — name every human-out-of-loop step even when bounded). Bounded by: **reversible output only** (ADR-041 D5); **`countdown_auto_fire=None` preserved** → categorically *cannot* headless-actuate an irreversible op (the boundary P5.1c crosses, not this slice); **opt-in default OFF** (B5); **config-time owner** stands behind every fire. Pairs naturally with the wave's **`RB-PIPELINE-EMAIL`** (P5.1c) — `…-SCHED` = reversible trigger, `…-EMAIL` = irreversible actuation. | Most honest (names the new posture); cheap to inscribe; reads as *milder than `RB-AUTOFIRE`*, never softened-into-nothing. |
| **(b) No new residual** — it's within ADR-041 D5's *already-safe reversible-output envelope*; the scheduler merely **automates a path D5 already declared "fires headless freely, the safe default."** Inscribe as a *reference note* on ADR-040/ADR-041, not a new RB-* marker. | Defensible: no *new authorization* and no *irreversible* surface is crossed, so arguably nothing *new* to name. **But** risks under-naming the "first headless *initiation*" novelty — the RB-* discipline leans toward naming it. |

**Lean: (a) a new, milder `RB-PIPELINE-SCHED`** — but **this is the architect's honesty call** (the "never soften a residual" / roadmap §177 discipline applies). 

**"Actuates-never-decides" — how it holds (carry into ADR-042).** Mirror ADR-040 D2's framing: *the operator defined the schedule (**when**: cron/interval) + the pipeline (**what**: sources + prompts); the timer only **initiates** the configured run at the configured time.* No LLM judgment enters scheduling — **cron/interval arithmetic is code** (orchestration = code/config, ADR-041 §9). The scheduler *decides* even **less** than ADR-040's sweeper (it doesn't actuate a *gated* thing — it starts a *safe* thing), while *initiating* more (a whole multi-stage run). The load-bearing safety invariant is **B0/§0's `countdown_auto_fire=None`**: a scheduled run **cannot** cross into irreversible actuation — that guard is what keeps `RB-PIPELINE-SCHED` strictly milder than `RB-AUTOFIRE`.

## B5. Opt-in posture + config

Mirror `CountdownAutoFireConfig` (`autonomy/config.py:17-30`): a config block (lean home: `config/autonomy.yaml` §`pipeline_scheduler`, or a dedicated `config/pipeline.yaml`) carrying `enabled: bool = False`, `sweep_interval_s`. **Absent ⇒ disabled (fail-closed)**; started in lifespan **only when enabled**; cancelled cleanly in teardown (the ADR-040 D7 + lifespan template).

| Option | Trade-off |
|---|---|
| **(a) Default OFF, opt-in (lean)** | Consistent with the `RB-AUTOFIRE` discipline + gives the operator explicit control over **starting a second background task** (ADR-025 D6 — a periodic writer-occupying sweeper). The system never *silently* begins firing schedules on a fresh deploy. |
| **(b) Default ON when ≥1 enabled schedule exists** | The output is reversible, so the *safety* weight of auto-starting is low; arguably "I created a schedule" *is* the opt-in. **But** it auto-starts a background task without an explicit feature-enable, and is less consistent with the established opt-in posture. |

**Lean: (a) default OFF.** Tie to B4: the *honesty weight* here is **lower** than `RB-AUTOFIRE` (reversible output), so the opt-in is more about **liveness/resource control of the second background task** than about gating an irreversible crossing — but default-OFF-fail-closed is the consistent, established posture.

## B6. New ADR-042 (or amend ADR-041) + amendment set + dual-lens

**Extend-vs-new-ADR:** ADR-041 D10 explicitly names **"Extends this ADR (or ADR-042)."**

| Option | Trade-off |
|---|---|
| **(a) New ADR-042 (lean)** | The scheduler is a **new contract surface** (schedule schema, sweeper discover/act/re-arm semantics, catch-up posture, `RB-PIPELINE-SCHED`) that later producers (P5.1c, any future scheduled-actuation) bind to → inscribe-before-producer wants its own document; keeps the dual-lens focused on the scheduler; ADR-041 stays the clean "P5.1a primitive" record. |
| **(b) Amend ADR-041 in place** | One document for the whole pipeline contract. **But** ADR-041 scoped itself "P5.1a only" + bundling dilutes both records and the focused review. |

**Lean: (a) new ADR-042.** **Amendments carried:** ADR-041 **D8** (persistence gains the schedule table/columns) + **D10** (P5.1b realized, no longer deferred); **ADR-040** (a note: the *sibling* scheduler reuses its *pattern*, shares **none** of its spine-critical actuation code; `RB-PIPELINE-SCHED` references `RB-AUTOFIRE` as the milder neighbor); **ADR-025 D6** (a **second** bounded background-task surface beside the single writer).

**Dual-lens — two orthogonal failure-family lenses** (`requires_cross_family_review: true`; `dual-lens-r0b.md`):
- **Lens A — scheduler safety + headless-initiation correctness** ("the unattended scheduler done wrong"): fires **only** due+enabled schedules (never disabled; never **double-fire across a restart** — the ADR-040 boot-re-arm hazard, now recurring); catch-up honored (no stale backfill storm); **`countdown_auto_fire=None` preserved** under the new caller (a scheduled run can **never** headless-actuate a HARD pending); `next_fire` re-arm correct (no missed re-arm → schedule silently dies; no double-arm → double fire); scheduled run **attributed to the config-time schedule owner** (not null/system); discovery-on-reader + act-on-writer preserves single-writer + reader-liveness.
- **Lens B — spine + auto-fire no-regression** ("did the scheduler break the existing constitution"): `_countdown_sweeper` / `_writer_approve_helper` / the gate **byte-untouched** (the sibling shares **nothing** spine-critical); `_execute_local_call` + `score`/`decide_tier`/`emit_gate_decision` **zero-diff**; **no new routing `LLMPurpose`** (scheduling = cron arithmetic = code; the only LLM stays analyze/reduce content-gen); **`run_pipeline` byte-identical** (the scheduler is a second *caller*, not an edit to the runner); the second background task **clean-teardown** (no lifespan leak); the existing manual `/run` path unchanged.

*(Genuinely orthogonal: "the scheduler fires wrong / over-initiates" vs "the scheduler regressed the auto-fire spine / gate / runner.")*

## Constitutional carry-forward watch-list (carry into the plan + ADR-042)

- **Orchestration = code/config, never LLM.** Cron/interval timing is **code**; the source list + analysis prompts stay config (ADR-041 §9). **No new routing `LLMPurpose`** — the only LLM is the analyze + reduce content-gen.
- **The scheduler actuates, never decides** (ADR-040 timer discipline) — it initiates a *configured* schedule + a *configured* pipeline; it does not *choose* whether/what/when beyond the config.
- **Gate + executor + auto-fire spine byte-frozen.** `_execute_local_call` + `score`/`decide_tier`/`emit_gate_decision` + `_countdown_sweeper` + `_writer_approve_helper` zero-diff; the sibling scheduler **shares nothing** with the countdown actuation path.
- **`run_pipeline` byte-identical — the scheduler is a *second caller*, not a runner edit** (ADR-041 D7). Threads `result.run_id` into `create_pipeline_run` exactly as `/run` does (§0).
- **ADR-041 D5 reversible-only envelope preserved — `countdown_auto_fire=None` holds.** **No headless actuation of any HARD/irreversible pending in P5.1b.** That crossing is **P5.1c** (`RB-PIPELINE-EMAIL`), gated separately.
- **Single-writer + reader-liveness (ADR-025 D6) preserved** — discover on the reader, run on the writer; the second background task must never block the writer + must shut down cleanly.
- **Opt-in, fail-closed** (B5) — scheduler default OFF; absent config ⇒ disabled.
- **Honest residual** (B4) — if `RB-PIPELINE-SCHED` is named, inscribe it as the **real, milder** posture (first headless *initiation*, reversible-bounded) — never softened, never over-claimed.
