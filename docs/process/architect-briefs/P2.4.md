**Subject:** Implement P2.4 — **memory data-model completion**: flesh `Entity` from schema-only stub into a real producer/consumer surface; build `ProjectArchive` (the per-room narrative "身份证"); and add the **用户偏好** (user-preference) system. These are the structured cross-room memory *containers* that the P2.5 re-entry experience ("AI 记得我") reads back. P2.4 ships the containers + their write/read contracts; the *re-entry consumer* that assembles them into a catch-up experience is **P2.5**.

## The crux — Principle 5 + Principle 11: who writes memory, and what may NOT be LLM-inferred (the lead constitutional check)

This slice creates the project's first **entity/preference** memory, and `chat-history` (category-4 + "用户偏好的特殊处理") already pins two hard constitutional lines that the brief inherits, NOT decides:

1. **Principle 11 — user preferences may NOT be LLM-inferred.** Verbatim from `chat-history`: *❌ "agent 觉得用户喜欢具体例子"* is **forbidden** (it's the "no ground truth → drift" principle). Allowed only: ✅ **explicit user declaration**; ✅ **behavior patterns stored as metadata — which are NOT preferences**; and the system may **propose** "set this habit as a preference?" — **the user decides**. So preference-*creation* is an explicit, user-confirmed code path — structurally the same discipline as promotion's D10 (no auto-promote) and rule (c)'s relocated judgment.

2. **Principle 5 — entity extraction is content-gen, and stays OUT of `memory/`.** Pulling "the user mentioned project X / read paper Y" out of a room *is* LLM work (content-gen) — but, exactly like rule (a)'s tagging producer and rule (c)'s validation connectors, that extraction lives **outside `memory/`** (agent layer), and `memory/` exposes a **deterministic, code-only creation API** that the producer calls. `memory/` never calls an LLM (rglob-enforced, covers any new file).

**So the recurring pattern from the promotion triad applies again, and the brief settles it as a constraint:** `memory/` owns typed containers + deterministic create/read APIs; LLM-driven extraction/inference is relocated to an out-of-`memory/` producer; anything *inferred* (not explicitly declared) requires explicit user confirmation before it becomes durable memory. The senior's design must honor this for all three subsystems. **What it does NOT settle** — the *producer's* exact shape, whether entities are auto-created vs proposed, and where the confirmation gate sits — those are push-backs.

## Architect-settled (the constraints — fixed because chat-history pins them)

1. **Principle 11: no LLM-inferred preferences.** Preference creation is explicit-user-declaration OR system-proposes-user-confirms. No agent-inferred preferences become durable memory. (chat-history "用户偏好的特殊处理".)
2. **Principle 5: extraction relocated out of `memory/`.** `memory/` exposes deterministic create/read APIs; LLM-driven entity/pref extraction lives in an out-of-`memory/` producer (deferred). `memory/` calls no LLM (rglob-enforced).
3. **Explicit-creation discipline.** Anything *inferred* (not explicitly user-stated) requires user confirmation before becoming durable — the same no-auto discipline as promotion D10. Auto-created-from-structure (e.g. a ProjectArchive derived from a closed room's events) is fine *because it's code-derived from canonical facts, not LLM-inferred*.
4. **Same SQLite file** (ADR-016 D5); column additions use the ADR-018 ALTER template; any new table is `CREATE TABLE IF NOT EXISTS` in `init_memory_schema`.
5. **Reserve extension fields from day one** (chat-history: "所有数据结构从第一天就预留 scope、evidence、entity_id 等扩展字段") — `scope`, `evidence`/provenance, so forgetting/team-scope/explainability don't need migrations later.
6. **P2.4 precedes P2.5** (ratified). P2.4 = containers; P2.5 = re-entry consumer.

If you propose a split, the architect re-numbers before any impl. **Settle this first — it shapes everything below.**
- **#1 — ADR count: one ADR-020 vs ADR-020 + ADR-021.** If one slice → likely one ADR-020 (memory data-model completion). If split, or if ProjectArchive's derive-vs-materialize decision is substantial enough → ADR-020 (Entity+prefs) + ADR-021 (ProjectArchive). Senior's call; lean follows the #0 split decision.
- **#2 — Entity producer + create discipline.** The create API is code-only in `memory/` (settled). Open: is an entity **auto-created** when a producer supplies it, or **proposed-then-user-confirmed** (like prefs)? Entities that are *factual* (the user said "my project is X") vs *inferred* (agent guesses an entity) may differ. Lean: factual/explicit → direct create; inferred → user-confirm gate (mirrors Principle 11's pref rule, generalized). Senior pins where the line is.
- **#3 — ProjectArchive: NEW table vs DERIVED view.** The headline ProjectArchive fork. `decision_log` (ADR-015 D5) is *derive-don't-materialize*; snapshot persists only in events. ProjectArchive's fields (`one_line_summary`, `decision_log`, `spinoff_questions`) overlap both. So: (i) a **persisted `project_archive` table** (a real new container, survives room close, directly queryable), or (ii) a **derived view** `produce_project_archive(events, room, ...)` over the canonical log + snapshot + decision_log (no new table; rebuilt on read). Lean: **lean (i) persisted** — unlike a within-room snapshot, the archive is a *cross-room, post-close, human-browsing* artifact that should survive even if events are later compacted, and re-entry wants a cheap read; but the derive-discipline (ADR-015 D5) genuinely tugs the other way, so **defend the choice**. Also: does P2.4 define the **re-entry read contract** now, or just a minimal reader (lean: minimal reader; the re-entry-shaped API waits for its consumer in P2.5 — the "wait for a real consumer scenario" discipline P1.6 set)?
- **#4 — 用户偏好: Entity rows vs separate store.** chat-history says "用户偏好 = 实体记忆". Lean: **preferences are Entity rows** (e.g. `EntityType` gains a `preference` value, or prefs are a scoped entity) — reuses the entity surface, honors "用户偏好 = 实体记忆", avoids a parallel store. Counter: prefs have a stricter creation rule (explicit-only) + a different read pattern (per-user settings) that might warrant a dedicated `preference` table. Senior pins; if Entity-rows, show how the explicit-declaration discipline is enforced on that path.
- **#5 — `EntityType` adequacy.** Current enum is `person|project|concept|paper`. Prefs (#4) may need a `preference` value; the knowledge-graph relation (deferred) may need more. Adding an enum value is a schema change — pin what P2.4 needs vs defers.

## Constraints (do not violate)
- **No LLM in `memory/`** (`handoff.md` §3.1; rglob covers new files). Extraction/inference is out-of-`memory/`.
- **No LLM-inferred preferences** (Principle 11; chat-history). Explicit-declaration or propose-then-confirm only.
- **No auto-durable inferred memory** — inferred entities/prefs need a confirm gate (generalized D10).
- **Same SQLite file + migration templates** (ADR-016 D5, ADR-018 D5). Any `entity`-column add uses the PRAGMA-guarded ALTER; verify the on-disk migration round-trip (mirror ADR-018's test).
- **Determinism** (Principle 11): readers + any derived archive are deterministic (scan-order-independent; stable ordering).
- **Dependency direction**: new code in `memory/`, imports `core/` (+ `memory/`); `core/` MUST NOT import `memory/`.
- **⚠️ RC-23 / RC-24** — ADR-020/021 must not write a literal `Status: Accepted`/`Status: Proposed` substring in prose when citing other ADRs (paraphrase); any new constitutional guard is a **real AST check**, not a whole-file substring scan.

## RC-15 dual-lens R0-B dispatch recommendation

**Lean: DISPATCH dual-lens R0-B** — but a closer call than P2.3, stated honestly.

**Mechanical RC-15 (~2/4):** (1) new concurrency/transaction surface — *yes, moderate* (entity upsert + possibly a persisted ProjectArchive write); (2) new cross-package edge — no (stays `memory/`); (3) contract referenced by ≥5 future tasks / an integration boundary — **yes**: ProjectArchive + Entity are the **direct contract P2.5 re-entry binds to**, and prefs are read by every future personalization surface; (4) runtime/failure-mode-rich — moderate (three subsystems, more surface).

**Why I lean DISPATCH:**
- **(a) A new constitutional line — Principle 11 no-inferred-prefs.** This is the first slice to build *preferences*, and the no-LLM-inference rule is a genuine Principle-11 boundary a cross-family lens should stress: "can an inferred preference become durable without a confirm gate? does the create API make inference un-representable?" Analogous to P2.3's Principle-5 check, on the *other* constitutional principle.
- **(b) It's the fattest slice + defines the P2.5 contract.** Three subsystems = more surface for an independent lens; and getting the Entity/ProjectArchive container shape wrong is expensive once re-entry binds to it.

**The honest counter (rule against me if):** if push-back #0 **splits** P2.4 down to a smaller MVP (e.g. Entity + prefs only, ProjectArchive deferred to fold into P2.5), the surface shrinks and a **proxy-only** R0-B may suffice for the smaller slice — RC-20's runtime-surface co-variance. So the R0-B decision is **coupled to the #0 split decision**: bigger slice → dual-lens; minimal-MVP split → proxy-only defensible. **My net: DISPATCH dual-lens for the full three-subsystem slice; revisit if #0 splits it down.** `requires_cross_family_review` left **false** in the bootstrap; flip if you accept (and after #0 settles the slice size).
