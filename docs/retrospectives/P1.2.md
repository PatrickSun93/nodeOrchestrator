## 2. Workflow inflection — P1.2 was the formalization round

P1.1 was a module-level engineering exercise: build LLM layer, find drift forms, codify forcing functions. P1.2 was both that (build autonomy module) AND a workflow-formalization round.

### What got formalized

| Before P1.2 | After P1.2 | Where |

| Reviews paste-into-chat | Locked path per-task subfolder | `docs/process/reviews/{task-id}/` + README; `-A`/`-B` naming; absence-as-evidence |
| ADR drafting unclear (architect self-drafted ADR-001/002/003/005) | Senior drafts; architect reviews/accepts. ADR-005 documented bootstrap exception | `docs/process/senior-planner.md` § "ADR drafting" |
| Retrospective candidates lost in chat | Accumulated in `P1.2-candidates.md` | This convention |

### Why the formalization mattered

P1.1 ran without these. It worked because the architect held all the context. P1.2 had 3 named ADRs, 4 review rounds, 6 retrospective candidates, 8 new constitutional tests — context that doesn't fit in one session's working memory. The formalization is the "you can step away for 24h and the project still makes sense" investment.

**Test of the formalization**: by C3, senior session was reading the brief from disk, writing plan to locked path, drafting ADRs without the architect having to redirect. By C4, the cycle was running at 7 atomic tasks across 7 commits with zero re-routing. The formalization paid off within one module of being inscribed.

## 5. Workflow observations across the four review rounds

### Senior plan-vs-impl pattern

Every C2/C3/C4 plan-vs-impl audit found **2-4 items**. Steady-state output:

| Round | Items found | Disposition |
|---|---|---|
| C2 (no plan-vs-impl; freeze went direct to R0-A) | — | — |
| C3 plan-vs-impl | 1 🟡 (test docstring typo) + 3 🟢 | Y1 routed to junior single-commit fix |
| C4 plan-vs-impl | 1 🟡 (missing constitutional test) + 3 🟢 | Y1+G1+G3 routed to junior single-bundle fix |

**Observation:** senior plan-vs-impl find rate stabilized at 1 🟡 + 2-3 🟢 per round. The 🟡 always routes to a junior single-commit fix before R0-A dispatch (a "trivial-fix routing" exception to the full senior-plan cycle). This routing was not part of the original `senior-planner.md` workflow — it emerged across C3 and C4 as a useful shortcut.

**Recommendation for P1.3 / `senior-planner.md`:** codify the "trivial-fix routing" shortcut explicitly. Criteria: single-file or two-file scope, ≤30 LoC, ≤1 new test, clear acceptance criteria from the surfacing review, no schema flip. Routes directly architect → junior, bypassing senior task plan. Bundle multiple trivial fixes if same impl branch + same review source.

### R0-A find pattern

Every C2/C3/C4 R0-A found additional items beyond senior's plan-vs-impl. Find-overlap between senior and R0-A: ~10% (they verify each other's resolutions but rarely re-find the same new issues).

This validates P1.1 retro §4's prediction: senior plan-vs-impl and R0-A are non-overlapping audit surfaces. Senior sees "plan ↔ impl"; R0-A sees "impl ↔ everything around impl (ADR, narrative, edge cases)."

**Architect-partner's R0-A specifically caught:**

- C2: 2 🟡 doc-drifts (handoff §4.3, event-model.md "16 types").
- C3: 1 🟡 (asymmetric eff_auto floor) + 4 🟢.
- C4: 1 🟡 (ADR-007 §3 contradiction in emission impl) + 4 🟢.

The 🟡 findings were each substantive: a doc-spec drift (C2), an architectural symmetry gap (C3), and an ADR-guidance contradiction (C4). These are not nits; they are the kind of finding that compounds badly if missed.

### Cross-family R0-B verdict

Three consecutive skips, no contract bug surfaced. RC-2 verdict above (§3): empirically defended for P1.2's shape of work but qualified for P1.3+ where the work shape changes.

**Recommendation for P1.3:** explicitly distinguish in the role-prompt or `senior-planner.md`: (a) architectural inscribing has 24h+ distance test; (b) impl-of-accepted-plan does not require the same delay. ## 9. Meta-lesson

P1.1 retro's meta-lesson named the four-layer review pipeline (type system → constitutional tests → doc-spec discipline → process discipline) as the substrate that catches drift.

**P1.2's meta-lesson is the layer below that one: roles.** The four-layer pipeline only works if four distinct lenses look at the work. P1.2 explicitly inscribed those roles:

- **Architect** (decision authority)
- **Architect-partner** (process meta + review, NOT decision)
- **Senior planner** (plans + plan-vs-impl + ADR drafting, NOT decision)
- **Junior implementer** (code, NOT plan or decision)
- **External reviewers** (independent lenses A and ideally B from different model family)

The single biggest project risk is **role collapse**: any one of these roles silently absorbing another's responsibility. Specific failure modes P1.2 surfaced:

- Architect self-drafting + self-reviewing ADRs (RC-3 — fixed)
- Architect-partner landing R0 fixes directly (RC-5 — fixed mid-session)
- Same-family reviewer pairing (RC-2 — partial verdict; P1.3 will test under different work shape)

The role boundaries are not bureaucratic. They are the mechanism by which the project gets *more than one independent perspective* on any decision. A self-loop has no error-correction — review IS the error-correction signal, and only cross-role review surfaces what self-review misses.

If P1.3 lands clean while honoring the role boundaries, that's not a coincidence — it's the system working. If P1.3 lands clean while collapsing a role boundary (e.g., architect-partner does plan-vs-impl, or architect drafts an ADR), pause and check whether what landed is what would have landed under correct roles. The role boundaries are the more load-bearing investment.

P1.1 ended on "architecture review is a layered pipeline." P1.2 ends on "the layers only work if the roles are distinct." Both are true; the second is the deeper precondition.
