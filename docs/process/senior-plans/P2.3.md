## 1. Context

Rule (c) completes the `handoff.md` §4.5 promotion triad: (a) cross-room corroboration (ADR-017 `run_matcher`, advisory), (b) user-confirm (ADR-016 `promote_hypothesis`, the sole VK actuator), (c) external ground-truth validation. The load-bearing question is **how to represent "external ground truth" so the validation decision is deterministic code, not an LLM judging truth** (Principle 5; `memory/` calls no LLM, rglob-enforced). The resolution is **relocation, not elimination**: a future external connector produces a typed verdict; `memory/` reads it as a field — structurally identical to rule (b)'s `status == PENDING`.

My design (push-back #1, the core contribution): **representation (i) — a new `external_validation` EventType + `ExternalValidationMeta` in `core/`; rule (c) is a pure-derivation reader in `memory/`** (the event itself is the surface — push-back #3's "typed record as surface" — no flag, no table, no column). Three reasons make (i)+derive decisive: **Principle 1** (external validation is a fact → canonical log, like promotion's `decision` event); **connector-decoupling** (a connector writes via `core/event_store.append` only, never touching `memory/` — the integration boundary the brief worries about); **derive-don't-materialize** (ADR-015/016 — no batch computation to cache, unlike rule (a)'s grouping, so no flag/ALTER). This resolves #2 (maximally advisory — a pure reader can't violate D10), #3 (provenance via the typed event), and #5 (minimal dormant footprint) at once. All verified against `origin/main` (cites in §5/§7); ADR-019 carries the full reasoning.

P2.3 ships the **contract + consumer**; the connectors that produce signals are out of scope (none exist — why rule (c) was deferred). Rule (c) is dormant-until-fed by design, like rule (a)'s auto-tagging producer.

### P2.3-3 — `memory`: rule-(c) pure-derivation reader

- **What**: `src/orchestrator/memory/validation.py` — `list_externally_validated_candidates(conn) -> list[Hypothesis]`. Pure code, no LLM, **no writes**.
- **Where**: new file `src/orchestrator/memory/validation.py`. Reuse `store._row_to_hypothesis`.
- **Why**: ADR-019 D2.
- **Acceptance criteria**:
  1. Returns the `status == 'pending'` Hypothesis rows that have **≥1** `external_validation` event with `verdict == 'confirmed'` referencing them (`validated_hypothesis_id`), ordered by `id` ASC, as frozen `Hypothesis` models.
  2. **Python-parses event metadata** (no JSON1 assumption — mirror ADR-016 D6 lookup): scan `external_validation` events via `conn.execute("SELECT metadata FROM events WHERE type = 'external_validation'")`, `json.loads` each, filter `verdict == 'confirmed'`, collect `validated_hypothesis_id`; then `SELECT * FROM hypothesis WHERE id IN (...) AND status = 'pending' ORDER BY id ASC`.
  3. **Confirmed-only**: `refuted` / `inconclusive` events are ignored (not surfaced); rule (c) **never mutates `status`** (P2.3-3 writes nothing to `hypothesis`/`verified_knowledge`/`events`).
  4. **Dangling/non-PENDING references degrade gracefully**: a confirmed event referencing a missing or non-PENDING hypothesis yields no candidate (the join filters it) — no error.
  5. **Determinism** (Principle 11): same events + rows → same candidate list regardless of scan order (the candidate set is a pure function; `ORDER BY id ASC` for stable output).
  6. **Idempotent / side-effect-free**: calling it twice changes nothing (it writes nothing).
  7. Cleanup cases: no-events / no-confirmed / multiple-confirmed-per-hypothesis (deduped to one candidate row). **No defensive malformed-metadata handling** (Y1 → α): `external_validation` metadata is **guaranteed well-formed by append-time `validate_metadata`** + `ExternalValidationMeta`'s `extra="forbid"` — a malformed event raises `MetadataValidationError` at `EventStore.append` (event_store.py) and never lands in the `events` table, so a malformed row is **unreachable** through the sanctioned path. The reader trusts that contract and does **no** metadata-shape handling (no skip branch). The only way such a row exists is a raw `INSERT` bypassing `EventStore.append` — a deeper invariant break; if a belt-and-suspenders parse guard is ever kept it must **raise** (a constitutional canary that surfaces the bypass loudly), **never silently skip** (fail-loud, mirroring ADR-018 D4's empty-tag `ValueError`).
- **Out of scope**: a materialized flag / `run_external_validation` writer (ADR-019 D5 — forward hook); `refuted` handling; multi-source aggregation.

## 5. Where you'd (architect) push back — the five brief push-backs, resolved

This is where the plan earns its keep; all verified against `origin/main`.

- **#1 The representation (THE design question) → (i) `external_validation` EventType + `ExternalValidationMeta` in `core/`, consumed by a pure-derivation reader.** Three deciding reasons (ADR-019 D1/D2): **(Principle 1)** external validation is a *fact* → the canonical append-only log, exactly like a promotion `decision` event (ADR-016 D8) and a snapshot event (ADR-014) — a `memory/` table (ii) would put a fact outside the canonical log; **(connector-decoupling)** a connector writes via `event_store.append` (core-only, stable API) and never touches `memory/` internals — option (ii) would couple an external integration to `memory/` tables (backwards); **(derive-don't-materialize)** rule (c)'s candidacy is a per-row existence check, not a batch computation to cache, so unlike rule (a) it needs no flag/column/ALTER (ADR-015 D5). The new EventType is ADR-gated (this ADR); the cost is the 19th constitutional type (real, justified — a genuine event class, not a catch-all). Verified `core/event.py:68-94` (EventType + "adding a type requires an ADR"), `:322` (`TYPED_METADATA`), `:156` (the `str | pattern` deliberate-duplication precedent), `event_store.py:64` (`metadata` JSON `TEXT`). **The single biggest call — flag if you prefer option (ii) table or a materialized flag (Design A); both are heavier and I argue against them, but #1 is yours to settle at accept.**
- **#2 Advisory vs stronger (the D10 temptation) → advisory, maximally** (ADR-019 D3). Rule (c) is a pure reader — it *cannot* create a VK or even flip a flag, so D10 orthogonality is by construction. Surfaced honestly: rule (c) is the strongest signal (external truth), which tempts a D10 exception — but D10 holds regardless of signal strength because promotion is a *permanent* user act (a VK row + a canonical `decision` event) and advisory is reversible-by-ignoring; the signal's strength doesn't change the act's irreversibility, and an auto-promoting connector would be smuggling truth-judgment into automation (the exact Principle-5 + D10 violation this rule risks). Not challenging the lean. **If you ever want more than advisory, that's an explicit D10 amendment — not an impl choice.**
- **#3 Reuse `candidate_for_promotion` vs distinct provenance → distinct, via the `external_validation` events themselves** (ADR-019 D2/D4). Not reusing rule (a)'s flag (which would conflate "cross-room corroborated" vs "externally validated" into one boolean). The typed event carries `source`/`verdict`/`evidence_ref` — strictly richer provenance than any flag; a future "all candidates" surface unions rule-(a) flags + rule-(c) derivations, badged. Distinct reader (`list_externally_validated_candidates`), distinct from `list_promotion_candidates`.
- **#4 `refuted` vs the `status` lifecycle → confirmed-only this slice** (ADR-019 D2). The reader filters `verdict == 'confirmed'`; `refuted`/`inconclusive` are still recordable in the canonical log (the verdict enum admits them) but rule (c) ignores them and **never mutates `status`** (`status == VERIFIED` is `promote_hypothesis`'s contract). Advisory-refutation is a forward hook. Confirm or challenge.
- **#5 A third dormant mechanism — worth it? → yes, and minimal** (ADR-019 D5). Principle 9 (inscribe the contract before producers); the external-integration boundary is the expensive-to-change-later part every connector binds to. The pure-derivation shape **directly answers the "dead machinery" worry**: it inscribes only the EventType + meta + a reader — **zero dormant write/flag machinery** (a materialized flag would be the dead machinery; deriving avoids it). Same justification rule (a) used, with a lighter footprint. **If you read rule (c) as premature despite this, I'd rather hear it now — but I judge the minimal-contract version worth shipping.**

**No unresolved decision requiring an architect call** beyond ADR-019 accept + the dispatch confirmations (§6). If the architect overrides #1 (representation) or #2 (advisory), those reopen.
