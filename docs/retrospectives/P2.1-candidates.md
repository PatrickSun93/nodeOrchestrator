## RC-23 — `_parse_adr_status` whole-file substring search misreads any ADR that quotes another ADR's status (accept-gate false-positive)

**Surfaced:** 2026-05-29, during P2.1 R0-A-on-plan (architect-partner), verifying the senior's D6 rationale for choosing new ADR-017 over an ADR-016 amendment.

**Routing:** dev-harness (workflow CLI / ADR-008). Architect routed 2026-05-29 — **record as a W-series fix candidate; other agents solve it in the W-series**. P2.1's product cycle does NOT fix it (architect-deferral literal-reading — do not bundle a harness fix into the product cycle). This RC is the record.

**Observation:** `_parse_adr_status` (`src/orchestrator/workflow/cli.py:136-141`) lowercases the **entire ADR file** and substring-searches, checking `accepted` before `proposed`:

```python
lowered = content.lower()
if "status: accepted" in lowered or "**status:** accepted" in lowered:
    return "accepted"
if "status: proposed" in lowered or "**status:** proposed" in lowered:
    return "proposed"
```

This is a whole-file scan, not a status-*line* parse. Any ADR whose **body** quotes or discusses another ADR's status trips it. Concrete instance: ADR-017 line 91 (inside the D6 rationale itself) reads *"ADR-016 is `Status: Accepted`."* — so `_parse_adr_status(ADR-017)` returns **`accepted`** even though ADR-017's own status line (line 3) reads `Proposed`. **Verified empirically**: ran the parser logic against the file → result `accepted`, tripped at line 91.

**Why it matters (the real finding):** the accept-gate (`transitions.py`, `awaiting_architect_accept → awaiting_junior_impl` on `adr_status == "accepted"`) then **auto-passes on the next `workflow advance` with no architect accept** — silently defeating the architect-accept gate. This is exactly the failure class the senior's new-ADR-vs-amendment choice (ADR-017 D6) was trying to avoid; ADR-017's own prose re-introduced it. It recurs for **any** future ADR that references another ADR's status, or even discusses "proposed/accepted" states in prose. The `accepted`-checked-first ordering makes it worse: a single stray "status: accepted" substring anywhere wins over the document's real `Proposed` line.

**Same state-machine-gap family as [[RC-21]] (merge-fragile impl detection) + [[RC-22]] (cycle-boundary filter vs reconcile):** naive signal-detection that breaks on a realistic input shape the detector's author didn't anticipate. RC-21/22 were branch-ahead + timestamp fragility; RC-23 is prose-substring fragility in ADR status detection.

**Candidate remedies (W-series decides):**
- **(a) Parse only the status line** (lean): match the first line matching `^\s*\**status:\**\s*(accepted|proposed)` (anchored, line-scoped); ignore the rest of the file. Kills the whole-file-substring class outright.
- **(b) Restrict the search to the ADR header region** (e.g., up to the first `##`).
- **(c) Require a line-start anchor** so mid-prose mentions can't match.

Lean: **(a)** — line-scoped regex. Cheapest robust fix; one function.

**P2.1's immediate unblock is tracked separately** (not this RC): R0-A-on-plan F1 surfaced that until ADR-017 is reworded (no literal `Status: Accepted` substring) OR the architect overrides, P2.1's gate is tripped. That is a P2.1-plan-branch concern; this RC is the durable dev-harness record of the underlying parser defect.
