---

**Subject:** Implement P2.1 — a **shared, canonical tag registry** for `memory/`: one vocabulary that both `Hypothesis` and `VerifiedKnowledge` draw their `topic_tags` from, so tags are consistent across rooms and across the hypothesis→VK lifecycle. This is the foundation the P2.2 matcher (cross-room rule-(a)) and `lookup_verified_knowledge` both depend on. Matching/consumption is **not** in this slice — P2.1 ships the vocabulary + the write/read plumbing only.

## Why a registry (the design rationale we settled)

The deferred matcher's whole problem was tag *consistency*: matching on tags only works if the same claim gets the same tags across rooms. Free-form tags (esp. LLM-assigned) paraphrase and never match. The structural/code path (architect-settled) needs a **shared canonical vocabulary** so consistency is a structural property, not a semantic guess:

- **LLM stays in content-gen** (an agent proposes tags — a later slice), **code owns structure** (normalization + registry membership + matching). `memory/` never calls an LLM. This is the project's standing "controlled vocabulary" instinct (event types, room types, scopes, skill ids).
- **Honest ceiling** (carry into the ADR): pure-code matching cannot *guarantee* open-domain consistency — that needs either a rigid closed vocab or semantics (embeddings, the deferred path). The registry is **best-effort**: it makes consistency *possible and cheap* (reuse an existing canonical tag) but does not *force* it (the reuse-pressure — showing an agent the existing tags — is a later agent-wiring slice). P2.1 ships the mechanism; the intelligence that drives reuse comes later.

## Scope

**In scope (P2.1):**

- **`tag` table + registry** (`src/orchestrator/memory/`): a canonical tag vocabulary. Each row is a normalized canonical tag (+ `created_at`; senior pins exact columns — push-back #4). Lives in the event_store SQLite file (same pattern as ADR-016).
- **`normalize_tag(raw: str) -> str`** — pure, deterministic canonicalization (lowercase / strip / collapse internal whitespace / …; exact rules senior pins — push-back #1). Defines the canonical form.
- **`resolve_tags(proposed: list[str], conn) -> ...`** — normalize each proposed tag, split into {already-in-registry} vs {new}; **new tags auto-register** (architect-settled: emergent/descriptive registry, no candidate-gating). Returns the canonical tag list (+ which were new — shape is senior's call, push-back #5). Pure code, no LLM.
- **`Hypothesis.topic_tags` field** (`schema.py`) — add `topic_tags: list[str] = Field(default_factory=list)`, mirroring VK; **first ALTER-TABLE column-add to the `hypothesis` table** (idempotent `PRAGMA table_info` guard + `ADD COLUMN ... NOT NULL DEFAULT '[]'`; this is the migration template the matcher brief flagged — it lands here now).
- **Write-path wiring**: `record_hypothesis(..., topic_tags=...)` routes its tags through `resolve_tags` and stores the canonical strings. **VK shares the registry this cycle** (architect-settled): `promote_hypothesis`'s `topic_tags` also route through `resolve_tags` at write time, so Hypothesis and VK draw from one vocabulary.
- **Read-path consistency**: `lookup_verified_knowledge` normalizes its query `topic_tags` through `normalize_tag` so queries hit canonical stored tags. **This refines ADR-016 D6** ("exact match" → "normalized-exact match") — senior pins how to document the refinement (amend ADR-016 D6 in place vs. ADR-018 records the refinement; push-back #2).
- **ADR-018** (cross-room tag registry) — Proposed; pins the registry shape, normalization contract, auto-register semantic, the Hypothesis/VK shared-vocabulary decision, the ADR-016 D6 refinement, and the ALTER-TABLE template.
- **Tests** (test-coverage-standard): registry round-trip; `resolve_tags` (dedup, normalize, new-auto-register, reuse-existing); `normalize_tag` boundary cases; the column-add migration round-trip (on-disk, mirror ADR-016 external-Y11); `record_hypothesis` + `promote_hypothesis` store canonical tags; `lookup_verified_knowledge` hits via normalized query; determinism.

**Out of scope (deferred):**

- **The matcher** — P2.2 (the consumer; rides on this registry).
- **Agent-side tag-proposal wiring** ("show the agent existing tags + prompt it to reuse") — this is the *reuse intelligence* and it touches the agent layer (content-gen). Separate later slice. P2.1's `record_hypothesis`/`promote_hypothesis` callers (tests) supply tags directly.
- **Storing `topic_tags` as FK tag-ids** (normalized storage) — `Hypothesis.topic_tags` / `VK.topic_tags` stay denormalized JSON string lists (canonical strings). FK-to-`tag` storage is heavier; defer unless a query needs it (push-back #5).
- **Backfilling the registry from existing rows** — emergent-only (registry grows from new resolves); existing test-data rows are not back-filled (push-back #3; confirm).
- **Curated / closed vocabulary, synonym-merging, alias resolution** — the registry is descriptive (auto-register). Synonym-merging is semantic → out (would reopen the LLM line). Forward hook.

## Architect-settled decisions

1. **Shared canonical registry** — one `tag` vocabulary; both `Hypothesis` and `VerifiedKnowledge` resolve their `topic_tags` through it. (Settled: "VK 这次要共用".)
2. **New tags auto-register** — `resolve_tags` adds unseen normalized tags to the registry automatically; no candidate-gating / confirmation step. (Settled: "自动入库 会更加好".) The registry is descriptive (what's been used), not curated.
3. **Boundary = vocabulary + plumbing only** — table + `normalize_tag` + `resolve_tags` + Hypothesis/VK write-path wiring + lookup normalization + tests. **No** agent reuse-wiring, **no** matcher. (Settled: "确认".)
4. **`Hypothesis.topic_tags` is necessary** and added this cycle (architect-settled earlier); optional/default-empty at the schema level (an untagged hypothesis is valid; it just contributes nothing to future matching).
5. **Structural / code only** — `memory/` never calls an LLM; normalization + resolution + matching (later) are pure code (the gating decision from the matcher discussion stands).

## Constraints (do not violate)

- **No LLM in `memory/`** (`handoff.md` §3.1; `tests/memory/test_constitution.py` rglob). `normalize_tag` / `resolve_tags` are pure code.
- **Determinism** (Principle 11): `normalize_tag` and `resolve_tags` are deterministic; same inputs → same canonical output + same registry effect.
- **ADR-016 honored**: D3/D10 (promotion eligibility / no-auto-promote) untouched. D6 (lookup) is *refined* (normalized-exact) — document it (push-back #2); do not silently change the contract.
- **Dependency direction**: registry lives in `memory/`; may import `core/`; `core/` MUST NOT import `memory/`. No new cross-package edge.
- **⚠️ RC-23 — do NOT trip the accept-gate parser.** `_parse_adr_status` substring-scans the whole ADR file for "status: accepted". When ADR-018 references ADR-016/ADR-017, **do not write the literal string `Status: Accepted` / `Status: Proposed` in the prose** — paraphrase ("ADR-016 is already accepted"). Otherwise ADR-018 auto-passes its own accept-gate while Proposed (this is exactly the bug RC-23 records, surfaced on ADR-017). Verify: after drafting, `grep -i "status:.*\(accepted\|proposed\)" ADR-018` should match only ADR-018's own status line.

- **#2 ADR-016 D6 refinement mechanism.** Lookup now normalizes the query (so canonical stored tags are hit). Amend ADR-016 D6 in place, or have ADR-018 record the refinement and cross-link? - **#5 `resolve_tags` return shape + storage form.** What does it return (canonical list? + new-tags set? a small result object?), and does `Hypothesis.topic_tags`/`VK.topic_tags` keep storing canonical **strings** (lean: yes, denormalized — minimal change) vs FK tag-ids (defer)?
