Two sharp lines, both fixed by `chat-history` (not re-litigated): **Principle 5** (extraction is content-gen, out of `memory/`) + **Principle 11** (no LLM-inferred preferences — explicit declaration or propose-then-confirm only). All design verified against `origin/main` + `chat-history` 类别3/类别4 + 用户偏好的特殊处理 (cites in §5/§7).

### P2.4-4 — Preference API (Principle-11 explicit-only)

- **What**: `memory/entity.py` — `record_preference` + `list_preferences`.
- **Where**: `src/orchestrator/memory/entity.py` (**shares the file with P2.4-3 → sequential**, §3).
- **Why**: ADR-020 D2 (Principle 11).
- **Acceptance criteria**:
  1. `record_preference(key, value, user_id, *, scope=EntityScope.PERSONAL, conn, now=None) -> Entity` — **requires `user_id`** (`min_length >= 1`; empty/missing raises) = the explicit declaring/confirming user. Writes an `Entity` row: `type=PREFERENCE`, `attributes={"key": key, "value": value}`, `evidence={"declared_by": user_id}`, scope.
  2. **Principle-11 structural enforcement test** (load-bearing): there is **no path** to create a `PREFERENCE` entity without a `user_id` — `record_entity(type=PREFERENCE, ...)` raises (P2.4-3 AC#1), and `record_preference(user_id="")` raises. So an LLM-inferred preference with no user is un-representable.
  3. `list_preferences(*, user_id=None, scope=None, conn) -> list[Entity]` — thin wrapper over `list_entities(type=PREFERENCE, ...)` (reuses the entity surface — #4); deterministic.
  4. Round-trip: `record_preference("response_style", "concise", user_id="peidong")` → `list_preferences(user_id="peidong")` surfaces it with `declared_by` provenance.
- **Out of scope**: propose-then-confirm producer flow (out of `memory/` — only the confirmed result, with user_id, reaches `memory/`); behavior-pattern metadata (not a preference).

## 5. Where you'd (architect) push back — the forks, resolved

#0 (split) is architect-decided (one slice, one ADR-020). The remaining forks, resolved in ADR-020; all verified against `origin/main` + `chat-history`.

- **#2 Entity create discipline → `record_entity` is the deterministic sink; the inferred-vs-factual confirm-gate is the producer's (relocated).** `memory/` structurally *cannot* judge inferred-vs-factual (that needs the room's content = LLM work = out of `memory/` per Principle 5), so the gate necessarily lives in the producer, exactly like extraction (ADR-020 D1). `record_entity` serves explicit/factual or code-derived entities directly + carries the `evidence` provenance field (chat-history 可解释性链条); inferred entities are confirmed by the producer first. The **strong structural enforcement** (required confirming user) is reserved for preferences (#4), where Principle 11 is absolute. **Flag if you want a structural confirm-marker on general entities too** (I argue the relocation + the pref-only structural gate is the right line).
- **#3 ProjectArchive → PERSISTED `project_archive` table (not derived).** The archive is a post-close, cross-room, human-browsing 身份证 that must **survive the event lifecycle** — `chat-history`'s 遗忘机制 (超期降级) compacts events, and a derived-over-events view would degrade/break, but the archive's purpose is durable narrative identity; plus re-entry wants a cheap durable read. ADR-015's derive-discipline governs live within-room views (decision_log), not durable post-close artifacts. **Don't duplicate-derive**: the caller composes `produce_decision_log` at close and passes the serialized result in; `memory/` stores a frozen copy, never re-derives. **Principle 5**: the semantic fields (one_line_summary, spinoff_questions) are content-gen produced OUTSIDE `memory/` and passed in (mirrors summary_snapshot carrying LLM current_focus); `memory/` persists, never generates. Minimal reader now; the re-entry-shaped contract waits for P2.5 (P1.6 wait-for-consumer). **The headline call — flag if you prefer the derived view despite the compaction argument.**
- **#4 用户偏好 → Entity rows (`type=PREFERENCE`), created only via `record_preference(user_id required)`.** `chat-history` pins "用户偏好 = 实体记忆", so prefs reuse the entity table + reader (no parallel store). The dedicated `record_preference` **requires `user_id`** (mirrors promotion's user_id, ADR-016 D8) → an LLM-inferred preference with no user is **un-representable**; `record_entity` rejects `type=PREFERENCE` to close the bypass. propose-then-confirm: the propose is the producer's; only the confirmed result (with user_id) reaches `memory/`.
- **#5 `EntityType`/`EntityScope` → add `PREFERENCE`; new 4-value `EntityScope` (personal|team|project|global).** P2.4 needs `PREFERENCE` (#4) + `project` scope (archives/prefs); knowledge-graph relation type values defer. `EntityScope` is separate from `VKScope` (VK doesn't need `project`).
- **#1 ADR count → one ADR-020** (follows #0's one-slice decision; the three subsystems share the framing + storage, and prefs-as-entity couples (A)+(C)).

**No unresolved decision requiring an architect call** beyond ADR-020 accept + the dispatch confirmations (§6). If the architect overrides #3 (persist vs derive) or #2 (entity confirm-marker), those reopen.
