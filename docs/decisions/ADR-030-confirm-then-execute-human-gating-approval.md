# ADR-030: Confirm-then-Execute — the Human-in-the-Loop Gating-Approval Flow

**Status:** Proposed — 2026-06-03 (senior-drafted for P3.6; cross-track confirm-flow decision spanning the ADR-025 contract + ADR-027/028 gating/executor + ADR-026 view; `requires_cross_family_review: true` — the gating-approval trust surface is the `dual-lens-r0b.md` criterion. Architect ratification pending; this draft is the candidate text, not a decision.)

**Scope:** P3.6 (D-B=(c)) — the live **confirm-then-execute** loop that the MVP deferred (ADR-027 D6 / ADR-028 D1 "confirm-then-execute stays deferred — GUI-coupled"). A `COUNTDOWN_CONFIRM`/`HARD_CONFIRM` tool-call is **gated but not executed** today; this ADR adds the human-approval second factor: the GUI surfaces a pending gated call → the user approves → a **new backend confirm endpoint** validates the pending call and appends the gate-approval `TOOL_CALL` → the **existing** runtime executor (ADR-028) runs it unchanged. Governs: the **durable pending-call record** that makes a pending call confirmable (D1), the **snapshot re-point** that surfaces it (D2), the **confirm endpoint contract + backend-authoritative validation + idempotency** (D3), the **COUNTDOWN-vs-HARD confirmation semantics** (D4), the **partial-turn envelope on confirm** (D5), the **GUI confirm surface + 不暴露 + no-forge** (D6), and the **human-in-the-loop trust-surface invariants** the dual-lens R0-B probes (D7). Does **NOT** govern: the autonomy gate's **decision logic** (`score`/`decide_tier`/`emit_gate_decision` — unchanged, ADR-027 D2); the executor's execution/dispatch logic (`execute_pending_tool_calls` — unchanged, ADR-028); auto-fire-on-timer (deferred — D4); agent re-dispatch on the tool result (still deferred, ADR-028 D4); auth (localhost-trust MVP, ADR-025 D7).

## Context

Verified against `origin/main` @ b0e7fae (P3.4/P3.5 closed). The gate path and its representation gap:

- `agents/tool_dispatch.py::process_tool_calls` appends a `TOOL_CALL` event **only** in the `AUTO_EXECUTE` branch (`tool_dispatch.py:100,105`); the `COUNTDOWN_CONFIRM`/`HARD_CONFIRM` branch records an in-memory `ToolDispatchDecision` and **persists nothing** (`tool_dispatch.py:125-134`). `EventType.TOOL_CALL` has **exactly one appender in `src/`** (verified: `grep type=EventType.TOOL_CALL` → only `tool_dispatch.py:105`) — the property ADR-028 D6 t4 leans on.
- `autonomy/emission.py::emit_gate_decision` appends an `AUTONOMY_DECISION` audit event for **every** non-refusal tier (incl. countdown/hard), carrying `operation_tool_id`, `operation_initiating_agent`, `tier`, `score`, trace — but **not** `call_id` and **not** the tool `params` (`emission.py:86-108`). The `Operation` it scores never receives the `ToolCall.id`.
- `derived/snapshot.py` D2.3 derives `tool_calls_pending_confirm` by correlating a **`TOOL_CALL` event** with a preceding countdown/hard `AUTONOMY_DECISION` (`snapshot.py:157-190`). Because no `TOOL_CALL` is ever appended for a countdown/hard call, **`tool_calls_pending_confirm` is structurally empty in the running application** — the only `TOOL_CALL` events are AUTO ones whose AD tier is `auto_execute` ("tool already executed; not pending").
- `api/app.py::_post_intent` already runs `execute_pending_tool_calls(...)` over the post-`run_turn` window on the single-writer thread, then publishes new events to the `RoomEventBus` (`app.py:354-367`). The executor (`tools/executor.py`) keys on `TOOL_CALL` events and carries a **full-room `call_id` double-execution guard** (`executor.py:97-104`), race-free under the single writer.

**The gap this ADR must close.** The P3.6 brief (and ADR-027/028's deferral prose) describe `tool_calls_pending_confirm` as "the read-only handle" for the pending calls and frame (c) as "a new endpoint over data already on the frozen wire." Against the live code that premise does not hold: (i) the snapshot field is empty, and (ii) even the `AUTONOMY_DECISION` event lacks the `call_id` + `params` needed to reconstruct the call to execute. **A pending gated call is therefore not confirmable from existing events** — confirm-then-execute requires the pending call to be **persisted with its full payload at gate time.** This is the load-bearing decision (D1); it is a *recording* addition to the dispatch path, **not** a change to the gate's decision logic.

**Brief constraints superseded by the ⭐D-B=(c) ruling (R0-B Y4 — single source of truth for the junior).** The P3.6 brief was written under the (a/b) frontend-only lean; the architect's (c) ruling supersedes three of its statements, which this ADR + the senior plan are authoritative over: (1) "adds zero Python for the frontend-track scope" → **false under (c)** — B1–B3 add Python; (2) "No backend / API / gate / executor change" → **superseded** — (c) adds a new `/confirm` API route + a `process_tool_calls` recording addition (the gate *decision* logic and the executor stay unchanged); (3) "binds the same frozen ADR-025 contract" → **superseded** — `/confirm` is a deliberate ADR-025 contract change (the new endpoint + wire types). The frontend-track-independence claim also collapses for the confirm feature (it couples to the backend), exactly as the brief's ⭐D-B(c) note anticipated. Everything else in the brief (the §⭐ spine, D-A scope, D-C 不暴露) stands.

## Hard requirements — the constitutional spine (NON-NEGOTIABLE; inscribed, carried forward)

1. **Backend-authoritative; the GUI never forges a `TOOL_CALL`.** Appending a `TOOL_CALL` (the gate-approval / "decision/forge" the spine forbids — ADR-026 HR#1/HR#5) is done **only** by backend code, **only** after it independently validates a persisted pending record exists and is in the correct state. The client sends **only** an opaque `pending_event_id` + an `approve|cancel` verb — never `tool_name`/`params`/`author`. The server reconstructs the `TOOL_CALL` from the **persisted, gate-produced** record, never from client input.
2. **Idempotency — confirming twice never double-executes.** A pending call has a durable id; exactly one `TOOL_CALL` is ever appended per pending call; a second confirm of the same pending call is a validated no-op/reject. Two layers enforce it (D3): the endpoint's still-pending check **and** the executor's full-room `call_id` guard, both atomic on the single writer.
3. **Downstream-of-gate preserved.** The executor still runs **only** for a `TOOL_CALL` event (ADR-028 carry-forward #1). The confirm endpoint produces that `TOOL_CALL` **after** the gate already decided the tier (countdown/hard) and after the human approved — it adds **no** new decision surface, re-runs **no** gate (`score`/`decide_tier`/`emit_gate_decision` untouched; no re-gating).
4. **No new `LLMPurpose`.** Confirm is a mechanical validation + append; it calls no LLM and makes no LLM-judged routing/decision.
5. **状态机不暴露 / 不暴露 (D-C).** The GUI confirm surface renders the **humanized** tool activity only; never the raw `autonomy_tier`, the `countdown_confirm`/`hard_confirm` tokens, the `mcp__` prefix, or "skill"/"plugin"/"MCP"/"autonomy level".

## Decisions

### D1. The durable pending-call record — a new `TOOL_CALL_PENDING` event (the representation fix)

`process_tool_calls`'s `COUNTDOWN_CONFIRM`/`HARD_CONFIRM` branch — which today persists nothing — appends a new `EventType.TOOL_CALL_PENDING` event carrying `ToolCallPendingMeta{tool_name, call_id, params, tier, initiating_agent}` (a new typed metadata in `core/event.py`, frozen + `extra="forbid"`). This is the **only** addition to the dispatch path:

- The `AUTO_EXECUTE` branch is **byte-for-byte unchanged** — it still appends `TOOL_CALL` and the executor still auto-runs it. B1 itself adds only `TOOL_CALL_PENDING` (a **distinct** event type), so **at the B1 commit `EventType.TOOL_CALL` still has exactly one appender** (the AUTO branch).
- **`TOOL_CALL` gains a second appender at B3 — and this ADR broadens ADR-028 D6 t4 to admit it (R0-A-on-plan Y1 + R0-B Y1; architect-ratified 2026-06-03).** The confirm endpoint (D3) appends a `TOOL_CALL` on approve, so **after the full P3.6 slice `EventType.TOOL_CALL` has two appenders** — (i′) `agents/tool_dispatch.py:105` (the AUTO branch; grep-verifiable, unchanged) and (i″) the confirm-approve path. **Both are downstream-of-gate**, by different paths: (i′) appends only for an `AUTO_EXECUTE` gate decision; (i″) appends only as the **human-approval** second factor over a gate-produced `TOOL_CALL_PENDING` record (the gate already decided countdown/hard). This **generalizes** ADR-028 D6 t4's structural half from "exactly one grep-verifiable appender" to "**exactly two appenders, each downstream-of-gate**" — recorded here as an **ADR-028 D6 t4 amendment** the architect ratifies as part of ADR-030. The previous draft's claim that t4 was "preserved verbatim" was wrong (it was true for B1-in-isolation, false for the slice) and is retracted.
- **The confirm appender needs its own named constitutional guard (R0-A Y1 — the security crux t4 most directly broadens).** Unlike the AUTO appender, the confirm appender's downstream-of-gate-ness is **not** grep-verifiable (it's a runtime trust surface). So t4(i″) is pinned by a behavioral guard + test: the confirm endpoint appends a `TOOL_CALL` **only** by reconstructing `{tool_name, call_id, params}` + `author=agent:<initiating_agent>` from a persisted `TOOL_CALL_PENDING`, **only** after the still-pending check (D3 step 2), **never** from request fields. The `tests/tools/test_constitution.py::test_t4_tool_call_sole_appender_in_src` test is **amended** (in the B3 atomic) to allow the two legitimate appenders (`tool_dispatch.py` + the confirm endpoint) and assert no third.
- The gate **decision logic is untouched** (`score`/`decide_tier`/`gate`/`emit_gate_decision` — ADR-027 D2). `emit_gate_decision` still appends the `AUTONOMY_DECISION` audit event first; this ADR only **persists the recorded outcome** of an already-decided countdown/hard call so it can later be confirmed. The "decision" was made by the gate; the new event is a durable *record*, not a new decision.
- **ADR-027 D2 / ADR-028 amendment note (honest inscription):** those ADRs state P3.4 "changes nothing in `process_tool_calls`." This ADR amends that narrowly: `process_tool_calls` now **records** a pending call (a new append in the previously-empty countdown/hard branch). Its **decision behavior** (what tier each call gets, what AUTO appends) is unchanged; the empty-gate-diff claim for `score`/`decide_tier`/`emit_gate_decision` still holds. The amendment is recorded here per CLAUDE.md ("ADR amendment IS required when changing the contract"); the architect ratifies it as part of this ADR.

**Rejected alternative — enrich `AUTONOMY_DECISION` with `call_id`+`params`:** rejected (D1) because `emit_gate_decision`/`Operation` never receive the `ToolCall.id` (a signature change to the frozen emission/scoring path), and the AD event is an *audit-trace* shape locked by a constitutional test — overloading it with execution payload conflates audit with actuation. `process_tool_calls` is the **only** site holding both the tier (from `emit_gate_decision`'s return) and the `call_id`+`params` (from the `ToolCall`), so the pending record belongs there as its own event.

### D2. Snapshot re-point — `tool_calls_pending_confirm` derives from `TOOL_CALL_PENDING` (the empty-field fix)

`derived/snapshot.py` D2.3 is re-pointed: a `TOOL_CALL_PENDING` event `P` is **pending** iff **no event appearing after `P`'s position in room order** carries the **same `call_id`** as a resolution — i.e. no later `TOOL_CALL` (confirmed-and-appended), `TOOL_RESULT`/`TOOL_FAILED` (executed), or `TOOL_CALL_CANCELLED` (D3 cancel). `ToolCallRef` keeps its shape (`event_id`, `tool_name`, `autonomy_tier`) but `event_id` now points at the **`TOOL_CALL_PENDING`** event (the confirm handle) and `autonomy_tier` is sourced from its `tier` field (no more "unknown" anomaly path — the tier is carried explicitly).

**The `call_id`-collision posture (R0-A Y2 / R0-B G2 — resolved by position-anchoring, consistent with D3).** This is a **new** dependency on `call_id` resolution (the current snapshot keys pending on `(author, tool_name)` at `snapshot.py:159,167`). `call_id`s are **LLM-generated and documented collision-prone cross-turn** (`executor.py:97-98`). So the resolution scan is **position-anchored to `P`** — only events *after* `P` resolve `P` — **not** a position-blind "any event with this `call_id`" scan. This makes the predicate correct under a re-emitted `call_id`: a turn-1 `TOOL_RESULT(abc)` does **not** resolve a fresh turn-5 `TOOL_CALL_PENDING(abc)` (the result is *earlier* than the turn-5 pending event). **D3 step 2's endpoint still-pending check uses the identical position-anchored scan** (the two predicates were inconsistent in the prior draft — D2 "later" vs D3 "existing"; they are now both position-anchored to the target `TOOL_CALL_PENDING`, eliminating the GUI-shows-confirmable / endpoint-refuses liveness defect R0-A Y2 traced). The position scan is well-defined + race-free under the single writer (all appends serialized, ordered by `(timestamp, id)`). This fixes the structurally-empty field and gives the GUI a live, authoritative pending set. **ADR-014 amendment** (the snapshot derivation contract): recorded here; the cross-family R0-B re-derivation lens probes the new predicate.

### D3. The confirm endpoint — `POST /rooms/{room_id}/confirm` (the ADR-025 frozen-contract change)

A **new** HTTP endpoint (the deliberate ADR-025 contract change D-B=(c) entails; ADR-025 D2's HTTP-write/WS-read-only split is preserved — confirm is a discrete request/response over HTTP, the auditable write chokepoint, exactly like `/intent`). Wire types (new, in `api/wire.py`, regenerated into `openapi.json`):

- `ConfirmRequest{pending_event_id: EventId, decision: Literal["approve","cancel"]}` — `extra="forbid"`; **no** `tool_name`/`params`/`author` (forge guard at the schema layer, mirroring `IntentRequest` ADR-025 D4).
- `ConfirmResponse{appended_event: Event, turn_events: list[Event]}` (the appended `TOOL_CALL` or cancel record + the executor's resulting events) and `ConfirmError{stage, appended_event_id, reason}` (D5).

Handler logic (backend-authoritative, **no decision surface** — purely mechanical validation; runs on the single-writer executor so check→append→execute is atomic, ADR-025 D6):

1. Resolve the room; load its events. **Not found** → `404`. **Find the `TOOL_CALL_PENDING` event** by `pending_event_id`. **Not found / wrong room / not a `TOOL_CALL_PENDING`** → `ConfirmError{stage:"append"}` (nothing persisted; safe to refresh-and-retry).
2. **Room-state gate (R0-B Y3 — architect-ruled add-the-check).** Reject a confirm on a **terminal (`closed`) room** → `ConfirmError{stage:"append"}`, reason `room_closed`. (A non-closed active room is fine; the gate is *terminal-state only*, not "must be `active`" — pending calls legitimately exist across the working states.) This is an **explicit** handler check, not inherited from `_post_intent` (which only verifies room existence); the prior draft's acceptance promised "closed room → fail closed" without the handler step — now the handler enforces it.
3. **Still-pending check (idempotency layer 1) — position-anchored (R0-A Y2).** Scan the events **after the target `TOOL_CALL_PENDING`'s position** for the **same `call_id`** carried by a `TOOL_CALL`/`TOOL_RESULT`/`TOOL_FAILED`/`TOOL_CALL_CANCELLED`. If present → the call was already confirmed/cancelled → **reject as a no-op** (`ConfirmError{stage:"append"}`, reason `already_resolved`); **never** append a second `TOOL_CALL`. The scan is **position-anchored** (after the pending event), **identical to the D2 snapshot predicate** — so a cross-turn re-emitted `call_id` does not false-reject (a turn-1 result is *before* a turn-5 pending event). This check + the executor's full-room guard (layer 2) have **no gap and are atomic on the single writer**: check→append→execute all run inside the confirm closure on `ctx.writer_executor` (`max_workers=1`), so no other write interleaves between the still-pending check and the `TOOL_CALL` append (no TOCTOU).
4. **`decision == "cancel"`** → append a `TOOL_CALL_CANCELLED` event (call_id, author = the confirming surface) recording the human declined; the pending call leaves the snapshot set. Return.
5. **`decision == "approve"`** → append a `TOOL_CALL` event reconstructed from the pending record: `ToolCallMeta{tool_name, call_id, params}` from `ToolCallPendingMeta`, **author = `agent:<initiating_agent>`** (the original proposer — the gate approved *that agent's* operation; the human supplied the approval, not the authorship). Then invoke the **existing** `execute_pending_tool_calls(window_events=[that TOOL_CALL], …)` (ADR-028, unchanged) — its full-room `call_id` guard is **idempotency layer 2**. Publish the new events to the bus (cursor-diff, as `_post_intent`). The audit trail reads: `AUTONOMY_DECISION` (gate chose countdown/hard) → `TOOL_CALL_PENDING` (recorded) → `TOOL_CALL` (agent-authored, approved via confirm) → `TOOL_RESULT`/`TOOL_FAILED`. **The human approval is audited by the confirm event flow itself; no `user_id`/`DECISION` is recorded in the MVP** (N1 — auth is out of scope, ADR-025 D7 localhost-trust, so there is **no `user_id` provenance**; a user-identity audit field is a forward hook when auth lands — the prior draft's `DECISION{user_id}` is dropped rather than inscribed with no source).

**Backend-now-authors-an-agent-`TOOL_CALL` (inscribed broadening):** ADR-025 D4 noted agent-authored events "only ever arise from `run_turn`/`dispatch_turn`." Confirm adds a second backend origin. The **forge invariant holds** — the client cannot author it (it sends only `{pending_event_id, decision}`); the server authors it from the *persisted gate-produced* record. This is backend-authoritative, not a client forge; ADR-030 is where it is inscribed.

### D4. COUNTDOWN-vs-HARD confirmation semantics — explicit-confirm MVP; auto-fire-on-timer deferred

Both `COUNTDOWN_CONFIRM` and `HARD_CONFIRM` require an **explicit human approval** to execute in the MVP; **nothing auto-fires server-side.** The tier difference is **affordance, not auto-execution** (D6): `COUNTDOWN` → a low-friction approve (a single, pre-emphasized 确认 + a visible countdown affordance communicating "this is routine"); `HARD` → a high-friction approve (explicit, more prominent, no pre-selection). If the user does nothing, the call simply **stays pending** (the countdown is a UI hint, not a server timer).

**Why defer auto-fire:** "auto-execute within the window unless cancelled" requires a **durable backend scheduler** — a timer that, after N seconds with no human action, appends the `TOOL_CALL` itself. That introduces a new concurrency + durability surface (which thread fires it vs the single writer; what survives a server restart mid-window; how the timer interacts with a concurrent cancel) and a posture where the system **executes a gated operation with no human in the loop** — the opposite of the trust surface this ADR is establishing. The explicit-confirm MVP is the conservative, terminating, scheduler-free choice. **Auto-fire is a clean follow-up slice** (it owns the durable-timer design); the architect may rule it in, which pulls in that slice. *This is the COUNTDOWN-semantics call the brief asked the senior to design; surfaced for architect confirm in the plan §5.*

### D5. Partial-turn correctness on confirm (carried forward from ADR-025 D5)

Confirm mirrors `/intent`'s partial-turn envelope so the GUI knows whether re-sending double-acts:

- **`stage:"append"`** — validation failed or the `TOOL_CALL`/cancel append failed (pending not found, already resolved, room gone): **nothing actuated → safe to refresh-and-retry.** `appended_event_id: null`.
- **`stage:"execute"`** — the `TOOL_CALL` **was** appended (the approval landed, the call is recorded + idempotency-guarded) but `execute_pending_tool_calls` raised: **do NOT re-confirm** — reconcile via replay (the executor's `call_id` guard makes any retry a no-op anyway). `appended_event_id` = the `TOOL_CALL` id.

The same `stage`/`appended_event_id` distinction may surface on the WS `{kind:"error"}` channel (asyncapi.md note) when a confirm-triggered execution fails after the events streamed.

### D6. The GUI confirm surface — read-only pending presentation + the confirm action (ADR-026 view extension)

- **Pending-decision surface** renders `Snapshot.tool_calls_pending_confirm` (now non-empty) and the live `TOOL_CALL_PENDING` events from the WS stream: "助手想要调用〈humanized tool name〉,等待你确认" + 确认/取消 affordances. The **confirm action** sends `POST /confirm {pending_event_id, decision}` via a new `useConfirm` hook (sibling to `useIntent`), with D5 partial-turn handling.
- **不暴露 (D-C, HR#5):** the `autonomy_tier` drives only the *affordance* (countdown low-friction vs hard high-friction) and is **never rendered as text**; the `mcp__` prefix is stripped to the humanized tool name; "skill"/"plugin"/"MCP"/"autonomy level"/"countdown/hard" never reach the user. The tool name is humanized via the `ui_strings` layer (extended for tool-name display); an unmapped tool falls back to a safe generic ("一个工具"), never the raw key.
- **No-forge (HR#1):** the confirm request carries only `{pending_event_id, decision}` — type-impossible (codegen'd `ConfirmRequest` omits `tool_name`/`params`/`author`) to smuggle a payload. The store derives the pending set from the event stream (the `applyEvent` chokepoint) so it stays live; the snapshot is the initial/reconcile source.

### D7. Human-in-the-loop trust-surface invariants (the dual-lens R0-B subject)

The properties the cross-family R0-B probes (`requires_cross_family_review: true`; `external-r0b-prompt.md`): (a) the GUI **cannot** append/forge a `TOOL_CALL` — only `/confirm` over a persisted record can; (b) **idempotency** — double-confirm (incl. two GUI tabs racing) appends at most one `TOOL_CALL` and double-executes never (both the still-pending check and the executor `call_id` guard, atomic on the single writer); (c) **COUNTDOWN** has no server-side auto-fire (no headless execution); (d) **partial-turn** on confirm distinguishes append-fail from execute-fail; (e) **backend-authoritative** — `tool_name`/`params`/`author` come from the persisted record, never the request; a confirm on a closed/transitioned room, an already-resolved pending call, or a forged `pending_event_id` all fail closed.

## Considered alternatives

- **Surface pending READ-ONLY only (D-B=(b)), no confirm action** — the architect-partner P3.6 lean; **ruled out by the architect** in favor of (c) (the live approval loop). (b) needs D2 (the empty-field fix) too, but not D1's full payload, D3, D4, D5.
- **GUI supplies the tool payload on confirm** — Rejected, **constitutionally** (HR#1): that is the forge the spine forbids; the backend must validate an independently-persisted pending record.
- **Enrich `AUTONOMY_DECISION` with `call_id`+`params`** instead of a new event — Rejected (D1): signature change to the frozen emission/scoring path + conflates audit-trace with actuation payload.
- **Auto-fire-on-timer for COUNTDOWN** — Deferred (D4): needs a durable backend scheduler + a headless-execution posture; the explicit-confirm MVP is scheduler-free and keeps a human in every loop.
- **Confirm over the WS channel** — Rejected (ADR-025 D2 carried forward): a client→server write over WS re-opens the forge-boundary/lifecycle complexity; HTTP POST is the one auditable write chokepoint.

## Consequences

**Easier:** the gate's deferred third tier finally closes the loop — a countdown/hard call becomes a real, auditable, human-approved execution through the **one** existing executor (no second decision surface); `tool_calls_pending_confirm` stops being dead; the live approval loop makes the product's autonomy story demonstrable.

**Harder:** a new cross-track surface (a contract change + a dispatch-path recording addition + a GUI trust surface) warranting the dual-lens R0-B; the `process_tool_calls` recording addition touches a previously-frozen function (narrowly, inscribed in D1); a new event type + metadata + snapshot-derivation change ripple through the constitutional/snapshot tests.

**Crash-window analysis (R0-B Y2 — recoverability posture).** The confirm closure runs `append(TOOL_CALL)` → `execute_pending_tool_calls` on the single writer (like `_post_intent` at `app.py:354-364`). Two crash windows:
- **Crash before/during the `TOOL_CALL` append** — only the durable `TOOL_CALL_PENDING` survives; no `TOOL_CALL` exists, so on restart the call is **still pending** (the position-anchored D2/D3 predicate finds no resolution) → **re-confirmable → recoverable**. This is the benign window the `TOOL_CALL_PENDING` durability buys.
- **Crash after the `TOOL_CALL` append but before the executor completes** — the `TOOL_CALL` is durable (SQLite WAL, per-`append`) but unexecuted; the still-pending check now finds it → a re-confirm is rejected `already_resolved` → a **lost execution**. This is the **identical** append-then-execute window `_post_intent` already carries (the AUTO path has it too); there is **no executor boot-recovery scan** ("find `TOOL_CALL`s without a `TOOL_RESULT`") today. It is a **general executor crash-recovery gap, out of P3.6 scope** — noted here (and in the plan risk note) because the human-in-the-loop semantics make a lost execution more user-visible on the confirm path (the user explicitly approved it). A boot-recovery scan is a clean follow-up slice; P3.6 inherits the pattern faithfully and does not regress it.

**Neutral:** explicit-confirm (no auto-fire) trades convenience for a scheduler-free, human-in-every-loop MVP (auto-fire is additive). The agent does not react to the confirmed tool's result in-turn (ADR-028 D4 no-re-dispatch carried forward — the result lands for the next turn).
