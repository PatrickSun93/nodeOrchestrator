# Architect brief — P6.7: cron evaluation for pipeline schedules (decision-surface)

**Task:** P6.7 — the **focused cron-evaluation follow-on** that ADR-042 **D3** deferred
out of P5.1b. P5.1b shipped the recurring scheduler **interval-only**: `kind ∈ {interval,
cron}` is in the schema (D2) and every seam is **kind-agnostic**, but `validate_schedule_expr(
"cron", …)` raises `ValueError` (→ create rejects `kind=cron` with **422**) and
`compute_next_fire("cron", …)` raises `NotImplementedError`. P6.7 implements cron evaluation
in the one isolated pure-code module (`pipeline/schedule.py`), un-gates the 422 for *valid*
cron, adds the adversarial correctness suite, and amends ADR-042 D3 (cron deferred →
implemented).

**Class:** **medium**, but `requires_cross_family_review: true` (already set in
`.workflow/P6.7.yaml`) → **dual-lens**. The risk profile is **inverted** from P5.1b: P5.1b's
risk was the *scheduler spine* (a second background task near the auto-fire neighborhood);
P6.7 touches **none** of that — its entire risk is **greenfield arithmetic correctness** in
one ~pure module (the "RSS-billion-laughs class" D3 named when it deferred cron *specifically
to get this dedicated correctness review*).

**Status of this doc:** a **DECISION-SURFACE**, not a plan and not decisions. Each point
carries an architect-ratifiable lean + tradeoff; routing is the architect's. **C1
(mechanism: hand-rolled vs `croniter`) the architect-partner escalates to the architect** —
it is a dependency-posture + greenfield-correctness call, the load-bearing decision of this
slice. No senior plan / ADR-042 amendment is drafted until the architect ratifies (≥ C1).

## 0. The seam P6.7 plugs into (verify-cited `origin/main` @ `7a5c1c5`)

The deferral is **localized to one module by construction** — this is the central finding
that shapes the whole slice:

- **All four `compute_next_fire` call sites are already kind-agnostic** and need **zero logic
  change** once the module learns cron: the sweeper claim-step (`api/app.py:837`), boot
  re-arm (`:985`), create initial `next_fire` (`:2216`), PATCH re-enable (`:2350`). Each
  calls `compute_next_fire(schedule.kind, schedule.expr, …)` already.
- **The 422 is not a separate gate** — it is the *emergent* consequence of
  `validate_schedule_expr("cron", …)` raising `ValueError`, caught at `api/app.py:2200-2203`.
  When validate stops raising for *valid* cron, the create endpoint **automatically** accepts
  it; **malformed** cron still 422s (the gate **narrows** from "all cron" to "malformed cron
  only" — it is not removed).
- **UTC throughout.** `now_ms()` (`core/event.py:33`) = `int(time.time()*1000)` = UTC
  epoch-ms; cron evaluates in UTC, identical to interval (no timezone surface — C2).
- **Runtime deps today = 4** (`pyproject.toml`): `pydantic`, `httpx`, `PyYAML`,
  `defusedxml`. `croniter` is **not** present. This is the posture ADR-040 D1 defended.

Net: the only **logic** change is `pipeline/schedule.py` + its tests. `api/app.py` changes
are **doc-only** (two docstrings/comments + regenerate the checked-in `api/openapi.json` — C6).
That makes Lens B (spine no-regression) almost trivially satisfiable and concentrates **all**
scrutiny on Lens A (cron correctness), exactly as D3 intended.

## C1. ⭐⭐ Mechanism — hand-rolled 5-field subset vs `croniter` (LOAD-BEARING; escalated to architect)

This is the one decision D3 explicitly left to "a focused follow-on with a dedicated
greenfield-correctness review." It pits **two first-class project values directly against
each other**, which is why it escalates.

| Option | What it buys | Cost / residual |
|---|---|---|
| **(a) Hand-rolled 5-field subset (arch-partner lean)** | **Zero new dependency** — preserves the 4-runtime-dep posture (ADR-040 D1, which rejected an external scheduler partly *on* new-dep grounds). Ships a *subset* contract we fully control (no surprise 6-field/macro/special acceptance). | A greenfield correctness surface — **but materially narrower than D3's "RSS-class" framing implied** (see the narrowing note below). Mitigation = the mandated adversarial suite (C5) + a bounded never-match guard (C4). |
| **(b) `croniter` dependency** | Battle-tested calendar/edge-case handling (DOM-vs-DOW union, leap, etc.) written + maintained upstream; less of *our* code to get wrong. | A **5th runtime dependency** (really +2 — `croniter` pulls `python-dateutil`) → new supply-chain surface, against the documented conservatism. `croniter` is a **superset** (6-field/`@macros`/`L`/`W`/`#`); shipping our *subset* still needs a hand-rolled **validation wrapper** to reject what we don't support — so the "less code / fewer bugs" benefit is partially clawed back, and its permissiveness is itself a contract risk. |

**The narrowing note (decisive for the lean).** D3's "RSS-billion-laughs class" framing was
written *before* the implementation was scoped. The actual hand-rolled surface is **smaller
than that framing**: **all calendar arithmetic** — leap years, month lengths, day/hour/minute
rollover, year-wrap, DST-is-a-non-issue-because-UTC — is owned by **stdlib `datetime` +
`timezone.utc`**, *not* hand-written. The hand-rolled part is only: (1) parse 5 fields into
allowed-value sets (`*`, `*/n`, `a-b`, `a-b/n`, `a,b,c`); (2) a per-minute match predicate
(incl. DOM-vs-DOW union, C3); (3) a **bounded** forward-search loop (C4). The genuinely-hard
part (the calendar) is delegated to stdlib; the DoS tail (the billion-laughs analog) is
neutralized by validate-time rejection (C5) + the search cap (C4).

**Arch-partner lean: (a) hand-rolled subset** — because the narrowed surface is a small,
fully-testable artifact (~est. 60-100 LOC + a thorough test file), the team has demonstrated
exactly this greenfield-correctness review muscle, and (a) honors a dependency posture the
project defended *in an ADR*. **But this is genuinely the architect's call**: the architect
may legitimately weight greenfield-correctness-aversion above dependency-conservatism given
D3's own "RSS-class" framing, in which case (b) is the right answer. **I surface both with my
lean; the architect decides.** (C2–C8 below assume (a); if the architect picks (b), C2/C3/C4
become "which subset of `croniter`'s surface do we expose + how do we restrict it," and C5
shrinks to the wrapper's reject tests.)

## C2. Cron subset scope — fields + syntax (if (a))

Standard **5-field** cron, **UTC-only** (same as interval; no timezone token):

```
 ┌ minute        0-59
 │ ┌ hour        0-23
 │ │ ┌ DOM       1-31
 │ │ │ ┌ month   1-12
 │ │ │ │ ┌ DOW   0-6   (0 = Sunday)
 * * * * *
```

| Sub-decision | Lean | Note |
|---|---|---|
| Supported tokens | `*`, `*/n`, `a-b`, `a-b/n`, `a,b,c` (compositional) | Covers the headline "every N min/hours", ranges, lists. Falls out of one compositional field parser. |
| DOW domain | **`0-6`, 0=Sun** | Decide: also accept **`7` = Sunday** (Vixie convention)? *Lean: accept 7 as an alias for 0* (cheap, expected) — or reject for a tighter surface. **Architect/senior call.** |
| Month / DOW **names** (`JAN`, `MON`) | **Exclude** (numbers only) | Tighter parse surface; names are pure sugar. |
| **Exclude-list (name explicitly so the senior doesn't gold-plate)** | 6-field (seconds); `@hourly`/`@daily`/`@reboot` macros; `L`/`W`/`#` specials; timezone tokens; names | Each is a future opt-in, not P6.7. |

## C3. ⭐ DOM-vs-DOW union semantics (the classic footgun — own point)

The single most error-prone cron semantic. Standard Vixie behaviour: when **both** DOM and
DOW are restricted (neither is `*`), a minute matches if **DOM matches OR DOW matches**
(union); when exactly one is `*`, only the other constrains; when both are `*`, day is
unconstrained. **Lean: implement the standard Vixie union** (it is what "cron" means to
users). This must be an **explicit** decision + a dedicated adversarial test (C5) — silently
implementing intersection is the most likely correctness bug in the whole slice.

---

## C4. Never-match / bounded forward-search guard (the infinite-loop + DoS floor)

`compute_next_fire(cron, …)` searches forward minute-by-minute from `after_ms`. Two
unbounded-loop hazards must be closed:

- **Never-matching expr** (e.g. `0 0 30 2 *` — Feb 30 never exists): the search must be
  **bounded** (lean: cap at ~4 years of forward minutes — enough to cover legitimate
  `0 0 29 2 *` Feb-29-only schedules whose next match can be ~4y out) and **raise
  `ValueError`** when the cap is exhausted, never loop forever.
- **Malformed expansion** (`*/0`, huge/inverted ranges): rejected at **validate** time before
  any search (C5), so the search only ever runs on a well-formed expr.

(The minute-step search is O(minutes-to-next-fire); worst-case ~2M iterations only for the
pathological Feb-29 expr — acceptable as a guard, not a hot path. A smarter field-advance is
a deferrable optimization, not a P6.7 requirement.)

## C5. Adversarial test surface (maps directly to Lens A)

If (a), the correctness suite **is** the mitigation. Required classes (each test must FAIL if
its guard is removed — the project's fail-on-revert discipline):

1. **Boundary rollover** — `59 23 * * *` crosses minute→hour→day; `59 23 31 12 *` crosses the
   **year boundary** (Dec 31 23:59 → next).
2. **Month-end / leap** — `0 0 31 * *` skips 30-day months + Feb; `0 0 29 2 *` matches only
   leap-year Feb 29 (exercises the C4 ~4y search); end-of-month ranges.
3. **`*/n` alignment** — `*/15` fires at :00/:15/:30/:45 (aligned to 0, **not** "15 min from
   an arbitrary start" — pin this misconception); `*/7` over 0-59 (ragged step: 0,7,…,56 then
   resets); `*/90` (step > range → only 0).
4. **DOM-vs-DOW union** (C3) — `0 0 13 * 5` = 13th **OR** Friday (union, not intersection);
   `0 0 * * 1` (DOW-only); `0 0 1 * *` (DOM-only); the both-restricted union case explicitly.
5. **Year-wrap** — `0 0 1 1 *` from mid-December → next Jan 1, year increments.
6. **≥6 malformed-reject (validate-time, the DoS/correctness floor)** — wrong field count (4
   or 6); out-of-range (`60` min / `25` hr / `32` DOM / `13` month / `8` DOW); **`*/0`**
   (step-zero); inverted range `5-2`; non-numeric `*/x`; whitespace-only/empty; plus the C4
   never-match raise.

All tests pass `after_ms` explicitly — **wall clock never read** (the existing
`test_schedule.py` discipline).

## Constitutional carry-forward watch-list (carry into the plan + ADR-042 amendment)

- **Orchestration = code/config, never LLM.** Cron arithmetic is **code** (ADR-041 §9 /
  ADR-042 D3). **No new routing `LLMPurpose`** — the only LLM in a scheduled run stays the
  analyze + reduce content-gen inside the **byte-unchanged** `run_pipeline`.
- **The scheduler actuates, never decides** (ADR-040 D2) — the operator defines the cron
  expr (**when**) + the pipeline (**what**); the evaluator only computes the next UTC minute.
- **Spine byte-frozen (Lens B).** `_execute_local_call`, `score`/`decide_tier`/
  `emit_gate_decision`, `_countdown_sweeper`/`_writer_approve_helper`, `run_pipeline`,
  `_schedule_sweeper` act/discover, all schedule endpoints' **logic** — **zero-diff**. The
  only logic change is `pipeline/schedule.py`.
- **ADR-041 D5 reversible-only preserved** — `countdown_auto_fire=None` untouched; a
  cron-scheduled run is still reversible-only, identical to an interval-scheduled run. P6.7
  adds **no** new authorization or actuation surface — it only computes *when*.
- **UTC-only** (C2) — consistent with interval; no timezone surface introduced.
- **Bounded everything (C4/C5)** — no unbounded parse expansion, no unbounded search; the
  greenfield-correctness floor D3 deferred this slice to enforce.
