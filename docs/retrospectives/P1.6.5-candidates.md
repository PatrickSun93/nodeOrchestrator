## RC-20 — Dual-lens R0-B independent-confirmation rate: 4 of 6 (first clean measurement)

**Surfaced:** 2026-05-29, at the close of P1.6.5 plan-stage dual-lens R0-B (after both lenses' findings were routed).

**Observation:** P1.6.5 ran both R0-B lenses at **plan stage against the same baseline** — the post-R0-A-absorption plan + ADR-016 (architect chose current-state parallel dispatch over wait-for-2nd-revision). Proxy lens first (`R0-B-cross-family.md`, in-session Claude contrarian, 6🟡/4🟢), then true cross-family external (`R0-B-cross-family-external.md`, DeepSeek V4 Pro, 5🟡/7🟢). **This is the first time in project history both lenses reviewed the same artifact and the overlap is directly measurable.**

### The numbers

External independently re-derived **4 of the proxy's 6** findings, without being told them (the external prompt steered probe directions but did not disclose proxy findings):

| Proxy finding | External | Class |
|---|---|---|
| Y2 — `append_in_transaction` bare-call footgun | 🟢-confirm | runtime |
| Y3 — FK-timing acceptance error ("CREATE raises") | Y8 (re-derived) | factual/test |
| Y4 — layering-guard set incomplete | Y10 (re-derived) | completeness |

| Y6 — keep `contradictions` (vs defer) | **not re-raised** (explicitly agreed deferred) | judgment |

The external added **3 net-new** the proxy missed, all runtime/schema-correctness:
- **Y7** — `conn ≠ event_store.conn` silent atomicity loss (unasserted invariant).
- **Y9** — no UNIQUE on `verified_knowledge.promoted_from_hypothesis_id`.
- **Y11** — shared-DB migration path untested (all tests `:memory:`).

So: **4/6 proxy findings confirmed (67%)**; the 2 not re-raised are both **non-runtime** (one cite/process, one already-agreed deferral) — neither a false positive; **3 net-new from the external**, all in the operational/runtime dimension the Claude family structurally under-weights.

### Why it matters — RC-15 dual-lens economics

[[RC-15]] (`dual-lens-r0b.md`) codified **when** to dispatch dual-lens (≥3 of 4 criteria) but left open the **economic** question: *is the in-session proxy lens trustworthy enough to lean on alone, or does the true cross-family external add enough to justify its dispatch cost?* P1.6.5 is the first cycle with a clean controlled measurement (same artifact, both lenses), and it answers both halves:

- **The proxy lens is TRUSTWORTHY.** 4 of its 6 findings were independently re-derived by a different model family. The 2 the external didn't re-raise are both non-runtime (cite-recount + agreed-deferral), not false positives. The proxy is not a throwaway "Claude reviewing Claude" — it caught real issues an external family confirmed.
- **The external lens is NOT redundant.** It added 3 net-new findings, every one runtime/schema-correctness (Y7 atomicity, Y9 schema constraint, Y11 test gap) — exactly the dimension the stated cross-family rationale targets. Y7 in particular is the **canonical cross-family catch**: a silent invariant (`conn is event_store.conn`) that *both* same-family reviewers (R0-A G2 + proxy G1) accepted as obvious — they praised D11 atomicity but stopped at "same connection = obvious." Textbook validation of *why* a different family is dispatched, not just *that* it found things.

**Conclusion this cycle: both lenses paid for themselves; neither dominates.**

### Sub-observation — the second lens also corrected an architect-partner routing over-reach

The external Y10 (+ architect-partner verification) corrected the proxy-Y4 routing: the proxy routing had said "add 4 guards incl `workflow/`"; the external flagged `workflow/` as dev-harness (zero product imports) → refined to 3 product-only guards. So the cross-family lens benefits the **routing synthesis**, not just the senior plan — a data point that architect-partner routing leans are themselves improved by the second lens.

### Status

**Open — single clean measurement (n=1 cycle).** P1.6.5 establishes the baseline (4/6 confirm + 3 net-new). Codification (e.g., "proxy sufficient for low-runtime-surface cycles; external mandatory for runtime/transaction-heavy contracts") needs 2–3 cross-cycle measurements of the confirmation rate. Per the project's RC-4 precedent (one instance ≠ codify), this stays a tracked candidate, not a graduated rule.

**Open question for the retro:** does 4/6 generalize, or is it an artifact of P1.6.5's particular shape? P1.6.5 is persistence + transaction-atomicity — a lot of runtime surface for an external family to find net-new in. A lower-runtime-surface cycle (e.g., a doc/process or pure-schema cycle) might show *higher* proxy/external overlap (external adds less net-new) — which would tilt the economics toward "proxy alone suffices for non-runtime cycles." The confirmation rate likely **co-varies with runtime-surface area**; the codification, when it comes, should be conditioned on cycle shape, not a flat rule.
