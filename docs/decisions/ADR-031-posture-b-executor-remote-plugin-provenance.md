# ADR-031: Posture-B Subprocess Plugin Executor + Remote-Plugin Provenance

**Status:** Accepted — 2026-06-04 (architect Peidong, P3.7-remote; senior-drafted, plan-stage dual-lens clean after routing-absorption). **The architect Accepts the `RB-FS/NET` residual**: an activated fetched plugin's subprocess is env/secret/DoS-scoped but retains the host user's filesystem-read + outbound-network privilege (gated by activation + digest + scoped-env, NOT a syscall sandbox); real FS/network sandboxing (container/seccomp/separate-UID) is deferred to P4 — accepting the real surface, not a softened one. The mandatory impl-stage dual-lens R0-B re-probes the subprocess isolation / provenance enforcement / fetch integrity on the implementation. (Plan-stage dual-lens routing absorbed — architect routed 2026-06-04 via orchestrator, `reviews/P3.7-remote/architect-routing-on-plan.md`, **all findings → α**). The architect ruled **B-coupled** (the Posture-B executor + the actual remote-fetch ship together) and **reuse-the-MCP-subprocess-mechanism** (no second subprocess protocol). **Plan-stage dual-lens absorbed:** R0-B R1 🔴 → α (narrow the L1/"real isolation boundary" claim — Posture B is **env/secret/DoS-scoped only**; FS/network remain an inscribed residual risk `RB-FS/NET`, see D1a); R0-B R2 🔴 → α ("structurally unreachable" → **test-enforced unreachable** + the segregated fetched-loader interface, D3); R0-A Y1 → α (pin the non-deprecated SDK symbol — ADR-032); R0-A Y2 → α (= R1 residual inscription, D1a); R0-A Y3 + R0-B Y3 → α (provenance-by-origin + staging segregated from the presence root, D3/D5); R0-A Y4 + R0-B Y2 → α (fetched child env operator-pinned in the activation entry only, D4); R0-B Y1 → α (orchestrator-level kill watchdog, D2); R0-B Y5 → α (digest-before-extract ordering, D5); R0-B Y6 → α (`MAX_POSTURE_B_CALLS_PER_TURN`, D1); R0-B Y7 → α (atomic-staging cleanup, D5). This ADR drafts the contract for architect Accept; the dual-lens verdicts are bumped to clean per RC-10. Not yet ratified.

**Scope:** P3.7-remote (P3 Wave-3 closer, heavy half) — the **A→B migration** of the plugin tool-code executor (in-process `importlib` → killable subprocess) **and** the **remote-plugin provenance / consent** surface it gates. Governs: the Posture-B execution model (D1), the reuse of the ADR-027 MCP-subprocess machinery (D2), the provenance model (D3), the activation/consent posture for untrusted provenance (D4), the minimal remote-fetch contract (D5), the demo (D6), and the constitutional carry-forward (D7). Does **NOT** govern: the autonomy gate decision logic (`score`/`decide_tier`/`emit_gate_decision`/`process_tool_calls` — **unchanged**, ADR-027 D2 / ADR-028 D6); the runtime executor's dispatch (`tools/executor.py::_execute_local_call` — **unchanged**; a Posture-B plugin tool runs through it via the `local_tools` registry, no executor edit); the remote MCP *transport* (ADR-032); a plugin registry/marketplace, remote upgrade/version-coexistence/uninstall (deferred P4); GUI plugin management (frontend track).

## Context

ADR-029 D4 Accepted **Posture A (in-process import) only because plugins are operator-placed — curation IS the trust boundary** — with three exposures fully inscribed and Accepted: **L1** (no technical isolation + zero env protection: in-process plugin code reads all `os.environ`), **L1b** (import-time top-level code runs ungated at boot), **L2** (Posture A VOIDS ADR-028 D5's absolute per-turn liveness bound — a buggy/hung in-process tool blocks the `max_workers=1` writer for **every** room, with no cap and no kill). ADR-029 D4 also **reserved Posture B as the REQUIRED posture once provenance becomes untrusted (P3.7 remote)** and itemized the A→B migration surface (Reversibility table / R0-B Y6): `plugins/code.py` (`importlib` + `LocalToolFn`) → a subprocess protocol; `LocalToolFn` → a subprocess-runner adapter.

Verified `origin/main` @ cbadf6d:
- `plugins/code.py:42-104` is the Posture-A in-process loader (`spec_from_file_location` + `exec_module` — module top-level runs in the **orchestrator process**; the L1/L1b/L2 surface).
- `tools/executor.py:297-347` (`_execute_local_call`) looks up `local_tools[name]` and calls `impl(params)`, wrapping every call fail-closed → `TOOL_FAILED` (ADR-028 D4). It is **mechanism-agnostic**: it does not care whether `impl` runs in-process or launches a subprocess.
- `mcp/transport.py` already implements the **exact** subprocess trust machinery B needs: `_build_scoped_env` (minimal-scoped env, never the orchestrator's full `os.environ` — the c2 lesson), `asyncio.wait_for`-bounded sync calls, and stdio_client kill-no-orphan teardown (ADR-027 D1/D4). ADR-029 D4 itself observed *"a Posture-B plugin executable tool ≈ a bundled MCP server."*
- `plugins/loader.py` discovers plugins by **presence** in `plugins/` (`_discover_and_validate`, `D5 presence=opt-in`) and has **no notion of provenance** — every plugin is implicitly operator-placed.

**The crux this ADR inscribes.** A **fetched/remote** plugin is **not operator-placed**, so curation — the entire basis of the Posture-A Accept — **no longer holds**. Therefore **Posture A is constitutionally invalid for remote provenance**: shipping remote-fetch on the in-process executor is the L1 (full host privilege + every secret) + L1b (import-time ungated) + L2 (server-wide DoS) surface **with no curation backstop** — a real vulnerability, not an accepted MVP posture. **Posture B (killable subprocess, scoped env, bounded-timeout, fail-closed) is REQUIRED, not optional** — the architect already ruled this in ADR-029 D4. B1 is therefore the **enabling precondition** for any remote-plugin capability; the two are coupled.

## Hard requirements — the constitutional spine (NON-NEGOTIABLE; carries ADR-005/006/027/028/029 forward — *not* new choices)

1. **The gate stays the sole chokepoint — unchanged.** A Posture-B/remote plugin tool routes through the **same** code gate (`process_tool_calls → emit_gate_decision`); tier from code-classified reversibility; unregistered/unclassified → `UnknownToolError` → refused (fail-closed). The empty-gate-diff invariant (ADR-027 D2) holds; this ADR extends it to an **empty-gate-diff-with-a-new-executor-mechanism**.
2. **The executor's decision path is unchanged.** B1 swaps the *mechanism* of a plugin `LocalToolFn` (in-process function → subprocess-launching closure); `tools/executor.py::_execute_local_call` is **byte-unchanged** (it still calls `impl(params)`). The empty-executor-diff invariant (ADR-028 D6) holds.
3. **Self-asserted tier is never authoritative.** A fetched plugin's claimed reversibility is advisory-capped → host-authoritative-or-default-0 (ADR-029 D5). A remote source cannot self-classify a write tool to dodge `HARD_CONFIRM`.
4. **Fetching ≠ trusting (discovery ≠ permission, one level up).** Remote/fetched plugin code is **never** auto-trusted on fetch; the *consent granularity changes* (presence=opt-in → an explicit activation entry, D4) but never to "auto-trust on fetch." No remote infra introduces an LLM routing/judgment decision; **no new routing/judgment `LLMPurpose`** (D7).
5. **Credential safety + scoped env become REAL (env/secret sub-surface only).** The Posture-B subprocess gets a **minimal scoped env** (the c2 env-leak lesson) — and Posture B is exactly what makes the **env/secret** boundary **real** for plugin code (it is **zero** under Posture A, ADR-029 D4 L1). **This resolves L1's env/secret sub-surface only — NOT its FS/network sub-surface** (an activated fetched plugin's subprocess keeps the host user's filesystem-read + outbound-network privilege; that is the Accepted residual **RB-FS/NET**, D1a). For **fetched** provenance the child env + any secret is **operator-pinned in the activation entry only** — a fetched plugin manifest **cannot self-request** env keys or `api_key_env` (D4).
6. **Fail-closed everywhere.** Unverified provenance / missing activation / fetch failure / TLS failure / integrity mismatch / subprocess crash-hang-timeout-orphan → **refuse / `TOOL_FAILED`**, never degrade-open, never crash/hang the orchestrator.
7. **Restore the ADR-028 D5 liveness bound.** The killable subprocess re-establishes the absolute per-turn bound Posture A voided (L2): a Posture-B tool call is bounded-timeout + killable, so a hung/runaway plugin tool does **not** block the single writer indefinitely.

## Decisions

### D1. The Posture-B execution model — killable subprocess, parent never imports plugin code

`plugins/code.py` is reworked: instead of `importlib`-ing the plugin tool module **in the orchestrator process**, the loader produces, for each `tool_impls` entry, a **`LocalToolFn` that launches a subprocess** running the plugin tool code. The subprocess gets a **minimal scoped env** (HR#5), a **bounded timeout** (HR#7), is **killed-with-no-orphan** on timeout/hang (HR#6 + D2 watchdog), and **fails closed → `TOOL_FAILED`** on crash/timeout/malformed output. **The parent process never imports the plugin module** — the `importlib`/`exec_module` of plugin code happens **in the child** (a generic harness, D2). This resolves **L1's env/secret sub-surface** (the scoped env), **L1b** (import-time code now runs **inside the scoped, killable child**, not the orchestrator), and **L2** (the killable subprocess restores the ADR-028 D5 bound). It does **NOT** resolve **L1's FS/network sub-surface** — that is the Accepted residual **RB-FS/NET** (D1a).

The resulting `LocalToolFn` drops into the **same** `local_tools` registry the executor already consumes — `_execute_local_call` runs it **unchanged** (HR#2). What changes is *what a plugin `LocalToolFn` is*, not how the executor dispatches it.

**Per-turn subprocess cap (R0-B Y6 → α).** A Posture-B plugin tool call is a **process fork** (much costlier than Posture A's in-process function call), so an unbounded count per turn is a subprocess-exhaustion DoS (PIDs/FDs/memory) — the same rationale that gave MCP `MAX_MCP_CALLS_PER_TURN = 10` (`tools/executor.py:43`). The executor enforces a **`MAX_POSTURE_B_CALLS_PER_TURN`** cap (the MCP analog) **only** for `LocalToolFn`s that are subprocess closures (Posture-B); operator-placed **Posture-A** in-process tools are exempt (fast, cheap). Calls beyond the cap in one turn → `TOOL_FAILED` (not executed, logged), mirroring the MCP cap. This complements the D5-bound (which bounds **one** hung call) by bounding **many** rapid calls.

### D1a. Posture B's residual trust surface — env/secret/DoS isolation ONLY, NOT host-syscall sandboxing (honest inscription — R0-B R1 / R0-A Y2 → α)

Posture B is **NOT a syscall sandbox.** It bounds three things and **only** three: **memory/process** (separate process), **secrets/env** (minimal scoped env — L1-env), and **liveness/DoS** (killable + bounded-timeout + per-turn cap — L2). An **activated** fetched plugin's child process **still runs with the orchestrator user's full filesystem-read + outbound-network privilege** — it can `open()` any file that user can read (`~/.ssh/id_rsa`, `.env`, `config/*.yaml`) and `socket()`/`requests.post` to exfiltrate. This is the **Accepted residual `RB-FS/NET`**, inscribed here **exactly as Posture A's L1/L1b/L2 were inscribed** in ADR-029 D4 — the ADR Accepts the *real* surface, not a softened one. **The operator who activates a fetched plugin (D4) assumes this residual** — activation+digest is the *don't-run-unapproved-code* authority, scoped-env is the *no-secrets* authority, kill+cap is the *no-DoS* authority; **none of them is a syscall sandbox.** A future reader must **not** over-read "real technical isolation boundary" (D1/Consequences) as "sandbox": it is an **env/secret/DoS** boundary. **Real FS/network sandboxing (container / seccomp / separate UID / chroot) is explicitly DEFERRED to P4** (Reversibility + the forward-watch below) — it is a container-orchestration problem, not a P3 subprocess patch; the env-scoping Posture B *does* deliver is a genuine improvement over Posture A's zero protection, and that improvement — not a sandbox — is what this ADR claims.

### D2. Reuse the ADR-027 MCP-subprocess mechanism — one subprocess protocol, not two (architect-ratified)

**The architect ruled: reuse the MCP-server subprocess machinery; do not build a second subprocess protocol.** A Posture-B plugin executable tool is treated as **a local stdio MCP server** (ADR-029 D4's "≈ a bundled MCP server", made literal). The shared machinery is **extracted from `mcp/transport.py` into a reusable seam**, split by scope (R0-A G1 — avoid mis-naming a transport-agnostic concern "subprocess"): **(a)** the **transport-agnostic** `asyncio.wait_for`-bounded sync bridge + fail-closed envelope (reused by **both** stdio **and** the remote streamable-http path, ADR-032 D2) → e.g. `mcp/_async_bridge`; **(b)** the **subprocess-only** machinery — `_build_scoped_env` + the kill-no-orphan teardown → e.g. `mcp/subprocess_trust.py`. The MCP transport and the Posture-B plugin executor both consume (b); the remote transport consumes only (a). A generic **child harness** wraps a plugin's `<module>:<callable>` (`tool_impls` ref) as a stdio MCP-server child: the harness imports the callable **in the child**, exposes it as a single MCP tool, and the parent drives it via the reused stdio client. The extraction is a **pure refactor** (MCP transport behavior unchanged — the empty-behavior-diff is a forcing function, plan P3.7-remote-4).

**Orchestrator-level kill watchdog (R0-B Y1 → α).** The kill-no-orphan guarantee must **not** rest on the MCP SDK's `stdio_client` teardown alone (a LAYER-2 / framework guarantee — SIGTERM → `PROCESS_TERMINATION_TIMEOUT` → SIGKILL; a SDK bug or a SIGKILL-surviving child / zombie-reap race could orphan). The subprocess-trust seam (b) adds a **LAYER-1 (orchestrator) watchdog**: after the SDK teardown returns, **check whether the child PID still exists; if so, force `SIGKILL` directly** (and reap). The orchestrator never trusts the framework to be the sole killer. (The same watchdog backstops the MCP stdio path; behavior for the well-behaved common case is unchanged.)

**Consequence (inscribe):** Posture B's marginal value over "just bundle an MCP server" is thin (ADR-029 D4 observed this) — but `tool_impls` remains the manifest surface for **packaging convenience** (a plugin author writes a Python callable, not a full MCP server); the harness is what bridges it to the one subprocess protocol. The cost (a plugin tool must now be subprocess-safe) is the price of the real isolation boundary the remote/untrusted case requires.

**[Extended P4.2-B3 → ADR-034, Accepted 2026-06-05]** `run_scoped_command` in `mcp/subprocess_trust.py` is the **non-MCP plain-exec entrypoint** on the one subprocess protocol: it reuses `scoped_env`, `_terminate_subprocess`, and `_kill_watchdog` to run plain `argv` commands (B3 subprocess local tools — `run_tests`/`run_lint`/`git_blame`/`git_log`/`git_diff`) with bounded stdout+stderr capture. This lightly extends this D2 contract; the substance is in ADR-034.

### D3. The provenance model — operator-placed vs fetched; fetched VOIDS curation

The loader gains a **provenance** mark per plugin: `operator-placed` (present in the local `plugins/` dir — the P3.5 case) or `fetched` (obtained via the remote-fetch mechanism, D5). **The provenance determines the required posture:**

- `operator-placed` → Posture A remains valid (curation holds; ADR-029 D4 unchanged) **or** Posture B (if the operator opts a local plugin into subprocess isolation). The P3.5 in-process path is **preserved** for operator-placed plugins (no regression).
- `fetched` → **Posture B is FORCED** (curation void — HR, the crux). A `fetched` plugin's `tool_impls` running in-process is **test-enforced unreachable** (R0-B R2 → α — *not* claimed "structurally unreachable"): the in-process `importlib` path still physically exists in the module (it serves `operator-placed` plugins), so the guarantee is a **runtime provenance guard + a discriminating test as the enforcement**, not a type-level impossibility. The loader refuses to register a `fetched` plugin's code via the Posture-A path; a test asserts the in-process loader is **never invoked** for `fetched` provenance, and a second test asserts a fetched bundle **cannot** be discovered as `operator-placed` (the segregated loader interface below).

**Provenance is host-set by ORIGIN, not plugin-self-asserted** (a plugin cannot claim `operator-placed` to dodge Posture B) — and it must be **un-launderable** (R0-A Y3 + R0-B Y3 → α). The mechanism: `load_plugins` gains a **second, segregated discovery root** — `fetched_plugins_dir: Path | None = None`, **NOT under** the `plugins/` presence-discovery root. Plugins discovered under `plugins_dir` are marked `operator-placed`; plugins discovered under `fetched_plugins_dir` are marked `fetched`. Because the two roots are **disjoint** and the fetch mechanism (D5) stages **only** into `fetched_plugins_dir`, the presence walk over `plugins_dir` **can never yield a fetched-origin bundle marked operator-placed** — closing the provenance-laundering vector (a fetched bundle re-discovered under `plugins/` and wrongly Posture-A-validated = the exact crux breach this ADR exists to prevent). Provenance-by-origin is the **HR#3 analog, one level up** (discovery ≠ permission → fetching ≠ trusting).

### D4. The activation / consent posture for untrusted provenance — fetching ≠ trusting

ADR-029 D5 deferred "a discovered-but-not-activated registry" to P3.7 "when provenance becomes untrusted." This ADR lands it as the **minimal operator-pinned activation allowlist**:

- A `fetched` plugin is **discovered-but-not-activated** by default — fetching it does **not** load it.
- It loads **only** if the operator adds an explicit **activation entry** pinning its **source** (the `https://` fetch URL) **and an integrity digest** (e.g. a SHA-256 of the bundle). The fetched bundle **must match** the pinned digest or it is **refused** (HR#6).
- This is the **remote analog of presence=opt-in** (ADR-029 D5): for the local dir, presence in `plugins/` IS the operator's opt-in; for fetched provenance, **the pinned activation entry IS the opt-in** — *fetching ≠ trusting*. The consent stays **operator-authoritative + fail-closed**, with **no registry/marketplace** (deferred P4).
- All the per-surface guards (gate, allowlist, advisory-cap, fail-closed loading, collision-check) from ADR-029 still apply unconditionally **on top of** activation.

**Env/secret injection for a fetched child is operator-authoritative ONLY (R0-A Y4 + R0-B Y2 → α — the c2 lesson at untrusted-remote scale).** The shared `_build_scoped_env` (D2-b) injects `server_cfg.env` **plus** the `api_key_env` secret — for curated stdio MCP that config is operator-authored (`mcp_servers.yaml`). For a **fetched** plugin the analog must **never** be manifest-authoritative: a malicious fetched manifest declaring `api_key_env: <orchestrator-secret>` would otherwise have the scoped-env logic **hand it the secret**, turning "minimal scoped env" into plugin-author-controlled. Therefore:
  - A **fetched** plugin manifest **cannot self-request** env keys or `api_key_env` — `api_key_env` is **forbidden** for fetched plugins (plugin tool code is *not* an authenticated external service; it has no legitimate need for an orchestrator secret).
  - Any env a fetched child receives beyond the 9-key minimal base (`_SAFE_ENV_KEYS`) is declared **in the operator-authored activation entry only** (a `plugin_subprocess_env: dict[str,str]` of operator-chosen **non-secret** keys), never read from the fetched manifest.
  - The **env-leak probe** (plan -5/-8) covers the **manifest-requests-a-secret** attack (a fetched manifest naming `api_key_env`/a secret key → refused, child env clean), **not only** the default-clean case.

This makes the activation entry the single operator-authoritative source for *both* "run this code" (digest) *and* "with this env" (subprocess-env) — a fetched plugin author controls neither.

### D5. The minimal remote-fetch contract — pinned source, integrity-checked, fail-closed

A new `plugins/fetch.py` fetches **one** plugin bundle from a **pinned `https://` source** into the segregated `fetched_plugins_dir` (D3):

- **Bundle format** is a **single archive** (`.zip` or `.tar.gz`) — a single byte-stream the digest can cover (R0-B Y5).
- **TLS-verified** (`https://` only — a non-`https://` source is refused; TLS-verify failure → refused, HR#6).
- **Digest-BEFORE-extract ordering (R0-B Y5 → α — the ordering IS the security property, the ADR-029-D2-step-ordering analog).** The digest is computed on the **compressed bundle bytes BEFORE any extraction**; only a digest-matching bundle is **then** extracted. Extracting first would expose extraction-time attacks (zip-bomb disk-exhaustion, path-traversal `../../.ssh/authorized_keys`, symlink attacks) **before** the digest check could fail — digest-too-late = arbitrary files already written. **No byte of the bundle reaches the filesystem in extracted form before the digest passes.**
- **Extraction is path-traversal-guarded** — extraction targets a temp dir; every member path is validated to stay within it (reject `..`/absolute/symlink-escape).
- **Atomic staging + half-stage cleanup (R0-B Y7 → α).** Download to a **temp file** → verify digest → **if valid**, extract to a **temp dir** → validate members → **rename** into `fetched_plugins_dir`; **if invalid at any step**, **delete the temp file / `rmtree` the temp dir** — `fetched_plugins_dir` is **never** touched by a failed fetch ("nothing staged" is the *designed mechanism*, not an aspiration; no defunct partial bundles accumulate, none re-discoverable).
- **Integrity-checked** against the activation digest (D4) — a mismatch → refused, nothing staged.
- **Fail-closed** on unreachable / fetch error / malformed bundle → refused, nothing staged, no orchestrator crash (per-plugin isolation, ADR-029 D6 analog).
- The staged bundle is marked provenance `fetched` by **origin** (discovered under `fetched_plugins_dir`, D3) → Posture B forced + activation required.

This is the **minimal pinned-source fetch only**. **Out (deferred P4):** a registry/marketplace, plugin upgrade / version coexistence / uninstall, auth beyond the bundle integrity check.

### D6. The demo — one fetched-and-Posture-B plugin, end-to-end + fail-closed

ONE demo (mirroring P3.4/P3.5's one-demo discipline): a plugin **fetched** (pinned source + digest) → **activated** → run under **Posture B** (subprocess) end-to-end → `TOOL_RESULT`. The demo also proves the **fail-closed paths**: a subprocess crash/hang/timeout → `TOOL_FAILED` + kill-no-orphan (the D5-bound restoration, incl. the D2 watchdog); an **env-leak probe** asserts the child env lacks the orchestrator's secrets **both** in the default case **and** when a fetched manifest *requests* a secret/`api_key_env` (→ refused, D4 / R0-A Y4); a **`MAX_POSTURE_B_CALLS_PER_TURN`** test asserts the per-turn subprocess cap (D1 / R0-B Y6); a **provenance-laundering** test asserts a fetched bundle cannot be discovered as `operator-placed` (D3 / R0-A Y3+R0-B Y3); a **digest-before-extract** test asserts a tampered/oversized bundle is rejected before extraction (D5 / R0-B Y5); an **unactivated** fetched plugin → refused; a **digest-mismatch** → refused (with the temp staging cleaned up, D5 / R0-B Y7).

### D7. Constitutional carry-forward — the constitution test extends to the new code

The new code (`plugins/fetch.py`, the provenance/activation module, the subprocess-runner + harness) makes **no** autonomy/routing/model decision. The `plugins/` + `mcp/` + `tools/` constitution tests extend to forbid the new modules referencing `decide_tier`/`emit_gate_decision`/`score`/`gate`/`select_model_and_provider`, forbid any `llm/` provider call, and assert the frozen `LLMPurpose` set is unchanged (**no new purpose**). Provenance + activation + fetch are deterministic code/config, never an LLM judgment (HR#4). This ADR **binds** ADR-005/006 (gate + fail-closed), ADR-027 D2/D4 (feed-the-gate-unchanged + the trust machinery reused), ADR-028 D5/D6 (the liveness bound restored + the executor invariants), ADR-029 D4/D5 (the A→B migration + presence→activation) — it does **not** restate them.

## Considered alternatives

- **B-executor-first (build + test Posture B on a local plugin; defer remote-fetch)** — **Overridden by the architect** (B-coupled ruled). Recorded: executor-first is lower-risk (the migration is the hard, testable part) but leaves the remote-plugin story incomplete for P3's last cut; the architect ruled the full untrusted-remote-plugin story end-to-end.
- **Build a distinct plugin-subprocess protocol** (not the MCP one) — **Rejected** (D2, architect-ratified): a second subprocess surface duplicates the dual-lens-vetted scoped-env/kill/timeout machinery; reuse is maximal-reuse, one trust boundary.
- **Keep Posture A for fetched code, rely on curation** — **Rejected, constitutionally** (the crux): a fetched plugin is not operator-placed; curation does not hold; Posture A for remote provenance is the L1/L1b/L2 surface with no backstop.
- **A signature / keyring trust model for fetched plugins** (vs. operator-pinned source+digest) — **Deferred** (D4): heavier (key distribution/rotation); the pinned-source+digest activation entry is the minimal operator-authoritative consent for the MVP. (Surfaced for architect confirmation, plan §5.2.)
- **A full plugin registry/marketplace + lifecycle** — **Deferred P4** (D5): out of the MVP's minimal-fetch scope.
- **FS/network syscall sandbox for fetched code (container / seccomp / separate UID / chroot)** — **Deferred P4** (D1a, R0-B R1 / R0-A Y2): a container-orchestration problem, not a P3 subprocess patch. The MVP's env/secret/DoS scoping is a genuine improvement over Posture A's zero protection; the FS/network residual (`RB-FS/NET`) is **Accepted + inscribed** (the operator who activates a fetched plugin assumes it), with the sandbox named as the P4 forward-watch.
- **In-process import isolation (RestrictedPython / audit hooks)** — **Rejected** (carried from ADR-029 D4 Posture C): not a real boundary in CPython.

## Consequences

**Easier:** remote/untrusted plugin code reaches the system through an **env/secret/DoS** isolation boundary (subprocess + scoped env + kill-no-orphan + per-turn cap), reusing the **one** dual-lens-vetted MCP-subprocess machinery; the ADR-028 D5 liveness bound is **restored** (L2 resolved); the **env/secret** boundary is **real** for plugin code (L1-env resolved); the executor + gate are untouched. **This is NOT a syscall sandbox** — the FS/network residual (`RB-FS/NET`, D1a) is Accepted + inscribed, the sandbox deferred P4.

**Harder:** a plugin tool must now be **subprocess-safe** (the in-process convenience of Posture A is gone — the price of the env/secret/DoS boundary); a new provenance + activation + fetch surface to get fail-closed; the harness bridging `tool_impls` → a stdio MCP child is new machinery (though it reuses the transport seam).

**Neutral:** Posture A is **preserved** for operator-placed plugins (no P3.5 regression); Posture B is **forced** only for fetched provenance; the activation allowlist is the minimal operator-pinned consent (a registry is additive later).
