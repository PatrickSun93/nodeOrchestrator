## 1. Framing

P3.4 builds an **MCP client** (`mcp/`: transport + a generic tool-adapter) that connects external MCP servers (stdio) and exposes their tools to agents, with **every MCP tool-call routed through the existing code autonomy gate** and external servers treated as a **trust boundary**. The clean substrate finding: the gate is **tool-source-agnostic** — `process_tool_calls` takes any `ToolCall{name, arguments}`, builds an `Operation`, and gates on `tools[name].reversibility` (code/config). So an MCP tool-call is **just a `ToolCall`**; P3.4 plugs MCP into this path and **builds no second decision surface**. The architect ruled all five decisions (ADR-027 absorbs them): (a) stdio transport + a filesystem demo connector; (b) dual-lens R0-B; (c) **pre-classify allowlist** (config classifies reversibility; only classified+allowlisted tools callable; unclassified→refused); (d) the trust posture (allowlist + credential indirection + scoped env); (e) MCP client now + config anticipating plugin-delivery (P3.5). The **constitutional spine (HR#1–6)** and **trust boundary (HR#7–10)** are non-negotiable and inscribed.

## 2. The gating spine — feed the existing gate, unchanged (HR#1–6)

P3.4 changes **nothing** in `score`/`decide_tier`/`gate`/`emit_gate_decision`/`process_tool_calls`. The wiring is a **registry merge**: at bootstrap, the `tools: dict[str, ToolMeta]` that already flows `run_turn → dispatch_turn → process_tool_calls` is built as `load_tools_config(tools.yaml) ∪ {mcp__<server>__<tool>: ToolMeta(reversibility=<config>)}`. An MCP tool-call (`ToolCall{name="mcp__<server>__<tool>"}`) then gates **identically** to a local tool:
- registered+classified → `score`→reversibility → `decide_tier`→tier → `emit_gate_decision` (audit `autonomy_decision`).
- **unregistered → `UnknownToolError`→refused** (`autonomy_refusal`; `ToolDispatchDecision(refusal_reason="unknown_tool")`) — HR#3 fail-closed.
- **the server's hints never touch the tier** — reversibility is the config value only (HR#2).

`mcp/` makes **no autonomy/routing/model decision** (HR#6) — a constitution test forbids `mcp/` referencing `decide_tier`/`emit_gate_decision`/`gate`/`select_model_and_provider` and any `llm/`-provider call, and forbids upstream layers (`core`/`autonomy`/`agents`/`llm`) importing `mcp/` (leaf consumer).

## 3. The pre-classify-allowlist mechanism (HR#2/#3; the crux — ADR-027 D3)

`config/mcp_servers.yaml` (frozen + `extra="forbid"` Pydantic models; a loader mirroring `load_tools_config`) declares **per server**: `transport/command/args` (stdio launch), `api_key_env` (credential indirection), `env` (minimal scoped subprocess env), and a **`tools` allowlist** mapping each callable tool → `{reversibility}`. At connect, the adapter runs `tools/list` (discovery) and builds a `ToolMeta` **only** for tools in the config allowlist, keyed `mcp__<server>__<tool>`, reversibility = the **config** value:
- **classified+allowlisted** → in the registry → callable (tier from reversibility).
- **discovered-but-unclassified** → **no `ToolMeta`** → not in the registry → `UnknownToolError`→refused. **Discovery ≠ permission** (HR#3, fail-closed).
- a config tool with `reversibility` omitted → `ToolMeta` default **0** (irreversible → HARD_CONFIRM) — conservative-low.
- the server's `readOnlyHint`/`destructiveHint` are **ignored for the tier** (optionally logged advisory-only).

**Namespacing** `mcp__<server>__<tool>` (double-underscore) — collision-free vs local tools (none carry `mcp__`); a §4 test asserts no collision.

## 4. The client + transport + adapter (`mcp/`; ADR-027 D1/D5)

A new `mcp/` package (optional `[mcp]` extra = the official `mcp` Python SDK):
- `mcp/transport.py` — the **stdio** transport: launch the server subprocess (`npx`/`uvx`) with a **minimal scoped env** (HR#10); the async SDK (`ClientSession` + `stdio_client`) wrapped behind a **sync** surface via a managed event loop. **Bounded-timeout bridge (R0-B Y1 → α MUST-FIX — HR#10 hang→fail-closed):** unlike P3.2's `llm_adapter` (timeout free from the HTTP client), a **stdio read has no built-in timeout** — a hanging server would block the sync thread forever. So the bridge wraps **every** SDK call in **`asyncio.wait_for(<coro>, timeout=<bounded>)`** (`run_until_complete(asyncio.wait_for(...))`); on `TimeoutError` it **kills the subprocess** (`proc.kill()` + `proc.wait()`, no orphan) and the tool-call **fails closed** (`TOOL_FAILED`). Bounded defaults (config-overridable): `connect`/`tools/list` ≈ **10 s**, `tools/call` ≈ **30 s**. (Tested with a deliberately-hanging mock server — §8-§3.)
- `mcp/client.py` — `connect(server_cfg)` → session; `list_tools(session)` → discovery; `call_tool(session, name, arguments)` → result (bounded timeout, size-limited, fail-closed).
- `mcp/adapter.py` — the **generic tool-adapter** (HR#6, no LLM/decision): `build_tool_registry(server_cfgs)` → `dict[str, ToolMeta]` keyed `mcp__<server>__<tool>` from the config allowlist (D3); `to_mcp_call(namespaced_name) → (server, tool)` for execution.
- `mcp/config.py` — the `MCPServersConfig` models + loader.

## 5. Execution + interpret (HR#4/#5; ADR-027 D6)

- **Execution keys on the `TOOL_CALL` event** (the gate's approval record). `mcp/execution.py` (transport-driven, **no LLM, no decision**): for a `TOOL_CALL` event whose tool is `mcp__*`, call `call_tool` (bounded timeout, size-limited) → append `TOOL_RESULT` (`ToolResultMeta{call_id, success, output_truncated_at}`) on success / `TOOL_FAILED` on crash/hang/timeout/malformed (fail-closed). It **never** contacts a server without a `TOOL_CALL` event → HR#4 structural.
- **MVP executes `AUTO_EXECUTE` only (arch Y1 → α-lite; scope, not constitutional).** `process_tool_calls` appends a `TOOL_CALL` event **only** for `AUTO_EXECUTE`; `COUNTDOWN`/`HARD` append none, and **there is no confirm-then-execute flow today** (`tool_calls_pending_confirm` only *tracks* pending calls; nothing consumes a user-confirm to append the `TOOL_CALL`). So a `COUNTDOWN`/`HARD` MCP tool is **gated-but-not-executed** in the MVP — **constitutionally correct** (the demo's `write_file` rev 2 → `HARD_CONFIRM` → not executed *is* the demonstration). **`confirm-then-execute` is GUI-coupled and deferred** (a later GUI-interaction slice: GUI surfaces the pending call → user confirms → a `TOOL_CALL` event is appended → the *same* executor runs it, unchanged). P3.4 **does not** wire a confirm flow (no scope creep).
- **Interpret = content-gen, outside `mcp/`** — a thin wiring in the agent/dispatch layer interprets the (untrusted) `TOOL_RESULT` via the **existing** `LLMPurpose.TOOL_OUTPUT_INTERPRET`, with the prompt framing the result as **untrusted external data** (describe, don't act). **No new `LLMPurpose`** (HR#5). (No existing interpret consumer — P3.4 adds this thin wiring; it stays out of `mcp/`.)

## 6. The trust boundary (HR#7–10; ADR-027 D4)

- **Server allowlist** — only servers declared in `config/mcp_servers.yaml` connect; an undeclared name → refused (fail-closed).
- **Credential indirection** — `api_key_env: <ENV_VAR>` per server; the secret is read from the env at connect, passed **only** into that server's scoped subprocess env (never inline).
- **Untrusted results** — `call_tool` results size-capped (max-bytes; over-cap → truncate + `output_truncated_at`, or reject); recorded as `TOOL_RESULT`, content-gen-interpreted with untrusted-framing; **no result drives a routing/autonomy decision**.
- **Subprocess isolation + fail-closed + scoped env** — bounded timeouts on connect + every `call_tool`; crash/hang/timeout/malformed → `TOOL_FAILED` (the orchestrator never crashes/hangs); the subprocess env is **minimal-scoped** (`{**minimal_base, **server.env, [api_key_env→secret]}`) — **not** the orchestrator's full env (the c2 env-inheritance lesson).

## 7. Atomic graph (single-junior serial — the security surface wants one careful hand)

Inscribe-before-producer: the adapter/config contract.
- **P3.4-2 — gating wiring + execution + trust boundary.** The registry merge (MCP `ToolMeta` ∪ the local registry, namespaced) at bootstrap; the gate path **unchanged** (verify `process_tool_calls` gates the namespaced MCP `ToolCall`); `mcp/execution.py` (downstream of `TOOL_CALL`, size-limited, fail-closed → `TOOL_RESULT`/`TOOL_FAILED`); the trust boundary (allowlist + credential indirection + scoped env + subprocess isolation). **§1 discriminating + §4** (allowlist/credential/size/env fail-closed; namespacing collision-free).

## 8. Test plan (heavy — security + external I/O)

- **§1 cross-module (load-bearing, discriminating):** MCP tool-call → `process_tool_calls` → gate tier → (AUTO) execute → `TOOL_RESULT` → interpret. **Discriminating:** an **unclassified** MCP tool (advertised by the server, absent from the config allowlist) → `UnknownToolError`→**refused** (not executed); a **low-reversibility** MCP tool (`write_file` rev 2) → **`HARD_CONFIRM`** (no auto-exec, no `TOOL_CALL` event) while `read_file` rev 10 → `AUTO_EXECUTE` (executed); the server's `readOnlyHint:true` on a low-rev tool **does not** change the tier (the config classification wins).
- **§2 concurrency:** concurrent MCP tool-calls; the subprocess/session lifecycle; transport read/timeout under load; the sync-bridge loop isolation.
- **§3 failure modes (heavy):** **hanging-mock server (R0-B Y1 MUST-FIX)** — a server that never responds to `tools/list`/`tools/call` → the `asyncio.wait_for` timeout fires → the tool-call **fails closed** (`TOOL_FAILED`) **AND the subprocess is killed** (assert `proc.kill()`+`proc.wait()`, no orphan), the orchestrator thread is **not** blocked; server **crash** mid-call / malformed-protocol → `TOOL_FAILED` fail-closed (no orchestrator crash); **oversized** result → truncated/rejected; **non-allowlisted** server → refused; `call_tool` with no `TOOL_CALL` event → never contacts the server.
- **§4 boundary/validation:** the **allowlist** (undeclared server refused) + **credential indirection** (secret only via `api_key_env`, scoped, not inline) + **result-size limit** + **subprocess env scoping** (the subprocess env does **not** contain the orchestrator's env/secrets — the c2-leak test) — all **fail-closed**; **namespacing collision-free** (`mcp__*` vs local tools).
- **§6 schema invariants:** `MCPServersConfig` + the adapter mapping frozen/validated; the `mcp/` **no-routing/judgment** + **no-new-`LLMPurpose`** + **no-upstream-import** constitution checks.
- **Feed-the-gate verification:** `score`/`decide_tier`/`emit_gate_decision`/`process_tool_calls` diff is **empty** (P3.4 adds no change to the gate's decision logic).

## 11. Self-discoveries (verified `origin/main`)

- **The gate is tool-source-agnostic** (`process_tool_calls`/`emit_gate_decision`/`score`/`decide_tier`) — an MCP tool-call is just a `ToolCall`; the wiring is a **registry merge**, not a new path. **Feed it, don't change it.**
- **`process_tool_calls` does NOT execute** — it appends a `TOOL_CALL` event **only** for `AUTO_EXECUTE` (the gate's approval record); there is **no existing tool-executor**. So MCP execution keys on the `TOOL_CALL` event → "execution downstream of gate" is **structural** (the executor never runs without the event).
- **`ToolMeta.reversibility` default is 0 = irreversible → HARD_CONFIRM** (`scoring.py:42`) — the conservative-low default the unclassified/omitted case inherits.
- **`UnknownToolError` (ADR-006) is the discovery≠permission mechanism** — an unclassified MCP tool isn't in the registry → refused, fail-closed (no code change needed; the adapter simply doesn't register it).
- **`TOOL_OUTPUT_INTERPRET` exists (content-gen) with no consumer** — P3.4 adds the thin interpret wiring (outside `mcp/`, untrusted-framing); **no new `LLMPurpose`**.
- **The official `mcp` SDK is not a dependency** + **no `mcp/` package** — both net-new (`[mcp]` extra, leaf package). The SDK is async → a sync-bridge (the P3.2 `llm_adapter` precedent) is needed.
- **The P2.7-S3 c2 env-inheritance lesson recurs** — the stdio subprocess must get a minimal scoped env, never the orchestrator's full env (the cross-family catch that R0-B should re-probe here).
